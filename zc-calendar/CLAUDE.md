# zc-calendar

Events that come round every year: the asset and its owner switches, the occurrence answers, the minute tick, attendance, the herald and event spawns.

- Depends on zc-core and zc-presentation only. zc-progression and zc-almanac read runs through zc-core's `occurrence/Occurrences` (filled by `CalendarBootstrap`; `CalendarService` answers `live`, `next`, `after`, `history` and each event's `zone`, every run numbered within its year); zc-objectives turns `CalendarAttendedEvent` into `CALENDAR_ATTENDED` (`ZigCalendarProducer`). Never import any of them.
- A calendar event is `CalendarEventAsset` at `Server/ZiggfreedCommon/CalendarEvents/<Owner>/<Id>.json`; the FILE NAME is the id and folders are inert, so ids collide across owners unless prefixed. An id `Calendar`, `Almanac` or ending in `_Live` (another switch's, `ID_RESERVED`) or carrying `|` or `@` (the attendance save format's separators, `ID_UNSAVABLE`) never runs and declares no feature (`CalendarEventAsset.isReservedId`).
- A Window is `Start`/`End` (`MM-DD`, BOTH days in), a `Rule` (`asset/WindowRules`, a `Type` union of five arms: Easter, Weekday, Fixed, which takes several spans as `Runs`, Monthly and Weekly) that wins over them, and `Years` that win over both: each entry is `WindowRules.YearDays`, never a Rule arm, whose `Start`/`End` or `Runs` (`[]` for none) date that WHOLE year and whose `Skip` leaves run numbers out (alone, of the runs the rest dates). The dates maths is `AnnualWindow` over `YearRule`. An End before its Start crosses the new year, every run starts in its own year (a rule that could not is `WINDOW_RUN_INVALID` and never runs), and a run belongs to the year it starts in. A run's number is its place in a list, a Monthly run's its month, a Weekly run's its calendar week (Monday start, week 1 holding January 1st), so numbers skip and are never 1..k. A run meeting one before it (in its list, or the year before's) is set aside, the one written first kept (`RUN_SET_ASIDE`, a WARNING per run); a Skip number the year lacks is `SKIP_UNKNOWN_RUN`, a WARNING; a number set aside or skipped is never reused. A window of `Years` alone has no run in a year it does not list, so `next` answers null once it runs out. `Clock` is a java.time zone id or offset, UTC by default. No usable Window or no FirstYear: the event never runs and the log says why.
- `asset/CalendarEventValidator` is the calendar's content audit (domain `calendar`; a consumer folds `audit()`): `CalendarEventAsset.problems()` under their own codes, an ERROR when the event never runs (`NEVER_RUNS`), else a WARNING, plus icons, Presentation and Herald keys, and each spawn's Event against the loaded set.
- `RecurrenceOf` turns the rule dating an event's year (`AnnualWindow.rule`) into zc-core's neutral `Recurrence`, which `CalendarService.recurrence` answers in one line: only a Monthly or Weekly rule that dates several runs a year is one, never a rule with one run a year, a list of spans or a year its `Years` entry sets out.
- Off means absent, never locked: the owner's `$Enabled` (in `mods/ziggfreedcommon/calendar.json`, `$`-prefixed because the shared reader treats other keys as event ids) and an event's `Enabled` make it not enabled, never live, with no history; the switches beat a force. Content vanishes by naming the event in its `Season` leaf (zc-core `season/SeasonGate`, which reads `<Id>_Live` and holds that spelling; `CalendarFeatures` takes it from there), or by gating on `ziggfreedcommon:feature` Param `<Id>` (switched on) or `<Id>_Live` (switched on and running); `ziggfreedcommon:calendar_live` and `calendar_year` are LOCK readings.
- Nothing looks at the clock before `BootEvent`: the boot's look resumes running events (`resumed`), and a world added during the universe's start never sees a calendar write. Native events fire on the tick thread, never a world thread.
- Reload through `CalendarContent` only: it folds the pack and owner layers under `CalendarService.lock()`, which the tick reads under, so a tick never sees half a reload. `CalendarOwnerLayers.reload()` empties the owner layer before it refills it, so it runs only inside that frame.
- Everything that acts on what it reads (the tick's look, the spawn listener's snapshot, a player's attendance read) reads under that one lock. A world thread waits for it while holding the engine's asset read lock, so nothing done while holding it may wait for the asset lock or a world thread: no synchronous asset write inside a `foldThenLook` frame, and never call `CalendarSpawns.reconcile` while holding it.
- `CalendarTicker.requestEvaluation` never takes the ticker's lock and `isStarted` reads a volatile: a content load asks for a look from inside the engine's asset write lock, which a look in progress may be waiting for.
- Compare runs by (event id, year, number) (`Occurrence.sameRun`), never by whether the window contains now, and order them by start (`IN_ORDER`), never by number: a number is the year's rule's name for a run (a month, a calendar week, a span's place), so it skips and never counts runs. A forced-on run is the run going on, else that year's first run not yet over, else its last, with its own days and number (a moving rule's included). `CalendarService.forceOn` takes that run as it writes the force (`CalendarForces.Pin`) and the force keeps it, never walking on: a run brought forward stops when its days end, one already over when forced (a replay) runs its usual length from the force. Reads never write a force (once its run is over they answer by the dates); only the tick's look clears a spent one, under the lock. A year the window dates no run has nothing to force: `forceOn` then writes nothing, so a refusal leaves the standing force as it was.
- Never remove a world-spawn rule: the engine's removal looks a rule up in a table that answers 0 for a rule it never set up and removes spawn configuration 0 instead. A rule no running event owns is retired (`MoonPhaseWeightModifiers [0]`). One rule per (role, environment) pair: the engine refuses a second with a SEVERE line.
- Attendance is once per player per run, (year, number) (`CalendarAttendanceComponent`, persisted: `<id>@<year>` for run 1, the form every older save holds, and `<id>@<year>#<n>` for any other run, a run counted once however its entry is written); the start banner rides that first credit, and the end banner goes to everyone online at a real end, never a switch-off. A tick is ONE queue `CalendarHerald.START_GAP_MS` apart, the first at once: its end banners, then the start banners its fresh runs owe; a queued one drops if the player left. A run followed at once by its event's next run shows no end banner. An event shows its banners on every run, only its year's first (`Herald.FirstRunOfYear`, the first by its dates, never by number), or never (`Herald.Enabled` false). Banners go only through zc-presentation `EventTitles`.
- A force lives in memory only and a restart clears it.
- A start or an end also re-sweeps every world's NPC placements (zc-objectives `objectives/calendar/CalendarPlacementSweep`, listening on the two native events), so a placement whose `Season` names the event, or one gated on `<Id>_Live`, follows the event; this module knows nothing of it.
