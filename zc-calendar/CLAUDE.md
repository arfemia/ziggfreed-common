# zc-calendar

- Depends on zc-core and zc-presentation only. Every reader of a run, in any module or a consumer, goes through zc-core's `occurrence/Occurrences`, which `CalendarBootstrap` fills with `CalendarService` (zc-core's `OccurrenceSource`; an event's `titleKey` and `icon` come from its `Presentation`, every run numbered within its year); zc-objectives turns `CalendarAttendedEvent` into `CALENDAR_ATTENDED` (`ZigCalendarProducer`). Never import a reader.
- `RecurrenceOf` turns the rule dating the year an event is in (`CalendarService.currentYear`: a run going on is its starting year's; `AnnualWindow.rule`) into zc-core's neutral `Recurrence`, which `CalendarService.recurrence` answers in one line: only a Monthly or Weekly rule that dates several runs a year is one, never a rule with one run a year, a list of spans or a year its `Years` entry sets out.
- Off means absent, never locked: the owner's `$Enabled` (in `mods/ziggfreedcommon/calendar.json`, `$`-prefixed because the shared reader treats other keys as event ids) and an event's `Enabled` make it not enabled, never live, with no history; the switches beat a force. Content vanishes by naming the event in its `Season` leaf (zc-core `season/SeasonGate`), or by gating on `ziggfreedcommon:feature` Param `<Id>` (switched on) or `<Id>_Live` (switched on and running); `ziggfreedcommon:calendar_live` and `calendar_year` are LOCK readings.
- Nothing looks at the clock before `BootEvent`: the boot's look resumes running events (`resumed`), and a world added during the universe's start never sees a calendar write. Native events fire on the tick thread, never a world thread.
- Reload through `CalendarContent` only: it folds the pack and owner layers under `CalendarService.lock()`, which the tick reads under, so a tick never sees half a reload. `CalendarOwnerLayers.reload()` empties the owner layer before it refills it, so it runs only inside that frame.
- Everything that acts on what it reads (the tick's look, the spawn listener's snapshot, a player's attendance read) reads under that one lock. A world thread waits for it while holding the engine's asset read lock, so nothing done while holding it may wait for the asset lock or a world thread: no synchronous asset write inside a `foldThenLook` frame, and never call `CalendarSpawns.reconcile` while holding it.
- `CalendarTicker.requestEvaluation` never takes the ticker's lock and `isStarted` reads a volatile: a content load asks for a look from inside the engine's asset write lock, which a look in progress may be waiting for.
- A forced-on run is the run going on, else that year's first run not yet over, else its last, with its own days and number (a moving rule's included). `CalendarService.forceOn` takes that run as it writes the force (`CalendarForces.Pin`) and the force keeps it, never walking on: a run brought forward stops when its days end, one already over when forced (a replay) runs its usual length from the force. Reads never write a force (once its run is over they answer by the dates); only the tick's look clears a spent one, under the lock. A year the window dates no run has nothing to force: `forceOn` then writes nothing, so a refusal leaves the standing force as it was.
- Attendance is once per player per run, (year, number) (`CalendarAttendanceComponent`, persisted: `<id>@<year>` for run 1, the form every older save holds, and `<id>@<year>#<n>` for any other run, a run counted once however its entry is written); the start banner rides that first credit, and the end banner goes to everyone online at a real end, never a switch-off. A tick is ONE queue `CalendarHerald.START_GAP_MS` apart, the first at once: its end banners, then the start banners its fresh runs owe; a queued one drops if the player left. A run followed at once by its event's next run shows no end banner. An event shows its banners on every run; with `Herald.FirstRunOfYear`, the start banner on the year's first run, the end banner when its last run ends, both by their dates (never by number); or never (`Herald.Enabled` false). Banners go only through zc-presentation `EventTitles`.
- A force lives in memory only and a restart clears it.
- An event with a `Moon` or a `Live` is a condition, not a run (`CalendarEventAsset.isCondition`): `canRun()` is false, so every run reader (the occurrence answers, attendance, history, yearly copies, the Almanac, stat season lines, spawns) reads it as absent; its own questions are `CalendarService.isSwitchedOn` and `isLive`, which the `<Id>`/`<Id>_Live` features and `calendar_live` read for every event. A Moon reads `moon/MoonPhases` (each world's phase, seeded on its thread and kept by `MoonPhaseChangeEvent`, `moon/MoonPhaseSystems`), never the world itself; a Live reads its members' `isLive`, and a loop is refused (`LiveRule.loopFrom`). Its banners are `CalendarConditionHerald`'s (each rise, or `Herald.OncePerDay`), the ticker's `rose`/`lapsed`.
