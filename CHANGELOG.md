# Changelog - Ziggfreed Common

The dev changelog for the shared, mod-agnostic Hytale primitive library. Newest first. No em-dashes.

## 1.4.0 (held, unreleased)

Nothing in this version has shipped yet. The whole cycle is landed but HELD pending one combined in-game smoke pass across the mod family; the pushed `v1.4.0` tag is stale and moves at actual release.

- The library builds as twelve focused Gradle modules (`zc-core`, `zc-presentation`, `zc-cast`, `zc-entity`, `zc-effects`, `zc-loot`, `zc-dialogue`, `zc-progression`, `zc-objectives`, `zc-instance`, `zc-world`, `zc-scaling`) plus a thin wiring root holding only the plugin entry point and `asset/FrameworkAssetRegistrar`. Nothing about the shipped mod changes: every class keeps its `com.ziggfreed.common.*` name, the module jars merge back into the one `ZiggfreedCommon-<version>.jar` a server loads, and the aggregate's contents are identical to before apart from the one new class below. A consumer needs no edit of any kind - same jar, same imports, same `manifest.json` dependency. What it buys is a compile-time dependency graph the build enforces: a module can only reach what its `build.gradle` declares, so an accidental edge (say the dialogue engine reaching into the instance-experience layer) fails the build instead of quietly welding two domains together. Only the aggregate jar is installable; the per-module jars in `zc-*/build/libs` are compile inputs, carry no `manifest.json`, and are not loadable mods on their own.
- **The runtime `Quest` and `Achievement` now CARRY what the shared parts need, so one gate, one text source and one offer provider answer for content authored in ANY format.** Each gains the authored `Requires` block, a `progress/ContentText` group (title / flavor / per-step keys, their already-bound arguments, and the plain fallbacks), a live `available` predicate, and - on a quest - the giver id and listing order, with `serverFirst` on an achievement. Everything above them follows from that. `quest/RequiresGates` is ONE gate implementing BOTH `QuestGates` and `AchievementGates`, registered for both engines by the objectives defaults; `AssetQuestGates` is retired into it, and with it the pool it could only ever answer for. It answers `canReceiveRewards` by default through `LootRewardKinds.canAddAll`, so a payout with nowhere to go parks instead of vanishing on every server rather than only where a consumer wrote that check. The library's text source reads the runtime object rather than its own pool, and `ProgressionTextSource.lore` gains the shared `quest.<id>.md.<state>` convention as its interface DEFAULT. A DEFAULT `NpcOfferProvider` ships at last: "have you anything for me" was a seam whose only registrations anywhere were test fixtures, so a grep said yes while every server said nothing.
- New: `achievement/FirstClaimStore` + `FirstClaims` - the server-first claim table as a seam with a working in-memory default, plus an additive `onLost` fan-out. The RULE (exactly one winner, and a loser keeps their criteria met so the decision can be revisited) is the gate's; only the durable table and the words a loser reads are a consumer's.
- New: `progress/runtime/ProgressionGates` - THE `GateEvaluator` and the one gate over it, built on first ask and holding no registration of its own: the factor vocabulary, the factor context and the requirement kinds are read LIVE off the runtime, so a consumer registering its own vocabulary long after the evaluator was first asked for feeds that same instance. `GateEvaluator.Builder` takes a `Supplier` form of both registries for exactly that, named `factorsLive` / `gateKindsLive` so the captured form keeps its own name and a null argument to it is still unambiguous. `SeamsFilledTest` walks the registration state after the defaults register and fails the build on a progression seam left with no production fill.
- `maxActiveQuests` accepts an `IntSupplier`, so a consumer whose cap is an owner config value a reload moves supplies the NUMBER and the engine's own `log_full` refusal runs against it. A consumer re-checking that in its own gate was making the same refusal twice. What the cap is measured against is `QuestEngine#logSlotsUsed`, over the new `Quest#occupiesLog()` switch: an errand a player picks up somewhere that keeps its own list neither fills the quest log nor is refused by it, which is one switch because it has to be both halves at once. A board contract sets it off, so somebody working three contracts still has their whole log.
- `RequiresGates` answers `canReceiveRewards` for an ACHIEVEMENT as well as a quest, so claim rewards with nowhere to land park rather than paying out into nowhere. A consumer that already pre-checked room before calling `claim` sees no change; one that did not now gets a refusal where it previously lost the payout.
- A requirement block is evaluated for EVERY subject now, including one carrying a handle this gate knows nothing about, and such a subject fails a positive condition rather than passing it. That is the library's standing rule for a reading with nothing behind it, and it is reachable only on a shared runtime where one consumer's subject meets another's content.
- New: `QuestEngine#isOfferable` - the GIVER-side visibility read, beside the open-listing `isVisible` it must not be confused with. `Visibility.hidden` keeps content off a browsable listing; at the one character authored to hand a quest out there is no browsing going on, so filtering a giver's list on the open-listing read leaves that character standing silently beside the thing they exist to hand out, and a whole authored chain becomes unreachable with nothing anywhere reporting it. The giver read asks only whether the quest is switched on and whether the player is past what it asks for first, which is what an author means by "keep this out of sight until it is relevant". The default offer provider uses it.
- `progress/ContentText` carries a per-step LINE as well as a per-step key: a fold that already knows how its own steps read may hand the composed line over for a step that authored no key, and a surface then draws that instead of a generic "unnamed step" for a whole catalogue at once. It is a `Supplier` because whatever composes a line is often installed later in a boot than a catalogue is folded, and a composer that throws costs its own line rather than the screen. Everything else on the group is still KEYS, never sentences.
- `QuestGates` gains `opensFor`, ONE accept-time question a gate answers instead of two. Accepting asks whether the player is past what a quest asks for first and whether the gate lets them take it, which for a gate reading an authored requirement block is the same block read the same way; asking twice paid for a full second evaluation, and every factor reading behind it, on a path that runs per quest whenever a giver's list or a quest log renders. The default implementation asks the two exactly as before, so a gate that answers them differently is unaffected, and the refusal tokens are unchanged either way.
- The default offer provider answers "has this character anything for me" cheaply, stopping at the first quest that can be taken now rather than building the whole list and resolving its titles. That question is asked once per character on screen, so it is the one that has to be cheap.
- `progress/ContentText` names itself with whichever key was written when no translation has landed yet, rather than answering nothing for content that also carries a convention key. A row painting its key is traceable back to the file it came from in a screenshot or a support log; a blank row is not. A composed step line may also answer null now, meaning "nothing to say yet", and the authored key takes over exactly as if no line had been offered - which is what a fold whose sentence composer is installed later in the boot needs.
- **`ziggfreedcommon:quest_completions` counts COLLECTIONS, not finishes, so a reward still sitting there uncollected is not a run already done under either it or `ziggfreedcommon:quest_completed`.** A quest authored to park its reward sits finished-but-uncollected until somebody comes to take it, and the count read that window as a completed run while the flag beside it read the opposite: content written "come back once you have run this three times" paid out on the third FINISH, before the third reward had ever been handed over. `QuestProgressStore.CompletionRecord` gains a fourth field, `claimedCount`, raised by `QuestEngine.markCompleted` - the one instant a quest is paid out, whichever route reached it (the auto-claim path, the collect of a parked one, an administrator's close-out) - and the factor reads that tally. The repeat rules deliberately keep counting FINISHES (`MaxCompletions`, a calendar `Reset` allowance). No player can make the two tallies disagree at a repeat decision: a parked quest is not offered, and `canAccept` refuses it until it has been collected. A deliberate force can - an accept that skips the eligibility check on purpose (a scripted start, an administrator) or a re-arm that clears the parked status - and the finish is the safe half to cap on, since a run somebody walked away from without collecting still spent its slot. Only a repeatable keeps a completion record, so a one-shot reads 0 on the count however many times it was finished and is gated on the flag instead. **Wire form**: the persisted value widens from three numbers to four (`last,period,total,claimed`). **A save from a released build carries no completion record at all**, since the record is newer than any tagged version, so an upgrading player starts counting at their first finish after the upgrade: a quest they had already completed reads 0 on the count while still reading 1 on the flag, and collecting a reward they had parked before the upgrade pays out while the count stays at zero, because collected is clamped to a finish tally with no memory of that run. No count, and no over-count. The three-number form is a development-tree courtesy for a value written earlier in this same unreleased cycle: it still reads, with collected equal to finished, since a finish WAS the payout under the rule it was written under, and the same clamp stops it counting its parked run a second time when somebody finally collects it. A consumer with its OWN `QuestProgressStore` decodes such a value through the named `CompletionRecord.withoutCollectedTally(last, period, total)` factory, which is deliberately the only way to say "every finish was collected" - an ordinary three-argument construction does not compile, so no writer can make that claim about a player's history by accident.
- **`dialogue/` now has ONE `DialogueEngine` per server, and every consumer registers into it ADDITIVELY.** The decode vocabulary was already process-wide while the BEHAVIOUR behind it was per consumer, so on a server running two dialogue mods whichever one opened a conversation decided which half of the vocabulary could actually execute: the other mod's actions silently no-opped and its gated lines silently hid. `DialogueEngine.shared()` is the engine, `DialogueEngine.registerShared(owner, type)` is how a consumer contributes an action or condition from its own `setup()`, and contributions stack, so one authored option may carry two mods' actions and both run. Behaviour is claimed per action / condition CLASS and that claim is first-wins, which is the one collision stacking cannot absorb: a second contributor for a class another mod holds is refused, `registerShared` answers false, and one boot line names the mod holding the class and the mod that asked - which is what the owner argument is for. The engine's maps are live rather than a snapshot, so a consumer that captured it early still holds the one later registrations land in. Two seams stay SINGULAR because two of either would be two answers to one question about one player: `installQuests` and `installFactors` are first-install-wins, and a later one naming a different instance is logged once and ignored (a repeat of the same instance is silent). `DialogueEngine.builder()` is UNCHANGED and still builds an isolated engine for a test sandbox. New alongside it: `DialoguePayloads`, the process-wide way a consumer says how ITS per-player payload is built for any player, so its own actions and conditions still answer correctly in a conversation another mod opened - `SimpleDialogueExecContext.payload(Class)` falls through to it only on a genuine miss, the explicitly packed payload always winning exactly as before, and a fallback is built at most ONCE per context, so a supplier that reconciles saved state on the way past runs once per screen rather than once per gated line. `SimpleDialogueExecContext` also resolves its memory store on first use rather than at construction, since a context is built on every render and every click while most conversations never touch a memory. `npc/NpcDialogueDepsRegistry` is `RegistryLedger`-backed and every registration names its owner (`setDefault(owner, supplier)` for the un-keyed slot, `set(key, owner, supplier)` for a named one), so two consumers taking the un-keyed default print one boot line naming both instead of swapping silently. Kweebec Nightmare is the exemplar consumer of the new shape.
- New: `registry/RegistryLedger#putIfAbsent(id, owner, value)` - the SINGULAR-slot form of `put`: the first claim wins and every later one is refused rather than replacing it, with the same identity rule everywhere else (a repeat of the same instance is silent, a different instance warns once naming the holder and the asker) and a boolean saying whether this call claimed the slot. For a seam where two live values would be two answers to one question, never for an ordinary open registry where contributions are meant to stack. `RegistryLedger` also gained an optional warn-sink constructor, so a caller collecting registration conflicts into a boot report (or a test asserting that one was reported) does not have to read the log.
- New: `CommonLog` - the library's one logger handle, holding the same `HytaleLogger` under the same pinned name as `ZiggfreedCommonPlugin.LOGGER` (which stays public and now delegates to it, so anything already holding it is unaffected). Library code logs through `CommonLog.LOGGER` so a log line no longer pulls the plugin entry point, and everything that entry point wires, into a package's dependency closure. Log output is unchanged.
- Fixes `entity/PlayerPuppetService` spawning a puppet with its head rendering rotated relative to its body: the spawn holder now pairs a `HeadRotation` component with the body `TransformComponent` at the same yaw, matching every first-party spawn path (the transform tracker always transmits a look orientation, and with no `HeadRotation` component present it falls back to world-absolute identity instead of the puppet's authored facing). `walkTick` mirrors the same yaw onto `HeadRotation` as a walking puppet turns, and `entity/performer/HolderPerformer#presentAt` mirrors it on every re-present (move/re-face) too.
A reusable cast / ability RUNTIME layer (`cast/` + `cast.step/`), lifted config-free from a consumer, so a mod that fires abilities reuses ONE battle-tested set of runtime seams instead of re-deriving the generic step-dispatch kernel, the on-hit dispatch, the per-hit resolver, the armed-state store, a guarded observer registry, ray/block targeting, and the per-world tick partition. All additive over 1.3.0; a consumer picks up only what it calls, and the layer ships EMPTY of content and of any step vocabulary (every built-in type, step handler, and drain system is consumer policy; the kernel is parameterized over the consumer's own context / step / result types). The `cast/` surface is ADDITIVE-ONLY once frozen.

- New: `cast.step` - the generic ordered step-dispatch KERNEL, parameterized over a consumer's OWN context `C`, step `S`, key `K`, and result `R` (common defines no step type of its own). `StepHandler<C,S,R>` is the handler SAM (`R execute(C, S)`); `StepRegistry<K,C,S,R>` is a per-consumer `register` / `@Nullable get` map that ships EMPTY, is last-write-wins + null-key-safe, and offers a protected backing-map constructor so an enum-keyed subclass can use an `EnumMap`; `StepSemantics<C,S,K,R>` is the tiny consumer-supplied contract (`stepsOf` / `keyOf` / `isSuccess` / `successResult` / `onMissingHandler`) that adapts a consumer's existing spec / step / result methods to the walk with NO `implements` on those types; `CastKernel<C,S,K,R>.run(ctx)` walks the steps in order, dispatches each by key, short-circuits on the first non-success result, succeeds on an empty chain, and defers the missing-handler behavior (logging + error result) to the consumer's `onMissingHandler`. Byte-parity with a hand-written dispatch loop. Unit-tested (`CastKernelTest`: order, short-circuit, missing-handler hook, null key, empty chain; `StepRegistryTest`: register/get/empty, last-write-wins, null-key, enum-backed subclass).
- New: `cast/OnHitRegistry` - a PER-CONSUMER on-hit builder registry (news up your own; two mods sharing this jar never see each other's type registrations). `register(type, OnHitBuilder)` keys case-insensitively, last write wins; `fromParams(Object|Map, sourceRef, sourcePlayerId)` converts an `onHit` JSON shape - a single object OR a list chained in declaration order via `andThen` (NO_OP entries skipped) - into a `BiConsumer<Store, Ref>`. A PARALLEL `registerAction(type, HitActionBuilder)` + `actionFromParams(...)` path (separate table) produces a `HitAction` instead, for a callback that needs the richer `HitContext` (a `CommandBuffer` accessor, damage amount, hit position); a type registered on one table is invisible to the other. An unknown type or a builder that throws degrades to the shared `NO_OP` / `NO_OP_ACTION` sentinel with a guarded FINE log. Ships with ZERO registered types. Unit-tested (`OnHitRegistryTest`: single/list dispatch, declaration-order chaining, NO_OP identity for null/malformed/unknown/empty, builder-throws degrade, case-insensitive keying, two-instance isolation, and the parallel HitAction table not colliding with the BiConsumer table).
- New: `cast/HitContext` + `cast/HitAction` - the evolvable successor to a raw `BiConsumer<Store, Ref>` on-hit hook. `HitContext` is an immutable, FIELD-ADDITIVE carrier (accessor typed `ComponentAccessor<EntityStore>`, so a live `Store` AND a `CommandBuffer` both fit - the deferred-mutation seam - plus target / source / sourcePlayerId / damageAmount / position / cause), built via a builder so a new field never breaks an implementer. `HitAction` is `void onHit(HitContext)` with a `NO_OP` and a null-dropping `andThen` chain.
- New: `cast/HitResolver` - a stateless per-already-resolved-target hit routine. `applyHit(store, HitRequest, target, hitPos)` runs the damage dispatch under an opaque `UnaryOperator<Runnable>` origin decorator (wrapping EXACTLY the dispatch), then the on-hit hook (a `HitAction` OR a bridged `BiConsumer<Store, Ref>` fired with no context allocation), then an opaque per-hit sound sink (`BiConsumer<Store, Vector3d>`) and an optional per-hit particle via `ModelParticleService`; it returns whether the dispatch completed without throwing (logged WARN or FINE per the request). The `DamageSink` builds the engine `Damage` itself from the request's source / cause / amount, so common constructs no `Damage` and every knob (source / cause / amount / fail labels / warn-vs-fine / per-hit sound + particle) rides an immutable `HitRequest` builder. All logging routes through the guarded common LOGGER. Unit-tested (`HitResolverTest`: the origin-decorator wrap point, the HitAction + BiConsumer-bridge dispatch, last-setter-wins, throwing-dispatch returns false, throwing-onHit is isolated, sound gated on a position, and both `Store` / `CommandBuffer` accessor forms round-tripping through `HitContext`).
- New: `cast/ObserverRegistry<E>` - a PER-CONSUMER guarded observer registry: `register(Consumer<E>)` + `fire(E)` over a `CopyOnWriteArrayList` with a PER-LISTENER try/catch, so one misbehaving listener neither throws out of `fire` nor blocks the listeners after it. Optional label constructor tags the guarded warn. Unit-tested (`ObserverRegistryTest`: fire-in-order, throwing-listener isolation, empty-fire no-op).
- New: `cast/CastParams` - static param-coercion helpers (`numberOr` -> `Number`, `stringOr` -> nullable `String`, `boolOr`) for a `Map<String,Object>` params bag; a mistyped value falls back, never throws. Pure, no engine. Unit-tested (`CastParamsTest`).
- New: `cast/ArmedStateStore` - a PER-CONSUMER store of per-caster transient combat state: next-hit damage multipliers / flat damage / on-hit chains keyed `(casterId, slot)`, plus a parallel invulnerability window. `armNextHit`/`armMultiplier`/`peekArmedMultiplier`/`consumeArmed` (a composite across all live slots: multipliers multiply, flats sum, on-hit consumers chain, and each live slot's OPAQUE `attribution` payload is exposed in encounter order via `ArmedState.attributions` for the consumer to fold) + `armInvulnerability`/`isInvulnerable`/`peekInvulnerability`/`clearInvulnerability` + `clearPlayer`, with expiry-on-read pruning. Each arm / invulnerability call carries a single `@Nullable Object attribution` the consumer attaches (its own attribution record, a source tag, ...); common never inspects it, so no consumer-domain vocabulary lives in this class. The payload-free `armMultiplier(UUID, double, long)` convenience overload is retained, and `ArmedState` / `InvulnerabilityState` are immutable (final fields + constructor). The CALLER supplies the UUID key and the store NEVER derives it - the consumer's caster-context stays the single key-derivation authority. Pure state, no engine calls. Unit-tested (`ArmedStateStoreTest`: product multiplier, summed flats, chained on-hit consumers, per-slot attribution exposure, the payload-free overload, the final-field constructor round-trip, consume-removes, expiry, invulnerability set/expire/clear with an opaque attribution round-trip, clearPlayer wipe).
- New: `cast/RaycastTargeting` - stateless static entity-raycast picking (`pickClosest` single nearest / `pickPiercing` all hits closest-first, capped) over the engine `Selector` + `CollisionMath.intersectRayAABB`, caster excluded by index; `inflateRadius` widens only the broad-phase search. `Hit` carries the ref + ray-t + pick-time position. World-thread.
- New: `cast/BlockRaystep` - stateless static look-ray block walker (`clearDistance` = distance to the first Solid block with optional wall pullback / `hitPosition` = exact hit point); an unloaded / off-map block is treated as clear and stepping continues. All step / distance / pullback values are caller-supplied. World-thread.
- New: `cast/WorldEvictors` - the STATIC (JVM-global) world seam: `worldOf(Store|Ref)` resolution + `registerEvictor(Consumer<World>)` + a guarded `onWorldRemoved(World)` fan-out. Eviction is JVM-global so a removed world reaches every consumer's per-world partitions in one place; a consumer's `RemoveWorldEvent` listener calls `onWorldRemoved`.
- New: `cast/WorldKeyedQueues<E>` - a generic per-world queue partition (`queueFor` add path / `peek` nullable drain path / `isEmpty` / `values` / `totalSize` / `evict`) that self-registers a `WorldEvictors` evictor in its constructor. A drain system MUST call `markDrainerAttached()`; a one-time WARNING fires if entries are added before any drainer attaches (entries a no system ticks would leak forever). Each per-world cast ticker swaps its private map for one instance with no tick-body change.
- New: `cast/AbstractWorldFrameSystem` - an abstract base for a drain that runs exactly once per world per server tick, extending the engine's own query-less `TickingSystem<EntityStore>` directly rather than a player-query-driven `EntityTickingSystem`: the engine itself calls a registered system's `tick(dt, systemIndex, store)` once per `Store` per tick, and since a `Store<EntityStore>` is one world's store that guarantee needs no dedup gate of its own. Resolves the world from the store, obtains a `CommandBuffer` via the store's public `forEachChunk` (the only public route to one from a query-less system), and calls the protected abstract `drainFrame(world, store, commandBuffer)` exactly once. NEVER registered by common - the ECS system registry is class-keyed, so each consumer registers its OWN concrete subclass.
- New: `cast/ModelParticleService` - static `ParticleUtil` wrappers: `spawnAt` (position-only, uncapped) + `spawnDirectional` (collects nearby players to reach the rotation-aware overload). A null asset id is a `false` no-op; any error is caught and returns `false` after a guarded FINE log; `true` on success. World-thread. `spawnAt` gained a duration-capped 4-arg overload riding the native `SpawnParticleSystem.maxDuration` field (the same field the first-party `PlayVfxEffect` trigger-volume effect authors via its own `Duration` leaf): a consumer firing a one-shot moment at a bare position can force-stop a particle system authored with an unbounded spawner (a negative `TotalParticles`, meant for a persistent per-entity VFX) instead of it spawning forever there - the fix behind a consuming mod's station completion-flourish leak. Unit-tested (`ModelParticleServiceTest`: the null-asset-id no-op contract on both overloads).
- New: `ui/rows/` - a fixed-slot icon + rich-text LEDGER row primitive, lifted from a consumer's session-summary HUD so any mod's reward / results / summary LEDGER reuses one row model + painter. `SummaryRow` is the immutable value (an icon item id + an already-composed, already-styled client-resolved `Message` + a descriptive semantic `Kind` - `PROGRESS`/`CONSUMED`/`PRODUCED`/`LUCKY` generic reward-ledger roles; all colour/bold is baked into the `Message` by the caller, the renderer never branches on `Kind`). `SummaryRowRenderer.render(cmd, rowSelectorPrefix, maxSlots, rows)` paints the list into a FIXED set of pre-declared `.ui` slots the CONSUMER declares (row `i` = `rowSelectorPrefix + i`, each holding an `ItemGrid #Icon` + a `Label #Name`), hides unused / overflow slots, and RETURNS the overflow count for a "+N more" row (`renderWithOverflow` sets that label too). Transport-agnostic (engine `Message` + UI builder only), so any `UICommandBuilder` sink reuses it - a HUD partial update, a page `sendUpdate`, a full `build`. Shipped as a SIBLING to `ui/toast/ToastLine` (same icon-id + `Message` shape, but a transient toast is welded to the toast transport + a `quantity` badge + a per-kind SFX `ToastKind`, whereas a `SummaryRow` is a persistent fixed-slot ledger row) rather than unified, so neither surface forces its semantics onto the other and no third model is forked. The consuming mod keeps only its policy (icon / name resolution, colour conventions, tallies -> rows).
- New: `ui/hud/KeyedCustomHud` - the shared base for a custom in-world HUD overlay, lifted config-free from a consumer's own HUD base so any mod's HUD reads ONE implementation instead of a per-mod copy. Owns a `HudPosition`-driven anchor on a single root element (fixed-height or content-height), two push-throttle strategies (a check-only gate + a CAS atomic acquire), and the native keyed register/lookup/broadcast over Update 5's `HudManager`; a concrete HUD supplies only its identity + layout. Self-contained (no consumer world-lookup utility or logging facade required) - player lookup and "any alive world" broadcast resolution live here, and logging is a locally-guarded call. A consumer with its own HUD base re-parents onto this and keeps only its own conveniences; a consumer with none extends it directly.
- New: `i18n/Msg` - a minimal, mod-agnostic client-resolved `Message` factory, lifted from a consumer's own `i18n.Msg` so several consumer mods can share one arg-binding implementation. Unlike a per-mod `Msg`, `tr(prefix, key, args...)` takes the CALLER's own namespace prefix as an explicit argument (this class carries no fixed namespace); `key`/`raw`/`trNamed`/`keyNamed` round out the translation surface, `join`/`cat` are the same param-safe-composite pair a per-mod `Msg` already carries (`cat` folds through a shipped locale-neutral glue key so a composite still resolves correctly when nested as another translation's param; the registered id is `ziggfreedcommon.fmt.cat`, authored as `fmt.cat` in `ziggfreedcommon.lang` because `I18nModule` derives the prefix from the lang FILENAME), and `bold`/`color` are thin fluent style wrappers. The arg-binding invariant (a localized arg is always a nested `Message`, never a pre-resolved String) carries over unchanged.
- New: `entity/PlayerPuppetService` - the "mount the player, hide their body, show a puppet performing the work instead" presentation mechanism, lifted config-free out of a consumer's in-game-proven P0 spike harness. `spawn(accessor, PuppetSpawnRequest)` clones a source player's live `PlayerSkin` (the copy ctor -> `PlayerSkinComponent` -> `CosmeticsModule.createModel` recipe) onto a new networked, `NonSerialized`, `Visible` entity at a caller-resolved position/yaw, with optional held-item mirroring (a bare `InventoryComponent.Hotbar` - the generic "any entity carrying Hotbar + Visible gets networked equipment" mechanism) and an optional `ActiveAnimationComponent` pre-seed on the spawn holder (the render-guaranteed route: a viewer whose tracker marks the puppet newlyVisible on ANY later tick auto-catches-up to the tracked clip, independent of when a direct animation packet happens to land). `PuppetSpawnRequest` is an immutable builder (`sourceRef`/`position`/`yawRadians`/mutually-exclusive `mirrorHeldItem`|`heldItemIdOverride`/`initialAnimation(slot, clipId)`), mirroring `cast.HitResolver.HitRequest`'s established shape. `despawn(puppetRef, Store|CommandBuffer)` (two overloads) and `playAnimation(accessor, puppetRef, slot, itemAnimationsId, clipId, sendToSelf)` (a single-shot primitive; the caller owns its own repeat-beat cadence) round out the spawn surface. Plus the paired SCALE self-hide primitive - `hideByScale(accessor, ref[, nearZeroScale])` returns the prior `EntityScaleComponent` scale as a revert payload for `revealByScale(accessor, ref, priorScale)` (`null` payload removes the component instead of resetting it to `1.0`); a `ModelSwap`-route hide reuses the existing `PlayerModelService.restore` instead of duplicating it. Every spawn-side method takes a `ComponentAccessor<EntityStore>` (the interface both `Store` and `CommandBuffer` implement, the same seam `cast.HitContext` uses) so an interaction-handler-locked caller and a live-`Store` caller both work through ONE method. Plus two pure spatial helpers (`offsetPosition`, `yawRadiansFromDegrees`). WORLD-THREAD ONLY; every engine call is try-guarded to a no-op/null, never a throw. Unit-tested (`PlayerPuppetServiceTest`: the pure helpers, the builder's mutual-exclusivity/default contract, and the try-guard no-throw contract on every engine-touching entry point via a deliberately-null accessor).

- New: `npc/placement/NpcBaseRoleAsset` + `NpcBaseRoleConfig` + `NpcBaseRoleValidator` (`Server/ZiggfreedCommon/NpcBaseRoles/<baseId>.json`, Pattern B raw passthrough) - a PACK-authorable base role, so shipping the template a generated placement role clones needs no Java at all. The file's `Payload` IS the role's own JSON body in the engine's ordinary role shape and the filename is the base-role id; every asset fold registers each entry into the same registry `NpcRoleGenerator.registerBaseRoleResource` feeds (asset load precedes plugin `start()` role generation, so the timing holds). A base id already registered from Java is OVERWRITTEN by the asset (`defaults < pack < owner`), logged once at INFO naming both.
- New: `npc/placement/PlacementRegistryLedger` + `registry/RegistryLedger<T>` (zc-core) - a generic owner-attributed registry ledger: who registered each id, an identity-compared warn-once on an overwrite (so re-registering the SAME provider stays silent), a per-id failure count plus last message, and an `info()` snapshot for an admin listing. It is what lets a consumer's admin surface tell "nobody claimed this id" apart from "claimed, but its provider keeps throwing". `PlacementRegistryLedger` is a thin FQN-preserving subclass over it.
- New: `factor/` (zc-core) + `factor/HytaleFactors` and `entity/HeldItemUtil` (zc-entity) - ONE shared condition-factor vocabulary, so a gate on a number another mod owns means the same thing everywhere it is authored. `FactorContext` (nullable orthogonal leaves: param, world, store, subject ref, opaque payload), `FactorProvider` (a nullable `Double`; null = cannot answer), an instantiable ledger-backed `FactorRegistry` (each consumer builds its own; a dialogue's is installed into the shared engine's single factor slot), the ONE `FactorCondition` codec `{Factor, Param?, Min?, Max?}`, and a `FactorConditions` array evaluator. **Null-sentinel fail-closed everywhere**: an unregistered id, a provider that cannot answer, and a provider that throws all read alike, and a gate that cannot be evaluated never opens - which makes a condition with NEITHER bound a genuine presence check ("only where that mod is installed"). The codec is a FACTORY, not a single static, so each consumer names its own Asset Editor dropdown dataset (an unserved dropdown renders as an EMPTY pick list, which is worse for an author than a plain text field); `FactorCondition.CODEC` is the no-dropdown instance. `HytaleFactors` is the PORTABLE standard library - `hytale:stat` (any registered `EntityStatType` channel, the subject's folded max), `hytale:tool_power` / `tool_durability_percent` / `tool_quality` / `tool_item_level`, plus the new `hytale:held_tag` (through the shared `codec/TagMatch`) and `hytale:held_item` - registered into a consumer's own registry with one `registerInto` call. **The namespace names the vocabulary's OWNER, not whoever registered it**: every id there addresses data the ENGINE owns, so two mods converging on `hytale:tool_quality` is agreement rather than a collision, and a consumer whose own site resolves an id differently (a work session holding a tool snapshot rather than reading the live hand) registers its own provider under the SAME id in its own registry - same vocabulary, context-appropriate resolution.
- New: dialogue `{"Type":"World", ...}` and `{"Type":"Factor", ...}` conditions. `World` holds the three `Where` axes and hands them to `world/WorldSelector`, so the rank ladder, the bare-word-is-an-exact-name rule and the exclude-is-a-FILTER rule all come from the one authority; the world read is `store.getExternalData().getWorld()` through a guarded helper, so `DialogueContext` needs no new member. `Factor` holds the four authored leaves and hands them to the shared `FactorCondition`, resolved against the `FactorRegistry` installed into the shared engine's one factor slot (`DialogueEngine.installFactors`), with the player supplied as both store and subject. Both fail closed: an unreadable world, a `Where` with no positive axis, an unregistered factor id, and a server where nobody installed a registry at all each hide the gated content. So a pack can gate a dialogue option on a stat or a held item with zero Java.
- New: `dialogue/DialogueOnce` - `Once`, the authored SEEN-NESS knob, on a `Start` entry or an option. `"Once": true` (once per character) or `"Once": {"World": "<name or pattern>"}` (once per world FAMILY); the boolean is shorthand for the empty group, normalized by the sugar pre-pass so the codec only ever sees an object, and a future axis is a new nullable leaf rather than a mode. **Entry-level Once is spent by COMPLETING the beat** - the player chooses any option on the routed node, the page's implicit farewell row included - so leaving mid-beat re-shows it, and nothing is written on a path where the actions never ran. **Option-level Once is keyed by `LabelKey`, never by index**, so reordering a node's options can neither resurrect nor spend one; an `OnceId` leaf covers a duplicate-label or label-less option, and an option with neither stays repeatable with a warn-once plus a validator finding; two Once-bearing options in ONE node landing on the same identity is its own validator error (`ONCE_DUPLICATE_IDENTITY`), since they would otherwise share a single flag. The `World` scope is keyed by the pattern's literal CORE precisely because an instance world is destroyed and re-created under a fresh uuid name, which would otherwise re-show a first-visit beat on every fresh instance.
- New: `dialogue/DialogueMemory` - `Memories`, the authored NAMED state, declared once at the dialogue top level with its scope and lifetime and then referred to by BARE NAME everywhere else. Three nullable orthogonal leaves: `World` (per world family, taking the same name-or-pattern string as `Once`), `ResetWithQuest` (filed inside that quest's own namespace, so a consumer's quest reset forgets it too - a DECLARED lifetime replacing any convention an author used to hand-compose), and `Shared` (visible to every dialogue that declares it; mismatched declarations are a validation error, because two dialogues would otherwise silently mean different state). Use sites are the `Remember` / `Forget` actions (option sugar `"Remember": "<name>"`, bare-key expansion orders 32/33 so a memory write trails the band a consumer registers its own quest sugar in) and the `Remembered` / `NotRemembered` conditions. The map decodes through `codec/InheritMapCodec` like `Nodes`, so a `Parent` child re-declares or adds ONE memory and inherits the rest. New findings raw flags made impossible: an undeclared name (error), a shared-scope mismatch (error), a blank name (error), a blank world scope and a scope pattern that would match every world (both errors), declared but never written (warning), never read (info).
- Changed: `dialogue` drops `SetFlag` / `Flag` / `NotFlag` from the engine's PRE-SEEDED generic types, replaced by `Once` and `Memories` above. Unreleased-1.4.0 change; additive registration means this is not a ban, since a consumer that genuinely wants raw flags registers its own action and condition types into the shared engine. `DialogueFlagStore` and the key-composition machinery survive as INTERNAL plumbing - the new knobs write through the same store, and `dialogue/DialogueStateKeys` owns every shape (`once:e:`, `once:o:`, `mem:d:`, `mem:s:`). **A `ResetWithQuest` PREFIXES its quest segment onto the whole key while a world scope wraps only the FINAL segment**; that ordering is load-bearing rather than cosmetic, because a consumer clears a namespace by a LEADING-prefix match and a prepended world scope would escape the clear and soft-lock the dialogue permanently. A scope the current world does not match makes a write a no-op and a read unset; a pattern matching no loaded world warns once per pattern per process, since a typo would otherwise re-show a first-visit beat forever. **No author ever sees a composed key again.** Kweebec's authored dialogues used no flags and its in-memory store is untouched.
- New: `ZiggfreedCommonPlugin` registers its OWN `AddWorldEvent` / `RemoveWorldEvent` / `PlayerReadyEvent` / `PlayerDisconnectEvent` listeners rather than relying on a consumer to forward them, and `cast/WorldEvictors.onWorldRemoved` gains an already-evicted self-guard: with two consumer mods installed the eviction fan-out previously fired TWICE per world, which is harmless for a map removal and corrupting for a refcounted unpin.

Two whole progression lifecycles, one loot vocabulary, and the shared cores underneath both, so a mod shipping quests, achievements, drops, stamped gear, or NPC conversations reuses one engine family instead of growing its own. The library gains a module (`zc-loot`), renames one (`zc-quest` becomes `zc-progression`), and keeps its single-jar identity throughout. Additive over the rest of 1.4.0 except the retirements named below, every one of which retires an UNRELEASED surface.

- New: `zc-progression` - **TWO lifecycle engines over ONE set of shared cores**. A quest is an ACTIVE SET (accepted, tracked, abandoned, handed in, back on a cooldown); an achievement is ALWAYS ON (every criterion of every catalogued achievement listens from the first event and one earns itself the moment its criteria are met). Those lifecycles are genuinely different, so they ship as PEER engines (`quest/QuestEngine`, `achievement/AchievementEngine`) rather than one engine with a lifecycle switch - full unification was rejected because the special-casing would thread through every method. What they share is shared for real: the objective vocabulary and its matching, the reward-kind registry, the gate model, the asset machinery, the authoring GROUP CODECS, and the native-event plumbing. Both ship ZERO content and ZERO domain vocabulary, enforced by an agnosticism test that walks the module source. Roughly 254 tests in the module.
- New: `progress/` - the cores both engines rest on, and nothing here may name either of them. `ObjectiveDef` is one authored objective (kind, target, match mode, qualifier, amount, zone, order, hand-in lock); `ObjectiveKind` + `ObjectiveKindRegistry` are the OPEN kind vocabulary, per consumer, pre-seeded with 21 engine-generic kinds (`BREAK_BLOCK`, `PLACE_BLOCK`, `CRAFT_ITEM`, `KILL_ENTITY`, `DEAL_DAMAGE`, `PICKUP_ITEM`, `TALK_TO_NPC`, `CATCH_FISH`, `TURN_IN`, `COMPLETE_QUEST`, `TAKE_FALL_DAMAGE`, `PLAYER_DEATH`, `SPRINT_DISTANCE`, `SWIM_DISTANCE`, `BREED_ANIMAL`, `FEED_ANIMAL`, `HARVEST_ANIMAL`, `COMPANION_COMBAT`, `REACH_LOCATION`, `CONSUME_ITEM`, `STAT_THRESHOLD`) and open to a consumer's own; `MatchFlavor`/`MatchMode`/`ObjectiveMatch` carry BOTH matching dialects deliberately unmerged (one is case-sensitive, one is not, and collapsing them would silently re-target somebody's content); `ZoneRef`, `ObjectiveProgressState` (plus its byte-stable `"current/required"` wire form), `ObjectiveIndex` (the inverted kind-to-objectives index the dispatch hot path walks, owner-agnostic via accessors), `DispatchOptions` (two independent switches, three named combinations) and `ProgressDispatchTap` (the side channel both dispatches feed) round it out.
- New: `progress/ObjectiveKindRegistry#STAT_THRESHOLD` - the VALUE-BASED kind whose `Target` is a native entity stat channel id and which completes when that channel reaches `Amount` (high-water). It settles through an optional factor-registry seam at accept / self-heal / content-touching dispatches, so it completes even when no consumer ever fires it; a consumer that wants instant credit may fire it on change as well. `Target` is required, and an authored `STAT_THRESHOLD` without one is a validator warning rather than a criterion nobody can ever meet.
- New: `progress/gate/` - the ONE requirement model behind every `Requires` block, so a gate means the same thing on a quest, on an achievement, and on whatever comes next. `GateClause` is four independently optional leaves: `Factors` (the shared numeric gate over the factor vocabulary, identical to the one a dialogue option or an NPC placement is written with, FAIL-CLOSED so content gated on an absent mod stays gated), `Permission` (a native Hytale paradigm, so it is a built-in leaf), `Quests` (completed-quest prerequisites, built in because the quest engine itself owns that answer), and `Custom` (requirement kinds a mod registered under its own namespaced id). `GateSpec` adds `AllOf`/`AnyOf` groups, `GateKind`/`GateKindRegistry` are the open registration table, and `GateEvaluator` walks the lot. Skill levels get NO bespoke leaf anywhere: a consumer registers its friendly spelling as SUGAR that desugars onto factor conditions.
- New: `progress/asset/` - the authoring GROUP CODECS both engines append, declared ONCE so their field names cannot drift apart and a shared renderer never needs two branches. `ContentTextAsset` (`TitleKey`/`FlavorKey`), `ObjectiveLeafAsset` (the objective/criterion leaf), `RewardEntryAsset`, `ContentListingAsset` (`Category`/`SortOrder`/`Tags`/`Chains`), `ContentMeta` (`Meta`), and `ProgressEditorDataSets` for the Asset Editor pick lists. Every leaf is `appendInherited`, so content with a `Parent` can be re-sorted or re-titled without losing what it did not mention.
- New: `progress/asset/ContentMeta` - `Meta: {"<namespace>": {...}}`, the labelled box on every content asset for whatever the mod that RUNS the content needs to say about it (which ladder rung it is, which conversation follows it, which server feature has to be on) without any of that vocabulary entering a schema meant to serve every mod at once. **Nothing interprets a block it does not own**: a namespace is kept exactly as authored and handed on, so an asset written for two mods still loads with only one of them installed. Inheritance is per namespace (a child inherits every namespace it does not mention and replaces whole the one it does; there is deliberately no deep merge, because a block has no schema at this level and a merge would have to guess). A consumer declares an ordinary `BuilderCodec` for its own block and calls `ContentMeta.decode`, which hands back the typed value AND reports any key the codec does not know, so a typo surfaces as a named warning instead of a silently ignored knob.
- New: `progress/asset/ContentTextAsset.TextArgs` - `TextArgs: {"Title": [...], "Flavor": [...]}`, auto-calculated text arguments filling `{0}`, `{1}`, ... of the keys beside them, so a line reading "Mine 20 ore" carries the 20 from the content itself instead of from a translator retyping it. `@amount` is the pre-seeded sentinel (the objective's or criterion's own amount, handed over as a raw value; the consumer formats it and passes it as a nested `Message` per the localization invariants). It lives on the shared text group rather than in any consumer's `Meta` block, because auto-calculated args are a generic authoring capability and one carrier is better than several.
- New: `progress/asset/ContentListingAsset#Chains` - `Chains: [{"Id": "<free string>", "Tier": n}, ...]`, MULTI-MEMBERSHIP tiered ladders on both content kinds. A piece of content may be a rung of several ladders at once, each with its own tier (a mining achievement can be rung 3 of the copper ladder and rung 1 of the whole-game one), so a surface can render a whole climb as one entry rather than a row of near-identical ones. Chain ids are unnamespaced free strings; prefix by convention if collisions worry you. It is ONE leaf, so authoring it replaces an inherited list whole. Validator findings: a duplicate chain id within one item, a non-positive tier.
- New: `quest/` + `quest/asset/` + `quest/event/` - the consumer-agnostic QUEST lifecycle: a per-consumer `QuestEngine` owning matching, ordering, cooldowns, hand-ins, completion and payout bookkeeping, with the consumer supplying storage (`QuestProgressStore`, plus a ready-made in-memory one), gates, inventory access and naming. `quest/asset/` is the authoring half (`Server/ZiggfreedCommon/Quests/<id>.json`, Pattern A with engine-native `Parent` inheritance and a per-objective-id merge, so a child re-tunes one objective and inherits the rest), plus `QuestGeneratorAsset`/`QuestGeneratorExpander` (a generator writes a whole family as ordinary `Parent` children over an authored axis, resolved through the consumer's registered `QuestValueEnumerator`s), the pool and its validator. `quest/event/` is five native `IEvent<Void>` POJOs (accepted, objective progressed, completed, claimed, abandoned) dispatched through the engine's own event bus, so a third party listens the way it listens to anything else.
- New: `quest/Quest.Repeat` - the whole vocabulary for a quest that comes back around, evaluated by the engine for every consumer rather than re-implemented per fold. **Authoring the group AT ALL is what makes a quest repeatable**, so `Quest#repeat()` is `@Nullable` and its presence is the flag (a `Repeat.NONE` sentinel was rejected: a sentinel is a value a caller can mistake for an authored one). An EMPTY group means externally governed - the quest has no clock of its own and whatever offers it decides when it returns, which is what a rotating, period-based offer needs. Inside it sit four INDEPENDENT constraints, ANDed by one evaluator, plus the clock origin: `Cooldown` (a rolling wait), `CooldownFrom` (`Claim`, the reward being taken, by default, or `Complete`, the objectives being met - the form a rotating offer wants, so walking back to collect after the offer rotates does not burn a slot in the NEW period), `Reset` (`{Period: Daily|Weekly, At, Weekday, Times}`, a calendar allowance where COMPLETING consumes the period regardless of when the reward is taken; anchors are UTC server clock only, a timezone leaf being a later additive knob if one is ever wanted), and `MaxCompletions` (a lifetime cap). This replaces the earlier draft's `StampOnPark` boolean, which said less in more places: `CooldownFrom: Complete` is the same semantic under a name that explains itself, and it composes with the other three instead of standing beside them. Store additions are ADDITIVE (a last-completion stamp and a per-period count beside the existing cooldown stamp), so a consumer's persisted blobs decode unmoved. An ADMIN reset wipes the completion record (a reset means starting over); `selfHeal` and abandon preserve it, so a lifetime cap stays enforceable in play.
- New: `time/DurationGroup` - the ONE structured way a duration is authored anywhere in the library: a nested `{Days, Hours, Minutes, Seconds}` group of nullable non-negative numerics, summed, so `"Cooldown": {"Hours": 24}` and `{"Minutes": 1440}` are the same wait and neither needs a parser for a `"24h"` string. Empty or all-zero is a validator error wherever a duration is required. The existing scalar `*Seconds` keys retrofit onto it in a later cycle.
- New: `achievement/` + `achievement/asset/` + `achievement/event/` - the ALWAYS-ON peer lifecycle over the same cores. `AchievementEngine` owns matching, counting, earning, collecting, points, milestones and pins; the consumer supplies storage (`AchievementProgressStore`, plus an in-memory one) and `AchievementGates` (`canProgress`/`canUnlock`/`canReceiveRewards`/`visible`, all default-yes). **Criterion progress is keyed by POSITION** (`"<id>#<index>"`, with a one-way fallback to a legacy no-index key), so appending a criterion is safe while reordering one is a data migration - asserted directly in the engine test. Two reward lists, two moments: `Rewards` land on earning, `ClaimRewards` wait to be collected. `Scoring` carries `Points` plus `CountsTowardTotal` (default true), and an authored `CountsTowardTotal` is honored by a consumer's fold - the MMO's does, with a feat-of-strength still forcing it false. `achievement/asset/` shares the text / objective-leaf / reward-entry / listing / gate groups with quests; `Criteria` is an ORDERED array a `Parent` child replaces whole, precisely because progress is keyed by position. `achievement/event/` is three native `IEvent<Void>` POJOs (unlocked, progressed, claimed).
- New: `progress/runtime/ProgressionRuntime` - **ONE quest and achievement engine pair per server, however many mods contribute to it.** This library owns the instance; a consumer EXTENDS it with registrations from its plugin `setup()` rather than standing up a pair of its own: a store swap (so a consumer's persistence, its fixtures and its database seam survive untouched), domain-keyed producer REPLACEMENT (the library's generic block-break / kill / craft / pickup producers stand down per replaced domain, which kills double-fire structurally rather than by a runtime check), and gates, factors, reward kinds and objective kinds through the registries that already existed. Content is published into the shared instance by each consumer's fold. The first read or the first player ready calls `ensureBuilt()`, which seals the sealed parts, composes the contributions, builds both engines and logs ONE diagnostic naming who answered for what. Nothing decides WHETHER to run: there is one runtime, always, and the only question is which parts it was built over. **Why it is shared and not per consumer:** two runtimes over two stores is double-tracking, where the half a surface reads is not always the half that can pay out, so a hand-in reads as ready and does nothing - a failure class that can exist at most once on a server rather than once per mod. The engines are built once and never rebuilt: everything they reach the outside world through is a forwarder over `ProgressionParts`, so a late registration is honoured on the next call and every cached reference stays valid. `ProgressionRuntimeClaim` retires into this surface. Two seams ship with it: `ProgressionCallScope` (a consumer wraps mutating calls so a claim driven from someone else's UI still fires the consumer's own full feedback) and `ProgressionTextSource` (a merged catalogue, so content authored in a consumer's older format still renders titled in a surface that never heard of that format).
- New: `zc-objectives` - the STANDALONE progression runtime surface, so this library is not only an engine a mod has to wire but something a bare server can run on. It registers a persisted per-player component (`store/`) as the shared runtime's store, folds the shared `Quests` and `Achievements` asset stores in, contributes four generic native-event producers (block break, mob kill, craft, pickup), and ships an in-game two-tab Quests | Achievements page opened from an ordinary item: `Ziggfreed_Objective_Book` ("Objective Book"), obtainable through authored content or `/give` and never auto-granted, since a library has no business pushing an item into a player's bag on its own initiative. The book reads the shared runtime everywhere, so it shows a consumer's content and its own in one list rather than an empty tab. A consumer that wants a different book redeclares the item at the ITEM layer and points it at its own page, the way any pack re-authors a shipped item. The module sits ABOVE both `zc-progression` and `zc-presentation` because the book needs the engines AND a page while `zc-progression` may never import presentation, which is the one position that adds no reverse edge.
- Changed: the shipped `.lang` files split PER DOMAIN instead of one `ziggfreedcommon.lang` monolith per locale. A file's basename minus `.lang` is a key PREFIX the engine folds in verbatim, and every file under a locale merges into one map, so `ziggfreedcommon.fmt.lang` holding `cat` resolves as `ziggfreedcommon.fmt.cat` and a resolved key is byte-identical to what it was in the monolith - a split MOVES keys (the in-file key drops the segment the filename now carries) and changes nothing a client sees. A key lives in exactly ONE file, because a collision is first-writer-wins with a warning and filesystem-order nondeterminism, which is not something to leave to chance. This cycle splits `ziggfreedcommon.lang` and files every NEW key family this way (`ziggfreedcommon.fmt`, `ziggfreedcommon.progression`, plus `items.lang` for the shipped item names); the module a key belongs to owns its file, so a lang file travels with the code that reads it.
- New: `asset/NestedAssetId` (zc-core) - folder grouping that can contribute to an id. The engine names an asset after its FILE and nothing else, which leaves an author choosing between folders that read well and ids that do not collide. A folder marked with a LEADING UNDERSCORE contributes its name (sans `_`, lower-cased) as an id prefix, stacking in path order joined with `_`, so `Quests/MMOSkillTree/Zones/_Wilds/Trork_Trouble.json` is `wilds_trork_trouble` while every unmarked folder stays organizational and inert - an existing tree keeps the ids it has and nothing moves under an author until they opt in. The asset scan is recursive, so `Server/ZiggfreedCommon/Quests/<Namespace>/<Feature>/<Questline>/` is a free organizational choice. Wired into Quests and Achievements this cycle; every other type keys plainly off its filename until a later pass wants the same grouping. **Pick a marked folder name as carefully as a filename**: renaming one renames every id beneath it, and an id is what a player's saved progress is filed under.
- New: `zc-loot` - a module for the ONE loot core, so a station's rare find, a chest, a mob's bonus drop and a quest reward that rolls a table all behave identically on identical JSON. A `Roll` is `{Trigger, Conditions, Chance, Ladder, Grants, Cue}` read in that order; `RollEvaluator` is the PURE decision and `LootEngine` the half that acts, entirely through seams (item sink, drop-list sink, command dispatcher, reward registry), so a caller supplying none still gets a full evaluation with no effects. `LootableAsset` (`Server/ZiggfreedCommon/Lootables/`) and `LootRef` (an inline `Roll` OR a reference to a shared lootable, one vocabulary either way) are the authoring surface; `LootableValidator` audits roll structure once for every consumer; `LootFactors` turns an instance run's score and outcome into ordinary factor readings so a win gate is an ordinary condition. `Chance` carries the full `{Base, Factors, Clamp}` formula wrapper, and the unclamped multiplicative sites keep bare `Term[]` arrays through the one shared evaluator. Roughly 176 tests.
- New: `loot/stamp/` - the same shape for stats written onto an item. `StatRollEntry` / `RollPoolAsset` / `StampSpec` are the authored side; `StampCapEngine` is the pure decision (lowest budget binds, per-stat ceiling on top, and a fully-capped attempt is DENIED so nothing is charged for a stamp that cannot land); the WRITE sits behind the pluggable `Stamper` contract, with `StackStatsStamper` (writing the shared `stats.StackStats` per-stack metadata blob) as the default the wiring root installs on `StamperRegistry`. Rolled-random and authored-specific stamps are the same path with a different spec.
- New: `loot/stamp/Stamper#describe(StatRoll)` - a default-bodied hook returning a `Message` for one committed roll, so the stamper that OWNS the stat vocabulary is the thing that names what it wrote. The default returns null and the engine renders its own honest fallback, which means a consumer opts in by implementing one method rather than registering anything. The write boundary is unchanged: the write itself stays display-blind, and this is the one nuance on top of it.
- Changed: **there is now ONE world-targeting vocabulary, and it tells the truth about the main world.** `WorldNameMatcher` is reduced to what it always should have been - the pattern GRAMMAR that parses and scores and never SELECTS - and its `resolve`/`Entry` selection half retires along with the parity test that existed only to keep two ladders agreeing. `WorldSelector` plus `MatchRank` is the one selection path, so no consumer keeps a private ladder. `WhereValidator` absorbs the audit the placement and dialogue validators each kept privately - one shape check plus `MATCHES_NO_LOADED_WORLD` for a `Where` describing none of the loaded worlds, under one domain - with an empty world roster meaning "cannot tell" rather than "no".
- Changed (HARD BREAK): **named world selectors die as vocabulary.** There is no `WorldSelectors` asset type, no `Where.Names` axis and no `mods/ziggfreedcommon/world-selectors.json`: a `Where` carries `Match` / `GameplayConfig` / `ExcludeMatch` and nothing else, so what a file targets is readable where it is written instead of through an indirection that reads exactly like a missing wildcard. Rewrite `"Names": ["<selector>"]` as the patterns that selector held - `"Match": ["default"]` for a fresh Hytale world's main world (a bare word is an EXACT name, so it reaches that world and no other), `"GameplayConfig": ["ForgottenTemple"]` for an instance family. **"My main world is named something else" is served by each asset's own owner layer**, the ordinary `defaults < pack < owner` move on the handful of files that target it, with no new concept.
- Changed (HARD BREAK): **a dialogue world SCOPE authors `World`, one string.** `Once`, a `Memories` declaration and `DialogueFlagScope` take a world NAME or a pattern in the full `WorldNameMatcher` grammar rather than a selector name; the pattern IS the exact-versus-fuzzy knob, so there is no second leaf. State keys by the literal name or the pattern's literal CORE (`*KweebecNightmare*` files under `KweebecNightmare`), which is the stable handle across an instance being destroyed and rebuilt under a fresh uuid name, and a narrower core (`*KweebecNightmare_Barn*`) scopes per arena. A bare `*` is treated as no scope at all. The runtime warn-once re-bases from "unknown selector name" to "pattern matches no loaded world", and the validator reports only what a decoded file can prove wrong. Separately, `DialogueCondition.World` nests its axes under a `Where` group like every other world-targeting field, and an omitted `Where` fails closed.

Unit-tested (`InstanceRewardMergeTest`). Any consumer rolling a loot table (which intentionally yields repeated picks) routes its result through here.

## 0.3.2
- New: score-tiered **loot tables** in `instance/reward/` - a reusable, pack-authorable reward-pool primitive. `LootTable` rolls a fixed `Guaranteed` list plus `clamp(Rolls + score/ScorePerBonusRoll, 0, MaxRolls)` weighted picks among `Pool` entries the player's run score unlocks (`LootEntry`: a weighted, `minScore`-gated, quantity-ranged template, compact spec `[w<n>] [s<n>] <kind> <id> <qty|min-max> [displayKey]` - a superset of `InstanceReward`'s). Deterministic per injected seed (mirrors `SpawnRoster`'s weighted pick), so "better loot for a better score" comes from BOTH premium entries unlocking AND more rolls. Pattern-A `LootTableAsset` + `LootTableConfig` (`Server/<Mod>/LootTables/`, registered by `FrameworkAssetRegistrar`, `defaults < pack < owner`); a preset references one by the new `InstancePresetAsset.RewardTableId`. Common ships ZERO content (all pool JSON is consumer-authored). Unit-tested (`LootEntryTest`/`LootTableTest`); `LootTableAsset.CODEC` guarded by `AssetCodecInitTest`. Kweebec Nightmare's chase end-game rewards are the exemplar consumer.
- New: `instance/zone/ZoneHoldTimer` - a reusable co-op "hold this zone" objective primitive. The required number of occupants must stay in a zone TOGETHER for a configured duration, and the hold RESETS the instant the group breaks; it latches complete once the continuous hold elapses. PURE + engine-free (the caller injects the live occupant/required counts and its own `nowMillis`, mirroring `EncounterDirector`), unit-tested, with `isHolding()`/`remainingSeconds(now)`/`progress(now)` HUD queries. The consumer owns WHO counts as an occupant, WHERE the zone is, and what completion does. Reusable for an extraction pad, a capture point, king-of-the-hill, or a ward-defense hold. Lifted from Kweebec Nightmare's Chase extraction platform (the exemplar consumer); a future dungeon / raid consumer is the target.
- New: per-phase HELPER-THROWABLE cluster knobs on `instance/encounter/MultiPhaseBossAsset` (the reusable multi-phase boss). A boss phase can now author harvestable resource clusters the consumer's controller places + replenishes around the boss, so survivors gather + throw them at a high-HP boss to keep it killable: `ThrowableClusterId` (an opaque id the consumer resolves - Kweebec treats it as a prefab key), `Phase{1,2,3}ThrowableCount`, `ThrowableRingRadius`, and `ThrowableRespawnSeconds` (the configurable regrow timer). All optional, default off (zero counts), so existing bosses are unchanged. Placement reuses the existing `SpawnPlacement` ring + `EncounterDirector` primitives caller-side; common stays pure data. Kweebec Nightmare's Warden is the exemplar consumer (the boss-phase Emberbloom supply).
