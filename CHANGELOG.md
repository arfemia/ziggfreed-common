# Changelog - Ziggfreed Common

The dev changelog for the shared, mod-agnostic Hytale primitive library. Newest first. No em-dashes.

## 2.1.0 - unreleased

> **Draft, and open.** The entries below are landed and build-green; the section collects everything since 2.0.0, so the 2.0.1 draft's lines sit here beneath this cycle's own. `gradle.properties` reads `2.1.0`: the `PlacedBlockLedger.Policy` change below is a BREAKING one and a consumer pinned at `2.0.0` must fail by name at boot rather than hit a linkage error mid-placement, and the fourteenth module is a whole new surface. Nothing here has been through an in-game smoke pass beyond the headless boot the encounter module is gated on.

- **Gone: the Java boss and wave engine.** `MultiPhaseBossAsset`, `MultiPhaseBossConfig`, `EncounterDirector`, `EncounterRuleAsset`, `EncounterRuleConfig`, `SpawnRoster` and `SpawnUnit` (the whole `instance/encounter/` package) are deleted, and with them the `ZiggfreedCommon/Bosses` and `ZiggfreedCommon/EncounterRules` asset stores: a file a pack still ships under either path is not read and nothing warns about it. A boss's phases, adds and waves are a native encounter script's own (`zc-encounter`, above); the only shipper of the old content, Kweebec Nightmare 1.2.0, authors its Warden and its hunter waves that way.
- **New: the encounter audit catches a script named after an NPC role** (`ENCOUNTER_SCRIPT_ID_IS_ROLE_ID`). The engine keeps one builder per name across roles and encounter scripts, so a script sharing a role's id replaces the role at load (or the role replaces the script, whichever loads last) and the loser is gone from the builder map with nothing but an engine spawn-time refusal to say why. The finding fires from what is still visible: a spawn marker roster entry or an NPC placement naming a role that resolves to a loaded script, or a binding row naming a script that resolves to a loaded role; it names the script, the reference and the fix (a trailing `_Encounter` is the family's convention). `EncounterAudit.addRoleNameSource(kind, supplier)` is how a store the module may not import hands it the roles it names; the root registers the placement engine's, and the spawn markers are read directly.
- **New: `zc-encounter`, the fourteenth module, the boss framework over Hytale's own `EncounterManager`.** The fight is a native encounter script under `Server/EncounterManager/` and the engine runs it (states, phases, health thresholds, in-place role swaps, invulnerability, adds, the boss bar, the music, membership, hot reload); this module adds only what native cannot do, all OUTSIDE the script, and re-implements nothing. A script speaks to it through the engine's own `SignalWorldEvent` action with the reserved `zc:<moment>[:<detail>]` grammar (`zc:engaged`, `zc:phase:<State>`, `zc:wave[:<label>]`, `zc:defeated`, `zc:reset`; any other `zc:` id is the author's own beat), and `EncounterSignalSystem` (an `EntityEventSystem<EntityStore, WorldEventSignal>` queried on the encounter component, registered through `registerSystem`) turns each beat into a native `IEvent` on the engine bus through one `NativeEventSeam`: `EncounterEngagedEvent`, `EncounterPhaseChangedEvent`, `EncounterDefeatedEvent`, `EncounterWipedEvent`, `EncounterResetEvent` (always the last event of a run) and `EncounterSignalEvent`. Identity is read off `EncounterManager.getEncounterId()` on the signalling entity, never off the string. The run itself is `ZigEncounterRun`, a component registered with the codec-less overload so no chunk save carries it and a reload mints a fresh run; its subject is keyed by uuid and re-resolved through the script's own target slot every read, because an in-place `ChangeTargetRole` reissues the boss's reference. `EncounterDeathSystem` latches the precise defeat the instant the bound subject's death component lands (the authored `zc:defeated` is the fallback for a fight with no bound boss), `EncounterDamageSystem` observes the engine's INSPECT damage group without touching the value (two empty-map lookups on the miss path), and `EncounterTickSystem` re-resolves the subject and the members after the engine's own tick, re-stamps a spawn call's seeded party through `EncounterMembers.stampMember`, credits presence, applies and reconciles the health scale, watches for a wipe (`WipeGraceSeconds`) and a timeout (`MaxRunSeconds`), and moves the map marker. While a fight is OPEN (engaged, not yet settled) the tick holds the encounter's chunk ticking by resetting its active timer, the lever the engine itself pulls for a chunk a player stands in, so those two guards are measured by the encounter tick and never cut short by a chunk going cold once everybody has left or died; a run spawned WITH an owner key (a round's boss, stood up at its arena while the party is still at the other end of the map) is held from the moment it is added as well, because its owner, difficulty, party and multiplier live only on the codec-less run and an unload before the party arrived would hand back a fresh, unowned one; a settled run lets go and the chunk follows the engine's ordinary schedule, and an unowned run that has not engaged is never held (`EncounterChunkHold`). One `[encounter]` INFO line per run event, never per tick.
- **New: `EncounterBindingAsset`** (`Server/ZiggfreedCommon/Encounters/<Id>.json`, Pattern A, owner layer `mods/ziggfreedcommon/encounters.json`): what the server OWES for a script it does not describe, in nine nested groups with every leaf nullable (`Subject`, `Participation`, `Scale`, `Timing`, `Loot`, `Leaderboard`, `Progression`, `Feedback`, `Discovery`) plus `EncounterAsset` (the script id, defaulting to the row's own), `NameKey` and `Enabled` (false means the library neither spawns, binds, scales nor pays that encounter; the owner file flips it per id and `/zigencounter reload` re-reads it). `BindingRestatesNothingTest` fails the build on any codec key naming a phase, threshold, count, sound, role or spawner, the machine-checked statement that the script owns the fight.
- **New: `EncounterParticipationAsset`** (`Server/ZiggfreedCommon/EncounterParticipation/<Id>.json`, Pattern A, owner layer `mods/ziggfreedcommon/encounter-participation.json`): how credit for a fight is shared, matched to a run by the subject's mob id (`Match`, a `NamePattern`) and the world (`Where`, the shared selector), the three channel weights (`DamageDealt`, `DamageTaken`, `Presence`) as `FactorFormula` leaves read about each participant, `MinShare`, `CreditDead`, `CreditDisconnected`, `Enabled`. The most specific rule wins on the library's own ladders (the subject axis first, the world axis as the tie-break, first by id on a full tie); a binding row's own `Participation` group overrides the matched rule leaf by leaf. The library ships the match-all `Zc_Default` (dealt 1.0, taken 0.25, presence 0.1, `MinShare` 0.05, the dead and the disconnected credited); the structural posture under every rule is damage dealt counting one for one and nothing else. Credit lives in `ParticipationLedger`, pure, keyed `(runId, playerUuid)` and never by player alone (a player can stand in two overlapping fights), with shares normalised against the TOP contributor so the player who did most reads 1.0; a share under `MinShare` is attempt credit only.
- **Loot, feedback and discovery pay what the row owes.** `Loot.OnDefeat` is rolled once PER credited participant against their own factor readings, and every roll they won is kept with a chance equal to their share (the top contributor keeps everything), then issued as ordinary reward specs through `RewardGrants.grantAll`, so an item lands with the usual overflow rule, a command runs with `{player}`/`{share}`/`{encounter}`/`{run}` placeholders, and an OFFLINE participant's whole payout is parked on the same retry queue every other library payout uses (`QueueIfOffline`, `CreditDisconnected`); `ToKiller` adds the last hitter at a full share; `Loot.OnPhase`, keyed by the script's state name, spills on the ground at the subject through `NativeLootService`. `Feedback` names the FeedbackMoment fired to each member at the four beats (defaults `Encounter_Engaged` / `Encounter_Phase_Changed` / `Encounter_Defeated` / `Encounter_Wiped`; the moment files themselves are not in this cycle), each behind the subject's own `FeedbackAudience`, the settlement moments carrying the reader's own `share` and `rank` as typed numbers. `Discovery` places a world-map marker over the subject at the engage, moves it every `FollowSeconds`, and removes it at the reset. `Scale` is one keyed `HealthUtil` modifier (`zc_encounter_scale`): `HealthMultiplier x runMultiplier x (1 + HealthPerMember x (members - 1)) + HealthPerPowerPoint x power`, held between 1 and `MaxHealthMultiplier`, applied once the subject's stats are ready and reconciled after every phase signal.
- **New: five encounter `Type`s registered into the shared NPC builder vocabulary** through `NPCPlugin.registerCoreComponentType`, each legal only inside an encounter script, so a pack-only boss pays, notifies and scales with zero Java: `ZigGrant` (`Loot`, `ToMembers`, `ToKiller`, `QueueIfOffline`; pays the run's credited participants share-scaled, and says so when there is nobody to pay), `ZigFeedback` (`Moment`, `ToMembers`, `ToWorld`, `Args`), `ZigScaleTarget` (`TargetSlot`, else the sensor's target, else the bound subject), `ZigMembers` (`Count: [min, max]`, the wipe test a script cannot otherwise express) and `ZigFactor` (`Factor`, `Param`, `Value: [min, max]`, over the module's own registry: the portable `hytale:` readings about the subject, `ziggfreedcommon:encounter_members` / `_elapsed_seconds` / `_phase_index` / `_waves` / `_deaths`, and any factor a mod contributed process-wide). Builder keys are flat and array-ranged, the native builder vocabulary. Each Type writes one execution line under `[encounter]`, and every action answers the engine FINISHED on every path (nothing to do included), because a `false` from an action is the engine's "still running" and a blocking action list waits on it until it says otherwise (`ActionsAlwaysFinishTest` pins it).
- **Four seams the wiring root fills, each reporting once when consulted unfilled** (`EncounterSeams`; `EncounterSeamsTest` pins it): `EncounterAttribution` (filled with the progression runtime's composed kill attribution, so a turret's or a summon's hits credit its owner), `EncounterSubjectSource` (filled with the registered subject source, so a consumer's own handle and its notification preferences reach an encounter payout exactly as they reach a quest payout), `EncounterRewardQueue` (filled with the registered reward retry queue, read live through the new public `ProgressionRuntime.rewardRetryQueue()`), and `EncounterPowerSource`, which has no library answer and waits for a companion. `EncounterEdgeTest` fails the build on an import of `zc-instance` (bar the loot and effects packages that share its prefix), `zc-objectives`, `zc-progression`, `zc-dialogue` or `zc-commerce`.
- **New: the shipped native content, zero Java, overridable by id.** `Zc_Encounter_Base` (`Type: Abstract`): the Player sensor with the `EncounterMembers` collector, a parameterised `SubjectSlot`, `TriggerSpawners` from `SpawnMarker`, the release on the Target sensor ALONE (vulnerable, bar, music, `zc:engaged`), a `FightBehavior` macro slot, the defeat beat (`ClearEncounterBossBar`, `StopEncounterMusic`, `ReleaseTarget`, `zc:defeated`) and the `Complete` re-arm with `zc:reset` after `RearmSeconds`. Three macros in the vanilla shape: `Zc_Phase_At_Health` (the health-range transition plus the `zc:phase:` beat and an optional in-place role swap), `Zc_Adds_Wave` (`TriggerSpawners` plus `zc:wave`), `Zc_Defeat_Beat`. `Zc_Encounter_Example`: spawnable, runs with no player and no boss, walks every beat and every Type and re-arms; its binding row and the default rule make it the headless gate's target (`/zigencounter spawn Zc_Encounter_Example`).
- **New: `/zigencounter list | inspect <ref> | spawn <asset> [--world=] [--x= --y= --z=] | end <ref> | state <ref> <state> [--substate=] | validate | reload`**, the library's fifth command family, console-capable (a console spawn lands at the named world's spawn point, the default world when none is named, and brings that chunk up ticking first through `EncounterSpawner.spawnWhenLoaded`, because the engine unloads an entity added into a chunk that is not ticking on the spot), engine-derived permission nodes, `<ref>` a run-id prefix or a script id resolved off the live table. Its help and answers live in a nine-locale `ziggfreedcommon.encounter.lang` under the `admin.` key family (resolving as `ziggfreedcommon.encounter.admin.<key>`), beside the boss bar's fallback name and the example's name; `EncounterAdminKeysTest` fails the build on a spoken key nothing ships.
- **New: `EncounterValidator` + `EncounterAudit`** (`/zigencounter validate`, and once per boot at first player ready): a `zc:` beat that reads like a misspelt reserved moment, a `zc:phase:` with no state, a `zc:defeated` beat with no `ClearEncounterBossBar` in its action list (an ERROR, by rule), a binding naming a script that is not loaded or is an Abstract base, two rows binding one script, a spawnable script firing `zc:` beats with no row (a note), a `Subject.TargetSlot` the script never names, a loot table nothing defines, presence weighted on a script with no member collector, a `MinShare` outside 0 to 1, a `*` in the middle of a `Match`, and a blocking action list under a sensor marked `Once` (the engine spends a Once sensor after its first tick, so only the list's first action would ever run; a list that spans ticks keeps a plain sensor and ends with the state change that stops it). The scripts are read back as authored off the builder manager (`EncounterScriptScan`, pure: it follows a `Reference` and resolves `Compute` reads through the referenced file's `Parameters` under the referencing `Modify`). A boot self-test resolves `Zc_Encounter_Base` and `Zc_Encounter_Example` by builder index on the first world load and logs SEVERE if either is missing or the Types did not register.
- **New: `asset/OwnerLayerReader` in zc-core**, the one reader of an id-keyed `mods/ziggfreedcommon/<x>.json` into a keyed config's owner layer (drop the previous layer first, decode each entry against the pack layer's own answer through the same codec, reserved `$` keys, the newer-schema refusal); `CommerceOwnerLayers` delegates its four files to it and keeps only their names.
- **The manifest declares `Hytale:NPC` and `Hytale:EncounterManager` as dependencies**, so the NPC plugin and the encounter component type are live in `setup()` when the Types and systems register.
- **A boss fight's beats are quest and achievement progress.** `ZigEncounterProducer` (zc-objectives, beside the round producer, installed by the same `ProgressionDefaults.install` and named in its boot line) listens for `EncounterDefeatedEvent`, `EncounterWipedEvent` and `EncounterPhaseChangedEvent` on the shared bus (never `EncounterResetEvent`, whose reasons include a reload and a world unload) and fires `ENCOUNTER_ATTEMPT` for every participant the ledger saw when a fight settles either way, `ENCOUNTER_DEFEATED` for every CREDITED participant when the boss falls (attempt first, then the win, the order the round producer keeps), and `ENCOUNTER_PHASE` for every live member on each phase beat. `Target` is the encounter SCRIPT id, never the creature's, so a step holds through an in-place role swap; `Qualifier` is the run's difficulty label, or the phase's own state name for the phase kind; `Amount` is 1 per fire. Each fire carries an `EncounterPayload` (the whole event plus THIS participant's share), and one INFO line per beat says how many were dispatched, so a headless fight with nobody in it reads as "dispatched for 0" rather than as silence. The engine half every bus producer shares (resolve the player, hop onto their world, re-check the store's thread) is lifted out of the round producer into `PlayerMomentDispatch`; the round producer now calls it.
- **Three more seeded objective kinds, described by files like the rest.** `ENCOUNTER_DEFEATED`, `ENCOUNTER_ATTEMPT` and `ENCOUNTER_PHASE` join the twenty-three the registry seeds (the seeded path `INSTANCE_ROUND_*` take, because a registry is per consumer and a producer-side `register` reaches none of them), each with a `Server/ZiggfreedCommon/ObjectiveKinds/Encounter_*.json` beside the others and the `objective.encounter_*` sentence keys in all nine `ziggfreedcommon.progress.lang` files. `TargetNames.Encounter` is the seventh thing a kind's file can say its target names (an encounter id is neither an item nor a creature), folded per leaf like its six siblings and read back as `ObjectiveKind.targetsEncounter()` / `ObjectiveKindRegistry.isEncounterTargeted`. New `ShippedKindFilesTest` holds the seeded set and the shipped file set equal by name, so neither can drift from the other again.
- **A value-based kind can read its amount as a CEILING.** `ObjectiveKindAsset` gains an `AtMost` leaf (with `EditorSchema` defaults on it and on `ValueBased` / `Producible`, this codec's first), `ObjectiveKind` an `atMost` knob (`ObjectiveKind.atMost(id)`, `withAtMost`), and new `ObjectiveArithmetic` is the ONE compare both engines run: an accumulating kind adds, a value-based kind keeps the high-water mark, and a value-based kind that is also at-most is met the first time a fired value comes in at or under the authored amount, a value over it moving nothing. A ceiling's recorded progress is a binary met-or-not (`0/1` on the wire), so "no deaths" is not born completed the way a zero count would be; `QuestEngine` and `AchievementEngine` mint every state through `ObjectiveArithmetic.fresh` / `stored` and apply through `apply` (a fired moment) or `applyStanding` (a stat re-read, what a player already holds at accept), so the kind-agnostic sites read the ceiling too. The knob composes with `ValueBased` and means nothing on an accumulating kind; no seeded kind reads one. `ObjectiveKindRegistryTest`'s single-value-based case is restated as the set invariant (the value-based built-ins are exactly the threshold, no built-in is a ceiling); `ObjectiveArithmeticTest` pins the compare.
- **A world first a party won together is won by the whole party.** New `progress.runtime.SharedCredit`, a `MomentPayload` a producer marks its fires with when several subjects are credited for ONE event under one key (`EncounterPayload` carries the run id); `ProgressDispatch.produce` runs the engine half of such a moment inside `FirstClaims.withSharedCredit`, and `FirstClaims.claim` (which `RequiresGates.canUnlock` now asks instead of the table directly) remembers the credit a claim was WON under, so a later claim for the same achievement carrying the same credit is a win without asking the table again. Keyed on a run identity, never a window: a second party under a second run loses exactly as before, and a re-test with no credit in scope (the login sweep, a scripted grant) never co-claims. The installed table still records one claimant, the first. No achievement knob: a shared-credit moment shares its credit by construction, and there is no authoring case for telling four members of one party they lost to the fifth.
- **New: four neutral encounter FeedbackMoment defaults** in zc-presentation's own pack, `Encounter_Engaged` (a banner: the fight's name and how many are in it), `Encounter_Phase_Changed` (an Info toast with the phase's state name), `Encounter_Defeated` (a gold Reward toast with the reader's own share and the fight's length, plus a jingle) and `Encounter_Wiped` (an Info toast with the fight's length), the ids the binding row's `Feedback` group defaults to, with their `encounter.*` keys in all nine `ziggfreedcommon.feedback.lang` files; `ShippedFeedbackMomentsTest` widens by four and pins the engaged default's scoping. `EncounterFeedback` now binds `share` as WHOLE PERCENT POINTS of the top contributor's (a typed number a line shows as `{0}%`), and adds `participants` (the players the beat is about) and `source` (the script id) beside the beat's own args, for the banner leaves below.
- **`FeedbackMomentAsset.Broadcast` gains four orthogonal scoping leaves, each absent by default so no shipped moment changes:** `ToParticipants` (the players the moment lists under the fixed `participants` argument are always shown the banner, wherever they stand), `SameWorldOnly` (only the subject's own world), `RadiusBlocks` (only within so many blocks of the subject; 0 reaches nobody but the participants) and `MinSecondsBetween` (once shown, not again for so long, kept per moment and per the fixed `source` argument, and per world when world-scoped, so two fights announce separately while one fight's per-member fires collapse into one banner). `FeedbackEngine.broadcast` now sees the moment id and the subject it lacked (the subject's store and position anchor a scoped banner; a subject that is not a live player anchors nothing, so such a banner reaches only the participants), decides each viewer through the pure `BroadcastScope.admits`, and holds banners back through one bounded `BroadcastScope.Throttle`; `FeedbackAudience`'s javadoc says the scoping is the moment's authoring, never the per-player preference. `Encounter_Engaged` ships `SameWorldOnly: true`, `MinSecondsBetween: 60`, `ToParticipants: true`, no radius. `BroadcastScopeTest` pins the leaves, the overlay inherit, the admits table and the throttle.
- **New: `EncounterLeaderboardListener` (zc-instance), the instance layer's one edge to the encounter framework.** On `EncounterDefeatedEvent`, when the fight's binding row names a `Leaderboard.Bucket`, one `Leaderboard.record` per participant into `<Bucket>[:<party size>][:<difficulty>]` (the `ByPartySize` / `ByDifficulty` suffixes, `any` for a run with no label): the score is the participant's share in whole percent points (best score reads "who carried the most", total points accrue per fight), the time is the fight's length (kept lower on a win, so the fastest clear is free), and the stat bag carries `damage_dealt` and `damage_taken`. The board is the listener's own (`encounter-leaderboard.json` under the library's data directory), read back through `EncounterLeaderboardListener.board()`. New `InstanceBootstrap.installEncounterLeaderboard` is zc-instance's first bootstrap and its first line in the wiring root; `zc-instance/build.gradle` gains the edge and drops its stale mention of an encounter director. `InstancePresetAsset` stays boss-unaware.
- **New: the `ziggfreedcommon:counter` factor** (zc-core `factor/CounterFactors`, contributed process-wide from the progression bootstrap beside `hytale:mod_installed`): a player's lifetime TALLY as an ordinary reading, `Param` a flat counter key (`mob_kills` for a total, `mob_kills/Warden` for one line of a breakdown, the counter package's own grammar), so a `Requires` block, a dialogue condition, a placement or a shop offer can say "you have done this, this often" with no bookkeeping achievement. Whoever keeps the tallies installs a `CounterSource` (`CounterFactors.source`); an unknown key and a player who has never done the thing both read `0` (so every condition needs a `Min`), and no source, no `Param` or no live player reads `null`, never `0`, with the unfilled seam reporting itself once.
- **New: the `ziggfreedcommon:encounters` generator axis** (`EncounterQuestAxes.install(registry, owner)`, zc-objectives): every bound, enabled encounter read live off the folded binding rows at expansion, each row binding the axis's own token to the encounter SCRIPT id and `encounter_name_key` to the row's `NameKey`, with one filter, `{"Difficulty": "hard"}`, over `Progression.Difficulty`. A binding switched off is not listed. `QuestAxisRow.Builder.value` lets a row bind its axis's own token beside named bindings.

- **New: the `Flair` reward kind, the `FlairUnlocks` write facade, `ZigFlairChangedEvent` and `/zigflair`.** The library owns the flair GRANT now, beside the `ZigFlairComponent` record it already persists: `objectives/flair/FlairRewardKind` is the unprefixed `Flair` kind (`{"Kind": "Flair", "Params": {"Flair": "<id>"}}`, `FlairId` read as the same parameter, the id lower-cased at write), registered into the shared vocabulary by the new `FlairBootstrap` phase the wiring root calls right after the entity module registers the component. A flair the player already holds is a successful no-op (a repeatable paying it twice must not fail the payout, and nothing is announced for it); no live player, a missing record or an id carrying `|`/`:` fails LOUD, and `retryCommand` answers the `zigflair grant --player=<name> --flair=<id>` line built from the spec (null only for a spec the grant would refuse on its own terms), so an offline grant rides the consumer's uuid-keyed retry queue. `FlairUnlocks` is the ONE write path (`unlock` / `revoke` / `unlocked` over `(store, ref, playerRef)`, answering an `Outcome` whose `changed()` says whether anything happened): the kind, every `/zigflair` verb and any consumer alias go through it, and on a REAL change it fires `ZigFlairChangedEvent` (`playerId`, `playerRef`, `flairId`, `unlocked`) on the engine bus - synchronously, `hasListener`-gated, whole-body guarded - and, for a new unlock, draws the authored `Flair_Unlocked` feedback moment (a shipped neutral default: a gold toast reading the new `ziggfreedcommon.flair.lang` `unlocked` line with the flair's name, plus a jingle; a pack or an owner overrides the file by name). A flair's NAME is one ladder every surface shares (`FlairText.nameOf`: `flair.<id>.name` resolved namespace-agnostically through `ContentKeys`, whichever loaded lang file ships it, else the id spelled out), and `FlairChipReading` contributes it to the reward-chip ladder so the claim panel, the toast row and the book preview agree; a reward's own `NameKey`/`Icon` still win first. `/zigflair grant|revoke|list --player=<name> [--flair=<id>]` is the library's fourth command family (after `/zigcommerce`, `/zigprogress` and `/zignpc`), on zc-core's shared target-player walk with engine-derived permission nodes and no in-body check; `grant` on an id no loaded lang file names warns the sender and grants anyway (a pack may load later), `revoke` says whether the flair was there, `list` prints the sorted ids. Its help and answers live in a new nine-locale `ziggfreedcommon.flair.admin.lang` beside the player-facing `ziggfreedcommon.flair.lang`, the split the progression family already keeps; `FlairAdminKeysTest` fails the build on a spoken key nothing ships. The guarded engine-bus dispatch `QuestEvents` carried is lifted into zc-core as `event/NativeEventSeam` (one instance per event family, `publishTo` for a bus-less host or a test), and `QuestEvents` now sits on one with its `Publisher` name and `publishTo` unchanged; `FlairEvents` is the second family on it.
- **`Repeat.Reset` takes a window of ANY length, and the library gains the ONE cadence rule.** `Reset.Every` is a duration group (`DurationGroup` grows a `Weeks` unit, harmless for `Cooldown`) naming how long one window lasts - `{"Hours": 8}`, `{"Days": 1}`, `{"Weeks": 2}` - on the same epoch grid, shifted by `AtMinutes` and, for a window that is a whole number of weeks, by `Weekday` (a fortnight starts on the authored weekday exactly as a week does; any other length ignores it, and the audit's `REPEAT_WEEKDAY_ON_DAILY` says so). `Period` Daily|Weekly stays as sugar for `Every {Days 1}` / `{Weeks 1}`; both authored, `Every` wins and the audit reports `REPEAT_EVERY_AND_PERIOD` once per quest; an `Every` adding up to nothing is `REPEAT_EVERY_EMPTY` and reads as a day. BREAKING for a consumer that read the runtime enum: `Quest.Repeat.Reset` is now `(periodMs, atMinutes, weekStart, times)` with `every(ms)` / `daily()` / `weekly()` factories and `weekAligned()`, and its `Period` enum is gone (two readings of one window were two things that could disagree); `QuestAsset.Repeat.Reset.Period` keeps the authoring sugar and `periodMs()` is the folded length. New `quest/QuestCadence` (`NONE / REPEATABLE / DAILY / WEEKLY`, `QuestCadence.of(repeat)` and `Repeat.cadence()`) is the one classification every surface reads: the LONGER of the rolling `cooldownMs` and the calendar `periodMs`, bucketed at six days (weekly, so two and three weeks read weekly too) and twenty hours (daily), an empty group reading `REPEATABLE` and a one-shot `NONE`; the thresholds are spelled once, on the enum. Behaviour change for a consumer that bucketed on the rolling cooldown alone: a calendar daily (a `Reset` with no `Cooldown`) classifies `DAILY` through `cadence()`, so it counts toward whatever that consumer keys on the daily bucket.
- **`hytale:mod_installed` sees an asset-only pack.** The reading asked only the engine's plugin table, which files jars with an entry class and never a pack that is nothing but a `manifest.json` and assets - so a content pack read as absent while it was installed. `ModFactors` now asks the asset-pack registry (`AssetModule.getAssetPack`, keyed by the same `Group:Name` the manifest declares) when the plugin table says no; a code plugin still costs one lookup, an absent mod is still a definite `0`, and a registry that is not there yet is still "cannot tell".
- **New: the `ziggfreedcommon:quest_known` factor.** A fifth progression reading beside `quest_completed` / `quest_completions` / `achievement_earned` / `achievement_points`: `Param` a quest id, `1` when the shared catalogue holds it and a DEFINITE `0` when the built catalogue does not (presence is the whole question, the `mod_installed` reasoning, so both `Min: 1` and `Max: 0` are writable), `null` with no `Param` and `null` until the runtime is built (`ProgressionFactors.Reads` gains `runtimeReady()` so "not built" is never mistaken for "not catalogued"). It needs NO player, so a validator or a placement sweep can ask. Shipped with a `Progression_Quest_Known.json` naming overlay and `ziggfreedcommon.progress.factor.quest_known` in all nine `ziggfreedcommon.progress.lang` files. It exists because a dialogue `QuestState` condition on an unknown quest reads `NOT_STARTED` by design, so a conversation could not otherwise tell whether a quest another pack ships is on this server at all.
- **New: `match/ItemMatch`, the one item-identity matching core.** Three pure route predicates over a candidate item's already-resolved identity - exact `ItemId` (case-insensitive), native `Tags` (the shared `TagMatch` map: ANY-of family+values, plus a PRESENCE form where an authored family with an EMPTY value array matches on the key alone, exactly how the engine's expanded raw-tag map answers a single native tag), and resource FAMILY (any of the candidate's family set) - plus the `any` OR-composition, parameter-ordered to the native consumption precedence (exact > tag > family, read out of `InternalContainerUtilMaterial`). A chain gated only on durability, or on nothing, spends nothing and is as ready on the thousandth press as the first, so `readyToSpend()` requires both. ## 2.0.0 - 2026-08-31

This is the ONE version story for the cycle: the work below was developed under the internal 1.4.0 number and ships as 2.0.0 (no 1.4.0 was ever released; the previous public release is 1.1.1, and the 1.2.0/1.3.0 sections below are internal milestones that first ship here too).

- **A full inventory never eats a reward, and a ground drop is tick-safe.** The library installs its own default overflow policy at boot (`FeetDropOverflow`): an item reward that does not fit the bag lands on the ground at the player's feet through the shared `NativeLootService` spawn seam, so a full bag means a pickup rather than a lost reward; a consumer replaces the policy with `LootRewardKinds.overflow(...)`, or clears it with null to restore fail-and-park. Underneath, every `NativeLootService` spawn form answers whether the drop landed, and the one-accessor form re-queues a spawn the engine rejects for running inside a system tick (the store's write-processing assert) onto the owning world's thread, where it lands right after the tick - so a payout with no CommandBuffer to thread (a `Droplist` quest reward granted off a block-break moment) still reaches the ground. A spawn that genuinely cannot land warns naming the exact stacks that were lost.
- **A hand-in takes what the player actually brought, and "ready to hand in" means the errand is done.** Two questions where there was one. `QuestEngine.canDeliverTurnInAt` (and the `QuestStateReader` form behind it) now asks whether the player is carrying at least ONE of what a step still owes rather than the whole remaining amount, so a large delivery can be chipped away at over several visits and the button is offered on every one of them; the engine already credited a part-load, and only the OFFER was refusing it. So a quest whose other steps are still outstanding, or whose delivery is short, reads as in progress and greets the player normally, while its hand-in button stays there to take what they have. Both reader forms default to the partial answer, so a runtime that models no amounts keeps working.
- **One press discharges the whole errand.** `QuestEngine.attemptAllTurnIns` hands in every outstanding step a character or board is owed in one pass, repeating so a hand-in locked behind another hand-in settles in the same press, and crediting a part-load exactly as a single-step hand-in does. - New: `world/placed/PlacedBlockLedger` + `PlacedBlockRecorder` (zc-world) - the shared answer to "did the player put that block or item there themselves?". Any mod counting block breaks or pickups wants that refusal, and one authority is what stops a quest producer, an XP engine and a statistics counter from disagreeing about a single break, so the library owns both the record and the one ECS system that writes it. Placements are world-scoped and persisted to `mods/ziggfreedcommon/placed-blocks.json` (loaded at setup, written at shutdown); placed ITEM ids are counted rather than positioned, and are deliberately not persisted, since they expire in minutes. `Policy` is four independent knobs read LIVE - `enabled`, `strict`, `blockExpireMinutes`, `itemExpireMinutes` - so a consumer whose own config already carries them installs one policy and never re-pushes on a reload. The default is `strict`: nobody earns from a placement, whoever breaks it. Setting `strict` false narrows the refusal to the placer alone, which is the fairer reading in a shared world where one player's building work would otherwise poison every block their neighbours mine. A creative-mode placement is not recorded, because an admin walling in an ore vein for survival players is the opposite of the exploit, and neither is a placement something else CANCELLED, since no block was put down to remember. One native event is read by this library's producer AND by every consumer's own event system in an order nobody specifies, so a moment has to cost the ledger exactly once while every reader is told the same thing: a consumed BLOCK row keeps answering for a one-second grace window (a position is the moment), and a placed-ITEM read names its moment - `consumePlacedItem(uuid, itemId, momentKey)`, keyed on anything stable for that one event - so one pickup spends one remembered copy however many mods read it. - **`ziggfreedcommon:quest_completions` counts COLLECTIONS, not finishes, so a reward still sitting there uncollected is not a run already done under either it or `ziggfreedcommon:quest_completed`.** A quest authored to park its reward sits finished-but-uncollected until somebody comes to take it, and the count read that window as a completed run while the flag beside it read the opposite: content written "come back once you have run this three times" paid out on the third FINISH, before the third reward had ever been handed over. `QuestProgressStore.CompletionRecord` gains a fourth field, `claimedCount`, raised by `QuestEngine.markCompleted` - the one instant a quest is paid out, whichever route reached it (the auto-claim path, the collect of a parked one, an administrator's close-out) - and the factor reads that tally. The repeat rules deliberately keep counting FINISHES (`MaxCompletions`, a calendar `Reset` allowance). No player can make the two tallies disagree at a repeat decision: a parked quest is not offered, and `canAccept` refuses it until it has been collected. A deliberate force can - an accept that skips the eligibility check on purpose (a scripted start, an administrator) or a re-arm that clears the parked status - and the finish is the safe half to cap on, since a run somebody walked away from without collecting still spent its slot. No count, and no over-count. Authoring a role instead costs almost nothing: a character sharing a template's behaviour is a three-line native `Variant` (`{"Type":"Variant","Reference":"<template>","Modify":{...}}`), whose `Modify` may name only the parameters that template declared, and a character needing its own press-F prompt is a full role body. Common ships no roles and knows none; validating that a consumer's variants match the templates they reference is that consumer's own test, since it owns both files.
- New: `npc/placement/PlacedNpcComponent` + `npc/placement/NpcPlacementLedger` + `npc/placement/NpcPlacementReconciler` - **two authorities, and this is the correctness core: the ECS component decides DESPAWN, the persisted ledger decides PLACE.** Placement requires `ledgerMiss && anchorChunkLoaded` and NEVER places from absence alone, because chunk unload REMOVES the entity from the store and an entity sweep therefore cannot tell "never placed" apart from "placed, chunk asleep" - placing on absence would spawn a second NPC every time a player walked back into range. The sweep follows `entity/performer/PerformerReconciler`'s pure `KEEP`/`DESPAWN`/`REBIND` policy shape, HEALS an older-build NPC missing the component by re-stamping rather than duplicating it, guards the same-tick concurrent case (two players entering a fresh instance world in one tick) with an in-flight claim set, and debounces per world. `PlacementKeepAlivePins` balances the reference-counted `WorldChunk.addKeepLoaded` by hand (pin on first insert into a chunk's set, unpin on last removal, whole-world entry dropped by a `WorldEvictors` evictor), since the engine offers no automatic unpin and an unbalanced pin leaks for the life of the world. `NpcPlacementPositionCache` is keyed `(worldName, placementId, anchorKey)`, never by placement id alone, so two concurrent instances of one world do not point at each other's coordinates.
- New: `npc/placement/PlacementGate` + `PlacementGates` + `NpcPlacementOverrides` - the veto chain behind whether a placement appears: the asset's own `Enabled`, the persisted owner file `mods/ziggfreedcommon/npc-placements.json` (`{"<placementId>": {"enabled": false}}`, `"*"` for a global stop), and any consumer veto including the `Requires` evaluation. Any deny wins, the verdict carries a `reasonKey` so an admin surface can say WHY, and **a deny despawns what is already standing on the next sweep** rather than merely declining to spawn it again.
- New: `npc/placement/NpcPlacementBindings` + `PlacementBinding` + `PlacementInteractHandler` + `ActionPlacementInteract` - the consumer-vocabulary seam, following the same forward-verbatim-interpret-nothing paradigm the contribution channels already use. `Interact.Bindings` is a channel-keyed MAP through `codec/InheritMapCodec`, **not an array, and that is load-bearing**: an array leaf under `appendInherited` is a single leaf, so a `Parent` child authoring `Bindings` at all would drop every entry it inherited. Each entry is `{Param?, Value?, Values?, Amount?}`, all independently optional: `Value` is one opaque string, `Values` is a list of them for a channel that genuinely takes several, so no channel owner has to invent a separator inside a single string and an entry may contain any character. `Values` obeys the same one-leaf inheritance rule as its siblings (omit it to inherit the parent's list whole, author it to replace it whole). One `register(namespace, owner, handler)` call claims a `yourmod:` namespace AND supplies the press-F handler behind it; a generic NPC Action reads the placed NPC's component, resolves its placement, opens `Interact.Dialogue` when one is authored (the one behaviour this library understands on its own, since it owns the dialogue engine), and fans the bindings per namespace. A key with no namespace, and a namespace nobody claimed, are both validator findings rather than silent drops.
- New: `npc/placement/PlacementFactorRegistry` + `AnchorResolverRegistry` + `NpcRoleGenerator`'s base-role registry - three more open extension points so the engine is never closed to a fourth party: an authored `Requires` gate resolved by registered factor id, an `Anchor.Custom` provider that resolves positions this library knows nothing about (a station block, a dungeon boss room), and the role template a generated identity clones. All fail closed - an unregistered id yields no value, no position, or no role, never a crash - and all are validator findings.
- New: `npc/placement/NpcBaseRoleAsset` + `NpcBaseRoleConfig` + `NpcBaseRoleValidator` (`Server/ZiggfreedCommon/NpcBaseRoles/<baseId>.json`, Pattern B raw passthrough) - a PACK-authorable base role, so shipping the template a generated placement role clones needs no Java at all. The file's `Payload` IS the role's own JSON body in the engine's ordinary role shape and the filename is the base-role id; every asset fold registers each entry into the same registry `NpcRoleGenerator.registerBaseRoleResource` feeds (asset load precedes plugin `start()` role generation, so the timing holds). A base id already registered from Java is OVERWRITTEN by the asset (`defaults < pack < owner`), logged once at INFO naming both.
- New: `npc/placement/PlacementRegistryLedger` + `registry/RegistryLedger<T>` (zc-core) - a generic owner-attributed registry ledger: who registered each id, an identity-compared warn-once on an overwrite (so re-registering the SAME provider stays silent), a per-id failure count plus last message, and an `info()` snapshot for an admin listing. It is what lets a consumer's admin surface tell "nobody claimed this id" apart from "claimed, but its provider keeps throwing". `PlacementRegistryLedger` is a thin FQN-preserving subclass over it.
- New: `factor/` (zc-core) + `factor/HytaleFactors` and `entity/HeldItemUtil` (zc-entity) - ONE shared condition-factor vocabulary, so a gate on a number another mod owns means the same thing everywhere it is authored. `FactorContext` (nullable orthogonal leaves: param, world, store, subject ref, opaque payload), `FactorProvider` (a nullable `Double`; null = cannot answer), an instantiable ledger-backed `FactorRegistry` (each consumer builds its own; a dialogue's is installed into the shared engine's single factor slot), the ONE `FactorCondition` codec `{Factor, Param?, Min?, Max?}`, and a `FactorConditions` array evaluator. **Null-sentinel fail-closed everywhere**: an unregistered id, a provider that cannot answer, and a provider that throws all read alike, and a gate that cannot be evaluated never opens - which makes a condition with NEITHER bound a genuine presence check ("only where that mod is installed"). The codec is a FACTORY, not a single static, so each consumer names its own Asset Editor dropdown dataset (an unserved dropdown renders as an EMPTY pick list, which is worse for an author than a plain text field); `FactorCondition.CODEC` is the no-dropdown instance. `HytaleFactors` is the PORTABLE standard library - `hytale:stat` (any registered `EntityStatType` channel, the subject's folded max), `hytale:tool_power` / `tool_durability_percent` / `tool_quality` / `tool_item_level`, plus the new `hytale:held_tag` (through the shared `codec/TagMatch`) and `hytale:held_item` - registered into a consumer's own registry with one `registerInto` call. **The namespace names the vocabulary's OWNER, not whoever registered it**: every id there addresses data the ENGINE owns, so two mods converging on `hytale:tool_quality` is agreement rather than a collision, and a consumer whose own site resolves an id differently (a work session holding a tool snapshot rather than reading the live hand) registers its own provider under the SAME id in its own registry - same vocabulary, context-appropriate resolution.
- New: dialogue `{"Type":"World", ...}` and `{"Type":"Factor", ...}` conditions. `World` holds the three `Where` axes and hands them to `world/WorldSelector`, so the rank ladder, the bare-word-is-an-exact-name rule and the exclude-is-a-FILTER rule all come from the one authority; the world read is `store.getExternalData().getWorld()` through a guarded helper, so `DialogueContext` needs no new member. `Factor` holds the four authored leaves and hands them to the shared `FactorCondition`, resolved against the `FactorRegistry` installed into the shared engine's one factor slot (`DialogueEngine.installFactors`), with the player supplied as both store and subject. Both fail closed: an unreadable world, a `Where` with no positive axis, an unregistered factor id, and a server where nobody installed a registry at all each hide the gated content. So a pack can gate a dialogue option on a stat or a held item with zero Java.
- New: `dialogue/DialogueOnce` - `Once`, the authored SEEN-NESS knob, on a `Start` entry or an option. `"Once": true` (once per character) or `"Once": {"World": "<name or pattern>"}` (once per world FAMILY); the boolean is shorthand for the empty group, normalized by the sugar pre-pass so the codec only ever sees an object, and a future axis is a new nullable leaf rather than a mode. **Entry-level Once is spent by COMPLETING the beat** - the player chooses any option on the routed node, the page's implicit farewell row included - so leaving mid-beat re-shows it, and nothing is written on a path where the actions never ran. **Option-level Once is keyed by `LabelKey`, never by index**, so reordering a node's options can neither resurrect nor spend one; an `OnceId` leaf covers a duplicate-label or label-less option, and an option with neither stays repeatable with a warn-once plus a validator finding; two Once-bearing options in ONE node landing on the same identity is its own validator error (`ONCE_DUPLICATE_IDENTITY`), since they would otherwise share a single flag. The `World` scope is keyed by the pattern's literal CORE precisely because an instance world is destroyed and re-created under a fresh uuid name, which would otherwise re-show a first-visit beat on every fresh instance.
- New: `dialogue/DialogueMemory` - `Memories`, the authored NAMED state, declared once at the dialogue top level with its scope and lifetime and then referred to by BARE NAME everywhere else. Three nullable orthogonal leaves: `World` (per world family, taking the same name-or-pattern string as `Once`), `ResetWithQuest` (filed inside that quest's own namespace, so a consumer's quest reset forgets it too - a DECLARED lifetime replacing any convention an author used to hand-compose), and `Shared` (visible to every dialogue that declares it; mismatched declarations are a validation error, because two dialogues would otherwise silently mean different state). Use sites are the `Remember` / `Forget` actions (option sugar `"Remember": "<name>"`, bare-key expansion orders 32/33 so a memory write trails the band a consumer registers its own quest sugar in) and the `Remembered` / `NotRemembered` conditions. The map decodes through `codec/InheritMapCodec` like `Nodes`, so a `Parent` child re-declares or adds ONE memory and inherits the rest. New findings raw flags made impossible: an undeclared name (error), a shared-scope mismatch (error), a blank name (error), a blank world scope and a scope pattern that would match every world (both errors), declared but never written (warning), never read (info).
- Changed: `dialogue` drops `SetFlag` / `Flag` / `NotFlag` from the engine's PRE-SEEDED generic types, replaced by `Once` and `Memories` above. Unreleased-1.4.0 change; additive registration means this is not a ban, since a consumer that genuinely wants raw flags registers its own action and condition types into the shared engine. `DialogueFlagStore` and the key-composition machinery survive as INTERNAL plumbing - the new knobs write through the same store, and `dialogue/DialogueStateKeys` owns every shape (`once:e:`, `once:o:`, `mem:d:`, `mem:s:`). **A `ResetWithQuest` PREFIXES its quest segment onto the whole key while a world scope wraps only the FINAL segment**; that ordering is load-bearing rather than cosmetic, because a consumer clears a namespace by a LEADING-prefix match and a prepended world scope would escape the clear and soft-lock the dialogue permanently. A scope the current world does not match makes a write a no-op and a read unset; a pattern matching no loaded world warns once per pattern per process, since a typo would otherwise re-show a first-visit beat forever. **No author ever sees a composed key again.** Kweebec's authored dialogues used no flags and its in-memory store is untouched.
- New: `ZiggfreedCommonPlugin` registers its OWN `AddWorldEvent` / `RemoveWorldEvent` / `PlayerReadyEvent` / `PlayerDisconnectEvent` listeners rather than relying on a consumer to forward them, and `cast/WorldEvictors.onWorldRemoved` gains an already-evicted self-guard: with two consumer mods installed the eviction fan-out previously fired TWICE per world, which is harmless for a map removal and corrupting for a refcounted unpin.

Two whole progression lifecycles, one loot vocabulary, and the shared cores underneath both, so a mod shipping quests, achievements, drops, stamped gear, or NPC conversations reuses one engine family instead of growing its own. The library gains a module (`zc-loot`), renames one (`zc-quest` becomes `zc-progression`), and keeps its single-jar identity throughout. Additive over the rest of 1.4.0 except the retirements named below, every one of which retires an UNRELEASED surface.

- New: `zc-progression` - **TWO lifecycle engines over ONE set of shared cores**. A quest is an ACTIVE SET (accepted, tracked, abandoned, handed in, back on a cooldown); an achievement is ALWAYS ON (every criterion of every catalogued achievement listens from the first event and one earns itself the moment its criteria are met). Those lifecycles are genuinely different, so they ship as PEER engines (`quest/QuestEngine`, `achievement/AchievementEngine`) rather than one engine with a lifecycle switch - full unification was rejected because the special-casing would thread through every method. What they share is shared for real: the objective vocabulary and its matching, the reward-kind registry, the gate model, the asset machinery, the authoring GROUP CODECS, and the native-event plumbing. Both ship ZERO content and ZERO domain vocabulary, enforced by an agnosticism test that walks the module source. Roughly 254 tests in the module.
- New: `progress/` - the cores both engines rest on, and nothing here may name either of them. `ObjectiveDef` is one authored objective (kind, target, match mode, qualifier, amount, zone, order, hand-in lock); `ObjectiveKind` + `ObjectiveKindRegistry` are the OPEN kind vocabulary, per consumer, pre-seeded with 21 engine-generic kinds (`BREAK_BLOCK`, `PLACE_BLOCK`, `CRAFT_ITEM`, `KILL_ENTITY`, `DEAL_DAMAGE`, `PICKUP_ITEM`, `TALK_TO_NPC`, `CATCH_FISH`, `TURN_IN`, `COMPLETE_QUEST`, `TAKE_FALL_DAMAGE`, `PLAYER_DEATH`, `SPRINT_DISTANCE`, `SWIM_DISTANCE`, `BREED_ANIMAL`, `FEED_ANIMAL`, `HARVEST_ANIMAL`, `COMPANION_COMBAT`, `REACH_LOCATION`, `CONSUME_ITEM`, `STAT_THRESHOLD`) and open to a consumer's own; `MatchFlavor`/`MatchMode`/`ObjectiveMatch` carry BOTH matching dialects deliberately unmerged (one is case-sensitive, one is not, and collapsing them would silently re-target somebody's content); `ZoneRef`, `ObjectiveProgressState` (plus its byte-stable `"current/required"` wire form), `ObjectiveIndex` (the inverted kind-to-objectives index the dispatch hot path walks, owner-agnostic via accessors), `DispatchOptions` (two independent switches, three named combinations) and `ProgressDispatchTap` (the side channel both dispatches feed) round it out.
- New: `progress/ObjectiveKindRegistry#STAT_THRESHOLD` - the VALUE-BASED kind whose `Target` is a native entity stat channel id and which completes when that channel reaches `Amount` (high-water). It settles through an optional factor-registry seam at accept / self-heal / content-touching dispatches, so it completes even when no consumer ever fires it; a consumer that wants instant credit may fire it on change as well. `Target` is required, and an authored `STAT_THRESHOLD` without one is a validator warning rather than a criterion nobody can ever meet.
- New: `progress/gate/` - the ONE requirement model behind every `Requires` block, so a gate means the same thing on a quest, on an achievement, and on whatever comes next. `GateClause` is four independently optional leaves: `Factors` (the shared numeric gate over the factor vocabulary, identical to the one a dialogue option or an NPC placement is written with, FAIL-CLOSED so content gated on an absent mod stays gated), `Permission` (a native Hytale paradigm, so it is a built-in leaf), `Quests` (completed-quest prerequisites, built in because the quest engine itself owns that answer), and `Custom` (requirement kinds a mod registered under its own namespaced id). `GateSpec` adds `AllOf`/`AnyOf` groups, `GateKind`/`GateKindRegistry` are the open registration table, and `GateEvaluator` walks the lot. Skill levels get NO bespoke leaf anywhere: a consumer registers its friendly spelling as SUGAR that desugars onto factor conditions.
- New: `progress/asset/` - the authoring GROUP CODECS both engines append, declared ONCE so their field names cannot drift apart and a shared renderer never needs two branches. `ContentTextAsset` (`TitleKey`/`FlavorKey`), `ObjectiveLeafAsset` (the objective/criterion leaf), `RewardEntryAsset`, `ContentListingAsset` (`Category`/`SortOrder`/`Tags`/`Chains`), `ContentMeta` (`Meta`), and `ProgressEditorDataSets` for the Asset Editor pick lists. Every leaf is `appendInherited`, so content with a `Parent` can be re-sorted or re-titled without losing what it did not mention.
- New: `progress/asset/ContentMeta` - `Meta: {"<namespace>": {...}}`, the labelled box on every content asset for whatever the mod that RUNS the content needs to say about it (which ladder rung it is, which conversation follows it, which server feature has to be on) without any of that vocabulary entering a schema meant to serve every mod at once. **Nothing interprets a block it does not own**: a namespace is kept exactly as authored and handed on, so an asset written for two mods still loads with only one of them installed. Inheritance is per namespace (a child inherits every namespace it does not mention and replaces whole the one it does; there is deliberately no deep merge, because a block has no schema at this level and a merge would have to guess). A consumer declares an ordinary `BuilderCodec` for its own block and calls `ContentMeta.decode`, which hands back the typed value AND reports any key the codec does not know, so a typo surfaces as a named warning instead of a silently ignored knob.
- New: `progress/asset/ContentTextAsset.TextArgs` - `TextArgs: {"Title": [...], "Flavor": [...]}`, auto-calculated text arguments filling `{0}`, `{1}`, ... of the keys beside them, so a line reading "Mine 20 ore" carries the 20 from the content itself instead of from a translator retyping it. `@amount` is the pre-seeded sentinel (the objective's or criterion's own amount, handed over as a raw value; the consumer formats it and passes it as a nested `Message` per the localization invariants). It lives on the shared text group rather than in any consumer's `Meta` block, because auto-calculated args are a generic authoring capability and one carrier is better than several.
- New: `progress/asset/ContentListingAsset#Chains` - `Chains: [{"Id": "<free string>", "Tier": n}, ...]`, MULTI-MEMBERSHIP tiered ladders on both content kinds. A piece of content may be a rung of several ladders at once, each with its own tier (a mining achievement can be rung 3 of the copper ladder and rung 1 of the whole-game one), so a surface can render a whole climb as one entry rather than a row of near-identical ones. Chain ids are unnamespaced free strings; prefix by convention if collisions worry you. It is ONE leaf, so authoring it replaces an inherited list whole. Validator findings: a duplicate chain id within one item, a non-positive tier.
- New: `quest/` + `quest/asset/` + `quest/event/` - the consumer-agnostic QUEST lifecycle: a per-consumer `QuestEngine` owning matching, ordering, cooldowns, hand-ins, completion and payout bookkeeping, with the consumer supplying storage (`QuestProgressStore`, plus a ready-made in-memory one), gates, inventory access and naming. `quest/asset/` is the authoring half (`Server/ZiggfreedCommon/Quests/<id>.json`, Pattern A with engine-native `Parent` inheritance and a per-objective-id merge, so a child re-tunes one objective and inherits the rest), plus `QuestGeneratorAsset`/`QuestGeneratorExpander` (a generator writes a whole family as ordinary `Parent` children over an authored axis, resolved through the consumer's registered `QuestValueEnumerator`s), the pool and its validator. `quest/event/` is five native `IEvent<Void>` POJOs (accepted, objective progressed, completed, claimed, abandoned) dispatched through the engine's own event bus, so a third party listens the way it listens to anything else.
- New: `quest/Quest.Repeat` - the whole vocabulary for a quest that comes back around, evaluated by the engine for every consumer rather than re-implemented per fold. **Authoring the group AT ALL is what makes a quest repeatable**, so `Quest#repeat()` is `@Nullable` and its presence is the flag (a `Repeat.NONE` sentinel was rejected: a sentinel is a value a caller can mistake for an authored one). An EMPTY group means externally governed - the quest has no clock of its own and whatever offers it decides when it returns, which is what a rotating, period-based offer needs. Inside it sit four INDEPENDENT constraints, ANDed by one evaluator, plus the clock origin: `Cooldown` (a rolling wait), `CooldownFrom` (`Claim`, the reward being taken, by default, or `Complete`, the objectives being met - the form a rotating offer wants, so walking back to collect after the offer rotates does not burn a slot in the NEW period), `Reset` (`{Period: Daily|Weekly, At, Weekday, Times}`, a calendar allowance where COMPLETING consumes the period regardless of when the reward is taken; anchors are UTC server clock only, a timezone leaf being a later additive knob if one is ever wanted), and `MaxCompletions` (a lifetime cap). This replaces the earlier draft's `StampOnPark` boolean, which said less in more places: `CooldownFrom: Complete` is the same semantic under a name that explains itself, and it composes with the other three instead of standing beside them. Store additions are ADDITIVE (a last-completion stamp and a per-period count beside the existing cooldown stamp), so a consumer's persisted blobs decode unmoved. An ADMIN reset wipes the completion record (a reset means starting over); `selfHeal` and abandon preserve it, so a lifetime cap stays enforceable in play.
- New: `time/DurationGroup` - the ONE structured way a duration is authored anywhere in the library: a nested `{Days, Hours, Minutes, Seconds}` group of nullable non-negative numerics, summed, so `"Cooldown": {"Hours": 24}` and `{"Minutes": 1440}` are the same wait and neither needs a parser for a `"24h"` string. Empty or all-zero is a validator error wherever a duration is required. The existing scalar `*Seconds` keys retrofit onto it in a later cycle.
- New: `achievement/` + `achievement/asset/` + `achievement/event/` - the ALWAYS-ON peer lifecycle over the same cores. `AchievementEngine` owns matching, counting, earning, collecting, points, milestones and pins; the consumer supplies storage (`AchievementProgressStore`, plus an in-memory one) and `AchievementGates` (`canProgress`/`canUnlock`/`canReceiveRewards`/`visible`, all default-yes). **Criterion progress is keyed by POSITION** (`"<id>#<index>"`, with a one-way fallback to a legacy no-index key), so appending a criterion is safe while reordering one is a data migration - asserted directly in the engine test. Two reward lists, two moments: `Rewards` land on earning, `ClaimRewards` wait to be collected. `Scoring` carries `Points` plus `CountsTowardTotal` (default true), and an authored `CountsTowardTotal` is honored by a consumer's fold - the MMO's does, with a feat-of-strength still forcing it false. `achievement/asset/` shares the text / objective-leaf / reward-entry / listing / gate groups with quests; `Criteria` is an ORDERED array a `Parent` child replaces whole, precisely because progress is keyed by position. `achievement/event/` is three native `IEvent<Void>` POJOs (unlocked, progressed, claimed).
- New: `progress/runtime/ProgressionRuntime` - **ONE quest and achievement engine pair per server, however many mods contribute to it.** This library owns the instance; a consumer EXTENDS it with registrations from its plugin `setup()` rather than standing up a pair of its own: a store swap (so a consumer's persistence, its fixtures and its database seam survive untouched), domain-keyed producer REPLACEMENT (the library's generic block-break / kill / craft / pickup producers stand down per replaced domain, which kills double-fire structurally rather than by a runtime check), and gates, factors, reward kinds and objective kinds through the registries that already existed. Content is published into the shared instance by each consumer's fold. The first read or the first player ready calls `ensureBuilt()`, which seals the sealed parts, composes the contributions, builds both engines and logs ONE diagnostic naming who answered for what. Nothing decides WHETHER to run: there is one runtime, always, and the only question is which parts it was built over. **Why it is shared and not per consumer:** two runtimes over two stores is double-tracking, where the half a surface reads is not always the half that can pay out, so a hand-in reads as ready and does nothing - a failure class that can exist at most once on a server rather than once per mod. The engines are built once and never rebuilt: everything they reach the outside world through is a forwarder over `ProgressionParts`, so a late registration is honoured on the next call and every cached reference stays valid. `ProgressionRuntimeClaim` retires into this surface. Two seams ship with it: `ProgressionCallScope` (a consumer wraps mutating calls so a claim driven from someone else's UI still fires the consumer's own full feedback) and `ProgressionTextSource` (a merged catalogue, so content authored in a consumer's older format still renders titled in a surface that never heard of that format).
- New: `zc-objectives` - the STANDALONE progression runtime surface, so this library is not only an engine a mod has to wire but something a bare server can run on. It registers a persisted per-player component (`store/`) as the shared runtime's store, folds the shared `Quests` and `Achievements` asset stores in, contributes four generic native-event producers (block break, mob kill, craft, pickup), and ships an in-game two-tab Quests | Achievements page opened from an ordinary item: `Ziggfreed_Objective_Book` ("Objective Book"), obtainable through authored content or `/give` and never auto-granted, since a library has no business pushing an item into a player's bag on its own initiative. The book reads the shared runtime everywhere, so it shows a consumer's content and its own in one list rather than an empty tab. A consumer that wants a different book redeclares the item at the ITEM layer and points it at its own page, the way any pack re-authors a shipped item. The module sits ABOVE both `zc-progression` and `zc-presentation` because the book needs the engines AND a page while `zc-progression` may never import presentation, which is the one position that adds no reverse edge.
- Changed: the shipped `.lang` files split PER DOMAIN instead of one `ziggfreedcommon.lang` monolith per locale. A file's basename minus `.lang` is a key PREFIX the engine folds in verbatim, and every file under a locale merges into one map, so `ziggfreedcommon.fmt.lang` holding `cat` resolves as `ziggfreedcommon.fmt.cat` and a resolved key is byte-identical to what it was in the monolith - a split MOVES keys (the in-file key drops the segment the filename now carries) and changes nothing a client sees. A key lives in exactly ONE file, because a collision is first-writer-wins with a warning and filesystem-order nondeterminism, which is not something to leave to chance. This cycle splits `ziggfreedcommon.lang` and files every NEW key family this way (`ziggfreedcommon.fmt`, `ziggfreedcommon.progression`, plus `items.lang` for the shipped item names); the module a key belongs to owns its file, so a lang file travels with the code that reads it.
- New: `asset/NestedAssetId` (zc-core) - folder grouping that can contribute to an id. The engine names an asset after its FILE and nothing else, which leaves an author choosing between folders that read well and ids that do not collide. A folder marked with a LEADING UNDERSCORE contributes its name (sans `_`, lower-cased) as an id prefix, stacking in path order joined with `_`, so `Quests/MMOSkillTree/Zones/_Wilds/Trork_Trouble.json` is `wilds_trork_trouble` while every unmarked folder stays organizational and inert - an existing tree keeps the ids it has and nothing moves under an author until they opt in. The asset scan is recursive, so `Server/ZiggfreedCommon/Quests/<Namespace>/<Feature>/<Questline>/` is a free organizational choice. Wired into Quests and Achievements this cycle; every other type keys plainly off its filename until a later pass wants the same grouping. **Pick a marked folder name as carefully as a filename**: renaming one renames every id beneath it, and an id is what a player's saved progress is filed under.
- New: `zc-loot` - a module for the ONE loot core, so a station's rare find, a chest, a mob's bonus drop and a quest reward that rolls a table all behave identically on identical JSON. A `Roll` is `{Trigger, Conditions, Chance, Ladder, Grants, Cue}` read in that order; `RollEvaluator` is the PURE decision and `LootEngine` the half that acts, entirely through seams (item sink, drop-list sink, command dispatcher, reward registry), so a caller supplying none still gets a full evaluation with no effects. `LootableAsset` (`Server/ZiggfreedCommon/Lootables/`) and `LootRef` (an inline `Roll` OR a reference to a shared lootable, one vocabulary either way) are the authoring surface; `LootableValidator` audits roll structure once for every consumer; `LootFactors` turns an instance run's score and outcome into ordinary factor readings so a win gate is an ordinary condition. `Chance` carries the full `{Base, Factors, Clamp}` formula wrapper, and the unclamped multiplicative sites keep bare `Term[]` arrays through the one shared evaluator. Roughly 176 tests.
- New: `loot/stamp/` - the same shape for stats written onto an item. `StatRollEntry` / `RollPoolAsset` / `StampSpec` are the authored side; `StampCapEngine` is the pure decision (lowest budget binds, per-stat ceiling on top, and a fully-capped attempt is DENIED so nothing is charged for a stamp that cannot land); the WRITE sits behind the pluggable `Stamper` contract, with `StackStatsStamper` (writing the shared `stats.StackStats` per-stack metadata blob) as the default the wiring root installs on `StamperRegistry`. Rolled-random and authored-specific stamps are the same path with a different spec.
- New: `loot/stamp/Stamper#describe(StatRoll)` - a default-bodied hook returning a `Message` for one committed roll, so the stamper that OWNS the stat vocabulary is the thing that names what it wrote. - New: `ui/UiRetint` - the generic, mod-agnostic palette-to-selector retint primitive (the runtime `PatchStyle` recolor / texture-swap mechanism several consumers had each re-derived inline). `retintColor(cmd, sel, hex)` sets `.Background.Color` (the confirmed in-place 9-slice recolor); `retintButtonStates(cmd, elementSel, def, hov, pre)` sets a LIVE button element's per-state `.Style.{Default,Hovered,Pressed}.Background.Color` (the proven dialogue-option-row technique); `retintStyleStates(cmd, "@StyleName", ...)` is the best-guess named-style-definition form (one push reskins every button on a shared style, in-game-verify); `swapPatch(cmd, sel, texturePath, border, tint)` sends a typed `PatchStyle` texture swap via `setObject` (the runtime texture-PATH form is the one in-game-verify nuance); `isSixDigitHex` is the shared `#rrggbb` guard (each colour push is skipped for a null / non-hex value, never a bare-String `.Background`). It takes RESOLVED hex + selector params only - no theme model, no palette type, no gate, no consumer policy. The inline copies converge onto it: `ToastRenderer.apply` (the toast frame tint), `DialoguePage.applyOptionStyle` (the per-option button tint), `LeaderboardPage.style` + `PartyInvitePage.paintActiveTab` (the active-tab tint, keeping their label-style sets inline). A consumer's theme-retint helper is now a thin policy wrapper over it (mirroring how a consumer's page extends common's `ToastablePage`). Authority: `.claude/research/hytale-ui-runtime-patchstyle-textures.md`.
- New: `world/ForcedMusicService.applyFor(store, ref, containerId)` / `clearFor(store, ref)` - force a `MusicContainer` music bed onto one player by id. Resolves + validates the id via `MusicContainer.getAssetMap().getIndex`, sets the player's `ForcedMusicTracker` index, and pushes the `UpdateForcedMusic` packet directly to the player's handler (works whether or not the engine's `ForcedMusicSystems.Tick` runs in an instance world). `applyFor` returns false on a bad / unresolved id or invalid ref so the caller can retry (never latches index 0); `clearFor` sends index 0 to restore the default bed. World-thread, fully try-guarded. Lifted the MECHANISM from Kweebec Nightmare's `MusicBedService`; the dread-container candidate list + per-tier selection policy stay in the consumer, which iterates its own roster and calls `applyFor` per player.
- New: `world/AtmosphereService.setDayTime(world, dayTimeFraction, pauseTime)` / `setForcedWeather(world, weatherId)` / `lock(world, dayTimeFraction, weatherId)` - control a world's time-of-day and forced weather. `setDayTime` pins the clock (`0.0` = midnight / darkest, `0.5` = noon) and optionally pauses it; `setForcedWeather` validates the id (an unknown id would blank the sky, so it is skipped) before forcing both the live `WeatherResource` and the persisted `WorldConfig`, and a `null` id clears the override; `lock` composes a paused day-time set with a forced weather (the frozen-dark-midnight convenience). Each call self-hops via `world.execute` and is fully try-guarded. Lifted the MECHANISM from Kweebec Nightmare's `AtmosphereService`; the dark-weather candidate list + choice stay in the consumer.

## 1.0.0
First stable release. The static primitives, the branching NPC dialogue engine, and the full co-op instance + encounter framework are feature-complete for the 1.0 consumer surface (Kweebec Nightmare 1.0.0 is the exemplar consumer). This cycle adds runtime boss MAX-health scaling, per-encounter boss world-map marker knobs, and same-identity reward merging.

- New: `health/HealthUtil.scaleMaxHealth(store, ref, factor, key)` - raise an entity's Health-stat MAX by a multiplicative modifier (keyed for idempotency) and heal it to the new max. Idempotent: a no-op when the modifier is already present, the stat is not yet balanced, `factor` is 1.0, or the ref is invalid; world-thread, fully try-guarded. Lets a consumer scale a boss's HP by party size / difficulty at runtime without re-authoring the role. Kweebec Nightmare's Warden is the exemplar (party-size x per-difficulty scaling, applied on the first tick after spawn, re-applied once per phase entity).
- New: per-encounter world-map MARKER knobs on `instance/encounter/MultiPhaseBossAsset` (the reusable multi-phase boss) - `HealthPerPlayer` (the per-additional-player MAX-health fraction the consumer composes with its own difficulty multiplier; default 0.0 = no per-player scaling), `MarkerIcon` (the world-map POI texture id; default `Home.png`), and `MarkerUpdateSeconds` (the boss-follow re-place throttle; default 3s). All optional and default off / neutral, so existing bosses are unchanged. The consumer drops + moves the POI through the existing `worldmap/WorldMapMarkers`.
- New: `instance/reward/InstanceReward.merge(rewards)` - combine same-identity rewards (matching `kind` + `id` + `displayKey`) into one entry each, summing quantities, so a rolled loot table renders "x9 Moonbloom" ONCE instead of several repeated chips (and the claim store grants one merged entry instead of many). `COMMAND` entries never merge (each is a distinct side effect); first-seen order is preserved. Unit-tested (`InstanceRewardMergeTest`). Any consumer rolling a loot table (which intentionally yields repeated picks) routes its result through here.
