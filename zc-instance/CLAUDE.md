# zc-instance

- Depends on `zc-core`, `zc-presentation`, `zc-loot`, `zc-encounter` (read only: `EncounterBoards`, `StatBoardBossFights` and `/zigleaderboard` read the binding rows that name a fight's records, `DungeonRuns` listens for `EncounterDefeatedEvent`, and `DungeonValidator` asks `EncounterScripts` whether a `Complete.Bosses` id is a loaded script), `zc-world` (only `TickingSections.wake`, which a dungeon area's paste and clear need first: an entity added to a sleeping chunk section is parked out of the world, where neither the paste nor the clear sees it) and `zc-cast` (only the interaction-Type toolkit `interaction/type/`, for `ZigEnterDungeon`). `zc-objectives` and `zc-stats` are its library dependents.
- Never add an edge to `zc-objectives`, `zc-dialogue` or `zc-progression`. A round leaves as two events: `InstanceRoundStartedEvent` (`InstanceRounds.fireStarted`) when it begins and `InstanceRoundCompletedEvent` (`InstanceRounds.fireCompleted`) when it ends, each on the instance world thread; `winners` is empty on a loss or an abort.
- Every page takes an immutable `*PageDeps` plus a locale-free messages provider; the consumer supplies pre-built client-resolved `Message`s.
- A page names a player only through zc-presentation's `ui/name/PlayerDisplayNames.displayName`, on a Label's `.TextSpans` (a decorated name is a parameterized Message). `PlayerNamesGoThroughTheSeamTest` fails a page that reads `getUsername()` or writes a name on `.Text`; a bare username kept as data (a search haystack) carries `// NAME-DATA-OK: <reason>`. A notice about a player (the invite-sent toast) names them through `PlayerDisplayNames.plainName`, which carries no title.
- A consumer's own reward kind (such as `xp`) is a `RewardAuthoring` adapter on `RewardKinds.shared()`, never a table in this module.
- `world/InstanceWorlds` is the one engine-instance launcher: every copy spawns under zc's own name (never an `InstanceKey`) with its removal (WorldEmpty AND IdleTimeout) and delete flags set in the spawn's config step, and `removeWorld` runs only on its remover thread; a copy's area is keyed by `world/CopyKey`.
- `dungeon/` is the walk-in dungeon, a type of its own beside the queue's `InstancePresetAsset`: `DungeonAsset` (`Server/ZiggfreedCommon/Dungeons/`, owner file `mods/ziggfreedcommon/dungeons.json`; its copies start from zc's void template `Server/Instances/ZiggfreedCommon_Dungeon_Void/` unless a file names another), `CopyRouter` (pure, asked through `LiveWorlds`) the one place a party's area is chosen and reserved, copies named `<dungeon>-<n>`, `DungeonValidator` the boot audit's pass, and `/zigdungeon` the admin family. `DungeonEntry` is the one way in (refuse a dungeon `DungeonValidator.entryErrors` finds an ERROR in, since the boot audit runs only when asked; reserve, spawn or join the copy, paste while the player loads, teleport); `Areas` pastes and clears an area on the world thread (waking its sections first, sweeping Intangible entities the box query skips), `AreaLayout` fixes a copy's areas when it opens, `AreaMembers` is the 1 Hz membership ticker off the world thread, and `AreaSpawnProvider` (type `ZigDungeonArea`) respawns each player in their own area; never per-player respawn points, which persist by world name while copy names repeat. A player's way in is `DungeonEntry.enterWithParty` (their zc party's area, a party of one without one; only members who walk in are routed or counted), run by the `ZigEnterDungeon` interaction Type (`ZigEnterDungeonInteraction`, the chain's command buffer as its accessor, Finished only when sent; a pack puts the gate in front, `[ZigRequires, ZigEnterDungeon]`) and the `Dungeon` destination (`DungeonDestinations`, for a placement's press-F or a conversation, its entry queued on a world task of its own since a press-F arrives mid-system); both tell a refusal through `DungeonRefusals` (`entry.*` keys), never a second map. The admin's `enterAlone` keeps its own lines. `DungeonRuns` is an area's run, settled by `AreaMembers` (begun at the first arrival, failed when the area frees, on `Run.TimeLimitSeconds`, or with `Run.FailOnWipe` on a wipe its ticker reads in a world hop; cleared once every `Complete` leaf written holds: `Bosses`, `Objective`, which zc-objectives' `DungeonObjectives` moment listener matches and counts through `countObjective` since this module never sees the moment stream, and `SurviveTimer`), leaving as the round events with mod id `dungeon`, mode the `Difficulty` label and preset the dungeon id. At a clear `DungeonResults` writes each member present a completion Claim through `ClaimStore.award` (`Rewards`; id `dungeon:<id>:<run>:<player>`, returns key `dungeon:<id>:<difficulty>`) and opens a normal `ResultsPage` (never over a death screen; no Play Again, `ResultsActions.offersPlayAgain`), and a time-limit or wipe failure tells each member why. zc-encounter's run-tag seam is filled from `DungeonRuns.runOf`, so a fight in an area is filed under `dungeon:<id>`. Its lock is a leaf, and every round event, payout and line is posted to the copy's world thread, never run under a lock.
- `claims/` is the Claims tab (`MenuSlot.CLAIMS`, shown while a Claim waits) over zc-loot's `loot/claim/ClaimStore`: `ClaimsPage` reads and pays, `ClaimGrants` hands a Claim over through the bag guard and puts back what did not fit, `ClaimNotices` raises the toast when a Claim arrives and the notice once a session at login (never a grant, M428), and `/zigclaims give` rolls a loot table into a player's Claims, online or not. A payout that writes a Claim calls `ClaimStore.award`, never this package.
