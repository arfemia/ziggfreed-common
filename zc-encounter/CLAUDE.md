# zc-encounter

The fight is a native `EncounterManager` script under `Server/EncounterManager/`; this module adds only what the engine leaves out: native events off the script's beats, a participation ledger, health scaling and the payout.

- Never patch a native gap in Java as a backstop: whatever the script can express is authored in the script, and a gap the engine leaves is owned here by name.
- A need from a domain module (instance, objectives, progression, dialogue, commerce) goes through `seam/EncounterSeams`, never an import (`EncounterEdgeTest`; `instance.reward` and `instance.effect` are zc-loot and zc-effects, so they are allowed). The root fills attribution and subject; zc-instance fills the run tag (`EncounterRunTag`, a fight in a dungeon area belongs to the area's run, asked at the defeat and carried on `EncounterDefeatedEvent.runTag`); the power source is a companion mod's to fill.
- A fight pays only Claims (M428), through `payout/EncounterClaims` into zc-loot's `ClaimStore.award`, never the bag: the native `GrantReward` of a `ZigClaim` (`payout/ZigClaimReward`, `Server/Rewards/<Id>.json`, registered in `EncounterBootstrap`) pays a credited member of a defeated run from the shares the defeat kept on the run until its reset, a binding's `Loot.OnDefeat` and the retired `ZigGrant` write the same Claim, and an absent `Diminish` is the first each day (R260).
- A `ZigClaim` granted to a player no run indexes or rosters pays at a full share, so a continuing reset never drops its members from the index: `EncounterRuns.untrack(ended, next, encounter)` points them at the next run until its first tick re-indexes the roster, and remembers the encounter so `runRostering` finds a player who joined its roster that tick; a grant after a leash or a `zc:reset` in the same action list refuses.
- `EncounterBindingAsset` says what the server owes for a fight, never what the fight is: a knob describing the fight belongs in the script (`BindingRestatesNothingTest`).
- A run opens only for a script that puts up a boss bar or a binding row names (`run/EncounterAttachGuard`; a spawner's run is always kept), so the engine's bar-less scripts (hunt sites, elites, world events, crystals) are never engaged, wiped or listed. Whether a script sets a bar comes from `EncounterScripts`' one cached scan per id, read ahead at the boot self-test and on every builder reload, never mid-chunk-load; an unreadable script answers no.
- A bar-less fight counts through an `EncounterRules` row (`Match.Role`, an exact role id, never a pattern): zc-objectives' `EncounterRuleCredit` fires `ENCOUNTER_ATTEMPT` then `ENCOUNTER_DEFEATED` for the killer, targeted at the role id, and skips a live run's subject (`EncounterRuns.isLiveSubject`), which its run credits.
- Identity never rides in a string: the encounter is `EncounterManager.getEncounterId()` on the signalling entity, and a run's subject is a uuid re-resolved through the script's own slot, since an in-place role swap reissues the boss's reference.
- Register `EncounterSignalSystem` with `registerSystem`, never `registerEntityEventType`: the event type registers itself, and a second registration throws.
- Scripts signal with the reserved `zc:` grammar: `zc:engaged`, `zc:phase:<State>`, `zc:wave[:<label>]`, `zc:defeated`, `zc:reset`.
- Log one `[encounter]` INFO line per run event, never per tick, so a boot capture reads as the run's story.
- Shares normalise against the top contributor, who reads 1.0; below `MinShare` is attempt credit only.
- A phase drop hands everything over through `LootEngine.applyGrants` and applies nothing by hand: its items and drop lists through the `GroundSpillSinks` pair whose ground gathers ONE pile spawned at the subject, its commands through the engine's command leaf as the console with the phase's placeholders (`{encounter}`, `{phase}`, `{run}`). Its sinks carry no rewards leaf, so a reward kind there is refused with a warning and never paid.
- A `ZigGrant`'s `Loot` decodes once, at script load, through `BuilderActionZigGrant.decodeLoot` in the asset context the engine hands the script's builders, never a plain `ExtraInfo`: `LootRef`'s `Lootables` leaf is a contained-asset codec that throws outside an asset context. The encounter audit reads it through the same decode, and one that cannot be read is `ENCOUNTER_GRANT_LOOT_UNREADABLE`. A whole table written inline there is `ENCOUNTER_GRANT_INLINE_TABLE`: the engine's generated id is the script id plus the key stack, and a script's builders push no list position, so two can collide.
- Reset is always a run's last event; a run that engaged and never settled is settled as a wipe first.
- A `zc:defeated` beat pays only for a dead subject. The engine's `Target` sensor lets a boss go when it dies, leaves the world or runs past `Range`, so with a subject bound the beat is weighed against the world (`run/SignalledDefeat`; the subject found by uuid, since the beat has already released the slot): a subject alive, or gone without a death, was leashed, and the run settles as a wipe, pays nothing and resets at once with `ResetReason.LEASHED`. A fight with no subject bound keeps the beat as its defeat, and only the death system settles a defeat directly (`DefeatSignalRoutingTest`).
- An add is any NPC carrying the encounter entity's native `SpawnLineage`: the engine stamps one on every encounter and copies it onto whatever its `TriggerSpawners`, or a spawned NPC's own `Spawn`, raises. `system/EncounterAddSystem` (a `RefChangeSystem`, inside the store's lock) only notes the add against its run through `EncounterRuns`' lineage index; the encounter's tick scales it once by the row's `Scale.Adds` under `EncounterScaling.ADD_MODIFIER_KEY`, never the subject, which carries the lineage too. A row without `Adds` leaves every add as its role made it.
- The rest between fights is the binding row's `Timing.Rest`, stamped on the encounter entity as the persisted `ZigEncounterRest` and gated in the script by the `ZigRested` sensor, because a manually triggered spawn marker never reads its respawn time (`SpawnMarkerEntity.trigger`).
- Every registered action answers finished on every path: to the engine a `false` means still running, and a blocking action list waits on it (`ActionsAlwaysFinishTest`).
- An engaged or owned fight holds its chunk SECTION ticking, and its subject's, until it settles (`EncounterChunkHold`, called by `EncounterTickSystem` for the encounter entity and its subject, through zc-world's `world/TickingSections.holdTicking`, which never wakes, so the tick system may call it): on Update 7 a section sleeps on its own timer whatever its column does, and the engine unloads an entity added to a section that is not ticking. Spawn into a section nobody stands in through `EncounterSpawner.spawnWhenLoaded`; the plain `spawn` wakes a section in memory and refuses one that is not, so it never leaves an encounter parked.
- `Once` never heads a blocking action list: the engine spends a `Once` sensor after the instruction's first tick and strands the rest (`ENCOUNTER_ONCE_BLOCKS_LIST`). `Once` over a single-tick, non-blocking list is fine.
- A script named after a role replaces that role at load, and the role cannot be recovered (`ENCOUNTER_SCRIPT_ID_IS_ROLE_ID`).
- Encounter `Type` builder keys are flat and array-ranged (`Count: [min, max]`), the native builder vocabulary, unlike the nested asset codecs.
- The library manifest declares `Hytale:NPC`, `Hytale:EncounterManager` and `Hytale:Rewards`, so `NPCPlugin`, the encounter component and the native reward codec are live in `setup()`.
- A unit JVM cannot run the systems, the spawner or the Types: prove them with the dev-server boot, whose headless target is `/zigencounter spawn Zc_Encounter_Example` (then `end` it).
