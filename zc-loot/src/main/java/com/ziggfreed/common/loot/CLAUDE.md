# loot/ - the one loot core

One core serves every drop site (`Roll`, `LootRef`, `Lootable`), so identical JSON behaves identically wherever it is authored.

- A `Roll` reads `Conditions`, then `Chance`, then `Ladder`: a failed condition consumes no chance sample, a failed chance never evaluates the ladder, and the top-level and floor grants stack. A written `Chance` adds the lookup's `chanceBonusPercent` (a moment's bonus, `FactorLookup.withChanceBonus`: a broken block's gathering yield in a `ZigLootable`) before the 0..100 hold, read only in `RollEvaluator.effectiveChancePercent`.
- `Chance` is a `FactorFormula` group read as a percent held in 0..100 (`{"Base": 35}` is 35 percent), never a bare number: a bare scalar reads as absent, so the roll always fires and `LootableValidator` cannot see it. Check the shape, not the number.
- `Rolls` and `Pool.Entries` replace whole under `Parent`. To add to another table, name it in `ContributesTo`: id layering runs first and contributions fold on top, so `LootableConfig.resolve` answers the enriched table while `all` and `resolveAuthored` answer the files as written.
- A mod that composes extra rolls for a table from its own state registers a `LootableConfig.RollSource` under its owner id (`registerRollSource`, re-registering replaces, `unregisterRollSource`), never a parallel resolve of its own: `resolve` appends source rolls after the `ContributesTo` ones, in owner id order, so every reader (`LootEngine.resolve`, `resolveRolls`, a nested `Lootable` reward) sees them. A source never adds a pool, never conjures a missing table, and stays out of `all`/`resolveAuthored`, so its owner validates what it adds; a throwing source warns once and adds nothing. A roll pool composes the same way (`stamp/RollPoolConfig.EntrySource`, `registerEntrySource`): source entries follow the pool's authored ones in `resolve`, which every stamp read goes through. Both stores hold their sources in zc-core's `asset/OwnedSources`; a new read-time source on any store reuses it, never a third copy of the owner rules.
- `Roll.Expected` (default false) marks a roll's payout as the moment's expected one, a wage or a return rather than a find, and `Roll.HideInPreview` (default false) keeps a roll out of a table's preview list (`reward/LootablePreview`). Both are presentation only, the roll pays exactly the same.
- Each table a `LootRef` names keeps its own pool, since merging two bags would change both tables' odds. Picks draw with replacement, and `LootPool.MAX_PICKS` is an anti-runaway ceiling, not a balance knob.
- Deciding and doing are separate calls: `LootEngine.select` is pure and `rollAndGrant` applies it. A payout made later (a spoils screen, a claim) keeps its `select` answer, so what was shown is what is paid. Each `Selected` carries its payout's `chance` in percent: a roll's `Chance` as the pass read it (100 with none, a floor its roll's), a pool pick's chance of coming up at least once in its draw (`LootPool.pickChancePercent`); counts never enter it.
- Keep `RollEvaluator` pure: a new side effect is a new `LootEngine.Sinks` seam, and a pass-scoped reward is a `reward/CollectingRewardKind`, never a new seam. `Cue` is an opaque id, and this layer plays nothing.
- A site whose loot lands in the world takes its sinks from `GroundSpillSinks` (its javadoc is the reference), never a hand-built pair or a new knob: a site-specific drop routine is a `Ground`, and loot handed straight to a player takes `reward/LootRewardKinds.handToPlayer` (a pickup over the overflow policy, `Overflow.handleAll`), even inside a world-loot pass.
- A fractional amount that must pay out whole (a summed bonus tally, a multiplier read as a pass count) goes through `StochasticCount.resolve`: the floor always, the fraction as the chance of one more, at most one draw from the caller's source. Sum first and resolve once; never re-derive the rule at a site.
- A weighted pick goes through zc-core's `util/WeightedPick`. Build one `FactorSnapshot` per moment and never hold it across moments. `FactorGate` walks a `Conditions` array, but the bound test is `FactorCondition.accepts`: never re-implement `Min`/`Max` here.
- `LootableValidator.UNKNOWN_CONTRIBUTION_TARGET` is INFO, not WARNING: a `ContributesTo` waiting on a table another mod ships is the leaf working as designed.
- The library audits only on demand (`/zigloot validate`, `LootAudit.auditAll`, whose javadoc lists every domain it covers), never at boot outside zc-core's `ZIGGFREEDCOMMON_AUDIT_ON_BOOT` dev switch, save `drops/DropAudit`'s once-at-boot WARNING (below). A site that rolls a `LootRef` audits it with the 4-argument `LootableValidator.auditRef`, passing the collector types its pass carries (an empty set for none); a check that holds at every site (a `Moment_Item` Count) runs wherever the reward is authored.
- A `LootRef` decoded outside its asset store (a script action, a validator's re-read) needs an asset context: decode through an `AssetExtraInfo`, as zc-encounter's `encounter/types/BuilderActionZigGrant.decodeLoot` does; a plain `ExtraInfo` cannot resolve a named table.
- The moment-keyed bonus table (rows on breaks, hand harvests and kills, and the engine a consumer builds its own table from) lives in `trigger/`; read its router before touching a bonus row or a moment's landing.
- `drops/` puts a table inside a native drop list: `ZigLootableDrop` is the `ZigLootable` container Type registered into `ItemDropContainer.CODEC` (`LootDropsBootstrap`, unguarded). The engine rolls a list with no word of who caused it, so `DropContext` (per world thread) holds who the roll is for, filled by zc-objectives' `bonus/DropCredit` off the produced break and kill (idle until a ZigLootable decodes); with nobody known a gated row refuses and the rest pays. A placed block credits nobody, as the placed-block ledger rules for XP: its ungated rows pay like the vanilla entries, so an owner keeps a row off placed blocks by gating it. So does a vein's or a felled tree's further block (zc-world's `ShapedBreaks.rowsAllowed`, unless the shape's `Rows` lets them roll), so a player-only row pays once, on the block in hand, as a bonus row does (R879). Only items, native drop lists and nested tables drop (`reward/DropRows`); every other row pays nothing there and `DropAudit` warns of it once at boot (WARNING, standing down under the boot audit, which reads it through `LootAudit`). `getAllDrops` never answers empty, or the engine refuses the whole list at load.
- A table or a bonus row may gate on a mod through a top-level `Requires` (the mod gate, zc-core's `asset/` router): a refused file never contributes, rolls or reaches an audit, and a reference to a refused table reads as refused (`LootableValidator.modGateRefused`), never as an unknown table.
- The rest of a table's `Requires` (`LootableAsset.liveRequires`, zc-core `StoreGates`) is asked of the moment's player: `LootEngine.resolve` hands out the table's rolls and pool entries carrying it (`Roll.gatedBy`, `LootPool.Entry.gatedBy`; a contributor's rolls and entries carry its own too), and `RollEvaluator` and `Entry.isEligible` ask it through the lookup's `gateQuery()` before any condition or chance sample. A lookup with no question (`FactorLookup.none()`, a bare lambda) refuses every gated table. A bonus row's is asked in zc-objectives' `BonusRowReactions` before its chance.
