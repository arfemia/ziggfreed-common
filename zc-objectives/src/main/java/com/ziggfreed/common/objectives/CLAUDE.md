# objectives/ - the library's own parts of the shared progression runtime

- There is one `QuestEngine` plus `AchievementEngine` per server, held by zc-progression's `progress/runtime`. `runtime/ProgressionDefaults` registers this library's parts into it at library-default rank, so any consumer registration outranks them.
- The progress component type and the producer systems register at `setup()`, and the connect-time attach is unconditional (the component also holds dialogue memories). `ProgressionRuntime.usesDefaultStores()` gates only the player-ready maintenance pass.
- Never register a competing producer for an event `producer/` covers. A net-new moment registers its kind and calls `ProgressDispatch.fire`; a consumer reacts to a produced moment through a `MomentListener`, never a second ECS system on the same native event.
- Both halves of a hand-in (`QuestPossessionProbe`, `QuestInventoryConsumer`) and a `ProgressHandle` that answers for `Player` and `PlayerRef` are mandatory: without them hand-ins and rewards silently do nothing while every surface reports success.
- No test constructs a page: initializing one builds a logger in a static initializer that needs the engine's `HytaleLogManager`, which the default `test` task lacks. Paint code is tested under `engine-items` (`book/BookShellPaintTest`, `book/achievement/MilestoneTrackPaintTest`), and what a row is named by is asserted on the runtime object (zc-progression's `ContentTextArgsTest`).
- The library registers no reward retry queue: a failed reward is parked through `ProgressionRuntime.rewardRetryQueue()` only where a consumer filled that slot, and is otherwise logged and lost.
- `hytale/` holds the Types registered into Hytale's own Objectives (`NativeObjectivesBootstrap`, only once the Objectives plugin's data store exists, then proved): the one task `ZigMoment` for every objective kind (kinds are data and the engine keys a Type by class, so never a Type per kind), credited by `MomentTaskFeed` off the engine's own live task index and never a per-task listener, in the objective's own world only, and a value-based step seeded at attach from the quest engine's own `standingValue`, never a copy of it; a kind a mod fires straight into the engines never reaches it, which only `OffStreamMoments` (a dispatch tap, keyed off `ProgressDispatch.dispatchingStreamedMoment`) can see; and the completions `ZigRewards` and `ZigTrack`, which pay only through `ObjectiveClaims`, one Claim per participant per objective run, written once (`ClaimStore.award`, never a top-up).
- `gate/` is `ZigRequires`' read side: `RequiresCheck` (a player as the runtime's subject, any other entity through its own context, or a world with nobody in it, against a `Requires` block; nothing read off the world thread), the native condition Types `ZigRequiresBootstrap` registers unguarded through the plugin's codec registry (trigger volume, entity `Id`, NPC decision, choice requirement, and world event stage while WorldEvents runs), and the every-boot `RequiresVolumeAudit`; the interaction Type that speaks the line sits in `interaction/`. Of the conditions only the choice requirement speaks a line, since the engine's choice page shows no reason.
- Every surface (the book, the NPC quest page, the tracked HUD) reads the runtime's own subject and wraps each mutating call in the registered `ProgressionCallScope`; a subject built locally reads neutral through another mod's store and drops every write.
- A quest finishing, waiting to be collected and collected are announced only by the engine's notices (`Quest_Completed`, `Quest_Parked`, `Quest_Claimed`), drawn into an open page as they fire: the book, the NPC quest page, a conversation and any consumer surface raise no toast of their own for them (R877). Any other claim toast (an achievement's, a milestone's) lists the receipt (`GrantOutcome.receipt()`, painted by `render/ClaimToasts`), never the authored reward list. A Collect presses `attemptClaim` (`attemptClaimMilestone` for a rung) and answers a refusal with `ClaimToasts.refusedToast` (no room, elsewhere, nothing waiting), never a fit probe of its own.
- The progression admin page opens only through the static `admin/ProgressionAdminPages.open`, never a registered destination, and its audience defaults to deny. The Use Gates page (`admin/UseGateAdminPages.open`) shares those deps, so it opens for exactly whom the progression page opens.
