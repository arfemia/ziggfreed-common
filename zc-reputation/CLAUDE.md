# zc-reputation

Standing with a faction or one NPC, on Hytale's native reputation system.

- A reputation IS a native `ReputationGroup` (`Server/NPC/Reputation/Groups/<Id>.json`); `ReputationAsset` (`Server/ZiggfreedCommon/Reputations/<Owner>/<Id>.json`) is zc's companion keyed by the same id, matched without regard to case. The engine's maps are keyed exactly, so every native call takes the engine's own spelling (`ReputationDef.id()`), never the authored one.
- zc ships the one global ladder (`Server/NPC/Reputation/Ranks/`, seven files). The engine reads ranks and groups once at start: a change needs a restart. A group with no `NPCGroups` key, or one naming an unloaded NPC group, makes the engine throw on every NPC add.
- A reputation may add ranks of its own above the shared top: a `Ranks` entry whose id is not a shared rank, with a `From` floor above the top's. `ReputationLadder.of(global, floors)` is that reputation's ladder and `ReputationService.ladderOf` / `ladderFor` hand it to every reading: the factor, the rank watch and `REPUTATION_RANK` credit, the bar, the page, Beyond (past its own top) and the audit; `ladder()` is the shared ranks alone. A `From` on a shared rank, at or below the top's floor, or on another tier's floor is an audit ERROR and ignored, so the shared floors, and every NPC's attitude with them, never move. A second tier whose id another holds in another case is an ERROR and ignored too (ids match without case). An own rank with no `Name` is a WARNING (`TIER_WITHOUT_NAME`): it would read as its id.
- A `reputation_rank` lock line words itself: `ReputationFactors.contribute` registers a `FactorNames` param namer that composes `factor.rank_with` from the rank's name with that reputation and the reputation's `TitleKey`. A pack's `ParamNames` Keys entry for an exact Param still wins, and a reputation with no `TitleKey` keeps the generic line.
- Every engine call goes through `ReputationNative` (production `EngineReputationNative`; tests `FakeReputationNative`). `ReputationService.change` is the only zc writer: cap, the engine's `changeReputation`, then the fan-out (change event, the bar, Beyond payout) and a rank check. The bar is the World bar, or, for a change made while the player has a custom page open (`KeyedCustomHud.coveredByPage`), the centred row (`HudPanels.movedInCenter`), held until the page closes; never both. Both rows are labelled with the reputation's name alone (a World bars column leaves a name about 120 px, and a bar's end captions hold three or four letters), never its rank. The admin `/reputation` writes the native value directly and raises nothing; every reading still reads the native value.
- Effective standing = earned + the `Gear.Stat`'s folded MAX. Factors, the page, the bar and the rank checks read effective; the engine's NPC attitude reads earned; Beyond payouts count earned.
- Ranks are "effective rank, self-healing": `ReputationRankWatch` checks on every change, after every equip recompute (one listener on the installed equip bridge, run on a later world task) and once at login. A check credits the ranks from the reputation's starting rank (where its `InitialReputationValue` lands) up to the current one, or below the start only the ranks reached going down (`ReputationLadder.credited`, `ZigReputationRanksHeldEvent`, which zc-objectives turns into `REPUTATION_RANK`); only a rise during play raises the `Reputation_Rank` notice. The last-seen ranks are transient and single-process, dropped at disconnect; the first check after login is a silent hydrate.
- A kill's change runs on a later world task, never inside the death system that fired the moment.
- `page/` is the Reputation page: `ReputationView` decides its rows (one per met reputation, with the rank above or the next Beyond reward), its kit models (the list's `LedgerModel`, the reading page's `DetailView`: bar, description, How to earn from the companion's `Earn.Lines` or what zc can see, the ladder with what each rank opens, Beyond, the numbers) and the words; what a rank opens comes from zc-progression's `GatedContent` (zc-commerce lists its shop offers there at setup), so this module never imports commerce; `ReputationPage` paints that into `ZigReputationPage.ui` in the shared menu frame with the kit's painters and decides nothing; `ReputationPages.open` opens it on the player's own ref. `ReputationDestinations` registers the `Reputation` destination type at setup (its optional `Reputation` key names the reputation to open on, else the first met), and `ReputationMenuTab` fills `MenuSlot.REPUTATION` while the module is on and the player has met one.
- Off means absent: `$Enabled` in `mods/ziggfreedcommon/reputation.json` (read at setup and with the companions) or a companion's `Enabled: false` makes the reputation unknown (factors null, rewards refused, no page row); native standing is untouched.
- Never import zc-objectives here: it depends on this module, not the reverse.
