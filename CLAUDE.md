> **PARADIGM (remember this): a generic, mod-agnostic Hytale primitive belongs HERE, not duplicated in a consumer mod.** When a sibling mod (Kweebec Nightmare, a future minigame, the MMO) needs a reusable engine wrapper - 3D sound, camera, an asset-index resolve, a HUD/toast helper, a worldgen/terrain query, etc. - add it to `ziggfreed-common` and consume it; do NOT reimplement it per mod. New primitive = a new file here (+ its package router), then rebuild the jar consumers pin. A consumer keeping only the mod-SPECIFIC policy (round logic, content config) is correct; the reusable engine call underneath is what gets lifted. (Latest example: `world/SurfaceProbe`, lifted out of Kweebec's `ArenaBuilder` so any mod can floor-snap onto procedural terrain.)

> **PARADIGM (the goal is no-Java pack authoring): consumer CONTENT + display CONFIG belongs in `/Server/` pack JSON, NEVER Java-baked.** Anything a pack author should be able to create or tune without code - dialogues, the queue-mode cards, leaderboard tabs/columns, party knobs, reward lists, queue policy - is a codec asset loaded from `Server/<Mod>/<Type>/` (Pattern A structured codec - the codec IS the schema - or, for a legacy type not yet converted, an `extends`/`params` DSL), resolved `defaults < pack < owner`. The library ships at most a NEUTRAL structural fallback (e.g. `QueueModeSet.fallback()` has no baked icons) and ZERO content; the real values are authored in `/Server/ZiggfreedCommon/<Type>/`. A Java constant list / hardcoded JSON string that represents content is a smell - lift it to an asset. **Common OWNS its framework stores** (one class = one registrant; a consumer must NOT re-register them - it authors JSON into the path and reads the resolved config singleton back). ## Build

Gradle runs via PowerShell (Java 25). Self-contained `build.ps1` builds + installs:
```powershell
cd 'D:\dev\business\hyMMO\additional-mods\ziggfreed-common'; .\build.ps1
.\build.ps1 -Install:$false     # build only
.\build.ps1 -ModsDir <path>     # explicit install target (else $env:HYTALE_MODS_DIR)
```
Produces `build/libs/ZiggfreedCommon-<version>.jar` and copies the runtime jar (never `-sources`/`-javadoc`) into the Hytale `Mods/` folder when `HYTALE_MODS_DIR` is set. `.\gradlew.bat build` works too. The Hytale server jar is referenced `compileOnly` (path in `gradle.properties`: `hytaleHome`/`patchline`/`game_build`) and NEVER bundled; jsr305 is `api` on each module (the `@Nonnull`/`@Nullable` annotations must resolve for consumers that compile against this jar) but is deliberately NOT bundled into it.

## Modules (build-time only - one jar ships)

The library is built as THIRTEEN Gradle modules plus a thin wiring root, all sharing the ONE package root `com.ziggfreed.common`. **A module boundary is a build-time concern only**: the module jars are merged back into the single `ZiggfreedCommon-<version>.jar` a server loads, so no consumer import, class name, `manifest.json`, or build script changes because of it. Only the aggregate is installable - the per-module jars in `zc-*/build/libs` are compile inputs, carry no `manifest.json`, and are NOT loadable mods on their own (the shipped `.ui` pack references across module lines, e.g. a dialogue page importing the shared frames). The point of the split is that a module reaches only what its `build.gradle` declares, so an accidental cross-domain edge fails the build instead of quietly welding two domains together.

**Every inter-module edge is `implementation`, never `api`.** An `api` edge leaks its own dependencies onto every downstream module's compile classpath, which is exactly the isolation this table claims to have and would not have. Restore `api` on a single edge only when a module's PUBLIC SIGNATURE genuinely re-exports another module's type, and name that type in a trailing comment. One such re-export exists today and deliberately stays `implementation`: `zc-dialogue`'s `DialogueCondition.World#getSelector` returns a `world.WorldSelector`, and the one module depending on `zc-dialogue` reads NPC identity and never calls it, so no `world.WorldSelector` has to resolve on its compile classpath. The day a dependent DOES call it, that dependent declares its own `zc-world` edge, or this edge becomes `api`. (`jsr305` stays `api` in `gradle/zc-module.gradle` - consumers compiling against the aggregate must resolve the annotations.)

### The five split packages

Five packages deliberately span a module line, which a flat merged jar makes free. Each needs its reason recorded, or the exception quietly becomes the rule:

- **`com.ziggfreed.common`** - `CommonLog` in core, the plugin in the root. The logger handle must be reachable from every module; the plugin entry point must not be.
- **`com.ziggfreed.common.asset`** - the reusable bases in core, `FrameworkAssetRegistrar` in the root. The registrar reaches into six domains to register their stores and would cycle from anywhere else.
- **`com.ziggfreed.common.factor`** - the model / registry / condition in core so any module can gate on a factor; the portable `hytale:` standard library in zc-entity, because it reads engine entity and item data.
- **`com.ziggfreed.common.cast`** - `WorldEvictors` in core, the rest of the cast / interaction runtime in zc-cast. Every domain registers into the per-world eviction fan-out, and making three modules depend on the whole 38-class cast runtime for that one class defeats the guard. Keeping the FQN meant the call sites across the consumer mods never moved.
- **`com.ziggfreed.common.stats`** - `StackStats` in core (a pure item-metadata value record: codecs, an `ItemStack`, nothing else), the ECS bridging in zc-entity. A module that stamps a stack should not have to drag puppets and equip triggers along.

**Adding a package**: put it in the module whose domain it belongs to (`git mv` the directory into `<module>/src/main/java/com/ziggfreed/common/`; its tests mirror into the same module). If it needs something the module does not already declare, add a ONE-WAY `implementation project(':zc-x')` edge, never a cycle. Shipped `/Server/` and `/Common/UI/` resources live in the module that owns the code reading them; `manifest.json` stays root-only, and no module may carry one. A genuinely cross-domain test (`asset/AssetCodecInitTest`, which touches every asset codec) stays in the ROOT project's test set rather than forcing edges onto a module.

**A seam that SHIPS is a seam that is FILLED (build-enforced).** An interface declared here ships with a production default in its own module or a root fill in the SAME change; a seam kept intentionally empty for the next caller is deleted, not kept. Every seam degrades silently to "does nothing" when unfilled, so a gap never fails a build and never fails a boot - it fails a player, later, invisibly (an achievement nothing gates, a list that names nothing, an NPC with nothing to say). `SeamsFilledTest` (root test set) walks the registration state after `ProgressionDefaults.register()` and names any progression seam still standing empty: a gate for BOTH engines, a text source, an offer provider, a claim table, a store. A seam the WIRING ROOT fills at plugin setup rather than one those defaults register (the dialogue memory backend) is out of that test's reach, so it REPORTS ON ITSELF from inside its own module the first time it has to fall back, once per process, through `SafeLog`: `DialogueMemories.persistentBackendOrWarn` names the missing `DialogueMemories.install(PersistentStore)` fill and what it costs the player, and `FirstClaims.store` names the boot-lifetime claim table and the `FirstClaims.install` that replaces it. Give a root-filled seam a report of that shape (pinned by a test in its own module), never a `SeamsFilledTest` assertion that cannot fail. `NpcOffersLivePathTest` (root test set too, for the same reason - it needs the registered defaults) walks the whole live offer path a giver's screen and a conversation's "have you anything for me" line both take. **Both of those tests leave the shared progression runtime CLEARED on teardown**, so a future root test that reads registration state must register what it needs in its own setup rather than inheriting whatever ran before it.

**The wiring root is REGISTRATION ONLY (build-enforced).** The root is the one place an edge between any two modules is legal, so it will absorb every awkward dependency offered to it - and logic that settles there is logic no module can be tested or reasoned about without standing up the whole plugin. `RootRegistrationOnlyTest` (root test set) walks EVERY `.java` file under the root's `src/main/java` - it discovers them rather than naming them, so a fourth root file cannot slip in unscanned - and fails the build on a loop, a `switch` or an `else`. What passes: a try/catch guard, an `if` that tests for `null` or whose branch leaves at once by `return` or by `throw` (both are "refuse this input and get out"), and a null-defaulting ternary, including one wrapped across several lines. Escape hatch `// ROOT-LOGIC-OK: <reason>` with a real reason, on the line, inside the statement, or in the comment block above it. If the root has to DECIDE something, that decision belongs in a module behind a seam the root fills.

**The reverse-edge trap.** A module's position in the graph permanently forbids the edges above it. `zc-progression` sits below `zc-dialogue`, so it may never import dialogue, presentation or world - yet quests will want an NPC turn-in conversation, a results page, a waypoint and world-scoped objectives. `zc-loot` sits below both `zc-progression` and `zc-instance` and is more constrained still. **Every one of those needs is a SEAM the lower module declares and the wiring root or the consumer fills, never an import.** The first violation is not found until it is an unbreakable cycle three modules deep, mid-rewrite, so the rule is repeated in those modules' own routers.

### SubPlugins: not now, and the checklist for later

The `manifest.json` declares ONE identity (`Ziggfreed:ZiggfreedCommon`, one `Main`, one asset pack, no `Dependencies`), and that is a truthful statement of reality: the zc-* modules are compile-time slices with no independent lifecycle, so there is no runtime identity for the manifest to fail to express. **Do not add a `SubPlugins` block.** Every candidate engine ships EMPTY of content by design, so there is nothing to toggle; one jar means one classloader, so a "disabled" sub still links and merely never registers its stores (a silently half-initialised library instead of a clean failure); each sub would need its own required `Main`, splitting an indivisible boot sequence that already carries ordering constraints; and a sub-identity cannot carry its own asset pack (`AssetModule.registerPackFromJar` reads the jar's TOP-LEVEL manifest and registers one pack per jar).

Any ONE of these flips that answer:

- A domain acquires a genuinely optional **runtime cost**: a per-tick system, a registered ECS component/system, or a global event listener.
- A domain needs its **own `Dependencies`** - a sub-manifest can carry a different dependency map than its parent, which is the one thing the parent manifest structurally cannot express.
- A domain needs its own **`ServerVersion`** range or its own **`Permissions`** block (both are per-manifest).
- A third party credibly asks to depend on one domain **without** the rest's runtime.
- A domain becomes independently **releasable** with its own version cadence visible to consumers.

**Precondition before ever pulling the trigger**: the candidate module must first have a self-contained `setup()` / `shutdown()` that is SAFE TO SKIP, and every dependent must degrade gracefully when it is absent. Neither is true of any module today.

## Consuming this mod

A consumer mod adds ziggfreed-common as a `compileOnly files(...)` dependency (the local jar path until a remote + submodule gitlink exist) and lists it in its `manifest.json` `Dependencies` (or `OptionalDependencies`) so the server loads it first. NEVER bundle this jar into a consumer (double-loading engine-touching classes under two classloaders breaks identity). All primitives are static, config-free, and reusable as-is.

## Conventions

`@Nonnull`/`@Nullable` on params; **[`CommonLog.LOGGER`](zc-core/src/main/java/com/ziggfreed/common/CommonLog.java) for logging** (guard the raw LOGGER behind a try/catch on any path a unit test could reach - the flogger LOGGER throws in a log-manager-less unit JVM; `util/SafeLog` does that for you). Never log through `ZiggfreedCommonPlugin.LOGGER` from library code: it is the same handle, but reaching for the plugin entry point drags the whole wiring root into a package's dependency closure. `ConcurrentHashMap` for shared maps. Every engine-touching call is try-guarded so a missing asset / bad ref degrades to a no-op, never a throw into the caller. World-thread discipline: off-thread work hops via `world.execute` before any Store/Ref/Sound/HUD/camera read; packet writes (`writeNoCache`/`write`) are thread-safe off-thread. **No em-dashes anywhere.** Package root `com.ziggfreed.common`. **UI RICH TEXT (any primitive that shows text): colour/bold/italic = native `<color is="#hex">`/`<b>`/`<i>`/`\n` markup in the `.lang`, rendered on a Label's `TextSpans` (NEVER `.Text`, which prints the tags literally); per-locale, client-parsed; `TextButton`s + String sinks can't (NOR do they substitute `{0}/{1}` params - a parameterized `Msg.tr` prints the literal `"{0}{1}"` on a `TextButton.Text`). For CLICKABLE rich / parameterized text use [`ui/ZigRichButton`](zc-presentation/src/main/java/com/ziggfreed/common/ui/ZigRichButton.java): the vanilla `Button` ELEMENT (a `ButtonStyle` container) wrapping a child `Label #Label` set via `.TextSpans`, styled by `ZigButtons.ui` `@ZigRichRowBtnStyle` (theme-tintable). The `dialogue/` page does the Label case (`#NodeText.TextSpans`). Crucial UX infra, authority: `../../.claude/research/hytale-rich-text-textspans.md`.**
- **HARD RULE - every LABELED clickable button is a `ZigRichButton` (a `Button` + inner `#Label`), NEVER a `TextButton` whose `.Text` you set from Java.** We HAVE the rich-button primitive - use it. A `Button` + `#Label` pushed via `ZigRichButton.text` (`.TextSpans`) substitutes params + renders markup + resolves cleanly; a `TextButton.Text` sink is the wrong tool (it is the exact anti-pattern this primitive exists to replace). This applies to page tabs, save / confirm / cancel buttons, list-row action buttons - anything with a label. `SettingsUiUtil.setToggle` / `setTabActive` already drive the rich `#Label`; a page authors its buttons as `Button { Style: $Z.@ZigRichRowBtnStyle; Label #Label {...} }` (or `$Z.@ZigRichBtn`) and sets each label with `ZigRichButton.text`. Do NOT reach for a `TextButton` label just because it is a single key.
- **HARD RULE - every `ItemGrid` carries a `Style`, and it comes from the shared ladder.** An `ItemGrid` declaring no `Style:` renders NOTHING: the slot is laid out and reserves its width, so the row indents as though an icon were there, and the picture never appears. It fails silently and it fails in game only, since `.ui` files are never compiled or validated. `zc-presentation`'s [`Common/ZigButtons.ui`](zc-presentation/src/main/resources/Common/UI/Custom/Common/ZigButtons.ui) holds `@ZigIconGrid18` / `20` / `22` / `24`; a page imports that file and picks the rung matching its own grid's `Anchor` width and height (`Style: $Z.@ZigIconGrid20;`). Never declare a private `ItemGridStyle` in a page: the sizes are the only thing that varies, the ladder already covers them, and a fifth size is one more rung here rather than an eighth copy of the same eight fields.

**Submodule order (when a remote exists):** commit + push HERE first, verify the SHA is on the remote, THEN bump the gitlink in the parent hyMMO repo. Until a remote exists, consumers build against the local jar.
