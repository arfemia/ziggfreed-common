# ui/toast/ - transport-agnostic in-page toast engine

Router for `com.ziggfreed.common.ui.toast`. A mod-agnostic, in-menu toast overlay lifted from the MMO Skill Tree's `ui/toast/` (the MMO is the shared-file owner and now re-derives its own `ToastablePage` as a thin subclass over this engine). i18n is parameterized OUT: the engine takes pre-built client-resolved `Message`s only - it imports no consumer `Msg`/reward renderer (the one reward-aware class here, `RewardToastLines`, consumes zc-loot's already-composed chips and takes the overflow line from the caller). Element ids/styles are strictly neutral (`#Zig*`) so the `.ui` never collides with a consumer's own pack when both jars are installed.

- **[`ToastSpec`](ToastSpec.java) + [`ToastLine`](ToastLine.java) + [`ToastKind`](ToastKind.java)**: the immutable, transport-agnostic model. Build via `ToastSpec.of(kind, message)` then `withLines/withDuration/withTitle/withIcon`; lines carry an optional item-icon id + a pre-built `Message` (the consumer maps its own reward/feedback rows in, never re-resolved here). `ToastKind` maps each severity to a panel text/frame colour + a native `NotificationStyle`.
- **Per-kind 3D SFX, played on show, zero per-call wiring.** `ToastKind.soundId()` is a default base-game `SoundEvent` id (`SUCCESS`/`ERROR`/`WARNING` chime; **`REWARD` + `INFO` default to SILENT on purpose** - a REWARD toast is the VISUAL companion to a grant whose authority already plays the reward jingle, INFO is passive). `ToastSpec` adds `withSound(id)` (override) + `silent()` (suppress) + `effectiveSoundId()` (override else kind default, null when silent). `ToastablePage.showToast` plays it at the player via `sound/Sound3D` (world-thread - `showToast` runs in a page event handler - fully guarded; a missing asset degrades to silence). So a moment whose sound is owned elsewhere (a claim that plays its own cue, mastery's bespoke purchase cue) marks the toast `silent()`; a one-off REWARD with no authority sound opts in via `withSound`.
- **[`ToastStore`](ToastStore.java) is the SINGLE current-toast authority, keyed by player UUID, held STATICALLY** - pages reopen as fresh instances, so per-instance toast state would be lost on the reopen meant to render it. A monotonic `GEN` token (`show` -> `clearIfCurrent(gen)`) stops a stale scheduled auto-dismiss from clearing a newer toast.
- **[`ToastController`](ToastController.java) is the engine; [`ToastSurface`](ToastSurface.java) is the ONLY transport seam** (a `@FunctionalInterface push(UICommandBuilder)`). `show(...)` writes the store + pushes the show command, then schedules the hide via `HytaleServer.SCHEDULED_EXECUTOR`; `renderInto(cmd)` repaints the live toast into a full `build()` so it survives a page reopen. Bind the surface to a page `sendUpdate` (no reopen, scroll preserved).
- **[`RewardToastLines`](RewardToastLines.java) is the ONE bridge from the reward-chip reading to toast body rows** (the reason this module carries its single zc-loot edge): `lines(rewards, source, overflow)` reads `List<RewardSpec>` through `RewardChips.chipsFor` (the same ladder every chip surface uses, consumer source included), `fromChips` maps already-read chips, and `cap` is the row-budget primitive both share - a list past `ToastRenderer.MAX_LINES` keeps `MAX_LINES - 1` rows and spends the last on the CALLER's `overflow.apply(dropped)` line (its words belong to the caller's lang file; null truncates). Icons carry quantity ONE: the chip's own label already says how many, the same reason the book surfaces paint chips as single items. A consumer capping toast rows routes here, never a private copy (the MMO's `ToastablePage.showRewardToast` + `QuestToasts` both do).
- **[`ToastRenderer`](ToastRenderer.java) is the SOLE owner of the `#ZigToast` element-id contract** over the shared `Pages/ZigToast.ui` fragment (+ `ZigToastFrame.png`, a white 9-slice frame tinted per kind). Show/hide is driven by `Anchor` collapse to `0x0` (a `sendUpdate` can set `Anchor` but NOT flip `Visible` false->true); `MAX_LINES` reward rows are pre-baked because `sendUpdate` can only restyle existing elements, never append. `MAX_LINES` MUST match the `#ZigToastRow<i>` count in the `.ui`.
- **[`ToastablePage`](ToastablePage.java) is the page base** a consumer page extends: `showToast(kind, msg)` / `showToast(spec)` set the toast (call after an in-page action, then reopen the page), `renderToastInto(cmd)` paints it as the LAST root sibling (call last in `build`). **The auto-dismiss push is keyed on the player's CURRENTLY-ACTIVE toastable page (a static `ACTIVE` registry: `renderToastInto` registers `this`, `onDismiss` compare-removes), NOT the instance that scheduled the hide** - because the dominant reopen flow is `showToast(...)` then `openCustomPage(ref, store, new SomePage(...))`, a DIFFERENT instance, so a hide bound to the scheduling instance would never fire (the bug behind "menu toasts not auto-dismissing"). The world-thread push rechecks `ACTIVE.get(id) == this && !dismissed && ref.isValid()` so a delayed hide racing a navigation is dropped, not crashed. It also owns **`playerEntityRef(fallback)`, the one seam for reading PLAYER state off a page**: a page is opened ON an anchor, and at a press-F that anchor is the CHARACTER's entity, so the `ref` handed to `build` is the anchor while the one handed to `handleDataEvent` is the player's. Any player read taken straight off the `build` argument comes back empty (an empty quest list, a zero balance) until the first click corrects it, so resolve it through this instead and pass the caller's own ref as the fallback. The MMO subclass adds its reward-list helpers (`showRewardToast` over its `RewardListRenderer`); common's own `instance/result/ResultsPage`, `party/page/PartyInvitePage`, `instance/play/PlayModePage` extend this for in-page reward/feedback toasts.
