# ui/hud/ - the in-world HUD base, its layout value and a player's HUD preference

- Every custom in-world HUD extends `KeyedCustomHud` directly: supply identity and layout, call `applyConfiguredPosition` in `build()`, and push through `dueForPush`/`markPushed` (a tick loop) or `acquirePush`. An event-driven HUD returns 0 from `updateIntervalMs()` and folds bursts through `RepaintCoalescer`, with `aliveWorldOf(playerRef)` as the executor.
- `HudPosition` pins exactly one edge per axis and never sets `Horizontal` (a LEFT+RIGHT inset that stretches the panel to full width). A content-height anchor is proven only for a TOP pin inside a `LayoutMode: Top` wrapper; a BOTTOM pin needs an explicit height.
- A player's own HUD choices live in `settings/PlayerSettingsComponent` (a spot and a three-state Show per surface, `HideAll`), written only through `settings/PlayerSettings` on the world thread; the panels read them through `HudPreferences` (`isHidden`, `placementPick`, `isHideAll`), which folds in the owner's defaults and locks. A consumer persisting player data elsewhere listens for `ZigPlayerSettingChangedEvent`.
- `settings/HudSettingsPages.open` is the only way into the HUD settings page, which is now only the server's layout: it opens for the consumer's registered audience and answers false for anyone else, and it is deliberately not a registered destination, since it writes the owner file. Save reads every panel's draft before its first write, so a field that will not read writes nothing.
- What the page lists is a pure plan (`settings/HudSettingsRows.server`), because `UICommandBuilder` cannot be stood up in a unit JVM: change its controls in the plan, where `HudSettingsRowsTest` reads them.
- `/zighud` sits in the engine's adventurer permission group, so every player holds its verbs; the owner verb `default` sits in the world-editor group.
