# ui/hud/bar/ - the shared progress-bar HUD

Router for `com.ziggfreed.common.ui.hud.bar`. Two semi-transparent panels any mod drives with one call per movement; the library creates a row on demand, dresses it from what the reporting mod says, and knows nothing about what a value measures. Nothing is authored for a row to appear. The parent [`ui/hud/`](../CLAUDE.md) router holds the `KeyedCustomHud` base this builds on, the per-player `HudPreferenceComponent` the panels read, and the settings page + `/zighud` family that edit it.

- **THE RULING (maintainer, 2026-09-09): there is NO value-source seam here and none is to be rebuilt.** The asset store is the extension point (the root `CLAUDE.md`'s "The ASSET STORE is the extension point" rule); a `Source: <namespace>:<local>` string paired with a Java `register(namespace, provider)` call re-invents what the `HudBars` folder already does, so the seam was deleted outright rather than re-keyed. Whoever reports a movement hands the reading over WITH it (`HudBars.moved` takes a `HudBarReading`), the row keeps it, the paint draws from what the row holds, and nothing is asked of anyone at paint time. A bar only exists because something moved, so there is nothing to read back for. A row id is OPAQUE: no namespace convention, nothing split on a colon, matched whole (case-insensitively) against an override's `Source`; a mod names its row by the id of the thing measured.
- **TWO PANELS, and which one a row lands on is the CALLER's choice** (maintainer, 2026-09-09), made by which call it makes, never by anything this package reads out of the row: only the mod reporting a movement knows what the player is in the middle of. [`HudBarStackHud`](HudBarStackHud.java) is the tall ledger (`HudBars.moved` / `itemMoved`), [`HudBarGridHud`](HudBarGridHud.java) the wide block for values moving while a player is simply out in the world (`HudBars.movedOnGrid`). Both are attached to every player at ready, LATE, and `HudBars.panels()` lists them (a `HudBarLayout` each) for whatever offers a panel by id.
- **WHERE a panel sits is a PLACEMENT, an asset, never a corner hardcoded in Java** (maintainer, 2026-09-09; the closed-roster trap the root `CLAUDE.md` bans). [`HudBarPlacementAsset`](HudBarPlacementAsset.java) at `Server/ZiggfreedCommon/HudBarPlacements/<id>.json` is one named spot: `LabelKey`, a `Position` group ([`HudBarPosition`](HudBarPosition.java): `Preset` + `OffsetX` + `OffsetY`, every leaf nullable), `Columns`, `RowsPerColumn`, `Panels` (the panel ids it was measured for; absent = every panel), `Order`, `Enabled`. The library ships three: `TopLeft` (the ledger's home, at the SAME origin as the zone card mob-scaling draws there, (16, 90), deliberately OVER it because the ledger attaches later and is transparent behind its frame; 2 columns, 13 deep, offered to both panels), `TopRight` (6 columns growing leftward, for the grid) and `BottomLeft` (the grid's shipped default: 2 columns of 200px, (16, 16), below the player's own bars and clear of the hotbar, growing UPWARD). A pack adds a spot by dropping one file and every picker offers it; the owner layer is `mods/ziggfreedcommon/hud-bar-placements.json`. Fold: [`HudBarPlacementConfig`](HudBarPlacementConfig.java) (`placement(id)`, `offeredFor(panelId)` in `Order`-then-id order, enabled + fitting only; `ids()` feeds the Asset Editor pick list `ziggfreedcommon:hud_bar_placements`).
- **[`HudBarPanelAsset`](HudBarPanelAsset.java) is a panel** at `Server/ZiggfreedCommon/HudBarPanels/<id>.json`: `Enabled`, `LabelKey`, `Placement` (the spot's id), inline `Position` / `Columns` / `RowsPerColumn` (restatements OVER the spot, leaf by leaf, for an owner stating custom values), `MaxVisible`, `RepaintMs`. It carries no slot ceiling of its own: `maxVisible(documentSlots)` takes it from the caller, because that belongs to a DOCUMENT. `Default.json` names `TopLeft`, `Grid.json` names `BottomLeft`; a consumer's same-id file wins by pack order and `mods/ziggfreedcommon/hud-bar-panels.json` wins over both. [`HudBarPanelConfig`](HudBarPanelConfig.java)`.current()` / `.grid()` / `.panel(id)` always answer. [`HudBarPanelOwnerWriter`](HudBarPanelOwnerWriter.java) is the ONE path the panels owner file is written from in game (the settings page's Server tab and `/zighud default`): `setPlacement` (clears the inline leaves, since a nudge measured from one corner is nonsense against another), `setEnabled`, `setLeaves`; it keeps an existing entry's key spelling, re-reads through the same codec and repaints everyone.
- **[`HudBarPlacement`](HudBarPlacement.java) is the RESOLVED answer** every paint reads, per player: the player's own pick (`HudPreferences.placementPick`) when it exists, is enabled and fits the panel, swapping the WHOLE group (corner, offsets, spread) because an owner's inline nudge belongs to the owner's corner; else the spot the panel names with the panel's inline leaves folded over it; else the document's fallback (`HudBarLayout.defaultPosition`, 1 column, 1 row per column). A panel naming a spot nothing authored warns ONCE and sits at the fallback. `columns(documentColumns)` clamps to the document; `bottomUp()` / `rightToLeft()` read the corner. Every layer is a nullable leaf, never a mode.
- **Two parts to a row, orthogonal, never a Kind/Type enum.** A row DRAWS A FILL when it was moved with a reading ([`HudBarReading`](HudBarReading.java): `current` out of `maximum`, `fraction()` held to 0..1, a non-positive maximum reading full, `FULL` the bar drawn complete), and it CARRIES AN ITEM when it was moved as one (`HudBars.itemMoved`; its default row id is `item:<ItemId>`, `HudBars.itemRowId`, the ONE id shape this package owns). A fill row is two lines (name + gain over the bar); an item row is the first line alone (`#Bar` hidden). Fill rows sort above item rows within a panel.
- **A row may be HELD rather than fade on a clock** (maintainer, 2026-09-09). `HudBarLook.LINGER_HELD` is a linger meaning the row stays until something sends it away, and `HudBarDisplay.held()` carries it; `HudBars.fadeAll(playerRef, withinMs)` is what ends a set of them together. `HudBarHud.moved` gives a held row `Long.MAX_VALUE` outright rather than `now + linger`, so the arithmetic cannot overflow into a time already past and drop the row on its first sweep, and neither `moved` nor `rearmSweep` arms a sweep for one.
- **A row's number may be its own TOTAL rather than a delta** (same ruling): `HudBars.totalled` / `itemTotalled` state it outright, for a mod that already keeps a running total for that stretch of activity. `HudBars.moved` / `itemMoved` keep adding deltas, for a mod that only knows what just happened.
- **A row may word its own number**: `HudBarDisplay.counting(key)` names the localization key the figure binds on, instead of the panel's plain `+{0, number}`, for a figure that is not a gain and reads wrong with a plus sign. The key takes the number as its one parameter so each client still writes its own digits.
- **[`HudBarDisplay`](HudBarDisplay.java) is what a consumer says about a row** beside every move: `label` (a client-resolved `Message`), `icon` (the shared `IconSpec`), `color`, `order`, `lingerMs`, plus `leadCaption` / `trailCaption` and `countKey`, every part nullable; `over(under)` folds two part by part, and `between(lead, trail)` / `colored(c)` / `counting(key)` / `held()` restate one part per move; `forItem(itemId)` is the display an item derives for itself. **The two captions are the words at a bar's ends**, DELIBERATELY not authorable on `HudBarAsset`: a caption is per-move data. An end with nothing to say is painted BLANK, never hidden, because hiding it would collapse its width out of the row. **[`HudBarLook`](HudBarLook.java) is the settled look**: `resolve(id, override, display)` folds the authored override OVER the display OVER the defaults (`DEFAULT_COLOR` `#7fb2e0`, `DEFAULT_ORDER` 1000, `DEFAULT_LINGER_MS` 5000); a row with no name from either layer shows its own id.
- **[`HudBarAsset`](HudBarAsset.java) is an OPTIONAL override, never a requirement** (Pattern A, PascalCase, every leaf nullable and inheriting under `Parent`), one file per override at `Server/ZiggfreedCommon/HudBars/<id>.json`: `Source`, `LabelKey`, `Icon`, `Color`, `Order`, `LingerMs`, `Enabled`. The library ships none, and no consumer needs to. Fold: [`HudBarConfig`](HudBarConfig.java) (`AbstractKeyedAssetConfig`, plus `bySource(rowId)`); owner layer `mods/ziggfreedcommon/hud-bars.json` through [`HudBarOwnerLayers`](HudBarOwnerLayers.java) + `OwnerLayerReader` (the same class reads the panels and placements owner files).
- **[`HudBars`](HudBars.java) is the way in**: `install(plugin)` (attach BOTH panels at `PlayerReadyEvent` LATE, detach at disconnect, live panels in `LIVE` by uuid then by panel key, and a `HudPreferences.watch` so a player's own pick or hide repaints theirs), `panels()` / `panel(id)`, **`moved` / `movedOnGrid` for a value**, **`itemMoved(playerRef, itemId, quantity)` for an item** and the caller-named `itemMoved(playerRef, rowId, itemId, quantity, display)`, `totalled` / `itemTotalled`, `fadeAll`. `repaintAllOnline()` covers both panels for the three asset load events and every owner-file write; a repaint re-anchors as it draws, so there is no separate position push.
- **[`HudBarHud`](HudBarHud.java) draws BOTH**, reading a [`HudBarLayout`](HudBarLayout.java) for everything that differs (panel id, hud key, document, root, declared columns and slots, the widths, the document's fallback corner); the two concrete classes are that layout and nothing else. Per-player state is one `LiveBar` per row id. Paints fold per tick through `RepaintCoalescer` and are held to one per the panel's authored `RepaintMs`, a **leading edge with a trailing flush**. ONE sweep is armed at the earliest expiry. `collectLive` drops expired and switched-off rows; `slotCap` (pure, tested) holds the count to `MaxVisible` and to what the spot's columns can hold; `choose(rows, cap, declaredSlots)` takes the most recently moved rows and draws them in `STACK_ORDER`; `columnsFor` / `rowsPerColumnFor` / `usedColumnsFor` / `ordinalInColumn` (pure, tested) split them across columns, a spot deeper than the document read at the document's depth; `paint` addresses every slot of every column, fills COLUMN BY COLUMN, hides an unused column outright, pushes the root anchor at `panelWidthFor(columns)`, and mirrors for the pinned edge: a RIGHT-pinned panel's first column is the rightmost, a BOTTOM-pinned column's first row is its lowest, so what is already on screen stays put when the next thing opens beside or above it. A panel the player hid paints only its own `Visible` false and keeps its rows.
- **The bar is a retinted `Group`, NOT a native `ProgressBar`, and this is load-bearing.** The native linear element carries no colour knob at all and every vanilla HUD bar ships one fill image per colour; a per-category texture set is the "one file per member of an OPEN roster" trap. So the fill stays an `Anchor` width push with a `.Background.Color` retint, dressed by COLOUR-AGNOSTIC overlays in the document (a dark well, a gloss, a shade, a `#Pulse` band for `PULSE_MS` after a move). Evidence: [[hud-progressbar-no-colour-knob]].
- **Geometry lives once in each `.ui`** and every slot references it; the widths the Java mirrors are named in each document's header comment. Slots are positional (`#ZigBarCol<c>` holding `#ZigBarC<c>R<r>`, letters between the indices because a UI element id is `[A-Za-z][A-Za-z0-9]*` and an underscore bricks the client) and their counts must match the layout. Both documents draw the native `ObjectivePanelContainer.png` patch, copied in beside them because a Custom UI document resolves texture paths only under `Common/UI/Custom/`.
- **Captions are SHORT, and the slot is 30px.** What goes in one is a number or a word of three or four letters (the MMO puts the level in and `MAX` at the cap, in every locale). A caption that does not fit is ellipsised by the client and reads as nonsense.
- **Consumers today**: the MMO's `skill/SkillHudBar` derives a skill's row from its skill registry and `SkillService.notifyXpGain` hands all of it over in one call, choosing the panel by whether the player is working a station and holding the row while they are; rpg-stations calls `itemMoved` for every produced or retrieved stack, the caller-named form for a lucky find, and `moved` for the session's own row.
- **Tests**: `HudBarAssetCodecTest`, `HudBarPanelAssetTest` (the leaves read back, a child inherits, the `MaxVisible` clamp, the fold always answers), `HudBarPlacementTest` (the placement file, `fits`, the picker listing, and every layer of the resolution), `HudBarSlotsTest` (`choose`, `slotCap`, `columnsFor`, `rowsPerColumnFor`, `usedColumnsFor`, `ordinalInColumn`, `HudBarReading.fraction`), `HudBarLookTest`. The drawing itself is packets and is validated in game (the `.ui` is not compiled).
- **Conventions**: `@Nonnull`/`@Nullable`; `util/SafeLog`; no product vocabulary anywhere in this package (no skill, no XP, no level: a row has a label, a reading, two captions and maybe an item, nothing more - an item is an engine concept); no em-dashes.
