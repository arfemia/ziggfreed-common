# ui/hud/bar/ - the shared progress-bar HUD

Router for `com.ziggfreed.common.ui.hud.bar`. Two semi-transparent panels any mod drives with one call per movement; the library creates a row on demand, dresses it from what the reporting mod says, and knows nothing about what a value measures. Nothing is authored for a row to appear. The parent [`ui/hud/`](../CLAUDE.md) router holds the `KeyedCustomHud` base this builds on.

- **THE RULING (maintainer, 2026-09-09): there is NO value-source seam here and none is to be rebuilt.** The asset store is the extension point (the root `CLAUDE.md`'s "The ASSET STORE is the extension point" rule); a `Source: <namespace>:<local>` string paired with a Java `register(namespace, provider)` call re-invents what the `HudBars` folder already does, so the seam was deleted outright rather than re-keyed. Whoever reports a movement hands the reading over WITH it (`HudBars.moved` takes a `HudBarReading`), the row keeps it, the paint draws from what the row holds, and nothing is asked of anyone at paint time. A bar only exists because something moved, so there is nothing to read back for. A row id is OPAQUE: no namespace convention, nothing split on a colon, matched whole (case-insensitively) against an override's `Source`; a mod names its row by the id of the thing measured.
- **TWO PANELS, and which one a row lands on is the CALLER's choice** (maintainer, 2026-09-09), made by which call it makes, never by anything this package reads out of the row: only the mod reporting a movement knows what the player is in the middle of. [`HudBarStackHud`](HudBarStackHud.java) is the tall ledger in the left column (`HudBars.moved` / `itemMoved`), [`HudBarGridHud`](HudBarGridHud.java) the wide block in the top-right for values moving while a player is simply out in the world (`HudBars.movedOnGrid`). Both are attached to every player at ready.
- **Two parts to a row, orthogonal, never a Kind/Type enum.** A row DRAWS A FILL when it was moved with a reading ([`HudBarReading`](HudBarReading.java): `current` out of `maximum`, `fraction()` held to 0..1, a non-positive maximum reading full, `FULL` the bar drawn complete), and it CARRIES AN ITEM when it was moved as one (`HudBars.itemMoved`; its default row id is `item:<ItemId>`, `HudBars.itemRowId`, the ONE id shape this package owns). A fill row is two lines (name + gain over the bar); an item row is the first line alone (`#Bar` hidden). Fill rows sort above item rows within a panel.
- **A row may be HELD rather than fade on a clock** (maintainer, 2026-09-09). `HudBarLook.LINGER_HELD` is a linger meaning the row stays until something sends it away, and `HudBarDisplay.held()` carries it; `HudBars.fadeAll(playerRef, withinMs)` is what ends a set of them together. For rows belonging to a stretch of ACTIVITY with a real beginning and end (a run at a workstation, a round, a journey) rather than to a single movement: a row quietly expiring part-way through takes a total the player is still building up off the panel with it. `HudBarHud.moved` gives a held row `Long.MAX_VALUE` outright rather than `now + linger`, so the arithmetic cannot overflow into a time already past and drop the row on its first sweep, and neither `moved` nor `rearmSweep` arms a sweep for one.
- **A row's number may be its own TOTAL rather than a delta** (same ruling): `HudBars.totalled` / `itemTotalled` state it outright, for a mod that already keeps a running total for that stretch of activity. The bar and whatever else that mod shows the same figure on then read the same source and cannot drift, and a row that went away and came back still reads right. `HudBars.moved` / `itemMoved` keep adding deltas, for a mod that only knows what just happened.
- **A row may word its own number**: `HudBarDisplay.counting(key)` names the localization key the figure binds on, instead of the panel's plain `+{0, number}`, for a figure that is not a gain and reads wrong with a plus sign (rpg-stations' session row counts cycles). The key takes the number as its one parameter so each client still writes its own digits; what it SAYS around them is the reporting mod's business, and the panel neither reads it nor learns what is being counted.
- **[`HudBarDisplay`](HudBarDisplay.java) is what a consumer says about a row** beside every move: `label` (a client-resolved `Message`), `icon` (the shared `IconSpec`), `color`, `order`, `lingerMs`, plus `leadCaption` / `trailCaption` and `countKey`, every part nullable; `over(under)` folds two part by part, and `between(lead, trail)` / `colored(c)` / `counting(key)` / `held()` restate one part per move; `forItem(itemId)` is the display an item derives for itself (its name through `i18n/NativeNames.itemNameMsg`, its own generated icon). **The two captions are the words at a bar's ends** - what the reading counts from and toward, in whatever terms the reporting mod measures in. They are DELIBERATELY not authorable on `HudBarAsset`: a caption is per-move data that changes as the value moves, so a file has nothing useful to say about it, and `HudBarLook` therefore takes them from the display alone. An end with nothing to say is painted BLANK, never hidden, because hiding it would collapse its width out of the row and shift the track the fill's pixel width is measured against. **[`HudBarLook`](HudBarLook.java) is the settled look**: `resolve(id, override, display)` folds the authored override (if any) OVER the display OVER the defaults (`DEFAULT_COLOR` `#7fb2e0`, `DEFAULT_ORDER` 1000, `DEFAULT_LINGER_MS` 5000); a row with no name from either layer shows its own id.
- **[`HudBarAsset`](HudBarAsset.java) is an OPTIONAL override, never a requirement** (Pattern A, PascalCase, every leaf nullable and inheriting under `Parent`), one file per override at `Server/ZiggfreedCommon/HudBars/<id>.json`: `Source` (the row it retunes, exactly as the owning mod moves it), `LabelKey`, `Icon`, `Color`, `Order`, `LingerMs`, `Enabled`. Every getter answers null for an unauthored leaf; `display()` folds the file into a `HudBarDisplay`; `Enabled: false` keeps the row off its panel and makes the reporting call answer false. **The library ships none, and no consumer needs to.** Fold: [`HudBarConfig`](HudBarConfig.java) (`AbstractKeyedAssetConfig`, plus `bySource(rowId)`); owner layer `mods/ziggfreedcommon/hud-bars.json` through [`HudBarOwnerLayers`](HudBarOwnerLayers.java) + `OwnerLayerReader`.
- **[`HudBarPanelAsset`](HudBarPanelAsset.java) is a panel** at `Server/ZiggfreedCommon/HudBarPanels/<id>.json`: `Enabled`, a nested `Position` group (`Preset` from the closed `HudPosition` roster as an editor dropdown, `OffsetX`, `OffsetY`), `MaxVisible`, `Columns`, `RowsPerColumn` and `RepaintMs`. **It carries no slot ceiling of its own**: `maxVisible(documentSlots)`, `columns(documentColumns)` and `position(fallback)` all take theirs from the caller, because those belong to a DOCUMENT and the two panels declare different numbers. `Columns` + `RowsPerColumn` are orthogonal knobs, not a layout mode: `columns = clamp(ceil(rows / rowsPerColumn), 1, maxColumns)`, so the stack's authored `2 / 8` keeps one narrow column until nine rows are moving while the grid's `6 / 1` opens a column per row and so grows sideways rather than down into the quest tracker below it. Defaults are `Columns` 1 (a panel nobody authored stacks, whatever its document declares), `RowsPerColumn` 1, `RepaintMs` 250. The library ships `Default.json` (TopLeft (16, 216)) and `Grid.json` (TopRight (24, 10), above the quest tracker); a consumer's same-id file wins by pack order and `mods/ziggfreedcommon/hud-bar-panels.json` wins over both. [`HudBarPanelConfig`](HudBarPanelConfig.java)`.current()` / `.grid()` / `.panel(id)` always answer.
- **[`HudBars`](HudBars.java) is the way in**: `install(plugin)` (attach BOTH panels at `PlayerReadyEvent` LATE, detach at disconnect, live panels in `LIVE` by uuid then by panel key), **`moved` / `movedOnGrid` for a value**, **`itemMoved(playerRef, itemId, quantity)` for an item** and **`itemMoved(playerRef, rowId, itemId, quantity, display)` for an item that landed in a way worth counting apart from its ordinary running total** (the caller names and dresses that row; the display folds over the item's own, so it only states what is different). Each creates the row on first sight, keeps what came with the move, records the gain, paints; false for no panel or a row an override switched off. `repaintAllOnline()` and `refreshPositionForAllOnline()` cover both panels for the two asset load events, which `FrameworkAssetRegistrar` wires so a reload lands live.
- **[`HudBarHud`](HudBarHud.java) draws BOTH**, reading a [`HudBarLayout`](HudBarLayout.java) for everything that differs (panel id, hud key, document, root, declared columns and slots, the widths, the default corner); the two concrete classes are that layout and nothing else. Per-player state is one `LiveBar` (the reading and item it was moved with, its last display, gain since it came up, last move, expiry) per row id. Paints fold per tick through `RepaintCoalescer` and are held to one per the panel's authored `RepaintMs` - a **leading edge with a trailing flush**, not a plain throttle: a move arriving when the window is already open redraws at once, one arriving inside it is drawn at the window's END rather than dropped, so a number on screen is never waiting on a LATER move to bring it up to date. ONE sweep is armed at the earliest expiry and re-arms itself while anything is live. `collectLive` drops expired and switched-off rows and resolves each row's look; `choose(rows, maxVisible, declaredSlots)` (pure, tested) takes the most recently moved rows of either kind and draws them in `STACK_ORDER`; `columnsFor` / `rowsPerColumnFor` (pure, tested) split them across columns; `paint` addresses every slot of every column, fills COLUMN BY COLUMN so a widened stack still reads top-to-bottom down its first column, hides an unused column outright, and pushes the root anchor at `panelWidthFor(columns)` so a one-column panel never draws its frame across an empty gutter.
- **The bar is a retinted `Group`, NOT a native `ProgressBar`, and this is load-bearing.** The native linear element carries no colour knob at all (its `CircularProgressBar` sibling does, so the omission is deliberate) and every vanilla HUD bar ships one fill image per colour - neither can serve a row whose colour is only known when it moves, and a per-category texture set is the "one file per member of an OPEN roster" trap that leaves a pack's new skill with no bar. So the fill stays an `Anchor` width push with a `.Background.Color` retint, and earns its finish from COLOUR-AGNOSTIC dressing in the document instead: a dark well behind it, a gloss across its top, a shade along its bottom, and a `#Pulse` band riding its leading edge for `PULSE_MS` after a move. Evidence: [[hud-progressbar-no-colour-knob]].
- **Geometry lives once in each `.ui`** (`@RowAnchor`, `@LineAnchor`, `@IconAnchor`, `@GainAnchor`, `@BarAnchor`, `@CapAnchor`, `@TrackAnchor`, `@FillAnchor`, `@GlossAnchor`, `@BaseAnchor`, `@PulseAnchor`) and every slot references it; the widths the Java mirrors are named in each document's header comment. Slots are positional (`#ZigBarCol<c>` holding `#ZigBar<c>_<r>`) and their counts must match the layout. Both documents draw the native `ObjectivePanelContainer.png` patch, copied in beside them because a Custom UI document resolves texture paths only under `Common/UI/Custom/`.
- **Captions are SHORT, and the slot is 30px.** They flank the bar and every pixel they take is a pixel off it, so what goes in one is a number or a word of three or four letters (the MMO puts the level in and `MAX` at the cap, in every locale: `MAX`, `MAKS`, `MÁX`, `МАКС`). A caption that does not fit is ellipsised by the client and reads as nonsense, which is exactly what a "Lv 5" prefix did before it was dropped.
- **Consumers today**: the MMO's `skill/SkillHudBar` derives a skill's row from its skill registry (row id the skill's own id; display its name, icon, category colour and order; reading its XP into the level; captions the level it is in and the one it is climbing to) and `SkillService.notifyXpGain` hands all of it over in one call, choosing the panel by whether the player is working a station and holding the row while they are; rpg-stations calls `itemMoved` for every produced or retrieved stack, the caller-named form for a lucky find, and `moved` for the session's own row.
- **Tests**: `HudBarAssetCodecTest`, `HudBarPanelAssetTest` (the position fallback, leaf-by-leaf `Position`, unknown preset falls back whole, the `MaxVisible` clamp against a document's count, the fold always answers), `HudBarSlotsTest` (`choose`, `columnsFor`, `rowsPerColumnFor`, `HudBarReading.fraction`), `HudBarLookTest`. The drawing itself is packets and is validated in game (the `.ui` is not compiled).
- **Conventions**: `@Nonnull`/`@Nullable`; `util/SafeLog`; no product vocabulary anywhere in this package (no skill, no XP, no level: a row has a label, a reading, two captions and maybe an item, nothing more - an item is an engine concept); no em-dashes.
