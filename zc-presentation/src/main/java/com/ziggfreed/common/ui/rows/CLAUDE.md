# ui/rows/ - fixed-slot icon + rich-text LEDGER row primitive, and the record of what a list build drew

Router for `com.ziggfreed.common.ui.rows`. Two unrelated row-shaped primitives, both mod-agnostic: a ledger-row model + painter (`SummaryRow` / `SummaryRowRenderer`), and the built-row record a two-panel list page keeps so its partial updates address real rows (`BuiltRows`). The ledger pair was lifted out of the MMO's since-removed session-summary HUD; that surface now lives in RpgStations, and each consumer keeps only its own policy - icon / item-name resolution, colour and bold conventions, tallies -> rows.

- **[`BuiltRows`](BuiltRows.java)**: what the last full `build` of a list actually drew - each row's INDEX and the GROUP it was drawn under, with `addHeader()` for a section heading that occupies an index but answers to no id. It exists because a `sendUpdate` runs against the DOM that build produced, so `#List[i]` means row `i` OF THAT BUILD: `indexOf(id)` answers from the record (`-1` = the caller reopens instead of addressing a row that may now be a heading, whose inner elements the row template lacks - a command written against a selector that resolves to nothing DISCONNECTS the player), and `moved(id, liveGroup)` is the one rule that decides whether a partial can still tell the truth (a row that has left the group it was drawn under would keep the wrong heading and leave that group's counts lying, so the page rebuilds). Ids match case-insensitively and ignore surrounding space; a group is any opaque string the caller picks (a section enum's `name()`, a bucket word). Per page instance, world-thread only, not thread-safe. **Consumers**: `objectives/questlist/ZigNpcQuestPage` (group = its `NpcQuestSections.Section`, the page that actually reopens on a move), `objectives/book/ObjectiveBookPage` + `BookQuestsTab` (group = `BookQuestsTab.listOf`, the pinned carried block vs the browse list under it), `commerce/page/ZigBoardPage` and `ZigShopPage` (both reopen on every mutation, so they read the record for `indexOf` alone). A new two-panel list page adopts it rather than keeping its own `List<String>` of row ids.

- **[`SummaryRow`](SummaryRow.java)**: the immutable value - an icon item id + an already-composed, already-styled client-resolved `Message` + an OPTIONAL second-line `Message` (`subText`, nullable) + a descriptive semantic `Kind` (`PROGRESS`/`CONSUMED`/`PRODUCED`/`LUCKY`/`ENHANCE`, generic reward-ledger roles; `ENHANCE` = an existing item modified in place, e.g. a stamp/durability outcome). All colour/bold is baked into the `Message` by the caller (`Message.color`/`Message.bold` composed via the consumer's own `Msg.cat`); this type only carries the result. `Kind` is metadata (ordering / per-kind icon fallback), NOT read by the renderer.
- **[`SummaryRowRenderer`](SummaryRowRenderer.java)**: paints a `List<SummaryRow>` into a FIXED set of pre-declared `.ui` slots the CONSUMER declares - `render(cmd, rowSelectorPrefix, maxSlots, rows)` addresses row `i` as `rowSelectorPrefix + i` (each expected to hold an `ItemGrid #Icon` + a `Label #Name`), hides unused/overflow slots, and RETURNS the overflow count for a "+N more" row (or `renderWithOverflow(...)` sets that label too). Never `cmd.append` - the fixed-slot HUD/page convention. Works over any `UICommandBuilder` sink (HUD partial update, page `sendUpdate`, full `build`).
- **The optional SECOND line is opt-in per CALLER, not per row model.** `subText` only ever reaches the client through the `render(..., subLabelId)` overload, which paints it into a second Label the caller names (RpgStations' summary panel passes `"#Sub"`) and HIDES that Label on a row without one, so a reused slot can never keep a stale second line. A caller that omits the id never addresses such a Label at all - deliberate, because a command written against a selector the consumer's `.ui` does not declare CRASHES the client, so single-line consumers must stay untouched. Why two Labels rather than a `\n` inside one `Message`: the native rich-text markup set (`<color is>`/`<b>`/`<i>`/`\n`) has NO font-size tag, so a second line renders smaller only as its own Label with its own style. The row slot's `.ui` shape that makes it collapse cleanly (heightless row + `FlexWeight: 1` vertical text column) is the consumer's, documented in RpgStations' `ui/CLAUDE.md`.
- **Sibling to [`ui/toast/ToastLine`](../toast/ToastLine.java), NOT unified (deliberate design call, 1.5.0 lift).** Both are the same shape at heart (optional icon id + a client-resolved `Message`), but a `ToastLine` is a TRANSIENT overlay welded to the toast transport (its `ToastController`/`ToastStore` lifecycle, a `quantity` badge, a `ToastKind` that also drives per-kind SFX) while a `SummaryRow` is a PERSISTENT fixed-slot ledger row with a generic parameterized-selector renderer. Unifying would force toast transport semantics onto a plain ledger (or drag the fixed-slot painter into the toast model); keeping siblings lets a consumer pick the surface that fits without a third forked model. The results strip is a third, distinct shape again: it paints the shared zc-loot [`loot/reward/RewardChip`](../../../../../../../../../zc-loot/src/main/java/com/ziggfreed/common/loot/reward/RewardChip.java) (icon id + label only), composed per instance reward by `instance/result/RewardChipRenderer` and rendered as a strip rather than a fixed-slot ledger; the claimed/pending state is page state on `ResultsPage`, never on the chip.
- **Consumers**: RpgStations' end-of-session summary panel (`ui/StationSummaryHud`, its rows built by `station/StationService#showSessionSummary` - the consumed / produced / lucky / enhance item ledger), plus the MMO's `integration/stations/StationSummaryEnricher`, which contributes the per-skill XP rows through RpgStations' `api/SummaryEnricher` seam. A minigame's rewards / results LEDGER can adopt it the same way (declare `#Prefix0..N` slots with `#Icon`/`#Name`, build `SummaryRow`s, call `render`); the results REWARD-STRIP (`ResultsPage` + `RewardChip`) is a separate surface today - adopting rows there is a rewards-UI design pass, not a mechanical swap.
- **Conventions**: engine `Message` only (no consumer `Msg`); rich text renders on a Label's `TextSpans` (never `.Text`); `@Nonnull`/`@Nullable`; no em-dashes.
