- **New: a quest-giver NPC role template.** zc-dialogue ships `Template_Zig_QuestGiver` (`Server/NPC/Roles/Passive/`, Type `Abstract`): a stationary, invulnerable giver whose press F runs `ZigPlacementInteract` (`Open: Quests` for a giver nothing placed). A consumer builds a giver as a role `Variant` whose `Modify` names only its five parameters (`Appearance`, `NameTranslationKey`, `Weapons`, `OffHand`, `DefaultOffHandSlot`); the `Armor` and the press-F `Hint` are literal, so a giver needing either of its own needs a full role body. Test: `ZigRoleTemplateTest`.
- **New: a native recipe index.** `recipe/` (zc-entity) indexes the engine's whole `CraftingRecipe` store for the questions a consumer deriving from engine recipes asks. `RecipeIndex.live().catalog()` hands back an immutable `RecipeCatalog` snapshot: `atBench(benchId)` (every recipe made at a bench, `Salvagebench` included), `consuming(itemId)` (every recipe with an input line that would take the item, by exact id, by a tag it carries or by a resource family it counts toward, after the engine's own output exclusions; an item's `Salvage_<ItemId>` is one of them), `producing(itemId)`, `craftingRecipeOf(itemId)` (the recipe authored inside the item, `<ItemId>_Recipe_Generated_0`), `recipe(id)` and `all()`, every list ordered by recipe id. STANDALONE recipe files and item-INLINE recipes are one shape (`NativeRecipe`, with `ownerItemId` set on an inline one), because the engine loads both into the same store; each carries its FULL input and output quantities (`RecipeMaterial`, keeping the first authored route in the engine's order: item, then tag, then resource family), its benches (`RecipeBench`: id, kind, categories, required tier), its primary output and its native craft time. The index is built from the asset map on first read, dropped on every `CraftingRecipe` and `Item` load and removal (registered in `FrameworkAssetRegistrar`), and rebuilt on the next read; `RecipeIndex.generation()` moves on every invalidation, so a consumer's own derived cache keys on one number. The catalog is pure (built from plain values), so a consumer's tests build one over hand-written recipes; `new RecipeIndex(Supplier<RecipeCatalog>)` is the same lifecycle over any source. A recipe authoring neither `Output` nor `PrimaryOutput` reads with no outputs, since the engine reports none for it.
- **New: an ITEM in the factor context, and five factors that read it.** `FactorContext` (zc-core) gains an `item()` leaf (`Builder.item(ItemStack)`, `hasItem()`), carried through `withParam` like every other leaf and absent by default: the item a moment is ABOUT (a piece placed on a work surface, a stack a recipe consumed), independent of whatever the subject holds. The portable vocabulary (`factor/HytaleFactors`, zc-entity) gains `hytale:item_quality` (the quality index the STACK carries: the engine copies its item's index into every stack it makes and saves it with the stack, so this is the quality the stack was made with or re-qualified to), `hytale:item_level`, `hytale:item_durability_percent` (a stack that tracks no durability reads 100) and `hytale:item_stat` (Param a stat channel id: the ADDITIVE amounts the item's own armor, weapon and utility `StatModifiers` author toward it; a multiplicative modifier adds nothing, and an unregistered channel is named in the log once, as for `hytale:stat`), so every registry built through `HytaleFactors.registerInto` carries thirteen `hytale:` ids. `ziggfreedcommon:item_stamp_points` (`loot/stamp/StampFactors`, zc-loot; Param optional, a stat id, matched without regard to case) reads the stamped points through `StamperRegistry.inspect`, whichever stamper is active, and is contributed process-wide at setup through `FactorContributions`. All five answer null where the context carries no item, so a gate on an item a moment does not have stays shut. Each ships a naming overlay (`Hytale_Item_*.json`, `Stamp_Item_Points.json`) and a `factor.<id>` name in `ziggfreedcommon.progress.lang` (en-US).
- **One item reader under both item families.** `entity/ItemReadings` (zc-entity) is the reader every item-shaped factor values a stack through: `quality`, `itemLevel`, `durabilityPercent` and `statTotal`, each over a stack or an item asset, each answering null rather than zero when it cannot tell. The held-tool readings (`hytale:tool_quality`, `tool_item_level`, `tool_durability_percent`) read through it too and are unchanged from 2.1.x: `tool_quality` reads the held ITEM's current quality (`ItemReadings.quality(Item)`), not the stack's copied index, so it never drifts when an item's quality is reloaded or the quality index order moves between boots; that per-stack reading is `hytale:item_quality`'s alone. `HeldItemUtil.qualityValueOf` / `itemLevelOf` / `durabilityPercentOf` keep their signatures and answer through the same reader.
- **New: a quality read by its id.** `ItemReadings.qualityId(ItemStack)` and `qualityId(Item)` (zc-entity) name the native `ItemQuality` a quality index resolves to, by id rather than by ordering value, for a matcher keyed on a quality tier: over a stack, the index the stack carries (its item's only when the stack carries none); over an item, the quality its asset names now, for a caller holding the item alone. Each answers null for no usable stack or item, or an index that resolves to no loaded quality.
- **New: which metadata a stack carries, and which of it may go with the stack.** `ItemReadings.metadataKeys(stack)` (zc-entity) reads the top-level metadata keys a stack carries without the engine's `ItemStack#getMetadata`, which is `@Deprecated` (not marked for removal, though the engine's own comment says it goes once stack metadata moves to components): the stack's own `ItemStack.CODEC` encodes it and the `Metadata` leaf's keys are copied out, the stack untouched. A bare stack reads an empty set; no stack, or a stack the read cannot encode, reads null (it never throws), which a consumer about to destroy the stack treats as a refusal. `inventory/DisposableItemMetadata` (zc-core) is the ONE server-wide list of metadata keys some mod has declared safe to destroy together with their item: `declare(String...)` / `declare(Collection)` at setup, `isDeclared(key)`, `declared()`, and `undeclared(keys)`, the keys nobody declared in one pass; keys match exactly, case included, and a declaration is never retracted. `ItemReadings.undeclaredMetadataKeys(stack)` asks both in one call. A stat stamper declares what it writes through the new `Stamper.metadataKeys()` (default empty), which `StamperRegistry.register` declares, so a third-party stamper needs no second call; the library's own `StackStatsStamper` answers `ZigStackStats` (its `StackStats` record) and the engine's `ItemDisplay` (the tooltip `StampTooltip` writes beside it), declared when the wiring root registers it. A declared key is disposable whoever wrote it: the list names keys, not writers, so an `ItemDisplay` override goes with its item whether the library's tooltip or another mod's custom name wrote it, display text meaning nothing once the item is consumed. What to do about an undeclared key is the consumer's policy, never the list's. Tests: `DisposableItemMetadataTest` (zc-core), `StamperMetadataKeysTest` (zc-loot; each registration case declares a key no other case can have declared and checks it was undeclared first, since the list is process-wide and never cleared, and the library stamper's two keys are read through `metadataKeys()` alone) and the `engine-items` tagged `ItemMetadataKeysTest` (zc-entity: a bare stack, a stack carrying metadata, a stamped stack, an undeclared key, an unreadable stack).
- **Tests build real engine items, in a test task of their own.** The engine's item classes cannot load their codecs under any log manager but the engine's own `HytaleLogManager`, so no log-manager-less test could construct an `ItemStack` or `Item`. `gradle/zc-module.gradle` adds a second test task to every module, `engineItemTest`, which starts its JVM with `java.util.logging.manager` set to `HytaleLogManager` and runs ONLY the tests tagged `engine-items` (JUnit 5 `@Tag`). The default `test` task excludes that tag and runs every other test with no log manager, exactly as in 2.1.x and as a consumer mod's own test JVM does, so the library's logging guards (`SafeLog`, `GuardedLogger`) stay exercised; `SafeLogTest` now also asserts it runs with no engine log manager installed, so it cannot pass vacuously. `check`, and so `gradlew build`, runs both tasks. Tagged today: `ItemReadingsTest` (zc-entity), and the stack-building cases of `HytaleFactorsTest` (zc-entity), `FactorContextTest` (zc-core) and `StampFactorsTest` (zc-loot). One engine asset-store swap serves every module's `engine-items` tests: zc-core's test fixture `testing/EngineAssetStores` (`java-test-fixtures`; `emptyItems()`, `qualities(...)`, `statChannels(...)`), which never reaches the shipped jar; the per-test copies in zc-entity, zc-loot and zc-encounter are gone. Test: `EngineAssetStoresTest`.
- **New: gear sets, asset-driven set bonuses over the equip bridge.** `stats/gearset/` (zc-entity) plus the **GearSets** store, `Server/ZiggfreedCommon/GearSets/<Set_Id>.json` (`GearSetAsset`, Pattern A, every top-level leaf `appendInherited`; owner layer `mods/ziggfreedcommon/gear-sets.json` through the shared `OwnerLayerReader`): `Text` (the shared `ContentTextAsset` group, `TitleKey` naming the set), `Enabled` (default true), `Members` (item ids matched without regard to case, a duplicate counting once, an item free to belong to several sets) and `Bonuses`, the tiers in order. A tier's condition is a CONJUNCTION of independent minimums, never a bare count: `Pieces` (distinct members on anywhere, a held copy of a worn piece counting once), `Armor` (distinct members in armor slots), `Held` (the active-hand item is a member AND is not also worn in an armor slot, compared by id without regard to case, so a spare copy of a worn piece in hand never stands in for the set's weapon), `Utility` (the utility-slot item is a member), each nullable, a tier authoring none an error; `Held` and `Utility` are authored `1` to require them and left out otherwise, `0` being an error; every tier whose condition holds applies, so tiers stack by construction and two may share a count (the full-armor tier carries the look, the weapon tier beside it adds stats only). A tier carries its own `Text.TitleKey` (the one line the notice shows), an `Effect` (a native `EntityEffect` held while the tier is active; the id must be dedicated to the set, since the engine takes it off whenever no active tier wants it, whoever put it on) and `StatModifiers`, the native item block byte for byte, decoded through the library's own `StatModifierSpec` leaf (`Amount`, `CalculationType` and `Target`, the two words closed `EditorSchema.oneOfDocumented` dropdowns with their defaults, matched without regard to case, an unknown word failing the read, unauthored reading `Additive` / `Max` / 0; the engine's `StaticModifier.CODEC` matches `CalculationType` only in its exact spelling, requires it, and gives the Asset Editor no line per word, while `toModifier()` still builds the engine's own `StaticModifier`) inside an `InheritMapCodec` so a `$Comment` may sit in the map. Under `Parent`, `Bonuses` replaces wholesale and every other leaf merges. `GearSetConfig` folds the layers and owns the derived `GearSetIndex` (item id to enabled sets, asked one lookup per item the player has on, plus `allEffectIds`, every folded set's looks), dropped by its own merge methods.
- **The gear-set engine** (`GearSets`) hangs ONE `EquipStatBridge.AppliedListener` on the installed bridge (`EntityBootstrap.installGearSets`, right after `installEquipStatBridge`; the listener is a stored `static final`, so a re-run is a no-op under the bridge's identity dedup), never a fourth trigger system. `EquipStatBridge` gains one additive public read, `equippedSnapshot(store, ref)` -> `stats/EquippedSnapshot` (`heldItemId`, `offhandItemId`, index-aligned `armorItemIds`, lower-cased `distinctItemIds`), sharing the private container reads with the stat walkers, and its pure `planUtility` core with `UtilityPlan` / `UtilityPut` / `StatKey` is now PUBLIC, a permanent contract from 2.2.0 with javadoc to match, since a tier's block is one more prefixed source over the same diff-skip and stale-key sweep (`plan`, the per-slot core, stays package-private). On every fire the engine reads the snapshot, picks the active tiers per candidate set (`GearSetDecision`, pure), resolves each block to stat indices (`StatIndexCache`; an unregistered channel named once and skipped), diffs against the map (`GearSetPlan`, pure; keys `zigset:<setId>:<tierIndex>:<offset>` from `GearSetKeys`, the tier addressed by its POSITION), puts and removes through `putModifier` / `removeModifier` (never `setStatValue`), settles the look through the `GearSetEffects` seam by one rule (`effectChanges`, pure): every effect it answers for that no active tier wants comes off, and every effect an active tier wants that the entity does not have RIGHT NOW goes on (asked of the entity, never of the table), none while the player is dead; remembers the write in a transient `GearSetApplied` table keyed by player UUID and forgotten whenever the player's entity leaves its store, whatever the `RemoveReason` (a disconnect removes the entity with `UNLOAD` after the disconnect event has fired, and a world change with the same reason; the eviction runs on the world thread after any recompute queued before it, so no row outlives a session, and the next world's first recompute is a hydrate, which is right after a world change: the stat map and the effects came along in the component holder and no tier flipped, so strays are swept from the live map, the look is reconciled by asking the entity, and nothing is announced); saves the looks it answers for on the player (`GearSetLooksComponent`, below); and announces each tier that really flipped. Death and respawn: the engine clears every effect on both while the row keeps listing the look, so `GearSetLifecycleSystems.Respawned` (a `RespawnSystems.OnRespawnSystem`, the `DeathComponent` coming off) hands the player to `GearSets.onRespawned`, whose recompute, deferred to the world thread, puts the look back with no notice; `GearSetLifecycleSystems.Left` (a `RefSystem` on `PlayerRef`) is the eviction, the only one: no disconnect listener and no per-world eviction; both systems are registered by `installGearSets`. The first recompute in a store is a HYDRATE: with no row in the table the sweep reads every `zigset:` key actually present on the stat map (`EntityStatValue.getModifiers()`), so a modifier stranded by a previous boot goes whatever set wrote it, the effects it answers for (`hydrateAnswersFor`) are every effect id any folded set names, a DISABLED set's included, plus every id the player's saved `GearSetLooksComponent` record holds (an `Infinite` look is saved with the player, so a set switched off, or deleted outright, while its wearer was offline still has its look taken off at their login), and nothing is announced. `GearSetLooksComponent` (registry id `ZiggfreedCommon:GearSetLooks`, codec key `Effects`, a string array) is the look effect ids the engine answers for on the player, saved with the player entity beside the `EffectControllerComponent` it describes (ECS state, no player-data database domain): registered first in `installGearSets`, unconditionally and before the bridge check, attached by a `PlayerConnectEvent` hook on the holder before the entity joins a store (the `ZigFlairComponent` shape), and replaced in place at every recompute, never added by a recompute, which runs inside system ticks. What it records is `GearSets.answeredAfter` (pure): the looks the engine asked to be on (none while dead), plus every look whose remove that recompute returned false, so a look leaves the record only once a remove of it has gone through and is tried again at each later recompute (the row holds the same set) and each login; a look whose effect asset no longer exists is dropped instead, since the engine's `EffectControllerComponent` skips an effect whose asset is gone as it loads the player, so nothing is left to take off. A LATE `PlayerReadyEvent` runs the bridge's own `recomputeAll` (the hydrate authority); a content load, re-import or owner reload (`GearSets.onContentChanged`, from the registrar's merge) drops the index and runs every online player through the bridge again on their own world thread. Nothing in the engine can touch another writer's key: every prefix comes from a `TierRef` and every stray is filtered on `GearSetKeys.isOurs`, pinned by a test that records every key the plan asks about.

- **New: a particle system or a sound ON an entity, delivered to the players who see it.** `entity/EntityViewers` (zc-core) writes one packet to every player whose tracker currently shows an entity (the entity's own `EntityTrackerSystems.Visible.visibleTo`, the map the engine's beam and mount systems iterate), answering how many received it: zero for a null ref, an entity with no tracker record, one nobody is near, or one spawned THIS tick, which the tracker has shown to nobody yet, so a caller falls back (a positional play at the entity's place) rather than lose the cue; never a world-wide broadcast, since a packet keyed on an entity id means nothing to a client that has not been sent the entity. Over it, `cast/ModelParticleService.spawnOn(store, entity, List<AttachedParticle>)` sends `SpawnModelParticles` on the entity's `NetworkId` (`AttachedParticle` is the protocol `ModelParticle` leaf in library types: the system, a scale, an optional `Color` tint, the `EntityPart` and named model node it rides, entity-local offsets, the detached and clear-on-remove flags; `toProtocol()` maps it field for field), and `sound/Sound3D.playOn(id, entity, volumeModifier, pitchModifier, store, label, warn)` sends `PlaySoundEventEntity` (the engine's own `SoundUtil.playSoundEventEntity` is not used: it broadcasts to every player in the world). No playback cap exists on the attached-particle route, so an endless system stays world-positioned, and nothing can stop a sound once sent. `ModelParticleService` also gains the FULL-ARITY world-positioned `spawnAt(store, asset, pos, yaw, pitch, roll, scale, color, maxDurationSeconds)`, the one engine overload that carries both a colour and the playback cap, so a tinted burst keeps its leak guard, and `tint(hex)`, a `#rrggbb` reader into the protocol colour (null for anything else).
- **New: whether a particle system ends on its own, asked before it rides an entity.** `cast/ParticleLifetimes` (zc-cast) reads the loaded `ParticleSystem` asset's own `LifeSpan` (`lifeSpanOf(systemId)`, null for a blank or unknown id or no asset map loaded, never a throw), and `provablyEnds(Float)` (pure) holds that a system ends only when that span is positive, since zero or less is the engine's documented unlimited and an unreadable system is unproven; `systemProvablyEnds(systemId)` composes the two. It is the guard in front of `ModelParticleService.spawnOn`, whose route has no playback cap: a system that passes may ride an entity, and any other belongs at a position under a cap. A system whose spawners merely run dry cannot be proven from the server, so only the `LifeSpan` counts. Test: `ParticleLifetimesTest`.
- **New: an effect on a spawned puppet.** `entity/PlayerPuppetService.spawn` adds an empty `EffectControllerComponent` to the puppet's holder BEFORE the spawn, the way the engine's own role builder and player setup do, so a consumer puts a native `EntityEffect` (an aura, a ModelVFX) on the double by reference and the tracker networks it to its viewers. The puppet carries no `EntityStatMap`, so the engine's effect TIMER never runs on it and a timed effect would never end there: `effect/NativeEffectUtil.applyInfinite(Store | ComponentAccessor, ref, effectId)` (the engine's `addInfiniteEffect(ref, index, effect, accessor)` overload, the same fail-closed guards and the same once-per-id unresolved warning as `apply`) puts the effect on with no expiry, and the consumer takes it off with `remove` on its own clock. `NativeEffectUtilTest` gains the null-ref and blank-id cases.
- **New: a loot pass tells an expected payout from a find.** `loot/Roll` gains `Expected` (Boolean, default false): what the roll hands over is the moment's expected payout, a wage or a return, rather than a windfall.
