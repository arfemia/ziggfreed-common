- **New: the engine instance seam, `world/InstanceWorlds` and `world/CopyKey` (zc-instance).** zc-instance is the one launcher of the engine's instance worlds. `InstanceWorlds.spawn(template, worldName, forWorld, returnPoint, emptyCloseSeconds, extraConfig)` spawns a copy through `InstancesPlugin`'s five-argument `spawnInstance` under zc's own name, never an `InstanceKey`, and in the spawn's config step sets the removal conditions (native `WorldEmptyCondition` AND `IdleTimeoutCondition`, the latter `emptyCloseSeconds`), `DeleteOnUniverseStart` and `DeleteOnRemove`, then runs the caller's `extraConfig`. It refuses a name that is live or still spawning. `teleportIn(ref, accessor, worldFuture, overrideReturn, arrival)` is the five-argument `teleportPlayerToLoadingInstance`, `exit(ref, accessor)` the engine's `exitInstance`, `safeRemove(world)` its safe remove, and `removeOffThread(world)` removes a copy on a daemon remover thread, only while its name still holds that world object. `InstanceBootstrap.shutdown()` stops the remover (`InstanceWorlds.shutdown()`); it starts on first use. `CopyKey(world, area)` keys an area of a copy (`SOLE_AREA` 0, `sole(world)`). A copy left by a hard stop is deleted at the next start; a world zc did not spawn is never touched. No test (smoke).
- **New: Claims, `loot/claim/` (zc-loot).** Rewards are collected, never handed over unasked, so whatever pays a player a Claim writes it here and the player presses Claim when their bags have room. `Claim(id, source, titleKey, titleArgs, difficulty, rewards, createdAt)` is one payout a player has earned and not taken (`withRewards`, `is`; the id is matched without regard to case). `ClaimStore` (`shared()`, `init(dataDir)`) keeps every player's Claims in one versioned file, `claims.json` in the library's data folder, written atomically through the engine's `FileUtil` on every change; a file declaring a newer version, or one the build cannot read at all (malformed or cut short), is left unread and unwritten, as `claims-diminish.json` is: `init` resets the refusal before each load, a missing or empty file writes normally, and while a file is refused that session's Claims answer from memory and are lost at restart unless the file is repaired first. `award(player, claim, spec, diminishKey, nowMs)` is the one way a Claim is paid: it answers false and counts nothing for a Claim with no rewards or one whose id the player still holds, so a roll that lands nothing never spends a player's first clear of the window; else it counts one clear of `diminishKey` under `spec`, scales each reward's quantity by that clear's multiplier (a fraction paid whole through `StochasticCount`, a reward scaled to nothing dropped), writes the Claim unless nothing is left, and fires the native `ClaimAddedEvent(player, claim)`. `list`, `has`, `count`, `take`, `takeAll` and `putBack` read and hand over. A Claim never expires. `PendingRewardStore` stays the retry queue. Test: `ClaimStoreTest` (the file round trip, tagged `engine-items`).
- **New: diminishing returns, `loot/diminish/` (zc-loot).** `DiminishSpec` is authored as `"Diminish": { "Steps": [1, 0.5, 0], "Window": "Daily" }`: `Steps` is the multiplier for each clear in a window, the last repeating, and `Window` is `Daily` or `Weekly` (midnight UTC, weeks from Monday, through zc-core's `PeriodMath`). Read it with `window()`, `steps()` and `multiplier(priorClears)`, or build one with `of(window, steps...)`; `Window.periodIndex` and `byWord` are the window's own reads. `DiminishLedger` (`shared()`, `init(dataDir)`, its file `claims-diminish.json`) counts clears per player and key: `count(player, key, spec, nowMs)` answers the multiplier the clear pays at, starting over in a new window, pruned to current windows. A newer-version or unreadable `claims-diminish.json` is left unread and unwritten, its counts kept in memory for the session, as `claims.json` is. A diminished Claim pays what it shows: `RewardHandler.scalableRetryCommand(spec, subject, sourceId)` (default null) answers a kind's replay line with its amount written as `InstanceReward.AMOUNT_PLACEHOLDER` (`{amount}`), and `DeferredRewards` keeps that line wherever, filled with the reward's own amount (`DeferredRewards.quantityParam` names the parameter that amount is read from), it reads exactly as `retryCommand`, which `Item`, `Stamped_Item`, `Command`, `Currency` (through the new `CommerceCommandLine.give(player, currencyId, String amount)`), a `Reputation` gain and an authored kind file whose `Command` writes that amount parameter (but no `<Param>Max` or `<Param>Min` range end above zero) all do, so the payout fills the scaled quantity, while a command line with no `{amount}` to fill (`InstanceReward.scalesWithQuantity()` false) is kept whole with the step's chance or dropped, so its chip and its payout always agree. Tests: `DiminishSpecCodecTest`, `ClaimStoreTest`.
- **New: the Claims tab, `instance/claims/` (zc-instance, zc-presentation).** `MenuSlot.CLAIMS` sits after `REPUTATION`. `ClaimsDestinations` registers the destination `Claims` (owner `ziggfreedcommon`; `"Open": "Claims"`; `CLAIMS`, `ICON` `Furniture_Dungeon_Chest_Epic`), whose menu `entry()` shows only while the viewer holds a Claim (`ClaimStore.has`), so the tab appears with the toast that names it, and `open(store, ref, player, selectedId)` opens the page. `ClaimsPage` (a `ToastablePage<ClaimsEventData>` over `Pages/ZigClaimsPage.ui`) lists Claims newest first with reward chips and a detail, built by `ClaimsView` (`ACTION_CLAIM`, `ACTION_CLAIM_ALL`, `newestFirst`, `pick`, `ledger`, `detail`, `empty`, `title`, and `chip`, public so a results screen draws a Claim's rewards with the same chip) from `ClaimsPageDeps(claims, sink, text)`, whose `library()` is the library's own store, `ZcRewardSink` and `ClaimsText`. `ClaimGrants.claim` and `claimAll` hand a Claim over through the bag guard and put back what does not fit, answering a `Result(taken, emptied, granted, kept, failed)`; this is Kweebec Nightmare's `claimPending` and `KweebecRewardSink` lifted. `ClaimNotices` raises a toast naming the tab on `ClaimAddedEvent`, and once a session, at the first ready after login, a notice counting what waits; both work on a zc-only server. `/zigclaims give --player=<name|uuid> --lootable=<id>` (`ZigClaimsCommand`, `ZigClaimsGiveCommand`, `ClaimTargets`) rolls a loot table into a player's Claims online or not (source `admin:<lootable>`, title `title.admin`); `--player` tries an online player by exact name, then a uuid, then the profile service (the `ServerAuthManager` session and `ProfileServiceClient.getProfileByUsernameAsync`), and an online starts-with match last, so a full name typed for an offline player never lands on an online player whose name merely starts with it. `InstanceBootstrap.installClaims(plugin)` opens the store and ledger and registers the rest. New `ziggfreedcommon.claims.lang`. Tests: `RailIconsTest` and `RailLabelLengthTest` take the tab; `ZigMenuTest.theAlmanacSitsAboveQuestsAndAchievements`, an exact slot-order test, is deleted.
- **New: the boss Claim, `payout/ZigClaimReward` and `payout/EncounterClaims` (zc-encounter, zc root).** A native reward type, `"Type": "ZigClaim"` under `Server/Rewards/<Id>.json` (`Lootable`, one table id; `Diminish`; `ShareScaled`, true by default; `TitleKey`), registered in setup from `EncounterBootstrap` on `RewardAsset.CODEC` through `getCodecRegistry`, so an encounter script's native `{"Type": "GrantReward", "Reward": "<Id>"}` names it and the engine checks the id at script load. Accessors: `lootable()`, `diminish()`, `diminishOrDefault()`, `shareScaled()`, `titleKey()`, `grant(PlayerRef)`. `EncounterClaims` is the one boss Claim path. A grant finds the player's run (the member index, else `EncounterRuns.runRostering`) and pays only a defeated run, from the shares its defeat settled (`ZigEncounterRun.settledShares`, kept until the reset's roll-over), each won roll kept at `rand < share` (`ShareScaled` false pays at share 1). It writes through `ClaimStore.award` with the Claim id `boss:<script>:<run>:<reward>:<player>` and the Diminish key `boss:<script>:<reward>:<difficulty>`; with no `Diminish`, the first win each day pays (`FIRST_EACH_DAY`, `[1, 0]` Daily). An uncredited member gets nothing, and so does a wiped, leashed or fresh run. Only a player no run indexes or rosters (a world event's grant) is paid at share 1, under `reward:<id>` (Claim id `reward:<id>:<player>:<ms>`). A `ZigClaim` with no `Lootable` decodes and pays nothing, with an INFO line. A Claim's title is the reward's `TitleKey`, else the binding's `NameKey`; loot cues play when a Claim is written for a player in the same world. Known limit: the native `GrantReward` pays only the encounter's live roster (`getMemberTtl`), so a credited player who is offline or out of range at the grant gets none. Test: `ZigClaimRewardCodecTest`.
- **Changed: a boss's payout is a Claim, never the bag (zc-encounter).** `EncounterLoot.grantDefeat` (a binding's `Loot.OnDefeat`) and `grantShares` write one Claim per credited participant through `EncounterClaims` (reward name `OnDefeat`, `EncounterClaims.ON_DEFEAT`, first win each day), never `RewardGrants.grantAll`. A credited participant who is offline still gets one where the rule's `CreditDisconnected` allows. The defeat receipt is one row, `claim.waits` (`EncounterClaims.CLAIM_WAITS_KEY`: "Your reward is waiting under Claims in your menu."). The `ZigGrant` script action redirects to the same path with one WARNING per script. A row's `Loot.ToKiller` and `QueueIfOffline` are read and ignored with one WARNING at the row's first payout (`EncounterBindingAsset.Loot.retiredLeaves()`), so the killer is paid at the share they earned. zc's example binding drops `QueueIfOffline`. The offline reward queue is gone (Removed, below), and the wiring root no longer fills it. Test: `EncounterSeamsTest`'s two methods on the queue are deleted.
- **New: credit for damage to a fight's adds, `DamageToAdds` (zc-encounter).** A fourth participation weight beside `DamageDealt`, `DamageTaken` and `Presence`, on an `EncounterParticipation` rule and on a binding row's `Participation` group, a number or a factor formula like its siblings: what one point of damage a player deals one of the fight's adds is worth. An add is any NPC carrying the encounter entity's native `SpawnLineage`, which the engine stamps on the encounter when it is built and copies onto whatever the script's `TriggerSpawners` and `Spawn` actions raise (and what those spawn in turn); the bound subject carries it too and is never an add. Unauthored weighs nothing, and the library's `Zc_Default` rule authors 0, so every existing fight's shares are unchanged; a consumer pays a fight's head-cutters and add-killers by writing the weight on that fight's row. `EncounterDamageSystem` credits a hit on an add to the attacker's player exactly as it credits a hit on the subject (a projectile's shooter, a pet or summon through the attribution seam), only inside the run's own world and never on the subject (matched by uuid, for the tick after an in-place role change), and notes that player as a member. Its miss path stays allocation-free: the victim's lineage is read only while some live run's lineage is indexed (`EncounterRuns.anyLineageIndexed`). The ledger keeps the new counter apart from damage to the subject, so `damageDealt` (records, stats, the defeat event's map) still means the boss alone. New: `ParticipationLedger.creditDamageToAdds`; `ParticipationWeights.damageToAdds()` and its four-argument constructor (the three-argument one still links, the adds weighing 0); `ParticipantShare.damageToAdds()` and its nine-argument constructor (the eight-argument one still links); `ParticipationSpec.damageToAdds()` and its seven-argument constructor (the six-argument one still links); `EncounterParticipationAsset.getDamageToAdds()` and `EncounterBindingAsset.Participation.getDamageToAdds()`. `/zigencounter inspect` adds a participant's damage to the adds when they dealt any (`admin.inspect.participant.adds`, en-US). Tests: `EncounterBindingCodecTest`, `ParticipationLedgerTest`.
- **Changed: a continuing reset keeps its members on the next run (zc-encounter).** `EncounterLifecycle.reset` rolls the run over first, then calls the new `EncounterRuns.untrack(ended, next, encounterRef)`, which points the members at the next run and remembers its encounter until that run's first tick. `EncounterRuns.runRostering(store, member)` answers a live run's roster, then a successor's. So a `GrantReward` after a leash, a `zc:reset` or the tick timeout in the same action list refuses instead of paying every roster member a full share. `untrack(UUID)` is unchanged. Test: `EncounterRunsMembersTest`.
- **New: zc's default party, `party/ZcParty` (zc-instance).** `ZcParty.service()` builds the library's `PartyService` on first use (game and settings id `ZcParty.GAME_ID`, `ziggfreedcommon`; settings `Server/ZiggfreedCommon/Party/ZiggfreedCommon.json` through `PartySettingsConfig`: `MaxSize` 5, `InviteTimeoutSeconds` 60, `OwnerOnlyInvite` false), `pageDeps()` hands it to `PartyInvitePage` with no queue handler, and `shutdown()` stops its invite timers, last in `InstanceBootstrap.shutdown()`. `ZcPartyMessages`, `ZcPartyScreenMessages` and `ZcPartyText` read the new `ziggfreedcommon.party.lang`; the page paints `count = {0}/{1}` on a Label's `.TextSpans`, which fills it in the viewer's locale. `/zigparty` (`ZigPartyCommand`, in the adventurer group) opens the page bare; `invite --player=<name>`, `accept` and `leave` act from the command line. `InstanceBootstrap.registerParty(plugin)` registers it. A consumer registers only what it adds over this party. Known limit: an edited settings file takes effect after a restart. No test (smoke).
- **Changed: the party page shows its privacy toggle only beside a queue handler (zc-instance).** Privacy only decides how a party queues, so `PartyInvitePage` hides it when its deps carry no queue handler. A consumer with one, such as Kweebec Nightmare, sees no change.
- **New: `ZigRequires`, a gate for interaction chains and trigger volumes (zc-objectives).** `objectives/interaction/ZigRequiresInteraction` (`{"Type": "ZigRequires", "Requires": {...}, "Next": ..., "Failed": ...}`) runs `Next` for a player who meets its `Requires` block (the shared one: `Factors`, `Permission`, `Quests`, `Custom`, `AllOf`, `AnyOf`, `Not`). For one who does not, it runs `Failed` and shows the lock line naming the first thing they lack (`LockReasons`) as an ERROR toast. An unauthored block passes everyone, and a chain with no nameable player takes `Failed` silently. `objectives/gate/ZigRequiresTriggerCondition` (a `Conditions` entry `{"Type": "ZigRequires", "Event": "ENTER", "Requires": {...}}`) lets a trigger volume act only for a player who meets it, silently, and answers false for anything that is not a player. Both read through `objectives/gate/RequiresCheck` (`playerSubject`, `passes`, and `refusal`, which answers null for a player who passes or the lock line from the same single walk of the block, so the interaction reads a refused player's block once), the evaluator a quest's gate uses. `ProgressInteractionsBootstrap.registerProgressInteractions` registers the condition on the TriggerVolumes plugin (`TriggerVolumesPlugin.registerConditionType`, guarded), and the type joins the progress interaction specs. A new `server.lang` key names it in the trigger-volume inspector: `customUI.triggerVolumeEffectEditor.conditionType.ZigRequires` = "Requires". Test: `ProgressInteractionsBootstrapTest`, which held one exact-list test, is deleted.
- **New: the `ZigRequires` volume audit, `objectives/gate/RequiresVolumeAudit` (zc-objectives).** The engine decodes a trigger-volume effect's `Conditions` through the tolerant `TriggerVolumeCodecs.TOLERANT_CONDITIONS`, which drops a condition that throws with one WARNING naming no file and keeps the volume, so its gate admits everyone. A misspelt `Requires` key does not throw at all: it decodes asking for nothing. So every boot, on `BootEvent` and never behind `BootAudit.ENV`, the audit reads each loaded pack's `Server/TriggerVolumes/Effects/**.json` raw (folder or zip) and logs one SEVERE line per finding (label `[gate] audit`, domain `gate`), naming the pack, the file and the condition's index: `ZIG_REQUIRES_UNREGISTERED` (no `ZigRequires` type is registered), `ZIG_REQUIRES_MALFORMED` (the condition throws on decode), `ZIG_REQUIRES_UNKNOWN_KEY` (it decodes past a key no codec read) and `ZIG_REQUIRES_NEAR_MISS` (a `Type` that is `ZigRequires` only up to case or spaces). It reports and changes nothing: the engine still loads the volume. Prefab-carried volumes and a world's own volume data are not read. No test (smoke).
- **New: dungeons, `instance/dungeon/` (zc-instance, zc root).** A dungeon is one file, `Server/ZiggfreedCommon/Dungeons/<Id>.json` (`DungeonAsset`, store `ZiggfreedCommon/Dungeons`, registered in `FrameworkAssetRegistrar`), every leaf inherited under `Parent`: `Instance` (the template, default `ZiggfreedCommon_Dungeon_Void`), `Enabled` (true), `Share` {`PartyLocked` true, `MaxPlayers` 5 per area, `AreasPerCopy` 4}, `Area` {`Prefab`, a path under `Server/Prefabs/` with its extension; `Spacing` 2048 blocks; `EntryOffset`}, `Run` {`TimeLimitSeconds`, absent or 0 or less for none; `FailOnWipe` false}, `Complete` and `Rewards` (runs and the completion Claim, below), `Copy` {`EmptyCloseSeconds` 60}, `Difficulty` (a label, empty for normal), `Season` (zc's `SeasonLeaf`: open only while that season is live) and `Text` {`NameKey`, `DescriptionKey`}. `DungeonConfig` folds defaults, then packs, then the owner file `mods/ziggfreedcommon/dungeons.json` (`DungeonOwnerLayers`); `open(id)` answers an open dungeon. `DungeonValidator` (domain `dungeon`, label `[dungeon] audit`) joins the boot audit with these codes: `UNKNOWN_DUNGEON_TEMPLATE`, `UNKNOWN_DUNGEON_PREFAB` and `NO_DUNGEON_PREFAB`, and the shared `UNKNOWN_SEASON` and `UNKNOWN_TEXT_KEY` (warnings); `TEMPLATE_INSTANCE_KEY`, `SPACING_TOO_SMALL` (under twice the server's view radius in blocks while areas are shared), `PACKED_PORTAL_TIMER` (the template's written `TimeLimitSeconds` or its `PortalType`'s own, read as the engine's `PortalKey` reads it, a JSON null as unwritten) and `PACKED_WORLD_EVENTS` (errors, the last two only while `AreasPerCopy` is above 1). `CopyRouter` (pure, `shared()`) keeps one area per party per dungeon. It fills a live copy's free area before it opens `<dungeon>-<n>` (`copyName`), numbered past every name the server still holds, and skips a copy whose tick average (`TickingThread.getBufferedTickLengthMetricSet`) runs over `LAG_BUDGET_MS` (25), counting parties still on their way in. It reserves before the teleport, never into a copy within `CLOSE_MARGIN_MS` (10 s) of its close, and forgets a copy only once its name is free. Its parts: `Rules`, `Placement`, `Kind`, `CopyView`, `WorldProbe` (`LiveWorlds` the live one), `partyKey`, `dungeonOf`, `reserve`, `arrived`, `failed`, `left`, `closing`, `closed`, `copies`. zc ships the void template `Server/Instances/ZiggfreedCommon_Dungeon_Void/instance.bson` (Void world generation, `IsSavingChunks` and `SaveNewChunks` false, `DeleteOnRemove` true, no `InstanceKey`, its gameplay config `ZiggfreedCommon_Dungeon`). `/zigdungeon list`, `status` and `close <copy>` are the admin verbs (`ZigDungeonCommand`, `FAMILY` `zigdungeon`). New `ziggfreedcommon.dungeon.lang`. Tests: `DungeonAssetCodecTest` (the codec round trip), `AssetCodecInitTest.dungeonCodecsInitialize`; `BootAuditWiringTest`'s pass count is deleted.
- **New: areas and membership (zc-instance).** `DungeonEntry` is the one way in: `enter(ref, store, player, from, dungeonId, partyKey)`, `enterAlone` (the admin's: an empty area even where areas are shared) and `enterWithParty` (the party's way in, below) reserve through `CopyRouter`, spawn or join the copy through `InstanceWorlds` with `AreaSpawnProvider` installed in the spawn's config step, paste the area while the player sits on the loading screen, and teleport them to the area's anchor plus `EntryOffset`, their own return point where they stood. Each answers an `Outcome` whose `Result` is `SENT`, `UNKNOWN`, `CLOSED`, `NO_PREFAB`, `MISSING_PREFAB`, `AUDIT_ERROR`, `ON_THE_WAY`, `INSIDE`, `FULL`, `COPY_GONE` or `FAILED`; `PROBE` counts a copy still spawning as live, so a party waits on it rather than opening another. `Areas` (`shared()`, `prepare`, `released`) wakes the prefab's chunk sections first (zc-world's `TickingSections.wake`: an entity added to a sleeping section is parked out of the world), clears a used area (`TargetUtil.getAllEntitiesInBox`, players skipped, plus a sweep for the Intangible markers, drops and projectiles it never returns), then pastes with FORCE through `PrefabUtil.loadPasteRegionAsync` and `paste`, entities and block states included, logging each paste's world-thread time at INFO under `[dungeon]`.
