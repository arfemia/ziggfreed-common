A 0.6.x server keeps 2.2.0. Test: `ManifestTargetTest` (the range admits the server jar the build compiles against and that line's release, and claims no later line).

The comparison is a package-private `compare(ComparisonOperator, double, double)`. Test: `NativeInputGateTest`.
- **Fixed: in-place page updates on Update 7; new `ToastablePage.writeInPlace`.** Update 7 renames `PageManager`'s in-place page update to `updateLegacyCustomPage`, with the same body; a 0.6.8-built jar threw `NoSuchMethodError` inside a swallowed catch, so a toastable page's toast pushes and the Play page's status pushes stopped. `ToastablePage.writeInPlace(Player, CustomPageLifetime, UICommandBuilder)` (protected, final) is the library's one caller of the engine's in-place update; the toast push and `PlayModePage`'s status push write through it after their own world-thread recheck.

- **Fixed: a world spawn point is asked for without waiting.** Update 7 replaces `ISpawnProvider.getSpawnPoint(World, UUID)` with `getSpawnPointAsync`, answering a `CompletableFuture<Transform>`; a 2.2.0 jar threw `NoSuchMethodError` at all three callers, and the `WorldSpawn` placement anchor never resolved. The new `npc/SpawnPoints` (zc-dialogue) asks a provider (`ask`), reads a point that has landed without blocking (`now`, `failureOf`) and continues on the world thread once it lands (`whenLanded`), never joining the future, since a provider fitting its point to the ground loads the spawn column first. The `WorldSpawn` anchor keeps one query per world on its way across sweep passes, forces a sweep when it lands with a point (so it places even after the retry budget is spent) and logs a failed query once per world at WARNING. `NpcAutoSpawn.ensureSpawned` places at once when the point is at hand, else on the world thread when it lands, checking its once-per-world marker again first. `NpcSpawnService.resolveSpawnPosition` keeps its signature and answers only a point already at hand, else the player's position. Tests: `SpawnPointsTest`, `WorldSpawnPointsTest`, `NpcAutoSpawnTest`.

- **Changed: what a stack's quality reads on Update 7.** Update 7 stores a quality on a stack only when one is stamped on it (`ItemStack#withQuality`, saved under `QualityOverride`); an unstamped stack reads its item's current quality. So `ItemReadings.quality(ItemStack)`, `qualityId(ItemStack)` and `hytale:item_quality` follow an item's reload for an unstamped stack and differ from the item readings (`hytale:tool_quality`) only for a stamped one: a "made with" quality must be stamped. A quality stamped on 0.6.8 (saved under the old `Quality` key) is dropped at its first Update 7 load, by the engine's inventories and this library's own stores alike: it is the one key the item codec renamed (`Quality` to `QualityOverride`), so stamped stats, a rename and a tooltip (`Metadata`) and a durability bonus (`MaxDurability`) load as saved, and nothing here migrates the quality. The reads and their descriptors are unchanged; the javadocs and the zc-entity router say so.
- **Technical: the quality and pending-reward tests assert Update 7's mechanics.** `ItemReadingsTest`, `HytaleFactorsTest` and `ItemMetadataKeysTest` pin Update 7's quality storage (the stack-versus-item split on `TestItems.requalified`, an unstamped stack following its item through a reload, a stamp saved under `QualityOverride`), and the unreadable-stack case now fails the metadata read, since Update 7's encoder reads every field directly. `PendingRewardStoreTest.everyWriteCarriesTheVersion` is tagged `engine-items`: Update 7's `FileUtil` logs at class init, which only the engine's log manager allows; a new untagged test pins that a write the engine cannot make never reaches the caller.
- **Fixed: entities go only into a ticking chunk section (new `world/TickingSections`, zc-world), and placement is idempotent.** On Update 7 a chunk section loads non-ticking whatever its column's state, and the column's flag no longer reaches its sections (0.6.8's `ChunkSystems.OnNonTicking` is gone). An entity added into a non-ticking section is parked into the section's entity list on the spot (`UpdateLocationSystems`): `Store.addEntity` answers null, `NPCPlugin.spawnEntity` skips its post-spawn, and the entity comes back as a `LOAD` add when a player's hot sphere or a `SET_TICKING` section request wakes the section; the parked copy is saved with the section. The placement sweep asked for the anchor's column (`getChunkReferenceAsync(SET_TICKING)`) and checked only `ChunkFlag.TICKING`, so a `WorldSpawn` placement placed at boot was parked with no ledger row and no `Fortify`, every later sweep in that state parked another copy, and a `Respawn` placement over a sleeping section `REPLACE`d its parked NPC. `TickingSections` reads a block's section (`stateAt`: `TICKING`, `PARKING`, `ABSENT`), wakes it (`wake`: `getChunkSectionReferenceAsync` with `SET_TICKING | HIGH_PRIORITY`; on the world thread a section in memory ticks before it returns), wakes one in memory and answers whether an add stays (`ensureTicking`, which never loads), runs a step once the section ticks (`whenTicking`), and holds a ticking section's active timer and its column's (`holdTicking`, which never wakes, so a system may call it). The sweep's place pass decides on the anchor's section: it wakes a sleeping section in memory on the spot and places into it on a second round of the same sweep, never the round that woke it, so the despawn pass first adopts any copy the wake brought back (one per instance; the rest are removed in that pass); a section not in memory is requested ticking, and only a landed request (a section ref still valid) sweeps again. Before any spawn the place pass checks for a copy of the instance by its persisted `ZiggfreedCommon:PlacedNpc` stamp (placement id and anchor key; a parked copy has no ledger row, so not by a row's uuid), among the copies the despawn pass kept or adopted and among the holders the anchor's section holds parked or saved (`EntitySection.getEntityHolders()`), and a found copy means no spawn; the check guards beside the round rule (a copy a wake brings back inside the same place pass is held back by that section's wait for the next round), so no boot or sweep adds a second copy. `Fortify` moved out of `NpcPlacementService.place`'s post-spawn, which the engine skips for an NPC it parks, and it cannot go in `preAddToWorld` (the holder has no `EntityStatMap` yet): the new `PlacementFortifySystem`, a holder system ordered after `EntityStatsSystems.Setup` and `BalancingInitialisationSystem` (the engine's own shape for health at the add), puts the bonus on every add of a placed NPC, spawn or load, and fills the enlarged pool on a spawn or when the bonus was missing; the modifier is saved with the entity, so a parked copy keeps it and one back from a park gets it. Every copy the despawn pass keeps or adopts, never a surplus one, gets its upkeep (`NpcPlacementService.upkeep`): its cached position from its transform, its keep-alive pin at that position and its `Fortify`, each idempotent. Before this an adopted copy got only its ledger row, and after a restart an instance had no pin and no cached position (both live in memory) until it was placed again; now the first sweep that finds it awake takes them again (the boot sweep skips a hub still parked, and `Fortify` is saved with the entity). `NpcSpawnService.spawnRole` never adds into a non-ticking section (it wakes one in memory and refuses one that is not, with a WARNING); `NpcAutoSpawn` places through `whenTicking`; `EncounterSpawner.trySpawn` wakes or refuses the same way and `spawnWhenLoaded` requests the section; `EncounterChunkHold` holds the section's timer as well as the column's, and the encounter tick holds its subject's section as well as its own. The keep-alive pins read the column's residency instead of its ticking flag, so a pin taken after a section wake holds and an unpin after the column stopped ticking no longer leaks the keep-loaded count. A placement logs one INFO line when it places. Public descriptors unchanged (`NpcPlacementService.fortify` keeps its descriptor and still fills the pool); `NpcPlacementService.isChunkLoaded` and `requestChunk` keep their descriptors for 2.2.0 linkage, and nothing in the library calls them; `isChunkLoaded` reads the column's `NonTicking` marker, since the final Update 7 release has no `ChunkFlag.TICKING`. The root `SectionTickingHygieneTest` fails a main source reading `ChunkFlag.TICKING` or passing `SET_TICKING` outside `TickingSections`. Tests: `TickingSectionsTest`, `AnchorSectionsTest`, `NpcPlacementReconcilerTest`, `NpcPlacementServiceTest`, `SectionTickingHygieneTest`.
- **Fixed: a stopping world answers a section wake once.** A world that takes no more tasks (its `execute` throws while it stops) failed only the future behind the continuation, so `TickingSections.whenTicking` never reached its `refused` callback and `EncounterSpawner.spawnWhenLoaded` never completed, which left `/zigencounter spawn` with no reply when it ran as the server stopped. Each now answers exactly once: `whenTicking` refuses on the thread that landed the wake, and `spawnWhenLoaded` answers `Refusal.ENGINE_FAILED` with one WARNING. A wake still loading when the world stops may get neither answer. Public descriptors unchanged. Tests: `TickingSectionsTest`, `EncounterSpawnerWakeTest`.
- **Fixed: a world's placement ledger rows survive a server stop.** `NpcPlacementReconciler.onWorldRemoved` (the library's world-removal evictor) dropped a removed world's `NpcPlacementLedger` rows and cached positions, and the engine removes every world when the server stops (`RemoveWorldEvent` as `EXCEPTIONAL`, the reason a crash carries), so each boot re-adopted the world's placed NPCs instead of matching their rows, and a placement without `Respawn` whose NPC had been killed stood again after a restart. It now drops them only for a world deleted with its removal, read from its `WorldConfig`'s `DeleteOnRemove` or `DeleteOnUniverseStart` (an instance or portal world torn down, a pruned world), so a torn-down instance still leaves no orphan row; a world unloaded with `/world remove` keeps its rows, and sweep state still clears on any removal. Rows a stop dropped before 2.3.0 stay dropped, so the first boot on 2.3.0 re-adopts once. Public descriptors unchanged. Test: `NpcPlacementWorldRemovalTest`.

- **New: the login title pass, `title/TitleBackfill` (zc-objectives).** A `Title` reward pays only when its achievement is earned or collected, so one earned before the reward existed never paid it. `TitleBootstrap` registers `TitleBackfill.onPlayerReady` on `PlayerReadyEvent` at `LATE`; on the player's world thread it reads the runtime's own achievement subject (`ProgressionRuntime.subjects().achievementSubject`), not behind `usesDefaultStores()`, and unlocks through `TitleUnlocks` every `Title` reward in an earned achievement's `autoRewards` and in a collected one's `claimRewards`, each unlock guarded on its own. It skips a player the owner's achievement switch is off for (`ProgressionRuntime.systemEnabled`). A title already held is a no-op with no notice. A title taken with `/zigtitle revoke` while its achievement stands comes back at the next login; revoke the achievement to take it for good.
- **Fixed: Claim rows added to an achievement already settled can be collected (zc-progression, zc-objectives).** An achievement with no `Claim` rows went straight to `CLAIMED` on earning and `tryClaim` needs `UNLOCKED`, so a row added to its list later could never be collected; the same held for a row added after a player collected. Every settle adds the rows it covered to the record's note, which never drops one: every row fingerprint any settle covered, as a multiset union (CRC32 over the kind, lower-cased, and the params in key order), and the most rows one settle covered (`AchievementProgressStore.claimRowsSettled`, a default pair that keeps nothing, kept verbatim by `InMemoryAchievementProgressStore` and `ZigAchievementStore` on `ZigProgressComponent`'s appended `AchievementClaimRows` leaf, forwarded by the runtime's store, forgotten by `clearAchievement`): `unlock` with nothing to collect notes no row, and `tryClaim` adds every current row. `AchievementEngine.offerAddedClaimRewards`, run inside `selfHeal` (so at every player-ready and when the book opens, on a zc-only server too), puts a settled achievement whose list now holds more rows than any settle covered back to `UNLOCKED`, paying, firing and moving nothing else (points, milestones, titles and the unlock moment stay put), and `tryClaim` then pays `claimRewardsOwed`: rows the note does not cover, at most as many as the list holds beyond the most rows one settle covered, the last first. So a retuned row reopens nothing, and a row that leaves the list (its mod missing, an owner override, a reload) and comes back is never paid twice. It assumes rows are appended at the end of `Claim`: a row inserted mid-list in the same change that retunes another may pay the retuned one instead, and a row added while a settled one is away from the list is taken as covered. A record from before the note is noted once by what it proves: earned before the achievement's new `ClaimAddedOn` day (`yyyy-MM-dd`, UTC; `Achievement.claimAddedOn`), it settled with nothing to collect, so every row is offered; any other is noted as covering the list as it stands (a collect by hand under rows nobody can know), and only a row added after that is offered. "As it stands" is the rows present at that first login: a `Claim` row gated on a mod missing then (its own `Requires`) and back later is offered once, though a player may have collected it before notes existed, which takes a record from before 2.3.0, a missing mod at the first login after the update and a gated row. A record from before the note with no unlock instant (`unlockedAt` 0) is never read as earned before `ClaimAddedOn`, so it errs toward offering nothing. One reopened whose added rows are gone again before a collect settles back, its note kept whole. A store that cannot keep the note offers nothing. `tryClaim` hands the collect gate the achievement holding only what that collect pays, so `RequiresGates.canReceiveRewards` weighs the room for the owed rows, never the ones already paid. While reopened an achievement reads `UNLOCKED`, so a consumer counting collected achievements (`isClaimed`) counts it out until it is collected again. `AchievementReader.waiting` reads `claimRewardsOwed`, and the Rewards block marks the rows already collected. A `ClaimAddedOn` that is not a day is a `BAD_CLAIM_ADDED_ON` WARNING. Test: `AchievementClaimRetrofitTest`.
- **New: `PlayerSettings.visible(PlayerRef, String)`, and the quest tracker obeys the hide-all switch (zc-presentation, zc-objectives).** `visible` is a surface's own Show with no hide-all over it; `shown` keeps answering the surface's own Show alone. `TrackedQuestHud` paints by `visible`, so `setHideAll` (`/zighud hide` with no panel) hides the tracker too, and the `PlayerSettings` watcher it already hangs repaints it on the change. `HudPreferences.isHidden` reads `visible` (same answer as before). `SurfaceRows.show`, every Show switch on the Settings tab (the tracker's included), reads `visible` and, turned on, clears the hide-all before it writes the Show.

## Titles for mod authors

A title is a small asset, and everything a mod does with one goes through a handful of public classes in zc-objectives' `title/` package and zc-entity's `entity/title/`.

- **Define.** Ship `Server/ZiggfreedCommon/Titles/<Owner>/<Id>.json` in your mod's asset pack (`"IncludesAssetPack": true`); the file name is the id, matched in any case, so prefix it with your mod's name. Leaves: `Enabled`, `Text` (`TitleKey`, `FlavorKey`), `Order` and `Hidden` (true keeps it off the picker's "Not earned yet" list and out of the count until a player earns it). Name it in your own lang file: `title.<id>.name` (what it is called), `title.<id>.flavor` (how it is earned) and `title.<id>.display` (where it sits around a player's name, `{0}` being the name; without one the name is followed by a comma and the title). A server owner overrides any leaf in `mods/ziggfreedcommon/titles.json`. `TitleValidator.audit()` checks your files.
- **Grant.** From content, a `Title` reward (`{"Kind": "Title", "Params": {"Title": "<id>"}}`) anywhere zc pays a reward. From code, `ZigTitles.grant(playerId, id)` and `ZigTitles.revoke(playerId, id)` from any thread, online or not (an offline player's change is queued and made at their next login, answered `QUEUED`); on the player's world thread with their entity in hand, `TitleUnlocks.unlock` and `revoke`. From the console, `/zigtitle grant|revoke --player=<name or id> --title=<id>`.
- **Read.** `ZigTitles.earned(playerId)`, `shown(playerId)`, `onOffer()`, `nameOf(id)` and `display(...)`, all from any thread and for offline players too, off the record `ActiveTitles` keeps (seeded at connect, refreshed on every change, kept across a restart).
- **Listen.** `ZigTitleChangedEvent`, a synchronous native event on the player's world thread, fires for each real change (`UNLOCKED`, `REVOKED`, `ACTIVATED`, `DEACTIVATED`) with the player, the title and the title now shown. A queued change fires it when it is made.
- **Gate.** `{"Factor": "ziggfreedcommon:title_earned", "Param": "<id>", "Min": 1}` holds for a player who has earned the title, and `ziggfreedcommon:title_shown` for one who shows it, in any `Requires` or `Conditions` block.
- **Open the picker.** From content, `"Open": "Titles"` anywhere a destination is read (a conversation line, a menu tile, a placement's press-F); its Back goes where `TitlePickerPages.deps` says. From code, `Destinations.open(TitleDestinations.titles(back), ctx)` for a menu tile whose Back returns to `back`, or `TitlePickerPages.open(store, ref, player, back)`, on the player's world thread; `ZigTitles.openPicker(store, ref, player)` opens it with the deps' Back. `TitlePickerPages.deps` themes it and routes its default Back.
- **Chat.** A title shows in chat only on a server whose owner writes `"$Chat": true` in `titles.json`, and only while the engine's own chat formatter stands. A chat mod with its own formatter names a player with their title itself: `ZigTitles.display(playerId, username)` for the name with the title alone, or `PlayerDisplayNames.displayName(playerId, username)` for the whole name every mod contributes to, and `TitleOwnerLayers.chat()` follows the owner's switch.
- **Mark a name.** A mod that adds its own mark to a player's name (a badge, a tag) contributes to `PlayerDisplayNames` under its own owner id: an order above 0 and below `TitleDisplay.ORDER` sits inside the title, one above it outside. It then shows wherever titles do, in chat too while `$Chat` is on.

## Damage types for mod authors

Hit with Hytale's own damage types, or with the library's `Arcane`, `Void` and `Life`; never ship a type of your own for one ability or one item, since a resistance keyed on the school then misses it.

- **Deal a type.** Name it in a damage node's `BaseDamage` (`{"Fire": 12}`) or a projectile's `Cause`, as vanilla does. `Arcane`, `Void` and `Life` sit under `Elemental`, so an `OutgoingDamage` effect on `Elemental` reaches them too. A resistance, from worn armor or an effect, needs an entry for the hit's exact type before any parent counts, so name every type it covers.
- **Tag a hit.** To tell your own hits apart (your bomb's blast from any other fire), give the damage node native asset `Tags`: `"Tags": {"Hit": ["My_Mod_Bomb"]}`. At damage time, `HitTags` reads the tags of the interaction that dealt the hit, so a system, an XP map or a quest can match on the tag while the hit keeps its plain type. A burn or poison your blast applies counts too: apply your own child of the effect (`"Parent": "Burn"`) carrying the same `Tags` and its own `DamageCalculator`, and each tick reads the tag.
- **Raise a type's damage from gear.** Add a native `StatModifiers` entry on `DamageBonus_<Type>` (whole percent points: 10 is +10%) or `DamageBonusFlat_<Type>` (damage points, added before the percent) to the item. The bonus counts for that type and every type filed under it, on any server running the library, and the item's tooltip names it.
- **Feed your own stats in.** A mod that keeps its own bonus stats registers them for a type with `TypedDamageBonuses.registerSource(typeId, percentStatId, flatStatId, gate)` (the `gate` decides per attacker; null always allows), instead of folding a second copy of the step. To switch every bonus off for some attackers (a world that plays plain combat), install one rule with `TypedDamageBonuses.installAttackerGate(gate)`; a server holds one, and MMO Skill Tree uses it for its per-world combat-bonus rule.
- **Retire a stat id.** Renaming a stat of your own? Register the old id with `StatAliases.register(oldId, newIds...)` at setup, so an item that saved a roll under it keeps the bonus under the new ids. An item asset's `StatModifiers` must name the new ids itself.
- **Runtime effects in buckets.** For a resistance or multiplier that moves with a stat, `effect/grid/RuntimeEffectGrid` writes one shared runtime effect per bucket and reconciles each entity onto the right one, so you never write an effect per player.
