> Built on Hytale Update 7 (0.7.x), like 2.5.2: the manifest's `ServerVersion` and `Dependencies` are unchanged, and no module gains an edge. Additive over 2.5.2: nothing is removed or changes shape, so a consumer built against 2.5.2 links unchanged. One behaviour changes for existing data: a board slot gated on a missing mod is left off the board (see "A stand-in drops where the mod is installed" below). New: zc-dialogue's `NpcPlacementAsset.SeasonEntry` (its `CODEC`, `of`, `getSeason`, `getRole`, `roleId`, `getInteract`, `getAnchor`, `getProps`, `tag`, `TAG_SEPARATOR`, `ALL_YEAR_TAG`), `NpcPlacementAsset.getSeasons`, `hasSeasons`, `activeSeason`, `inSeason`, `inEffect`, `anchorTag`, `ownsAnchorKey`, `anchorTagOf` and `withSeasons`, `NpcPlacementAsset.SeasonEntry.TAG_MARK`, `NpcPlacementValidator.SEASONS_DUPLICATE`, `SEASONS_INTERACT_BOTH_FORMS`, `SEASONS_EMPTY_ANCHOR` and `SEASONS_UNKNOWN_ROLE`, `NpcIdentities.declaredNpcIdOfEntity`, and `npc/placement/runtime/PlacementLooks` with its `OnLoad` system; zc-objectives' `InteractionRewards.givenBy`, `ProgressCredit.hasTargets`, `namesTarget` and `targetsIgnored`, and `objectives/runtime/KnownFactors`; zc-core's `ModGates.INSTALLED_MARK`, `isAbsenceGate` and `dropsWhereInstalled`, `DerivedFactorAsset.getRequires`, `DerivedFactorConfig.MOD_GATE_STORE`, `refusedByModGate` and `knownFactors`, and `DerivedFactorValidator.REQUIRES_CONDITION_IGNORED`; zc-commerce's `BoardAsset.slotsHere` and `BoardSlotAsset.passesModGate`. New key in `ziggfreedcommon.progression.lang`, in all nine locales: `reward.given_by`. Tests: `PlacementSeasonsTest`, `DerivedFactorModGateTest`, `BoardSlotModGateTest`, the mirror's cases in `ModGatesTest`, the `Targets` cases in `ProgressCreditTest`, the gated slot's case in `CommerceValidatorTest`, and `Factors` joins `FrameworkModGateWiringTest`'s gated stores.

## New

- **One NPC placement serving several seasons (zc-dialogue).** A placement takes `Seasons`, a list of entries, each naming one calendar event (`Season`) and, for while it is the entry in effect, its own `Role`, `Interact`, `Anchor` and `Props`. The entry in effect is the first one in list order whose season is running; each of its four leaves, when authored, replaces the file's own leaf of that name, and a leaf it leaves out reads the file's. A whole group is replaced, never merged: an `Anchor` is a set of places, so a merged one would stand the NPC at both, and `Interact` and `Props` already replace whole under `Parent`. With at least one entry, the placement stands while any listed season runs, and the file's own `Season` leaf is not read. An entry with a blank `Season` is in effect all year, a fallback at the end of the list. Who the character is never changes: the NpcId stays `Identity.NpcId`, else the file's own `Identity.Role`, never an entry's `Role`, so a quest, a talk step or a hand-in bound to the character works in every season.
  - The look changes in place: when the entry in effect names another role than the standing NPC wears, the library asks the engine's own role change for it (the same entity, uuid and ledger row, the new role's model on it). It happens at each season's start and end (the calendar's forced sweep), at every sweep that keeps the NPC, and whenever the NPC is loaded (a boot, a chunk coming back), so a server that was down at the switch shows the right look as soon as the NPC is in the world.
  - A move is a new standing: an entry with its own `Anchor` stands its own instance (its anchor keys carry the entry's season after a mark, `worldspawn:@winter_fair~0`), so at the switch the NPC at the old spot is removed and one is placed at the new spot, with the same NpcId. It happens at the same moments as a look change; an old copy asleep in an unloaded chunk is removed when that chunk loads. Its `Props` go and come with it. A copy standing under a tag no current entry carries (a pack update renamed or dropped that entry, or took its `Anchor` away) is removed the same way, so one character never stands twice.
  - The audit warns on an entry's `Role` this server has not loaded (`SEASONS_UNKNOWN_ROLE`: the character keeps the look it wears), an entry's `Anchor` with no group in it (`SEASONS_EMPTY_ANCHOR`: the character stands nowhere while it is in effect), a season listed twice (`SEASONS_DUPLICATE`) and an entry's `Interact` written both ways (`SEASONS_INTERACT_BOTH_FORMS`).
  - Under `Parent`, `Seasons` is one leaf: a child that authors it replaces the list whole. A file with only the plain `Season` leaf behaves exactly as before; one that gains `Seasons` drops its own `Season` line.
  - Example, one villager through two events in one file: their autumn look, lines and spot while `Autumn_Fair` runs (both may run at once; the first listed wins), then a winter look, winter lines and a spot by the world spawn once only `Winter_Fair` runs:

```json
{
  "Where": { "GameplayConfig": [ "ForgottenTemple" ] },
  "Identity": { "Role": "Yourpack_Miller", "NpcId": "Yourpack_Miller" },
  "Anchor": { "Structure": { "MarkerIds": [ "Temple_Kweebec_Merchant_Static" ], "Offset": { "X": 3, "Z": -7 }, "Yaw": 180.0 } },
  "Limits": { "OncePerWorld": true },
  "Lifecycle": { "KeepAlive": true, "Respawn": true, "Fortify": true },
  "Interact": { "Dialogue": "Yourpack_Miller" },
  "Seasons": [
    { "Season": "Autumn_Fair" },
    { "Season": "Winter_Fair",
      "Role": "Yourpack_Miller_Winter",
      "Interact": { "Dialogue": "Yourpack_Miller_Winter" },
      "Anchor": { "WorldSpawn": { "Offset": { "X": -18, "Z": -8 }, "Yaw": 180.0 } } }
  ]
}
```

- **A reward item pays the player it hits (zc-objectives).** `ZigGrantReward` takes `PayTarget: true`: the rewards go to the player the chain targets (a `Selector` hit, a wand's raycast) instead of the one using the item, through the same payout, retry queue and receipt toast a user's payout takes, and the receiver is told who it came from. Nothing about it is damage, so it lands with PvP off and inside the Forgotten Temple. With `PayTarget`, a chain that hit no player resolves `Failed`, so its `Next` (the item's spend, a credit) never runs for a miss and its `Failed` branch can answer it; a lost `Chance` roll still resolves `Finished`. A plain `ZigGrantReward` (no `PayTarget`) and a `ZigCreditProgress` in the same hit fork still pay and credit the user, as they did.
- **A hit names the character it struck (zc-objectives).** `ZigCreditProgress` takes `QualifierFromTarget: true`: the credit's `Qualifier` is the NpcId of the character the chain hit (`NpcIdentities.declaredNpcIdOfEntity`: a placed NPC answers its placement's NpcId, an NPC an identity overlay declares answers that id), so a step reads "give a gift to the miller" as `{ "Kind": "USE_ITEM", "Target": "Yourpack_Gift", "Qualifier": "Yourpack_Miller" }`. A hit on a player, or on an NPC nothing declares a character (a wild creature, whose role name is never used), credits nothing. Beside it, `Targets` lists the NpcIds (in any casing) a hit may count for: a hit on one of them credits and resolves `Finished`, and any other hit (another character, a player) credits nothing and resolves `Failed`, so a spend in the node's `Next` runs only for a gift that reached a listed character. Without `Targets` it behaves as above; `Targets` without `QualifierFromTarget` does nothing and is a load WARNING. Example, a gift that is spent only when it reaches one of the pack's villagers:

```json
{ "Type": "ZigCreditProgress", "QualifierFromTarget": true,
  "Targets": [ "Yourpack_Miller", "Yourpack_Weaver", "Yourpack_Shepherd" ],
  "Next": { "Type": "ModifyInventory", "AdjustHeldItemQuantity": -1 } }
```

  A gift pointed at a friend or at a villager, all of it in one chain:

```json
{ "Type": "Selector", "Selector": { "Id": "Raycast", "Offset": { "Y": 1.6 } },
  "HitEntityRules": [
    { "Matchers": [ { "Type": "Player" } ],
      "Next": { "Interactions": [
        { "Type": "ZigGrantReward", "PayTarget": true,
          "Rewards": [ { "Kind": "Lootable", "Params": { "Lootable": "Yourpack_Gift_Contents" } } ],
          "Next": { "Type": "ZigCreditProgress", "Qualifier": "Gift" } } ] } },
    { "Matchers": [ { "Type": "Player", "Invert": true } ],
      "Next": { "Interactions": [
        { "Type": "ZigCreditProgress", "QualifierFromTarget": true } ] } } ],
  "FailOn": "Entity" }
```

  Write the hit as `HitEntityRules`, as above: the `Selector`'s plain `HitEntity` skips an invulnerable target (the engine's `isTargetInvulnerable`, Hytale's `SelectInteraction`), which a fortified or temple NPC can be, while a rule's `Next` runs for every entity its matchers accept.

- **A derived factor file follows the mod gate (zc-core).** A `Factors` file takes a top-level `Requires` (the `Factors`-only block every store below zc-progression writes), and its plain `hytale:mod_installed` condition decides whether the file loads, as every keyed store's does. A factor dropped this way is absent by design: a gate arm or a condition naming it fails closed, a formula term naming it adds 0, a lock line naming it reads as not met, and no validator reports it as unknown and no log line warns about it. Only mod presence is read there; any other condition in it is reported (`REQUIRES_CONDITION_IGNORED`) and ignored. The store's drop line is `[zc] mod gate: Factors dropped <N> pack file(s) ...`. Example (`Factors/Yourpack_Miller_Skill.json`, a factor that exists only where a companion mod runs):

```json
{ "Requires": { "Factors": [ { "Factor": "hytale:mod_installed", "Param": "Yourgroup:Companion", "Min": 1 } ] },
  "Formula": { "Factors": [ { "Factor": "hytale:stat", "Param": "Companion_Level", "Weight": 0.05 } ],
               "Clamp": { "Max": 1 } } }
```

- **A stand-in drops where the mod is installed (zc-core).** A plain top-level `hytale:mod_installed` condition with `Max: 0` (and no `Min` above 0) is the mirror of the `Min: 1` gate: where that mod reads installed, the file, reward row or board slot carrying it is dropped at load (absent, never shown greyed); where it is missing, the condition passes as it always did. Every store that reads the `Min: 1` gate reads this one too (pack files, owner overrides, reward rows, Almanac slots), and a board slot now reads both: a slot whose own `Requires` gates on mod presence either way is left out of the board where it does not fit, and a board whose every slot is left out posts nothing. This changes what 2.5.2 did for one shape: a board slot whose top-level `Requires` names a missing mod with `Min: 1` was posted and shown locked in 2.5.2 (a lock that could never open on that server); it is now left off the board. The drop line has its own wording, so a parser of the missing-mod line never counts it: `[zc] mod gate: <Store> dropped <N> pack file(s) that load only without a mod (<Group:Name>)` (`owner override(s)` and `reward row(s)` alike). Example, a reward row that pays only without the companion mod:

```json
{ "Kind": "Currency", "Params": { "Currency": "Yourpack_Coins", "Amount": 10 },
  "Requires": { "Factors": [ { "Factor": "hytale:mod_installed", "Param": "Yourgroup:Companion", "Max": 0 } ] } }
```

  and a board slot open only without it: `{ "Difficulty": "Errand", "Optional": true, "Requires": { "Factors": [ { "Factor": "hytale:mod_installed", "Param": "Yourgroup:Companion", "Max": 0 } ] } }`.

## Changed

- **The derived-factor audit asks the server's factor vocabularies (zc-core, zc-objectives).** `DerivedFactorConfig.audit()`, which both the fold-time log and zc's boot audit read, asks the installed answer `DerivedFactorConfig.knownFactors(Predicate)` before it reports a formula term's factor as `UNKNOWN_FACTOR`. The library installs zc-objectives' `KnownFactors.isKnown` at setup: the progression runtime's vocabulary (a consumer's, where one registered it), the placement, loot and encounter vocabularies, and every id a mod contributed. Until then the default is the contributions alone. Every plugin's setup runs before the first fold logs, so the fold-time log and the boot pass both read the full answer; a term naming a factor registered in code (`hytale:stat`, `ziggfreedcommon:quest_completed`) is no longer reported, while one naming nothing registered, no loaded file and no factor the mod gate left out still is. No file released with 2.5.2 or earlier drew the false finding (every shipped `Factors` file was a naming overlay, which names no terms), so a live server sees no change.
- **A board slot the mod gate leaves off the board is not audited for fill (zc-commerce).** `BoardValidator` skips such a slot (`BoardAsset.slotsHere`) for `UNFILLABLE_SLOT` and for the required-count check; its band still counts as one the board posts, for the `Grades` naming check.

## Known limits

- With `Limits.MaxPerWorld` above 0, an old season's copy asleep in an unloaded chunk still holds its ledger row and counts toward the cap, so the new season's copy waits until that chunk loads and the old copy is removed. `OncePerWorld` is unaffected.

## Thrown items: nothing new needed

- A thrown item's hit already applies an effect to a player and credits the thrower with PvP off and in the Forgotten Temple, so this version adds nothing for it. Read in the release source (Hytale 0.7.7): a projectile striking a player starts its `ProjectileHit` root with no PvP check (`StandardPhysicsProvider` builds the chain's context with the thrower as its owner and the projectile as the entity it runs for, and puts the struck entity in `TARGET_ENTITY`; the collision filter skips only projectiles, the dead, entities that do not collide, and the thrower). `ApplyEffect` with `"Entity": "Target"` adds the effect to the struck player, asking only the effect's own `ApplyConditions`. PvP (`DamageSystems`' player damage filter) and the temple's `DisablePlayerIncomingDamage` (`CombatConfig`, read by the damage filter) cancel `Damage` events alone, so an effect lands and only a damaging tick of it is cancelled. Inside that chain `ZigCreditProgress` credits its owner, the thrower.
- Author the hit's credit with an explicit `Target` (the thrown item's id): inside a projectile's chain the item the library reads is the thrower's hand at the moment of the hit, not the throw. Example, in a thrown item's `ProjectileConfig`:

```json
"ProjectileHit": {
  "Interactions": [
    { "Type": "ApplyEffect", "EffectId": "Slow", "Entity": "Target" },
    { "Type": "ZigCreditProgress", "Target": "Yourpack_Snowball", "Qualifier": "Hit" },
    { "Type": "RemoveEntity", "Entity": "User" } ] }
```
