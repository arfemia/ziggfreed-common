The library's biggest cycle: a full shared PROGRESSION layer (quest and achievement engines, content authored as assets, always-on moment producers, an asset-driven feedback engine, admin surfaces and two full screens), ONE dialogue engine per server, a generic asset-driven NPC placement engine, one world-targeting vocabulary, and an asset surface the in-game Asset Editor can mount end to end. This is the ONE version story for the whole held cycle: the work was developed under the internal 1.4.0 number and ships as 2.0.0 - no 1.4.0 was ever released, the previous public release was 1.1.1, and the 1.2.0 / 1.3.0 / 1.4.0 notes beside this one first shipped here too.

- **New: shared quest and achievement engines, with content as assets.** A consumer registers its subjects, listeners and vocabulary into one `ProgressionRuntime`; content is authored at `Server/ZiggfreedCommon/Quests/...` and `Achievements/...` with native `Parent` inheritance, a shared `Listing` group (`Icon`, `Hidden`, `RequirePrerequisites`) on both types, id-keyed `Criteria` and `Objectives` (a criterion's key is what progress is stored under, so inserts and reorders can never re-point a player's tally), and one `Rewards {Auto, Claim}` group across everything that pays: quests, achievements, points milestones and bounty contracts alike. A quest's `Repeat` group is the whole comes-back-around vocabulary (a rolling `Cooldown`, `CooldownFrom` Claim or Complete, a Daily/Weekly calendar `Reset`, a lifetime `MaxCompletions`), evaluated by the engine for every consumer, and authoring the group at all is what makes a quest repeatable.
- **New: one persisted progress record, with a pinned wire format.** `ZigProgressComponent` holds a player's whole quest and achievement state and is attached to every player at connect. Its codec is golden-pinned as a published contract, so a consumer's database backend can store the blob and trust it to keep decoding; the default stores report dirty and flush to any registered persistence listener, so wanting a database is not a reason to replace them.
- **New: five always-on moment producers and a reaction seam.** Block break, mob kill, craft, pickup and place block are produced by the library, always (the per-kind claim mechanism is deleted); an additive `MomentListener` contribution sees every produced moment first and unconditionally, so a consumer reacts to what was produced instead of re-detecting the native event beside the producer. A `KillAttribution` seam credits a kill a turret, summon or pet landed to its owner, and a `KillQualifier` seam lets a kill moment carry a qualifier for the killed entity.
- **New: the shared placed-block ledger.** `world/placed/` is the one answer to "did the player put that block or item there themselves", persisted at `mods/ziggfreedcommon/placed-blocks.json` with four live policy knobs; the library's own break and pickup producers consult it, so nobody earns from breaking what they placed even on a bare server. It flushes off the world thread on its own traffic beat, so a crash loses at most half a minute of placements instead of the whole session.
- **New: an asset-driven feedback engine, with neutral defaults in the jar.** What a server does at a lifecycle moment is a `Server/ZiggfreedCommon/FeedbackMoments/<moment id>.json` file: a `Toast` for the player it is about, a `Broadcast` banner, a `Sound`, and a console `Command`, with a whole-toast `Tone` (Info / Success / Reward / Warning / Error) that keeps frame, headline and corner feed agreeing, reward rows listing what the moment actually paid, and per-case `Variants`. The library ships a plain default file for each of the seven moments its progression engines announce, so a bare server gets a notice and a jingle out of the box, and a consumer replaces any of them by shipping a same-id file.
- **New: the Objective Book.** A full-screen two-tab progression menu: the quests tab is a whole quest log (browse, accept, track, hand in, collect, abandon, inline objectives with order-group locking) and the achievements tab a two-panel browser with categories, search, sort and status filters, ladders, pins, an overview panel and the consumer's points milestones. Every default leaves the book working on a bare server; `ObjectiveBookDeps` is the consumer seam set. Its claim toasts list what they actually paid, and a locked quest names everything still missing rather than one line at a time.
- **New: the tracked-quest HUD.** A library-owned on-screen tracker drawn to match the native objective HUD, repainting on the quest engine's own events (accept, progress, complete, claim, abandon, track) rather than on a tick; a consumer supplies position, audience, colours and theme through `TrackedQuestHudDeps`, and a bare server needs none of it.
- **New: `/zigprogress` and the progression admin page.** An admin command family over the shared runtime (`quest`, `achievement` and `memory` groups plus a `reload` that refolds the shared content), with engine-derived permission nodes and full console support; and an in-game page listing every registered progression-system switch with honest On / Off / unknown states, reachable only from a consumer's own gated admin surface.
- **New: one lock-reason path, and factors that name themselves.** Every surface that refuses content reads the one token-to-line mapping, a locked detail panel can list ALL unmet requirements at once (`allFailures`), and a `Server/ZiggfreedCommon/Factors/` file can carry a factor's naming half (its words, its per-param keys) so every gate on it explains itself, whichever mod registered the factor in code. A new `hytale:mod_installed` factor gates a quest, achievement, dialogue option, loot roll, placement or shop entry on another mod being present, with no Java on either side.
- **New: rewards read the same everywhere.** One shared reader for `type`-plus-fields reward JSON, one chip ladder for a reward's name and picture, toast body rows built from that same reading, and presentation kind files for the roll-at-grant kinds shipped by the library itself; a display number binds as a typed param, never as server-formatted text, and a test keeps it that way.
- **New: the commerce screens grow filters and read as one family.** The storefront and board pages read at one family type size off one shared row and line template, the storefront gains two list filters (which run, and rotating or standing stock), and a bounty contract pays through the same `Rewards {Auto, Claim}` group as everything else, so a payout moved between a quest file and a contract file keeps its spelling.
- **New: ONE dialogue engine per server.** Every consumer registers its actions and conditions additively into the shared engine, so two dialogue mods on one server no longer fight over whose vocabulary executes (whichever loaded last used to take the slot, reading every conversation against the wrong mod's language file). Contributions stack, a class claim is first-wins with one boot line naming both mods, and `DialoguePayloads` lets a consumer's conditions answer correctly in a conversation another mod opened. Kweebec Nightmare is the exemplar consumer.
- **New: dialogue seen-ness and memories, no hand-composed flags.** `Once` on a `Start` entry or an option is the "show this once" knob (`true`, or a `Where` world-selector group for once per world family, keyed so an instance world rebuilt under a fresh uuid name still counts as the same place), and a declared `Memories` map carries named state with its own scope and lifetime (`Where`, `ResetWithQuest`, `Shared`), used by bare name through `Remember`/`Forget` and `Remembered`/`NotRemembered`. `SetFlag`/`Flag`/`NotFlag` leave the pre-seeded types; a consumer that genuinely wants raw flags can still register its own. Dialogue conditions can also gate on a world (`Where`) or on any registered factor, so a pack gates an option on a stat or a held item with zero Java.
- **New: a generic asset-driven NPC placement engine.** Where an NPC stands, in which worlds, behind which requirements, and what pressing use on it opens is ONE `Server/ZiggfreedCommon/NpcPlacements/<id>.json` asset: five independent anchor groups (world spawn, coordinates, a worldgen structure marker, a discovered zone, a custom provider) whose positions union, lifecycle knobs, an owner on/off file (`mods/ziggfreedcommon/npc-placements.json`), and a reconciler that never double-spawns across chunk reloads. A placement NAMES an NPC role and the role file owns the look; two placements of one role are two standings of ONE character, so a quest bound to it resolves at either, and an authored `NpcId` opts a standing out into a character of its own.
- **New: one world-targeting vocabulary.** The embeddable `Where` selector group (`Match` name patterns, `GameplayConfig` for instance families, `ExcludeMatch` as a filter) is the one authority every consumer asks "which worlds does this apply to", ranked by a deterministic specificity ladder instead of a priority knob. Named selector files are gone as vocabulary, and a `Where` matching no loaded world is a validator finding rather than content that quietly never appears.
- **New: minigame rounds count for progression.** A generic round-is-over event for minigames built on the instance layer, plus `INSTANCE_ROUND_WON` / `INSTANCE_ROUND_ENDED` built-in objective kinds, so progression content can watch a round with no bespoke bridge.
- **New: `ZigFlairComponent`.** A per-player unlocked-cosmetic-flair set the library persists and attaches at connect, so one mod can grant a flair and another render it with no per-mod component, and a server running only the renderer still remembers what a player unlocked.
- **New: the in-game Asset Editor can mount every authored file.** Every codec's exported schema declares each value shape its decode accepts, each field's effective default, and each closed vocabulary as a dropdown with a one-line meaning per value, so the editor edits the library's asset types instead of failing their panes; pack-extensible vocabularies deliberately stay plain strings.
- **New: owner files speak one file-level grammar.** Every `mods/ziggfreedcommon/*.json` owner file reserves `$`-prefixed top-level keys (`$Comment` documentation, a `$SchemaVersion` marker a future structural change can branch on), and `dialogues.json` joins the roster as an owner layer exactly like its five siblings: a bare map keyed by conversation id, each entry merged leaf by leaf over the stored conversation.
- **Changed: content keys resolve off the live language catalogue.** A consumer no longer registers which lang namespace its content keys live in (`ContentKeys.install` is gone); the `.lang` files it ships already say so, and resolution asks the loaded catalogue in a fixed, deterministic order, a consumer's word beating the library's own shipped default.
- **Unchanged: `cast/` and `cast.step/`.** The runtime layer the 1.4.0 note introduced ships exactly as documented there - zero edits, zero renames, zero deletions this cycle.
