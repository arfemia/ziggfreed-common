# dialogue/ - the generic branching NPC dialogue engine

Router for `com.ziggfreed.common.dialogue`. A self-contained, mod-agnostic dialogue runtime lifted from hyMMO (which is being re-integrated as its first EXTENDER). A consumer builds ONE [`DialogueEngine`](DialogueEngine.java) via the builder **in its plugin `setup()`**, supplies a few seams, and opens [`page/DialoguePage`](page/DialoguePage.java); the `.ui` ships once here and resolves client-side.

- **PARADIGM: the SCHEMA is shared, BEHAVIOUR is per-consumer.** Dialogue files live in ONE store the server reads once, so the decode vocabulary has to be everybody's: [`DialogueTypeTable`](DialogueTypeTable.java) is the process-wide table of every registered action / condition `Type` and every shorthand key, and it assembles the whole `NpcDialogue` codec graph once. What an action DOES and what a condition ANSWERS stay in the engine that registered them (its own handler / evaluator maps), so one mod's dialogue can never run another's code, an action this engine has no handler for is a no-op, and a condition it cannot answer hides its line. `DialogueEngine.Builder.build()` publishes its types into the table as a side effect - a consumer's code is unchanged, it just has to run in `setup()`.
- **ORDERING (load-bearing, evidence in `DialogueTypeTable`'s javadoc): `HytaleServer.boot()` runs `PluginManager.setup()` to completion, THEN dispatches `LoadAssetEvent`.** So every engine built during setup has registered its vocabulary before the first dialogue file is read. Building an engine LAZILY on first use is the one way to get this wrong: the file is read first, names a `Type` nothing registered yet, and fails to load. A registration arriving after a read still takes effect (the table re-assembles) and logs one warning saying so.
- **[`DialogueAction`](DialogueAction.java) + [`DialogueCondition`](DialogueCondition.java) are BOTH `Type`-discriminated polymorphic lists** (`Conditions` is an array of `{Type:...}` objects, symmetric with `Actions`). Generic actions: `Goto`/`Close`/`Remember`/`Forget`/`MarkTalked` + the carrier `OpenPage`. Generic conditions: `Remembered`/`NotRemembered`/`World`/`Factor` + the **boolean combinators `AllOf`/`AnyOf`/`Not`** (each holds a child `Conditions` list under `All`/`Any`/`Of`; their CODECS are assembled with the shared `conditionsArray` in the table, their EVALUATORS per engine so a combinator wrapping a domain condition is answered by the mod that owns it). Each leaf subtype carries its own field `BuilderCodec` (PascalCase keys, guarded by [`DialogueEngineTest`](../../../../../../test/java/com/ziggfreed/common/dialogue/DialogueEngineTest.java)). **An unknown `Type` FAILS THE READ** (`UnknownIdException` out of the dispatch codec) rather than being dropped, so a file naming a mod that is not installed is a startup error naming the file, never a silently missing line.
- **Option SHORTHAND is part of the schema, not a rewrite that runs before it.** A [`DialogueSugarLeaf`](DialogueSugarLeaf.java) declares a key, a fold order, the CODEC for its authored value and the factory that turns it into a canonical action; it is registered with its action (`DialogueActionType#withSugar`), so shorthand and action cannot drift. Every registered leaf becomes a real keyed field on the option codec AND on the `Do` atom codec, the decoded values land in [`DialogueSugarValues`](DialogueSugarValues.java), and [`DialogueSugar`](DialogueSugar.java) folds them into `Actions` at [`DialogueOption#getActions`](DialogueOption.java). Consequences worth knowing: a mistyped shorthand VALUE is a decode error naming the key; the in-game asset editor sees the shorthand like any other field; a leaf may declare MODIFIER keys it also reads (`Reward` reads `RewardOnce`); authored `Actions` run first and the shorthand is appended; a `Do` array folds in ARRAY order and SHADOWS the bare keys entirely (a bare key beside `Do` is a validator warning), while a modifier written beside `Do` still reaches the atoms inside it. A shorthand key that collides with an option field or with another leaf is refused with one warning.
- **A `Factor` condition gates a line on a number ANOTHER mod owns, through the ONE shared factor vocabulary.** `{"Type":"Factor","Factor":"yourmod:reputation","Param":"guild","Min":10}` holds the four authored leaves and hands them to [`factor/FactorCondition`](../../../../../../../../zc-core/src/main/java/com/ziggfreed/common/factor/CLAUDE.md) (`getCondition()`, memoized) - the same leaf, keys and semantics an NPC placement's `Requires` uses, so a factor id means one thing across the library. The number comes from the registry the engine was BUILT with (`DialogueEngine.Builder#factors(FactorRegistry)`, readable back as `engine.factors()`); the evaluation context carries the player as BOTH `store` and `subject`, the current world through the same guarded [`DialogueWorlds`](DialogueWorlds.java) read the `World` condition uses, and the authored `Param`. **Fail-closed at both altitudes**: an unregistered id / a provider that cannot answer / a throwing provider all hide the gated content, and so does an engine built with NO registry (one warn-once). A bounds-less condition is therefore a presence check - it passes only while the factor resolves at all, which is how "only where that mod is installed" is written - and the engine-handle reads are try-guarded, so a context that cannot expose a store simply supplies no subject rather than throwing.
- **[`quest/`](quest/) - the QUEST-AWARE vocabulary, pre-seeded like the generics.** Conditions `QuestState` (`Quest` + `State`, or `States` as an OR shorthand; the EFFECTIVE status, so a finished daily off cooldown re-offers itself), `ReadyToTurnIn` (`Quest`, possession-aware) and `HasReadyToTurnIn` (any quest); actions `AcceptQuest` / `TurnInQuest` written as the shorthands `Accept` (20) and `TurnIn` (30). All of them go through [`quest/DialogueQuests`](quest/DialogueQuests.java), which the consumer wires with `DialogueEngine.Builder#quests`: a `QuestStateReader` (zc-progression's NARROW read seam - **never `QuestEngine`**, which mutates: a condition that could reach it could accept a quest while merely rendering an option), a `Subject` factory, an ANSWER SET (`answersTo(contextId)` - one character standing for several quest-giver ids, tried in turn so a hand-in works wherever its giver stands), and the two write methods, which REFUSE by default. Unwired, every quest line reads NOT_STARTED and every accept / hand-in refuses. **`HasOfferableQuests` is here as a CLASS but is NOT seeded**: the missing half now exists (zc-progression's `NpcOfferProviders`, where a mod's catalogue and gates answer), so the condition asks rather than guesses - but a `Type` id resolves to ONE class process-wide, so a consumer already shipping its own must switch to this one deliberately, in place of its own. `QuestDialogueConditions.offerableType(quests)` is what it registers. A consumer with no condition of its own can register it straight away.
- **`MarkTalked` is the ONE way a conversation counts as having happened, and it has NO shorthand.** `{"Type":"MarkTalked"}` on the option that IS the beat (the greeting, the hail, the "I have returned"). Nothing credits because a player pressed F, because a page opened, or because a dialogue re-rendered: a discrete click is a decision a player made, a render is not. What the engine supplies for free is the TARGET, never the trigger - an absent `Target` is the character being talked to (alias set included) through the same `resolveTarget` every action uses, so an author never types an id to credit the character they are already writing for. It is written out in full rather than hidden behind a one-word shorthand because crediting is a deliberate statement about the story, not a flag. Pair it with option-level `Once` for "credit the first hail"; the two are independent knobs. The engine stops at resolving WHO, and hands over to [`DialogueTalk`](DialogueTalk.java) - a seam the NPC-identity layer fills (`npc/NpcTalkDialogue`, installed by the plugin), so **this package never imports `npc`**; with nothing installed the beat is a no-op rather than an error, because a conversation that cannot credit should still be readable. There is no second, shorthand spelling of it: the no-op `Talk` carrier the engine used to seed beside it is gone, so a file still authoring `"Talk"` fails the read naming itself rather than quietly crediting nothing.
- **World identity rides the ONE selector authority, never a second matcher.** `{"Type":"World","Names":[...],"Match":[...],"GameplayConfig":[...],"ExcludeNames":[...]}` holds the four axes and hands them to [`world/WorldSelector`](../../../../../../../../zc-world/src/main/java/com/ziggfreed/common/world/WorldSelector.java) (`getSelector()`, memoized), so the rank ladder, the many-to-many name resolution through `WorldIdentity`, and the exclude-is-a-FILTER rule all come from there unchanged. The world read is `store.getExternalData().getWorld()` via [`DialogueWorlds`](DialogueWorlds.java), so `DialogueContext` needs no new member. **Fail-closed**: an unreadable world, or a selector with no positive axis, matches nothing and hides the gated content - matching `conditionsPass`'s treatment of a throwing or unregistered evaluator.
- **[`DialogueOnce`](DialogueOnce.java) - `Once`, the AUTHORED seen-ness knob, on a `Start` entry or an option.** `"Once": true` (once per character) or `"Once": {"WorldSelector":"forgotten_temple"}` (once per world FAMILY); BOTH forms are read by the one codec (a boolean-or-group codec, so `false` reads as no Once at all), and a future axis is a new nullable leaf rather than a mode. **Entry-level Once is spent by COMPLETING the beat** - the player chooses any option on the routed node, the page's implicit Farewell row included (which is why that row reports `farewell`, not `close`) - so Escape mid-beat re-shows it. The flow is `DialogueEngine.resolveEntry` -> a pending key the page holds -> `consumeOnce` after the actions ran; nothing is written on a path that did not run them. **Option-level Once is keyed by `LabelKey`, never by index** (reordering a node's options can neither resurrect nor spend one); an `OnceId` leaf overrides it for a duplicate-label or label-less option, and an option with neither stays repeatable with a warn-once plus an `ONCE_NO_IDENTITY` finding, and two Once-bearing options in one node landing on the SAME discriminator raise `ONCE_DUPLICATE_IDENTITY` (they would otherwise share one flag). `DialogueEngine.optionAvailable` is the ONE predicate the page uses for both rendering and the click re-check.
- **[`DialogueMemory`](DialogueMemory.java) - `Memories`, the AUTHORED named state**, declared once at the top of the body (`"Memories": {"helped_refugees": {"WorldSelector":"emerald_wilds","ResetWithQuest":"guide_trust","Shared":true}}`) and used by BARE NAME everywhere else: actions `Remember`/`Forget` (shorthand `"Remember": "<name>"`/`"Forget": "<name>"`), conditions `Remembered`/`NotRemembered`. All three leaves are nullable and orthogonal - per world FAMILY, forgotten when a quest resets, and shared with every other dialogue that declares the same name. The map decodes through [`../codec/InheritMapCodec`](../../../../../../../../zc-core/src/main/java/com/ziggfreed/common/codec/InheritMapCodec.java) like `Nodes`, so a `Parent` child re-declares or adds ONE memory and inherits the rest. An UNDECLARED name still works (a plain per-dialogue memory) but warns once and is a validator error, because the declaration is the only place its scope and lifetime could have been written.
- **`Fragments` + `IncludeOptions` - shared option groups, structured.** A body declares `"Fragments": {"<name>": [ <option>, ... ]}` and a node names one or more with `"IncludeOptions": ["<name>"]`; the group's options are appended AFTER the node's own (a footer, not a header) by a post-decode fold in [`NpcDialogue#spliceFragments`](NpcDialogue.java), run from the dialogue codec's `afterDecode`. Because the fold runs after the whole body is read, a child inheriting a screen from a `Parent` picks up the CHILD's groups; an unknown name warns and is an `UNKNOWN_FRAGMENT` finding. The option objects are shared between the screens that name them - nothing about an option depends on which screen shows it (a `Once` is keyed by node at read time), so there is nothing to copy.
- **[`DialogueStateKeys`](DialogueStateKeys.java) + [`DialogueFlagScope`](DialogueFlagScope.java) are INTERNAL PLUMBING - no author ever sees a composed key.** `DialogueStateKeys` owns the shapes (`once:e:<dialogueId>:<node>`, `once:o:<dialogueId>:<node>:<labelKeyOrOnceId>`, `mem:d:<dialogueId>:<name>`, `mem:s:<name>`, every piece trimmed + lower-cased with any `:` folded to `.`); `DialogueFlagScope` folds a `WorldSelector` in, keyed by SELECTOR name so "already greeted here" survives an instance world being destroyed and re-created under a fresh uuid name. **A `ResetWithQuest` PREFIXES `q:<questId>:` onto the whole key, and the world scope wraps only the FINAL segment** - `q:<id>:mem:d:<dialogue>:w:<name>:<memory>`. That ordering is load-bearing, not cosmetic: a consumer clears a namespace by a leading-PREFIX match (hyMMO clears `q:<questId>:*` on quest reset), so a prepended scope would escape the clear and soft-lock the dialogue permanently. A selector the current world does not carry makes a WRITE a no-op and a READ unset; an unknown selector name warns once per name per process and is a validator finding, because a typo would otherwise re-show a first-visit beat forever. The storage seam itself is unchanged: [`DialogueFlagStore`](DialogueFlagStore.java) still has/sets these opaque keys, plus a `clear` (default no-op) behind `Forget`.
- **A `DialogueNode` can self-gate with its own `Conditions`** (the same shared list). When a `Start` candidate resolves to a node, `resolveEntryNodeId` ALSO requires the node's conditions to pass - so state-varied beats collapse into ONE node map with per-node runtime conditions instead of `(node x state)` duplication. A `DialogueOption` can carry a `Presentation` (nested `{Color, Icon:{Item,Glyph}}` codec): the page overrides the action-derived `DialogueOptionStyle` with a per-option colour (retinted hover/press) + an icon (a game item id via the `#OptIconItem` grid slot, or a fixed glyph token).
- **One registration binds schema + behavior + presentation + shorthand so they can't drift**: a [`DialogueActionType`](DialogueActionType.java) carries the codec + a [`DialogueActionHandler`](DialogueActionHandler.java) + an optional [`DialogueOptionStyle`](DialogueOptionStyle.java) kind + an optional [`DialogueSugarLeaf`](DialogueSugarLeaf.java); a [`DialogueConditionType`](DialogueConditionType.java) carries the codec + a [`DialogueConditionEvaluator`](DialogueConditionEvaluator.java). The executor dispatches by a handler MAP (not `instanceof`), which is what lets a consumer add an action without editing the engine. Registering a `Type` id a generic already uses OVERRIDES the behaviour for that engine while keeping the one shared shape (the MMO does this to `Talk`).
- **The opaque per-player handle is [`DialogueContext`](DialogueContext.java)** (`DialogueExecContext` narrows `dialogue()` to non-null and adds node/option; the base declares it as a nullable default so a memory/Once read can resolve its per-dialogue name from either). The engine only reads the generic state store + forwards the context to registered evaluators/handlers; a consumer's evaluator reaches its domain state via `payload(Class)`. Build it with [`page/SimpleDialogueExecContext`](page/SimpleDialogueExecContext.java) inside a [`page/DialogueContextFactory`](page/DialogueContextFactory.java). State storage is the consumer's [`DialogueFlagStore`](DialogueFlagStore.java) (MMO: a player component; minigame: in-memory per-round) - implement `clear` there for `Forget` to do anything.
- **Seams**: [`DialoguePageRouter`](DialoguePageRouter.java) (the `OpenPage` target -> open a page, default NONE), [`NpcNameProvider`](NpcNameProvider.java) (header name, default NONE), [`DialogueHeaderAnnotation`](DialogueHeaderAnnotation.java) (the one-line hint row, default NONE), [`i18n/DialogueI18n`](i18n/DialogueI18n.java) (namespace prefix + en-US `hasKey` probe; the ready-made [`I18nModuleDialogueI18n`](i18n/I18nModuleDialogueI18n.java) is zero-config). All bundled into a [`page/DialoguePageDeps`](page/DialoguePageDeps.java) built once at startup.
- **Reuse is NATIVE `Parent` inheritance at the ASSET level.** A dialogue FILE may carry a top-level `"Parent": "<id>"` and the engine's own asset loading merges it before anything here sees it - there is no resolver of ours in the path any more (`DialogueBodyResolver` and the `DialogueTemplates` store are both gone; a base is an ordinary file marked `"Abstract": true`). `Start`/`Nodes`/`Memories`/`Fragments` are `appendInherited` (omit a field -> inherit the parent's); the `Nodes` map uses [`../codec/InheritMapCodec`](../../../../../../../../zc-core/src/main/java/com/ziggfreed/common/codec/InheritMapCodec.java) so a child overrides/adds a node BY KEY while inheriting the rest (each `DialogueNode` is a `BuilderCodec` = `InheritCodec`, so its fields deep-merge too). Loc-keys are convention-derived (`dialogue.<id>.<node>.text`/`.opt.<i>`), so a child gets its own namespace for free. State-selection is runtime node `Conditions` + `AnyOf`; per-NPC quest ids are literal field overrides.
- **[`validate/DialogueStructureValidator`](validate/DialogueStructureValidator.java)** reports shared [`validation.Finding`](../../../../../../../../zc-core/src/main/java/com/ziggfreed/common/validation/Finding.java) values under domain `dialogue`. It covers everything that goes wrong SILENTLY: structure (`EMPTY_DIALOGUE`, `MISSING_START`, `START_MISSING_NODE`, `GOTO_MISSING_NODE`, `UNREACHABLE_NODE`), shared groups (`UNKNOWN_FRAGMENT`), the state surface (`WORLD_CONDITION_NO_AXIS`, `WORLD_CONDITION_UNKNOWN_SELECTOR`, `ONCE_UNKNOWN_SELECTOR`, `ONCE_NO_IDENTITY`, `ONCE_DUPLICATE_IDENTITY`, `MEMORY_UNDECLARED`, `MEMORY_SHARED_MISMATCH` (`validateAll` only), `MEMORY_UNKNOWN_SELECTOR`, `MEMORY_BLANK_NAME`, `MEMORY_NEVER_WRITTEN`, `MEMORY_NEVER_READ`), the factor axis (`FACTOR_CONDITION_UNKNOWN_FACTOR` warning, `FACTOR_CONDITION_NO_ID` error), the quest axis (`QUEST_CONDITION_NO_ID`, `QUEST_ACTION_NO_ID`, `QUEST_STATE_MISSING`, `QUEST_STATE_UNKNOWN`), the shorthand (`SUGAR_SHADOWED_BY_DO`, `DUPLICATE_ACTION`), and what THIS engine can serve (`UNKNOWN_ACTION_TYPE` / `UNKNOWN_CONDITION_TYPE` - the shared schema reads every mod's vocabulary, so a file may carry a line this game renders and then cannot act on). Conditions are walked on nodes, options and `Start` candidates, recursing through the combinators. Each extra argument enables one family of checks and `null`/EMPTY means "cannot tell" and skips it: pass `DialogueWorlds.knownSelectorNames()`, the engine's `factors()`, and the engine itself. A consumer that registers domain actions still runs its OWN pass for their refs and merges.
- **[`page/DialoguePage`](page/DialoguePage.java)** is the generic page (extends `ui/toast/ToastablePage`). Every exit path sends a response (the client spins otherwise). **The render reads the PLAYER, not the ref it was opened on:** `build`'s `ref` argument is whatever the opener handed the page manager, and every NPC-action route hands it the NPC (first-party `ActionOpenBarterShop` does the same), so `build` resolves the player from the `PlayerRef` the page holds - exactly what first-party `BarterPage.build` does. Read state off the raw argument instead and the FIRST screen is evaluated against an entity with none of the player's components (quest lines read not-started, factor gates fail closed) while every later click render is correct, which shows up as "the option only appears after you click something once". `DialoguePageRenderSubjectTest` guards both halves. **In-menu completion toast (optional):** when an action reports a just-completed thing via `DialogueActionExecutor.Mut.reportCompleted(id)` (carried back on `Outcome.completedId`) AND the consumer wired a `completionToast` (`completedId -> ToastSpec`) into `DialoguePageDeps`, the page floats that toast over the dialogue before reopening. Engine-side this is domain-free: the id is opaque (a quest, an objective, anything), the executor never builds a toast, the consumer supplies it; the overlay is inert for every dialogue that wires neither. The `.ui` lives in `src/main/resources/Common/UI/Custom/` as `Pages/ZigDialoguePage.ui` + `Pages/ZigDialogueOptionRow.ui` + `Common/ZigButtons.ui` + `Common/ZigFrames.ui` (neutral `Zig*` names so they never collide with a consumer's own `.ui`); all textures are base-game. The `.ui` is NOT gradle-validated - smoke-test in-game.
- **RICH TEXT = native inline markup in the `.lang`, rendered on a Label's `TextSpans`.** Hytale's client parses `<color is="#rrggbb">..</color>`, `<b>..</b>`, `<i>..</i>` (and `\n`) inside a localized string when it is shown via a **Label's `TextSpans`** property - this is the engine's OWN mechanism (vanilla `items.*.description` + `customUI.*` strings use it across all locales, so it is per-locale + client-resolved). The node text is set on **`#NodeText.TextSpans`** (NOT `.Text` - `.Text` shows the tags LITERALLY, the shipped bug), so any markup the consumer writes in its `.lang` value just works, in every locale, with zero engine support. Markup may carry `{param}` too. Option rows are `TextButton`s - **buttons have NO `TextSpans`**, so an option label cannot be coloured by markup; its colour comes from [`DialogueOptionStyle`](DialogueOptionStyle.java). Toasts/event-titles + the item-icon/grid `name` tooltip are String-only sinks (no rich text); the item `description` tooltip IS rich.

- **[`asset/`](asset/) - the pack-authored dialogue STORE layer (Pattern A, common-registered).** [`ZcDialogueAsset`](asset/ZcDialogueAsset.java) is a structured `AssetBuilderCodec` at `Server/ZiggfreedCommon/Dialogues/<id>.json` (registered by `../asset/FrameworkAssetRegistrar`): `Name` (echo), `Owner`, `Enabled`, `Abstract`, and `Payload` - the conversation body, decoded by the shared codec graph through a [`DeferredCodec`](DeferredCodec.java) that resolves the table's codec at the first read (an asset codec is a static field; the body's shape is not known until the mods have registered). The file name is the id, lower-cased at the one decode authority. [`asset/DialogueAssetStore`](asset/DialogueAssetStore.java) holds the decoded assets and answers `dialogues(owner)` - in-circulation, non-abstract conversations belonging to that owner or to nobody - so a consumer feeds that map straight to its `DialoguePageDeps` resolver with no decode step of its own.
  - **`DeferredCodec` forwards `InheritCodec` on purpose.** The engine only offers the merge path to a field whose codec is an inheriting one, and it asks at codec-assembly time; a plain forwarder would silently turn `Parent` into whole-replacement for `Payload`.
