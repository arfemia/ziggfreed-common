# dialogue/ - the generic branching NPC dialogue engine

Router for `com.ziggfreed.common.dialogue`. A self-contained, mod-agnostic dialogue runtime lifted from hyMMO (which is being re-integrated as its first EXTENDER). A consumer builds ONE [`DialogueEngine`](DialogueEngine.java) via the builder, supplies a few seams, and opens [`page/DialoguePage`](page/DialoguePage.java); the `.ui` ships once here and resolves client-side.

- **PARADIGM: per-consumer engine, NOT a shared mutable registry.** `DialogueEngine.builder()` pre-seeds the generic action/condition/sugar types, the consumer `.action(...)`/`.condition(...)`/`.router(...)`s its own, and `.build()` assembles the codec graph ONCE before any decode - so there is no registration race and one mod's domain types never leak into another's. The MMO registers quest/reward/gate types; a minigame builds with generics only.
- **[`DialogueAction`](DialogueAction.java) + [`DialogueCondition`](DialogueCondition.java) are BOTH `Type`-discriminated polymorphic lists** (`Conditions` is an array of `{Type:...}` objects, symmetric with `Actions`). Generic actions: `Goto`/`Close`/`Remember`/`Forget` + the carriers `Talk`/`OpenPage`. Generic conditions: `Remembered`/`NotRemembered`/`World`/`Factor` + the **boolean combinators `AllOf`/`AnyOf`/`Not`** (each holds a child `Conditions` list under `All`/`Any`/`Of`; assembled in `build()` after the shared `conditionsArray`, evaluated by delegating each child back through `conditionsPass`). The dispatch `CodecMapCodec`s are engine-instance-owned (assembled in [`DialogueEngine.Builder.build`](DialogueEngine.java)); each leaf subtype carries its own field `BuilderCodec` (PascalCase keys, guarded by [`DialogueEngineTest`](../../../../../../test/java/com/ziggfreed/common/dialogue/DialogueEngineTest.java)). **There are no raw authored FLAGS in the pre-seeded set** - seen-ness is the `Once` knob and named state is a declared `Memories` entry (both below). A consumer that genuinely wants raw flags registers its own action/condition types on its own builder; nothing in the engine stops it.
- **A `Factor` condition gates a line on a number ANOTHER mod owns, through the ONE shared factor vocabulary.** `{"Type":"Factor","Factor":"yourmod:reputation","Param":"guild","Min":10}` holds the four authored leaves and hands them to [`factor/FactorCondition`](../../../../../../../../zc-core/src/main/java/com/ziggfreed/common/factor/CLAUDE.md) (`getCondition()`, memoized) - the same leaf, keys and semantics an NPC placement's `Requires` uses, so a factor id means one thing across the library. The number comes from the registry the engine was BUILT with (`DialogueEngine.Builder#factors(FactorRegistry)`, readable back as `engine.factors()`); the evaluation context carries the player as BOTH `store` and `subject`, the current world through the same guarded [`DialogueWorlds`](DialogueWorlds.java) read the `World` condition uses, and the authored `Param`. **Fail-closed at both altitudes**: an unregistered id / a provider that cannot answer / a throwing provider all hide the gated content, and so does an engine built with NO registry (one warn-once). A bounds-less condition is therefore a presence check - it passes only while the factor resolves at all, which is how "only where that mod is installed" is written - and the engine-handle reads are try-guarded, so a context that cannot expose a store simply supplies no subject rather than throwing.
- **World identity rides the ONE selector authority, never a second matcher.** `{"Type":"World","Names":[...],"Match":[...],"GameplayConfig":[...],"ExcludeNames":[...]}` holds the four axes and hands them to [`world/WorldSelector`](../../../../../../../../zc-world/src/main/java/com/ziggfreed/common/world/WorldSelector.java) (`getSelector()`, memoized), so the rank ladder, the many-to-many name resolution through `WorldIdentity`, and the exclude-is-a-FILTER rule all come from there unchanged. The world read is `store.getExternalData().getWorld()` via [`DialogueWorlds`](DialogueWorlds.java), so `DialogueContext` needs no new member. **Fail-closed**: an unreadable world, or a selector with no positive axis, matches nothing and hides the gated content - matching `conditionsPass`'s treatment of a throwing or unregistered evaluator.
- **[`DialogueOnce`](DialogueOnce.java) - `Once`, the AUTHORED seen-ness knob, on a `Start` entry or an option.** `"Once": true` (once per character) or `"Once": {"WorldSelector":"forgotten_temple"}` (once per world FAMILY); the boolean is shorthand for the empty group, normalized by the sugar pre-pass ([`DialogueSugar.normalizeOnce`](DialogueSugar.java)) so the codec only sees the object, and a future axis is a new nullable leaf rather than a mode. **Entry-level Once is spent by COMPLETING the beat** - the player chooses any option on the routed node, the page's implicit Farewell row included (which is why that row reports `farewell`, not `close`) - so Escape mid-beat re-shows it. The flow is `DialogueEngine.resolveEntry` -> a pending key the page holds -> `consumeOnce` after the actions ran; nothing is written on a path that did not run them. **Option-level Once is keyed by `LabelKey`, never by index** (reordering a node's options can neither resurrect nor spend one); an `OnceId` leaf overrides it for a duplicate-label or label-less option, and an option with neither stays repeatable with a warn-once plus an `ONCE_NO_IDENTITY` finding, and two Once-bearing options in one node landing on the SAME discriminator raise `ONCE_DUPLICATE_IDENTITY` (they would otherwise share one flag). `DialogueEngine.optionAvailable` is the ONE predicate the page uses for both rendering and the click re-check.
- **[`DialogueMemory`](DialogueMemory.java) - `Memories`, the AUTHORED named state**, declared once at the dialogue top level (`"Memories": {"helped_refugees": {"WorldSelector":"emerald_wilds","ResetWithQuest":"guide_trust","Shared":true}}`) and used by BARE NAME everywhere else: actions `Remember`/`Forget` (option sugar `"Remember": "<name>"`/`"Forget": "<name>"`), conditions `Remembered`/`NotRemembered`. All three leaves are nullable and orthogonal - per world FAMILY, forgotten when a quest resets, and shared with every other dialogue that declares the same name. The map decodes through [`../codec/InheritMapCodec`](../../../../../../../../zc-core/src/main/java/com/ziggfreed/common/codec/InheritMapCodec.java) like `Nodes`, so a `Parent` child re-declares or adds ONE memory and inherits the rest. An UNDECLARED name still works (a plain per-dialogue memory) but warns once and is a validator error, because the declaration is the only place its scope and lifetime could have been written.
- **[`DialogueStateKeys`](DialogueStateKeys.java) + [`DialogueFlagScope`](DialogueFlagScope.java) are INTERNAL PLUMBING - no author ever sees a composed key.** `DialogueStateKeys` owns the shapes (`once:e:<dialogueId>:<node>`, `once:o:<dialogueId>:<node>:<labelKeyOrOnceId>`, `mem:d:<dialogueId>:<name>`, `mem:s:<name>`, every piece trimmed + lower-cased with any `:` folded to `.`); `DialogueFlagScope` folds a `WorldSelector` in, keyed by SELECTOR name so "already greeted here" survives an instance world being destroyed and re-created under a fresh uuid name. **A `ResetWithQuest` PREFIXES `q:<questId>:` onto the whole key, and the world scope wraps only the FINAL segment** - `q:<id>:mem:d:<dialogue>:w:<name>:<memory>`. That ordering is load-bearing, not cosmetic: a consumer clears a namespace by a leading-PREFIX match (hyMMO clears `q:<questId>:*` on quest reset), so a prepended scope would escape the clear and soft-lock the dialogue permanently. A selector the current world does not carry makes a WRITE a no-op and a READ unset; an unknown selector name warns once per name per process and is a validator finding, because a typo would otherwise re-show a first-visit beat forever. The storage seam itself is unchanged: [`DialogueFlagStore`](DialogueFlagStore.java) still has/sets these opaque keys, plus a `clear` (default no-op) behind `Forget`.
- **A `DialogueNode` can self-gate with its own `Conditions`** (the same shared list). When a `Start` candidate resolves to a node, `resolveEntryNodeId` ALSO requires the node's conditions to pass - so state-varied beats collapse into ONE node map with per-node runtime conditions instead of `(node x state)` duplication. A `DialogueOption` can carry a `Presentation` (nested `{Color, Icon:{Item,Glyph}}` codec): the page overrides the action-derived `DialogueOptionStyle` with a per-option colour (retinted hover/press) + an icon (a game item id via the `#OptIconItem` grid slot, or a fixed glyph token).
- **One registration binds schema + behavior + presentation + sugar so they can't drift**: a [`DialogueActionType`](DialogueActionType.java) carries the codec + a [`DialogueActionHandler`](DialogueActionHandler.java) + an optional [`DialogueOptionStyle`](DialogueOptionStyle.java) kind + an optional [`DialogueSugarExpander`](DialogueSugarExpander.java); a [`DialogueConditionType`](DialogueConditionType.java) carries the codec + a [`DialogueConditionEvaluator`](DialogueConditionEvaluator.java). The executor dispatches by a handler MAP (not `instanceof`), which is what lets a consumer add an action without editing the engine.
- **The opaque per-player handle is [`DialogueContext`](DialogueContext.java)** (`DialogueExecContext` narrows `dialogue()` to non-null and adds node/option; the base declares it as a nullable default so a memory/Once read can resolve its per-dialogue name from either). The engine only reads the generic state store + forwards the context to registered evaluators/handlers; a consumer's evaluator reaches its domain state via `payload(Class)`. Build it with [`page/SimpleDialogueExecContext`](page/SimpleDialogueExecContext.java) inside a [`page/DialogueContextFactory`](page/DialogueContextFactory.java). State storage is the consumer's [`DialogueFlagStore`](DialogueFlagStore.java) (MMO: a player component; minigame: in-memory per-round) - implement `clear` there for `Forget` to do anything.
- **Seams**: [`DialoguePageRouter`](DialoguePageRouter.java) (the `OpenPage` target -> open a page, default NONE), [`NpcNameProvider`](NpcNameProvider.java) (header name, default NONE), [`DialogueHeaderAnnotation`](DialogueHeaderAnnotation.java) (the one-line hint row, default NONE), [`i18n/DialogueI18n`](i18n/DialogueI18n.java) (namespace prefix + en-US `hasKey` probe; the ready-made [`I18nModuleDialogueI18n`](i18n/I18nModuleDialogueI18n.java) is zero-config). All bundled into a [`page/DialoguePageDeps`](page/DialoguePageDeps.java) built once at startup.
- **Reuse is NATIVE `Parent` inheritance (native-lite, 1.5.0), NOT a hand-rolled template DSL.** The old `extends`/`params`/`nodeOverrides`/`extraNodes`/`PruneIfEmpty` resolver (`template/`) was REMOVED. A body may carry a top-level `"Parent": "<id>"`; [`DialogueBodyResolver`](DialogueBodyResolver.java) resolves the chain (topological, memoized, cycle-guarded) and decodes each through [`DialogueEngine.decodeWithParent`](DialogueEngine.java) -> the engine's real `decodeAndInheritJson`. `Start`/`Nodes` + node fields are `appendInherited` (omit a field -> inherit the parent's); the `Nodes` map uses [`../codec/InheritMapCodec`](../../../../../../../../zc-core/src/main/java/com/ziggfreed/common/codec/InheritMapCodec.java) so a child overrides/adds a node BY KEY while inheriting the rest (each `DialogueNode` is a `BuilderCodec` = `InheritCodec`, so its fields deep-merge too). Option `sugar` still runs as a pre-pass (`engine.sugar().desugar` inside the resolver); loc-keys are convention-derived (`dialogue.<id>.<node>.text`/`.opt.<i>`), so a child gets its own namespace for free. Params/prune are gone: state-selection is runtime node `Conditions` + `AnyOf`; per-NPC quest ids are literal field overrides.
- **[`validate/DialogueStructureValidator`](validate/DialogueStructureValidator.java)** is the STRUCTURAL audit only (missing/dangling start, dangling Goto, unreachable, empty-after-resolve) returning neutral `Issue`s; a consumer that registers domain actions runs its OWN pass for their refs and merges. It also audits the generic STATE surface, because every way it can be wrong is otherwise SILENT: `WORLD_CONDITION_NO_AXIS`, `WORLD_CONDITION_UNKNOWN_SELECTOR`, `ONCE_UNKNOWN_SELECTOR`, `ONCE_NO_IDENTITY`, `ONCE_DUPLICATE_IDENTITY` (error - two Once-bearing options in ONE node resolving to the same `OnceId`/`LabelKey` share a single flag, so taking either retires both; the check compares composed state keys, so case-variant labels are caught), and the memory set `MEMORY_UNDECLARED` (error), `MEMORY_SHARED_MISMATCH` (error, `validateAll` only - it needs the whole set), `MEMORY_UNKNOWN_SELECTOR` (error), `MEMORY_BLANK_NAME` (error), `MEMORY_NEVER_WRITTEN` (warning), `MEMORY_NEVER_READ` (info; `Severity` carries an `INFO` level for it). It also covers the `Factor` condition: `FACTOR_CONDITION_UNKNOWN_FACTOR` (warning - the id resolves to nothing, so the content is permanently hidden; a WARNING rather than an error because the id may legitimately belong to an optional mod) and `FACTOR_CONDITION_NO_ID` (error). Conditions are walked on nodes, options and `Start` candidates, recursing through the combinators. Pass `DialogueWorlds.knownSelectorNames()` to the `knownSelectorNames` overloads to enable the unknown-name checks, and the engine's own `factors()` registry to the third-argument overloads to enable the factor check; a null or EMPTY set (and a null registry) means "cannot tell" and skips them, so validating before assets load never false-alarms.
- **[`page/DialoguePage`](page/DialoguePage.java)** is the generic page (extends `ui/toast/ToastablePage`). Every exit path sends a response (the client spins otherwise). **In-menu completion toast (optional):** when an action reports a just-completed thing via `DialogueActionExecutor.Mut.reportCompleted(id)` (carried back on `Outcome.completedId`) AND the consumer wired a `completionToast` (`completedId -> ToastSpec`) into `DialoguePageDeps`, the page floats that toast over the dialogue before reopening. Engine-side this is domain-free: the id is opaque (a quest, an objective, anything), the executor never builds a toast, the consumer supplies it; the overlay is inert for every dialogue that wires neither. The `.ui` lives in `src/main/resources/Common/UI/Custom/` as `Pages/ZigDialoguePage.ui` + `Pages/ZigDialogueOptionRow.ui` + `Common/ZigButtons.ui` + `Common/ZigFrames.ui` (neutral `Zig*` names so they never collide with a consumer's own `.ui`); all textures are base-game. The `.ui` is NOT gradle-validated - smoke-test in-game.
- **RICH TEXT = native inline markup in the `.lang`, rendered on a Label's `TextSpans`.** Hytale's client parses `<color is="#rrggbb">..</color>`, `<b>..</b>`, `<i>..</i>` (and `\n`) inside a localized string when it is shown via a **Label's `TextSpans`** property - this is the engine's OWN mechanism (vanilla `items.*.description` + `customUI.*` strings use it across all locales, so it is per-locale + client-resolved). The node text is set on **`#NodeText.TextSpans`** (NOT `.Text` - `.Text` shows the tags LITERALLY, the shipped bug), so any markup the consumer writes in its `.lang` value just works, in every locale, with zero engine support. Markup may carry `{param}` too. Option rows are `TextButton`s - **buttons have NO `TextSpans`**, so an option label cannot be coloured by markup; its colour comes from [`DialogueOptionStyle`](DialogueOptionStyle.java). Toasts/event-titles + the item-icon/grid `name` tooltip are String-only sinks (no rich text); the item `description` tooltip IS rich. (A server-side markup parser + a per-node-param scheme were both tried and removed - native `.lang` markup on `TextSpans` is simpler and already per-locale.)

- **[`asset/`](asset/) - the pack-authored dialogue STORE layer (Pattern B, common-registered).** `ZcDialogueAsset` + `ZcDialogueTemplateAsset` (raw-`Payload` over `../asset/AbstractRawJsonAsset`) deliver bodies + templates from `Server/ZiggfreedCommon/Dialogues/` + `/DialogueTemplates/` (registered by `../asset/FrameworkAssetRegistrar`; the dialogues store `loadsAfter` the templates store so `extends` resolves). `DialogueAssetStore` holds the raw `id -> JsonObject` bodies (+ an `Owner` per body) + the template bodies and exposes `resolveAll(engine, ownerFilter)` -> `Map<String,NpcDialogue>` (runs `DialogueBodyResolver` over a POOL of templates + bodies, emitting only the owner-matched bodies - so a `DialogueTemplate` is now just a native `Parent` BASE that others inherit by id, not a DSL `extends` target). The decode is per-consumer-engine, NOT a static codec, so a consumer builds its engine first then calls `resolveAll` filtered to its own `Owner` after assets load. Lifted from the MMO's `DialogueConfig`; Kweebec is the first consumer (authored `Clash_Intro.json` + `Nightmares_Intro.json` with `Owner:"kweebec"`, both DSL-free so unchanged by the native-lite switch).
