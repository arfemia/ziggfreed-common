# dialogue/ - the generic branching NPC dialogue engine

Router for `com.ziggfreed.common.dialogue`. A self-contained, mod-agnostic dialogue runtime lifted from hyMMO (which is being re-integrated as its first EXTENDER). A consumer REGISTERS its own actions, conditions and seams into the server's ONE [`DialogueEngine`](DialogueEngine.java) **in its plugin `setup()`**, and opens [`page/DialoguePage`](page/DialoguePage.java); the `.ui` ships once here and resolves client-side.

- **PARADIGM: ONE ENGINE PER SERVER, and every registration into it is ADDITIVE.** Dialogue files live in ONE store the server reads once, so the decode vocabulary has to be everybody's: [`DialogueTypeTable`](DialogueTypeTable.java) is the process-wide table of every registered action / condition `Type` and every shorthand key, and it assembles the whole `NpcDialogue` codec graph once. The BEHAVIOUR behind those types is pooled the same way: `DialogueEngine.shared()` is the server's one engine, `DialogueEngine.registerShared(owner, type)` is how a mod contributes to it from its own `setup()` (the owner is the contributing mod's name, and it is not decoration - see below), and contributions stack, so one authored option may carry two mods' actions and both run. A `Type` id is claimed by its first registration and a second mod naming it with a DIFFERENT class is reported by the table, since only one of the two shapes can be read. **Behaviour is claimed per action / condition CLASS, and that claim is first-wins too** - two mods contributing a handler for one class is the one collision stacking cannot absorb, so the later one is refused, `registerShared` answers false, and the engine's own `dialogue-vocabulary` ledger prints ONE line naming the mod that holds the class and the mod that asked. **Splitting behaviour per consumer was the old shape and it collided**: whoever opened a conversation decided which half of the server's vocabulary could actually execute, so the other mod's actions silently no-opped and its gated lines silently hid.
- **TWO seams are SINGULAR rather than additive, and only those two**: the quest runtime (`DialogueEngine.installQuests(owner, quests)`) and the factor vocabulary (`installFactors(owner, registry)`). Two of either would be two answers to one question about one player, which is a contradiction rather than a composition, so the first install holds the slot for the life of the server and a later one naming a different instance is logged once and IGNORED (a repeat of the same instance is silent, so a mod re-running its own setup costs nothing). Both are backed by [`registry/RegistryLedger#putIfAbsent`](../../../../../../../../zc-core/src/main/java/com/ziggfreed/common/registry/CLAUDE.md), which is where that rule lives. **Losing the factor slot is not free, so CONTRIBUTE the ids your own dialogues gate on**: the holder answers its own registrations plus the process-wide `FactorContributions` table, so a contributed id survives whoever wins, while an id registered only into your own `FactorRegistry` reads as unanswerable, and fails closed, on a server where another mod installed first.
- **[`DialogueEngine.builder()`](DialogueEngine.java) still builds a PRIVATE engine, and that is for TESTS.** A sandbox with its own vocabulary is exactly what a unit test wants (pair it with `DialogueTypeTable.resetForTests()` + `DialogueEngine.resetSharedForTests()`). Nothing in a running server should build one: a private engine can only execute the half of the vocabulary it registered itself, which is the collision the shared engine exists to end.
- **ORDERING (load-bearing, evidence in `DialogueTypeTable`'s javadoc): `HytaleServer.boot()` runs `PluginManager.setup()` to completion, THEN dispatches `LoadAssetEvent`.** So every mod that registered during setup has published its vocabulary before the first dialogue file is read. Registering LAZILY on first use is the one way to get this wrong: the file is read first, names a `Type` nothing registered yet, and fails to load. A registration arriving after a read still takes effect (the table re-assembles, and the engine's maps are live rather than a snapshot, so a consumer holding the engine from earlier holds the updated one) and logs one warning saying so.
- **[`DialogueAction`](DialogueAction.java) + [`DialogueCondition`](DialogueCondition.java) are BOTH `Type`-discriminated polymorphic lists** (`Conditions` is an array of `{Type:...}` objects, symmetric with `Actions`). Generic actions: `Goto`/`Close`/`Remember`/`Forget`/`MarkTalked` + the carrier `OpenPage`. Generic conditions: `Remembered`/`NotRemembered`/`World`/`Factor` + the **boolean combinators `AllOf`/`AnyOf`/`Not`** (each holds a child `Conditions` list under `All`/`Any`/`Of`; their CODECS are assembled with the shared `conditionsArray` in the table, their EVALUATORS per engine so a combinator wrapping a domain condition is answered by the mod that owns it). Each leaf subtype carries its own field `BuilderCodec` (PascalCase keys, guarded by [`DialogueEngineTest`](../../../../../../test/java/com/ziggfreed/common/dialogue/DialogueEngineTest.java)). **An unknown `Type` FAILS THE READ** (`UnknownIdException` out of the dispatch codec) rather than being dropped, so a file naming a mod that is not installed is a startup error naming the file, never a silently missing line.
- **Option SHORTHAND is part of the schema, not a rewrite that runs before it.** A [`DialogueSugarLeaf`](DialogueSugarLeaf.java) declares a key, a fold order, the CODEC for its authored value and the factory that turns it into a canonical action; it is registered with its action (`DialogueActionType#withSugar`), so shorthand and action cannot drift. Every registered leaf becomes a real keyed field on the option codec AND on the `Do` atom codec, the decoded values land in [`DialogueSugarValues`](DialogueSugarValues.java), and [`DialogueSugar`](DialogueSugar.java) folds them into `Actions` at [`DialogueOption#getActions`](DialogueOption.java). Consequences worth knowing: a mistyped shorthand VALUE is a decode error naming the key; **`Open`'s value is a [`ui/route/Destination`](../../../../../../../../zc-presentation/src/main/java/com/ziggfreed/common/ui/route/Destination.java)** - one word for a screen with no settings (`"Open": "Quests"`), an object naming its `Type` and fields otherwise - so nothing parses a routing string and a `Type` nobody registered fails the READ naming the file; the in-game asset editor sees the shorthand like any other field; a leaf may declare MODIFIER keys it also reads (`Reward` reads `RewardOnce`); authored `Actions` run first and the shorthand is appended; a `Do` array folds in ARRAY order and SHADOWS the bare keys entirely (a bare key beside `Do` is a validator warning), while a modifier written beside `Do` still reaches the atoms inside it. A shorthand key that collides with an option field or with another leaf is refused with one warning.
- **A `Factor` condition gates a line on a number ANOTHER mod owns, through the ONE shared factor vocabulary.** `{"Type":"Factor","Factor":"yourmod:reputation","Param":"guild","Min":10}` holds the four authored leaves and hands them to [`factor/FactorCondition`](../../../../../../../../zc-core/src/main/java/com/ziggfreed/common/factor/CLAUDE.md) (`getCondition()`, memoized) - the same leaf, keys and semantics an NPC placement's `Requires` uses, so a factor id means one thing across the library. The number comes from the registry installed into the shared engine's one factor slot (`DialogueEngine.installFactors(owner, registry)`, readable back as `engine.factors()`); the evaluation context carries the player as BOTH `store` and `subject`, the current world through the same guarded [`DialogueWorlds`](DialogueWorlds.java) read the `World` condition uses, and the authored `Param`. **Fail-closed at both altitudes**: an unregistered id / a provider that cannot answer / a throwing provider all hide the gated content, and so does an engine built with NO registry (one warn-once). A bounds-less condition is therefore a presence check - it passes only while the factor resolves at all, which is how "only where that mod is installed" is written - and the engine-handle reads are try-guarded, so a context that cannot expose a store simply supplies no subject rather than throwing.
- **[`quest/`](quest/) - the QUEST-AWARE vocabulary, pre-seeded like the generics.** Conditions `QuestState` (`Quest` + `State`, or `States` as an OR shorthand; the EFFECTIVE status, so a finished daily off cooldown re-offers itself), `ReadyToTurnIn` (`Quest`, possession-aware) and `HasReadyToTurnIn` (any quest); actions `AcceptQuest` / `TurnInQuest` written as the shorthands `Accept` (20) and `TurnIn` (30). All of them go through [`quest/DialogueQuests`](quest/DialogueQuests.java), which the consumer installs with `DialogueEngine.installQuests(owner, quests)`: a `QuestStateReader` (zc-progression's NARROW read seam - **never `QuestEngine`**, which mutates: a condition that could reach it could accept a quest while merely rendering an option), a `Subject` factory, an ANSWER SET (`answersTo(contextId)` - one character standing for several quest-giver ids, tried in turn so a hand-in works wherever its giver stands), and the two write methods, which REFUSE by default. Unwired, every quest line reads NOT_STARTED and every accept / hand-in refuses. **`HasOfferableQuests` is here as a CLASS but is NOT seeded**: the missing half now exists (zc-progression's `NpcOfferProviders`, where a mod's catalogue and gates answer), so the condition asks rather than guesses - but a `Type` id resolves to ONE class process-wide, so a consumer already shipping its own must switch to this one deliberately, in place of its own. `QuestDialogueConditions.offerableType(quests)` is what it registers. A consumer with no condition of its own can register it straight away. **The same package also owns the COMPLETION HAND-OFF** - the one policy deciding whether a conversation follows a quest settling, with consumer UIs registering a `QuestDialogueHost` to open it rather than each deciding for itself; a surface with nobody in front of the player (a quest log, an objective book) skips the beat by that shared rule, not by improvising one.
- **`MarkTalked` is the ONE way a conversation counts as having happened, and it has NO shorthand.** `{"Type":"MarkTalked"}` on the option that IS the beat (the greeting, the hail, the "I have returned"). Nothing credits because a player pressed F, because a page opened, or because a dialogue re-rendered: a discrete click is a decision a player made, a render is not. What the engine supplies for free is the TARGET, never the trigger - an absent `Target` is the character being talked to (alias set included) through the same `resolveTarget` every action uses, so an author never types an id to credit the character they are already writing for. It is written out in full rather than hidden behind a one-word shorthand because crediting is a deliberate statement about the story, not a flag. Pair it with option-level `Once` for "credit the first hail"; the two are independent knobs. The engine stops at resolving WHO, and hands over to [`DialogueTalk`](DialogueTalk.java) - a seam the NPC-identity layer fills (`npc/NpcTalkDialogue`, installed by the plugin), so **this package never imports `npc`**; with nothing installed the beat is a no-op rather than an error, because a conversation that cannot credit should still be readable. There is no second, shorthand spelling of it: the no-op `Talk` carrier the engine used to seed beside it is gone, so a file still authoring `"Talk"` fails the read naming itself rather than quietly crediting nothing.
- **World targeting rides the ONE authority, never a second matcher.** `{"Type":"World","Where":{"Match":[...],"GameplayConfig":[...],"ExcludeMatch":[...]}}` carries the shared [`world/WorldSelector`](../../../../../../../../zc-world/src/main/java/com/ziggfreed/common/world/WorldSelector.java) group as a NESTED field, so the rank ladder, the bare-word-is-an-exact-name rule and the exclude-is-a-FILTER rule all come from there unchanged - and an author who has written a `Where` on an NPC placement already knows this one. The world read is `store.getExternalData().getWorld()` via [`DialogueWorlds`](DialogueWorlds.java), so `DialogueContext` needs no new member. **Fail-closed**: an unreadable world, an omitted `Where`, or a `Where` with no positive axis all match nothing and hide the gated content - matching `conditionsPass`'s treatment of a throwing or unregistered evaluator. A malformed `Where` is the SHARED finding from `WhereValidator`, not a dialogue-flavoured near-duplicate of it.
- **[`DialogueStart`](DialogueStart.java) - `Start` is DECLARED SECTIONS, and the engine owns the order.** `{First?, Quests?, Then?, Fallback?}`: `First` is beats that outrank anything about quests (a first-visit greeting, a beat for one world, a factor gate), `Quests` is one row per quest keyed by quest id, `Then` is the beats tried after them, `Fallback` is the screen of last resort. **The ladder is FIXED and documented on the codec: First (as written) > a quest READY to hand in > one this character can OFFER > one that is ACTIVE > Then (as written) > Fallback**, with map order settling two rows reaching one band - so an author writes each beat where it belongs and never hand-sorts one against another (the hub intro's 19-entry ladder plus its ordering essay became 2 + 9 + 2 + 1). A conversation with no `Start` at all opens on the first screen whose own conditions pass, which is what makes a one-screen file nothing but `Nodes`. **A file authoring the retired LIST form fails the read** with a message naming the sections.
  - **A BEAT is `{Node | Pick, When?, Once?}`.** `When` is the ordinary shared conditions array (factors, world, memories, quest state, combinators) and `Once` is the entry-level knob unchanged - spent by COMPLETING the beat. `Pick` is a weighted draw between screens, one draw per open: each variant is `{Node, Weight?}` where `Weight` is the shared [`FactorFormula`](../../../../../../../../zc-core/src/main/java/com/ziggfreed/common/factor/CLAUDE.md) leaf written as a plain number OR the full formula group (so another mod's reading can decide how often a line comes up), omitted reads as 1, and a resolved weight of zero or less takes a variant out of the draw without deleting it. Every variant out means the beat does not fire. **The draw source is this thread's own random, never `Math.random`**, and an isolated builder engine can be given a fixed one (`DialogueEngine.Builder#random`) so a test pins a draw. Authoring `Node` AND `Pick` together is a validator ERROR rather than a precedence rule.
  - **A QUEST ROW is `{Ready?, Offerable?, Active?}`, and each is `true` | a screen name | a destination.** The engine reads the quest's own state through the same narrow seams a quest-aware line uses ([`quest/DialogueQuests`](quest/CLAUDE.md) for ready + active, zc-progression's `NpcOfferProviders` for offerable), so no condition is authored and the hand-written "X COMPLETED and Y NOT_STARTED" bridge pairs are gone. **Only AVAILABLE offers count** - a quest the player can see but not take is not something to hail them about.
  - **THE READY RULE (ruling 78a), which is load-bearing.** A ready quest never diverts `Start` unless its row exists, so a finished quest in the log does not quietly take over every conversation on the server. `"Ready": true` is the engine's default beat: it ROUTES to this character's quest list with that quest highlighted, never an inline hand-in - a conversation handing a quest in on the player's behalf would be handing in something they never chose to. An inline turn-in happens only where an author's own screen writes `TurnIn`. A row whose value is a destination routes anywhere; a quest-list destination is auto-highlighted with the row's own quest.
  - **A routed beat is resolved by the OPENER, before the page exists** ([`page/DialogueOpener`](page/DialogueOpener.java)): a page cannot hand the screen to somebody else halfway through building itself, so the ladder is walked once at open time and either the destination opens or the conversation does. That is also what keeps a `Pick` draw to ONE draw per open. `EntryResolution` carries the destination, and the engine turns "this quest, at this character" into something openable through the [`DialogueQuestView`](DialogueQuestView.java) seam the `npc` layer fills - the same one-way shape `DialogueTalk` uses, so **this package still never imports `npc`**.
- **[`DialogueOnce`](DialogueOnce.java) - `Once`, the AUTHORED seen-ness knob, on a `Start` entry or an option.** `"Once": true` (once per character) or `"Once": {"World":"*KweebecNightmare*"}` (once per world); BOTH forms are read by the one codec (a boolean-or-group codec, so `false` reads as no Once at all), and a future axis is a new nullable leaf rather than a mode. **`World` takes a world NAME or a pattern in the ordinary grammar, and the pattern IS the exact-versus-family dial** - there is no second Match leaf to compose with it. **Entry-level Once is spent by COMPLETING the beat** - the player chooses any option on the routed node, the page's implicit Farewell row included (which is why that row reports `farewell`, not `close`) - so Escape mid-beat re-shows it. The flow is `DialogueEngine.resolveEntry` -> a pending key the page holds -> `consumeOnce` after the actions ran; nothing is written on a path that did not run them. **Option-level Once is keyed by `LabelKey`, never by index** (reordering a node's options can neither resurrect nor spend one); an `OnceId` leaf overrides it for a duplicate-label or label-less option, and an option with neither stays repeatable with a warn-once plus an `ONCE_NO_IDENTITY` finding, and two Once-bearing options in one node landing on the SAME discriminator raise `ONCE_DUPLICATE_IDENTITY` (they would otherwise share one flag). `DialogueEngine.optionAvailable` is the ONE predicate the page uses for both rendering and the click re-check.
- **[`DialogueMemory`](DialogueMemory.java) - `Memories`, the AUTHORED named state**, declared once at the top of the body (`"Memories": {"helped_refugees": {"Where":{"Match":["emerald_wilds"]},"ResetWithQuest":"guide_trust","Shared":true}}`) and used by BARE NAME everywhere else: actions `Remember`/`Forget` (shorthand `"Remember": "<name>"`/`"Forget": "<name>"`), conditions `Remembered`/`NotRemembered`. All three leaves are nullable and orthogonal - per world (the shared `Where` group, so an instance world is reached by the `GameplayConfig` it runs rather than by a name carrying a fresh uuid), forgotten when a quest resets, and shared with every other dialogue that declares the same name. The map decodes through [`../codec/InheritMapCodec`](../../../../../../../../zc-core/src/main/java/com/ziggfreed/common/codec/InheritMapCodec.java) like `Nodes`, so a `Parent` child re-declares or adds ONE memory and inherits the rest. An UNDECLARED name still works (a plain per-dialogue memory) but warns once and is a validator error, because the declaration is the only place its scope and lifetime could have been written.
- **`Fragments` + `IncludeOptions` - shared option groups, structured, from either of two places.** A conversation declares `"Fragments": {"<name>": [ <option>, ... ]}` at its top level, and a whole SERVER declares one per file at `Server/ZiggfreedCommon/DialogueFragments/<name>.json` ([`asset/DialogueFragmentAsset`](asset/DialogueFragmentAsset.java), folded into [`DialogueFragmentConfig`](DialogueFragmentConfig.java)); a node names one or more with `"IncludeOptions": ["<name>"]` and cannot tell which kind it got. **A name is looked for locally FIRST and in the files second**, so a conversation that wants its own version of a server-wide footer just declares one. The group's options are appended AFTER the node's own (a footer, not a header) by a post-decode fold in [`NpcDialogue#spliceFragments`](NpcDialogue.java), run from `ZcDialogueAsset`'s `afterDecode` (and from the body codec's, for a consumer decoding a body straight from a string). A name NEITHER answers warns and is an `UNKNOWN_FRAGMENT` finding. The DialogueFragments store `loadsAfter`-orders BEFORE Dialogues (pinned by `FrameworkStoreOrderTest`) because the fold runs at read time and a group that has not loaded yet would drop its lines silently. The option objects are shared between the screens that name them - nothing about an option depends on which screen shows it (a `Once` is keyed by node at read time), so there is nothing to copy there. **The SCREEN is another matter: the splice never overwrites a screen's authored options and never writes into a screen it did not create.** A screen a `Parent` child does not restate IS the parent's own object, already spliced when the parent was read, so the fold starts from the authored list every time and writes the result onto a COPY in a map of the child's own - otherwise the child would show the shared lines twice and the parent conversation would change from a file that never mentioned it. Shared-file names are matched without regard to case; a conversation's own names are matched as written.
- **[`DialogueStateKeys`](DialogueStateKeys.java) + [`DialogueFlagScope`](DialogueFlagScope.java) are INTERNAL PLUMBING - no author ever sees a composed key.** `DialogueStateKeys` owns the shapes (`once:e:<dialogueId>:<node>`, `once:o:<dialogueId>:<node>:<labelKeyOrOnceId>`, `mem:d:<dialogueId>:<name>`, `mem:s:<name>`, every piece trimmed + lower-cased with any `:` folded to `.`); `DialogueFlagScope` folds the `World` leaf in, **keyed by the pattern's literal CORE** - `*KweebecNightmare*` files under `kweebecnightmare` - so "already greeted here" survives an instance world being destroyed and re-created under a fresh uuid name, and narrowing to one arena is just a longer core (`*KweebecNightmare_Barn*`). An exact world name is its own core. **A `ResetWithQuest` PREFIXES `q:<questId>:` onto the whole key, and the world scope wraps only the FINAL segment** - `q:<id>:mem:d:<dialogue>:w:<core>:<memory>`. That ordering is load-bearing, not cosmetic: the clear is a leading-PREFIX match on `q:<questId>:*`, so a prepended scope would escape it and soft-lock the dialogue permanently. A pattern the current world does not match makes a WRITE a no-op and a READ unset; a pattern matching NO loaded world warns once per pattern per process, because a typo would otherwise re-show a first-visit beat forever. A bare `*` is treated as no scope at all (matching every world and not scoping are the same state) and is a validator finding rather than a key with an empty core in it. The storage seam itself is unchanged: [`DialogueFlagStore`](DialogueFlagStore.java) still has/sets these opaque keys, plus a `clear` (default no-op) behind `Forget`.
- **[`DialogueMemories`](DialogueMemories.java) is THE store, and the CLEARING is its job rather than a consumer's.** It routes each key to the session backend ([`InMemoryDialogueFlagStore`](InMemoryDialogueFlagStore.java), shipped here) or the persistent one (a `PersistentStore` seam the wiring root fills, because the component it is kept on lives in the module that depends on this one), by the lifetime the AUTHOR declared; unauthored means persistent. **`ResetWithQuest` is honoured HERE and nowhere else**: the quest engine reports every re-arm through zc-progression's `QuestResets` seam, the wiring root fills it with `forgetQuest(Subject, String)`, and this reaches the player through `DialogueMemories.SubjectHandles` - the three entity handles a consumer's `Subject` handle declares it can point at. A consumer implementing the clear itself was the old shape and the reason a declared lifetime was a promise exactly one mod kept, with nothing telling any other it was being ignored. A handle declaring nothing simply means no live player, and nothing happens.
- **A `DialogueNode` can self-gate with its own `Conditions`** (the same shared list). Whenever a `Start` beat (or a quest row, or the fallback) resolves to a screen, the engine ALSO requires that screen's own conditions to pass - and skips to the next rung when they do not, so state-varied beats collapse into ONE node map with per-node runtime conditions instead of `(node x state)` duplication, and a beat naming a screen that is gated shut never dead-ends the conversation. A `DialogueOption` can carry a `Presentation` (nested `{Color, Icon:{Item,Glyph}}` codec): the page overrides the action-derived `DialogueOptionStyle` with a per-option colour (retinted hover/press) + an icon (a game item id via the `#OptIconItem` grid slot, or a fixed glyph token).
- **One registration binds schema + behavior + presentation + shorthand so they can't drift**: a [`DialogueActionType`](DialogueActionType.java) carries the codec + a [`DialogueActionHandler`](DialogueActionHandler.java) + an optional [`DialogueOptionStyle`](DialogueOptionStyle.java) kind + an optional [`DialogueSugarLeaf`](DialogueSugarLeaf.java); a [`DialogueConditionType`](DialogueConditionType.java) carries the codec + a [`DialogueConditionEvaluator`](DialogueConditionEvaluator.java). The executor dispatches by a handler MAP (not `instanceof`), which is what lets a consumer add an action without editing the engine. On the shared engine every claim is FIRST-WINS: a `Type` id, an action class's handler and a condition class's evaluator each belong to whoever registered them first, and a later registration of any of the three is refused. Neither refusal is silent any more: the table reports a `Type` id re-registered against a DIFFERENT class (only one of the two shapes can be read), and the engine's ledger reports a class two mods both wanted, naming holder and asker, with `registerShared` answering false to the caller as well. Re-pointing a generic at different behaviour is therefore a `builder()` sandbox's privilege only, which is the point: a running server's authored files all mean the same thing.
- **The opaque per-player handle is [`DialogueContext`](DialogueContext.java)** (`DialogueExecContext` narrows `dialogue()` to non-null and adds node/option; the base declares it as a nullable default so a memory/Once read can resolve its per-dialogue name from either). The engine only reads the generic state store + forwards the context to registered evaluators/handlers; a consumer's evaluator reaches its domain state via `payload(Class)`. Build it with [`page/SimpleDialogueExecContext`](page/SimpleDialogueExecContext.java), which the page does itself, packing NO payload: its memory store AND every mod's payload resolve on FIRST USE rather than at construction and are then kept for the life of the context, because a context is built on every render and every click while most conversations never touch a memory. Both are plain unsynchronized fields: a context never leaves the world thread that built it.
- **[`DialoguePayloads`](DialoguePayloads.java) is how a mod's payload survives somebody else's conversation.** The mod that opens a conversation packs its own payload into the context it builds, which is right while only one mod is talking; on a server running two, the character in front of the player may be somebody else's, and the mod whose payload is missing does not fail loudly - its gate reads locked, its quest reads never-started, its hand-in quietly does nothing. So a mod registers `DialoguePayloads.register(MyPayload.class, owner, supplier)` once in `setup()`, beside the actions and conditions that read it, and `SimpleDialogueExecContext.payload(Class)` falls through to that supplier ON A MISS ONLY: the EXPLICIT payload always wins and is never rebuilt, so a mod's own conversations behave exactly as they did and no on-render self-heal runs twice. A fallback is asked for at most ONCE per context (a context serves a whole render, and a supplier may reconcile the player's saved state on the way past, so asking per gated line would multiply that work); "nobody has one" is remembered too. A class is claimed by its first registration; a supplier that throws or answers null degrades to no payload, warned once.
- **Seams**: the shared [`i18n/ContentKeys`](../../../../../../../zc-core/src/main/java/com/ziggfreed/common/i18n/ContentKeys.java) answers every AUTHORED key, in the namespace of whichever mod ships it, so a conversation reads right whoever opened it; the page's OWN two lines are the library's, in `ziggfreedcommon.dialogue.*`, and a conversation overrides them per character with a `Chrome` block. The header note comes from [`DialogueHeaders`](DialogueHeaders.java), an additive vocabulary of named sources a conversation opts into by name. **None of it is bundled into a per-consumer object** - a consumer registers what it contributes and the page composes the rest itself.
- **Reuse is NATIVE `Parent` inheritance at the ASSET level, decided per FIELD.** A dialogue FILE may carry a top-level `"Parent": "<id>"` and the engine's own asset loading merges it before anything here sees it - there is no resolver of ours in the path any more (`DialogueBodyResolver` and the `DialogueTemplates` store are both gone; a base is an ordinary file marked `"Abstract": true`). `Start`/`Nodes`/`Memories`/`Fragments` are each `appendInherited` on the ASSET (omit a field -> inherit the parent's), and each field's own codec decides what an AUTHORED one means: `Nodes`/`Memories`/`Fragments` are [`../codec/InheritMapCodec`](../../../../../../../../zc-core/src/main/java/com/ziggfreed/common/codec/InheritMapCodec.java) so a child overrides/adds an entry BY KEY while inheriting the rest (each `DialogueNode` is a `BuilderCodec` = `InheritCodec`, so its fields deep-merge too), while `Start` is ONE ladder and a child writing one replaces it wholesale - the only way a child can take a parent's opening beat out of the running, and the reason its field codec deliberately does not merge (half a child's sections beside half a parent's would be a ladder nobody wrote). Loc-keys are convention-derived (`dialogue.<id>.<node>.text`/`.opt.<i>`), so a child gets its own namespace for free. State-selection is runtime node `Conditions` + `AnyOf`; per-NPC quest ids are literal field overrides.
- **[`validate/DialogueStructureValidator`](validate/DialogueStructureValidator.java)** reports shared [`validation.Finding`](../../../../../../../../zc-core/src/main/java/com/ziggfreed/common/validation/Finding.java) values under domain `dialogue`. It covers everything that goes wrong SILENTLY: structure (`EMPTY_DIALOGUE`, `MISSING_START`, `START_MISSING_NODE`, `START_NODE_AND_PICK`, `START_PICK_EMPTY`, `START_QUEST_NO_ID`, `GOTO_MISSING_NODE`, `UNREACHABLE_NODE` - a screen only a quest row or a draw opens counts as reachable, and a row's authored destination is audited by whichever mod registered its type), shared groups (`UNKNOWN_FRAGMENT`), the state surface (`WORLD_CONDITION_NO_AXIS`, `WORLD_SCOPE_MATCHES_EVERY_WORLD`, `ONCE_NO_IDENTITY`, `ONCE_DUPLICATE_IDENTITY`, `MEMORY_UNDECLARED`, `MEMORY_SHARED_MISMATCH` (`validateAll` only), `MEMORY_BLANK_NAME`, `MEMORY_NEVER_WRITTEN`, `MEMORY_NEVER_READ`), the factor axis (`FACTOR_CONDITION_UNKNOWN_FACTOR` warning, `FACTOR_CONDITION_NO_ID` error), the quest axis (`QUEST_CONDITION_NO_ID`, `QUEST_ACTION_NO_ID`, `QUEST_STATE_MISSING`, `QUEST_STATE_UNKNOWN`), the shorthand (`SUGAR_SHADOWED_BY_DO`, `DUPLICATE_ACTION`), and what THIS engine can serve (`UNKNOWN_ACTION_TYPE` / `UNKNOWN_CONDITION_TYPE` - the shared schema reads every mod's vocabulary, so a file may carry a line this game renders and then cannot act on). Conditions are walked on nodes, options and `Start` candidates, recursing through the combinators. A `World` condition's `Where` is audited through the SHARED `WhereValidator`, so a malformed one reports the same code under domain `where` that a placement carrying the same mistake does rather than a second dialogue-flavoured one. Each extra argument enables one family of checks and `null` means "cannot tell" and skips it: pass the engine's `factors()`, and the engine itself. A per-world `Where` scope reports its own malformed shapes through the SHARED `WhereValidator` (domain `where`, the same finding a placement carrying the same mistake gets, never a dialogue-flavoured copy) and adds only the one thing a SCOPE can get wrong: a selector matching every world, which is not per-world at all; whether a real pattern names a world that EXISTS is a runtime warn-once, since which worlds are loaded is not knowable from a conversation. A consumer that registers domain actions still runs its OWN pass for their refs and merges.
- **[`page/DialoguePage`](page/DialoguePage.java)** is the generic page (extends `ui/toast/ToastablePage`), and **[`page/DialogueOpener`](page/DialogueOpener.java) is the ONE way it is put on the screen** - opening a conversation is not always opening it, since a `Start` quest row may route elsewhere. Every exit path sends a response (the client spins otherwise). **The render reads the PLAYER, not the ref it was opened on:** `build`'s `ref` argument is whatever the opener handed the page manager, and every NPC-action route hands it the NPC (first-party `ActionOpenBarterShop` does the same), so `build` resolves the player from the `PlayerRef` the page holds - exactly what first-party `BarterPage.build` does. Read state off the raw argument instead and the FIRST screen is evaluated against an entity with none of the player's components (quest lines read not-started, factor gates fail closed) while every later click render is correct, which shows up as "the option only appears after you click something once". `DialoguePageRenderSubjectTest` guards both halves. **In-menu completion toast (optional):** when an action reports a just-completed thing via `DialogueActionExecutor.Mut.reportCompleted(id)` (carried back on `Outcome.completedId`), the page itself raises nothing: whatever finished announced its own feedback moment, and a moment draws into the page that is open, so its toast reaches this screen without the page knowing what a quest is. Engine-side this is domain-free: the id is opaque (a quest, an objective, anything), the executor never builds a toast, the consumer supplies it; the overlay is inert for every dialogue that wires neither. The `.ui` lives in `src/main/resources/Common/UI/Custom/` as `Pages/ZigDialoguePage.ui` + `Pages/ZigDialogueOptionRow.ui` + `Common/ZigButtons.ui` + `Common/ZigFrames.ui` (neutral `Zig*` names so they never collide with a consumer's own `.ui`); all textures are base-game. The `.ui` is NOT gradle-validated - smoke-test in-game.
- **RICH TEXT = native inline markup in the `.lang`, rendered on a Label's `TextSpans`.** Hytale's client parses `<color is="#rrggbb">..</color>`, `<b>..</b>`, `<i>..</i>` (and `\n`) inside a localized string when it is shown via a **Label's `TextSpans`** property - this is the engine's OWN mechanism (vanilla `items.*.description` + `customUI.*` strings use it across all locales, so it is per-locale + client-resolved). The node text is set on **`#NodeText.TextSpans`** (NOT `.Text` - `.Text` shows the tags LITERALLY, the shipped bug), so any markup the consumer writes in its `.lang` value just works, in every locale, with zero engine support. Markup may carry `{param}` too. Option rows are `TextButton`s - **buttons have NO `TextSpans`**, so an option label cannot be coloured by markup; its colour comes from [`DialogueOptionStyle`](DialogueOptionStyle.java). Toasts/event-titles + the item-icon/grid `name` tooltip are String-only sinks (no rich text); the item `description` tooltip IS rich.

- **[`asset/`](asset/) - the pack-authored dialogue STORE layer (Pattern A, common-registered).** [`ZcDialogueAsset`](asset/ZcDialogueAsset.java) is a structured `AssetBuilderCodec` at `Server/ZiggfreedCommon/Dialogues/<id>.json` (registered by `../asset/FrameworkAssetRegistrar`). **Every conversation field is a field of the FILE**: `Name` (echo), `Enabled`, `Abstract`, `Start` (the declared sections), `Nodes`, `Memories`, `Fragments`, all at the top level, which is what a hand-written file reads as and what the in-game asset editor offers. Each of the four conversation fields sits behind its OWN [`DeferredCodec`](DeferredCodec.java) resolving that field's codec out of `DialogueTypeTable` at the first read (an asset codec is a static field; the shapes are not known until the mods have registered), so each keeps its own `Parent` behaviour rather than sharing one envelope's. `afterDecode` assembles the [`NpcDialogue`](NpcDialogue.java) everything else reads - id set, shared groups spliced - and `getDialogue()` is null only for a file that authored none of the four. The file name is the id, lower-cased at the one decode authority. [`asset/DialogueAssetStore`](asset/DialogueAssetStore.java) holds the decoded assets and answers `dialogues()` - every in-circulation, non-abstract conversation, whoever wrote it - and `dialogue(id)` answers ONE by id with the owner layer folded on top, which is what the page reads: there is no per-consumer resolver and no decode step outside the store. **The owner layer (`asset/DialogueOverrides`, `mods/ziggfreedcommon/dialogues.json`) is a bare id-keyed map like its sibling owner files** (`$`-prefixed keys reserved via `util/OwnerFiles`, `$SchemaVersion` absent reads as 1), **and an entry folds over the stored conversation of its id LEAF BY LEAF** - the same per-node `InheritMapCodec` merge `Parent` uses, through `DialogueEngine.decode(id, json, base)` - so an owner retunes one node and keeps every screen, memory and shared group the pack authored; an id nothing stores is the owner's own conversation. **There is no per-file attribution leaf**: one folder is the SERVER's conversations, every reader takes the whole set, and an id written twice is settled where the readers' catalogues meet rather than by hiding a file from a mod. [`asset/DialogueFragmentAsset`](asset/DialogueFragmentAsset.java) is the second type in this folder: `Server/ZiggfreedCommon/DialogueFragments/<name>.json`, one `Options` list per file, read by the SAME option codec through the same deferred trick.
  - **`DeferredCodec` forwards `InheritCodec` on purpose.** The engine asks at codec-assembly time whether a field's codec merges, and it asks THIS class rather than the delegate - so this class asks the delegate the same question and forwards the answer: merge through an `InheritMapCodec`, plain-decode (whole replacement) through an array codec. A forwarder that always claimed to merge would break `Start`; one that never did would break `Nodes`.
  - **A doc string per conversation field lives on `DialogueTypeTable`** (`START_DOC` and friends), because the same four fields are read in two places - as the top-level fields of a FILE and as the body a consumer hands `DialogueEngine.decode` a string of - and a field documented twice is a field whose two descriptions drift.
