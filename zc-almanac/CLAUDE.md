# zc-almanac

- No library module may depend on this one: it sits beside zc-objectives, and a consumer reaches it through `page/AlmanacPages` and the `Almanac` destination. The book's Seasons statistics come the other way: `stats/AlmanacStatistics` is contributed to the kit's `LedgerContributions.STATISTICS` from `AlmanacBootstrap.registerVocabulary`, and its page opens the Almanac through that destination.
- The calendar is read only through zc-core's `occurrence/Occurrences` slot (`isEnabled`, `live`, `next`, `history`, `firstYear`, `zone`, `datesMove`, `recurrence`), through `OccurrenceAlmanacCalendar`; never import zc-calendar. A season the calendar does not answer for is absent: not listed, not counted. Days are counted in the event's own `zone`, the last day included (the day holding a run's last instant, `endMs - 1`, so a run ending at a time of day ends that day). The dates line says "Every year" only when `datesMove` is false; otherwise it names the framing run's year (`window.year`). A one-day event (start and end on one month-day) names its day once (`window.day`, `window.year.day`) and reads "Today only" on it, never "Last day". A monthly or weekly event (a `Recurrence` in its `Dates`) says how it comes round in place of the year line (`recur.*`), and its next run's days on a line of their own under it (`next.*`, `AlmanacLines.next`, the kit hero's `#HeroNext`), so a long rule never cuts the dates off; the ordinals, weekdays and month lists nest as keys, never English suffixes in Java.
- A season's page is `Server/ZiggfreedCommon/Almanac/<Owner>/<EventId>.json`, keyed by the calendar event id. Its achievements are the ones filed under category `Seasons` with the event id as subcategory; its keepsakes are the catalogue's yearly copies of its `Keepsake`, found by `Achievement.occurrence()` (the `<Keepsake>_<yyyy>` id as the fallback); an achievement filed under `Seasons` with no subcategory is cross-season: the banner shows the lowest-ordered one not yet earned (by `SortOrder`, then id), else the highest earned, counted by the engine's tally (seasons, never copies); a year chip counts the runs attended in that year (`AlmanacKeys.runsAttended`, shown at two or more, `year.runs`).
- `asset/AlmanacValidator` is the Almanac's content audit (domain `almanac`): a page's own `findings()` plus the cross-checks only the loaded set answers; whether a page's event is loaded (on or off) is asked of the `Occurrences` slot's `currentYear`, and whether its `Keepsake` names an achievement file that folds of the loaded files (`UNKNOWN_KEEPSAKE`, `AlmanacKeepsakeCheck.loaded`).
- A page's `Keepsake` is the one source naming its season's keepsake. `AlmanacKeepsakeCheck` warns where it and an `AnyYear` ladder's `MetaSelector` disagree, either way. It reads the loaded files only (never the calendar or the folded pool), and runs once per boot from `ProgressionRuntime.onBuilt`; on a boot that asks for zc's boot audit, `AlmanacValidator.audit()` carries and counts its findings instead, so each prints once.
- Tallies live in `AlmanacComponent` (save key `ZiggfreedCommon:Almanac`): `<event>/<stat>` for every season and `<event>@<year>/<stat>` for one, built only through `AlmanacKeys`. The format only grows: append, never rename a key, since a renamed stat starts over. `<event>@<year>/$runs` counts the runs attended in a season-year (one `CALENDAR_ATTENDED` moment per player per run); `$attended` stays that year's mark and the lifetime `$attended` counts years (a year marked before `$runs` existed is seeded to its one run at its next); read runs through `AlmanacKeys.runsAttended`.
- The server's own totals (`ServerTallies`) count what every player's record gains, under the same keys, in `mods/ziggfreedcommon/almanac-server-tallies.json` beside the owner files (`AlmanacOwnerLayers.directory()`; counts only, no player ids); the moment listener adds a record's growth, so `$attended` counts once per player per season and `$runs` once per player per run. A count is written by a 3-second debounce and again by the library's stop (`AlmanacBootstrap.shutdown`, from the wiring root's `shutdown()`), which writes only what changed since the last write, one write at a time (the engine's atomic writer shares one `.tmp` per file).
- The 2.2.0 builds before its release kept the totals in the library's data folder (`mods/Ziggfreed_ZiggfreedCommon/`, `plugin.getDataDirectory()`): `init(home, oldDir)` moves them once through zc-core's `util/DataFileMove`, and a move that fails keeps reading and writing the old file that run.
- The engine's `FileUtil.writeStringAtomic` loads on Update 7 only under the engine's log manager: a test that reads back a file `ServerTallies` wrote is tagged `engine-items` (those methods alone), and the untagged `ServerTalliesTest.aWriteThatCannotHappenNeverReachesTheCaller` proves a failed write never reaches the caller.
- A stat line ADDS each moment's amount, counted from the registered `MomentListener`; never add an ECS system for a moment the shared producers already fire, and never write progression from here.
- The kill switch is `$Enabled` in `mods/ziggfreedcommon/almanac.json`, mirrored as the feature `ziggfreedcommon:feature` Param `Almanac`. Off means absent: no page, no command answer, no menu tab, no hub tile, no counting. The menu tab's two knobs are `$MenuTab.Show` and `$MenuTab.OnlyWhileLive` in the same file (`AlmanacOwnerLayers` reads and writes them), and `AlmanacPages.menuTabVisible` is the one rule a tab or a consumer's tile asks. `AlmanacPages.headline` names every season on now (one, two, or the first and how many more); the MMO hub tile shows it, the menu tab does not.
- The page paints and delegates: what a season shows is decided in `view/AlmanacView` (records) and what it says in `view/AlmanacLines` (which countdown line, the dates line); `page/AlmanacPagePlan` maps them to the kit's records, and `page/AlmanacPage` only paints a plan through the kit. Each part of the body is a template appended into `#Sections` in the order the season's `Sections` writes it (`Pages/ZigAlmanac<Part>.ui`), addressed `#Sections[i] #Id`; `AlmanacPageDocumentTest` resolves each such selector inside the template appended at `i`. A part's button binds `Action` `section` with its index, answered from the plan the last build painted. `AlmanacPagePlanTest` holds the plan, and `AlmanacPageDocumentTest` drives the paint against the documents, so every id the page sets exists (a missing one drops the player). Nothing clips a child to the hero plate: every layer the page places stays inside 962 x 240.
- A season page's `Hero` is a shipped `Art` (shown while `ShowArt`) or a `Composition` of item pictures on the 962 x 240 plate; the `Composition` is one piece under `Parent` and the owner file (`WholeLeafCodec`), and a malformed one keeps the inherited one. A `Links` destination whose `Type` no installed mod registers is left out, never a failed read.
- A season page's `Sections` lays out its body in the order written, one part per entry (`Banner`, `Collection`, `Achievements`, `Tallies`, `Keepsakes`, `Links`; an entry naming two draws the first); with no `Sections` the page reads Tallies, Keepsakes, Achievements, Links. `Sections` replaces whole under `Parent` and in the owner's file, like `Links`, and a section's `Button` is a link (a storefront is `{ "Type": "Shop", "Shop": <id> }`).
- A player's owned marks are `$owned/<item>` in the same record (`AlmanacKeys.owned`, `AlmanacCollection`), only for items some page's `Collection` lists, set for good by `AlmanacInventorySystem` when one lands in any inventory section and by the page's look at the bag on open; never in the server's totals. It is the module's one ECS system: an item reaching a bag is no shared moment.
