# progress/gate/ - the one Requires vocabulary (zc-core)

- The package lives in zc-core so every module reads a whole `Requires`; its name stays `progress.gate` so imports hold. No domain vocabulary enters here: a consumer's own words are a registered kind, a factor, a member factor or a refusal family.
- The server's one `GateEvaluator` is `GateRuntime.evaluator()`, over live seams with working defaults (every contributed and file-defined factor, the subject's live player, the library's kind table), so a zc-only server needs no consumer (M513). zc-progression's `ProgressionGates.install` fills the seams with the progression runtime's parts and the quest completion probe and answers the same instance; never build a second one outside a test.
- Every unwired seam refuses; content that authors no requirements needs no wiring.
- A refusal is an opaque token, never a sentence. A collect-all `factor:` token carries `@<Param>`, and an `AnyOf` contributes exactly one token however many routes it offers.
- `passes` and `firstFailure` short-circuit, for per-row checks. `allFailures` and `allRefusals` walk every leaf (so they may call a `Custom` kind a short walk skips), and must agree with `firstFailure` on whether a block is shut.
- `check(spec, GateQuery)` is the hot-path ask: the subject plus the moment's held item, item, target and block, an optional local vocabulary that answers first for its own ids. It goes through the block's `CompiledGate` (kept on the `GateSpec`): providers looked up once and kept while `FactorRegistry.generation()` stands, and the verdict kept by the block's volatility (each factor's Factors file `Volatility`; unwritten is `Moment`, never kept; a `Quests` or `Custom` leaf is `Moment`; a local vocabulary is never kept) against `GateEpochs` (server epoch, moved by a group permission change, a Factors fold, a quest catalogue publish and a module's own reload of what a `Player` reading reads, such as a track's curve; per-player epochs moved by the player's moments, a quest's completed status moving outside one (`QuestEngine.markCompleted`, `clearQuest`, and `accept` over a finished quest), a move of their track readings (a level, best level or prestige count, never a move inside one level), permission changes, `AddPlayerToWorldEvent` and `PlayerReadyEvent`; nothing kept before `BootEvent`). A new writer of a `Player` reading's state outside a moment bumps the epoch itself, or a kept verdict goes stale. Once booted, an epoch move fires `ZigGateEpochMovedEvent` (null player: the server epoch), kept or not, but only while a listener's `GateEpochs.announceWhile` test says it wants one: a gate asked only at its own moments (a gear set's) registers that cheap test beside its bus listener, and a move nobody wants allocates nothing. Declare `Server` or `Player` only for a reading that truly changes only that way. `refusals(spec, query)` is the explaining twin, never kept.
- `RefusalLines` is the one token-to-line mapping (lang-keyed `Message`s, never a flattened string): the gate's tokens are its default family, a consumer registers its own prefix, and `contentTitles` and `memberFactor` are the seams a content owner fills (zc-progression's `LockReasons.install`).
- `Permission` is evaluated as the `hytale:permission` factor condition (one code path) but still refuses with the token `permission`.
- Nesting stops at one level, and `Not` takes clauses, never a nested `GateSpec`. A `Not` group shuts the gate by passing, so an empty one shuts the content for everyone and is reported as `BLANK_REQUIREMENT`.
- Four leaves (`Factors`, `Permission`, `Quests`, `Custom`); anything narrower is a registered `GateKind`, which may declare the parameter names it reads (`params()`) for the validator. Leaf names are frozen because quests and achievements decode the same block.
- `GateValidator` is the one audit of a block: unknown ids (WARNING), a Factors file's `ParamDataSet` and `AbsentReads`, a `Max`-only bound on a membership factor, a kind's undeclared parameters, and (`selfReads`, asked by a domain whose content changes what a gate reads) a block reading what its own content changes (`GATE_READS_OWN_STAT`, a gear set gated on a stat its tiers raise).
- A completion prerequisite (the `Quests` leaf or `ziggfreedcommon:quest_completed`) means `COMPLETED`, never `COMPLETED_UNCLAIMED`. Gate a one-shot on that flag and a run count on `quest_completions`, which counts collections.
- A store below the quest stores (loot tables, bonus rows, gear sets, reward rows) reads its `Requires` whole through `StoreGates`: the fold decides plain mod presence (`GateSpec.missingMod`), `StoreGates.live` is the rest, asked of the player when the file pays or applies, and the fold names once at INFO each file whose block reads more than mod presence (`reportWidened`).
- `FeatureLift` moves only a top-level plain feature or `hytale:mod_installed` condition (bounds-less or `Min: 1`) onto the hide axis. A nested or upper-bounded one stays a lock, and a nested presence check needs an explicit `Min: 1`: both ids read a definite 0, which a bounds-less condition passes.
- The completion probe is set after `build()`, because the engine that answers it is built after its gates.
- `FeatureLift.present(enabled, season, lifted)` is the one presence read: `Enabled`, the `Season` leaf (zc-core `SeasonGate.live`) and every lifted condition, all live. The quest and contract folds hand it to their engine when `isLive` says something can move, and the commerce hide axis answers through it. A season never enters `Requires`, so it never locks.
- `liftKnown` (quests, contracts, commerce) lifts features and mod presence; `liftModPresence` (achievements, and `StoreGates.live`) lifts mod presence alone. Never lift a third way.
