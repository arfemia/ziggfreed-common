# factor/ - the shared factor and condition vocabulary

- `null` is the only "cannot answer", and it fails every condition whatever the bounds. A provider returns null, never 0, for a reading it cannot make.
- A bounds-less condition passes on `0.0`, so a presence check needs `Min: 1`. `hytale:mod_installed` reads a definite 0 for an absent mod (`Min: 1` means installed, `Max: 0` means not), and `ziggfreedcommon:counter` reads 0 for a key never counted.
- The value side inverts: an unresolvable `FactorFormula` term adds 0. A value that must not exist without some factor is a gate in `Conditions`, never a term.
- `FactorRegistry` is per consumer. A lookup tries local registrations, then `FactorContributions`, then the wired `DerivedFactorSource`; `clear()` drops only local registrations.
- Claim a cross-mod id once at setup through `FactorContributions.register`, namespaced by the vocabulary's owner rather than the registrant (`hytale:` for an engine reading); setup order does not matter.
- A factor that is arithmetic over existing factors ships as a `Server/ZiggfreedCommon/Factors/` file, not code. A defining file's name is the factor id, and `Factor` plus `Formula` in one file is an error.
- A Factors file also carries a factor's traits (`FactorTraits`): `ParamDataSet` (the editor dataset its Param picks from, checked at load), `AbsentReads` (the definite number it reads when the asked thing is absent, so a condition with no Max that number meets is warned) and `Volatility` (`Server`, `Player` or `Moment`, the default; the most volatile word any file writes wins). A compiled gate keeps a verdict only over `Server` or `Player` readings, so declare one only when the reading truly changes that way and nothing else: `Server` with the server itself, `Player` only through that player's own moments, a permission change or a world change (what moves their epoch in `progress/gate/GateEpochs`).
- `FactorRegistry.generation()` is the one process-wide vocabulary clock: every registration, contribution, clear and Factors fold bumps it, and a reader that resolved a provider once (`providerFor`) rechecks against it.
- `FactorContext.held` is the stack standing for the hand (a use the engine is about to answer): the `tool_*`, `held_tag` and `held_item` readings read it before the live hotbar; `blockId` is the block the moment is about.
- Names come from `FactorNames` overlays, their keys written in full and never namespaced for the author. The one code seam is a `FactorNames.ParamNamer` (`registerParamNamer`), for a factor whose Param names its own module's content (zc-reputation's rank gates); it answers only where no overlay claims that exact Param, so an overlay always wins.
- A level on a track is zc-track's `ziggfreedcommon:track_level` (the best ever; `track_climb` the current climb, `track_tier`, `track_prestige`). Any other consumer number is mirrored onto a native stat channel (zc-entity's `stats/StatMirror`, which a track's `Mirror` uses too) and gated on `hytale:stat` (its folded max; `hytale:stat_percent` is the current value over it, 0..100).
- `hytale:held_item` takes an exact item id (the held item's own id alone) or a name pattern (zc-core `match/NamePattern`), which matches along the held item's `Parent` lineage (`inventory/ItemLineage`).
- `FactorCondition.codec(dataSetId)` is a factory: name only a dataset your mod serves (an unserved one renders an empty pick list); the library's own fields name an `asset/EditorDataSets` id. A dropdown is never validation.
- `FactorContext.item` is its own leaf: `hytale:tool_*` read the hand, while `hytale:item_*` (and `ziggfreedcommon:item_stamp_points`) read the item leaf and answer null where a moment carries none. Every item-worth reading (quality, level, durability, stat totals) goes through zc-entity's `entity/ItemReadings`. Quality differs on purpose: `item_quality` reads a quality stamped on the stack, else its item's current one, and `tool_quality` the held item's current one, so they differ only for a stamped stack.
- The item leaf is a plain `ItemStack` value (`hasItem()` is its guard; the engine's empty stack is no item), so unlike the entity leaves it stays readable after the moment that supplied it; a consumer that rebuilds its context on resume captures the stack and supplies it again. `item_durability_percent` reads 100 for a stack that tracks none; `item_stat` (Param = an `EntityStatType` id) sums only additive modifiers and reads 0 for an item authoring none toward it.
- Every `hytale:` factor and `ziggfreedcommon:item_stamp_points` has a `FactorNames` overlay (zc-core's `Factors/Hytale_*.json`, zc-loot's `Stamp_Item_Points.json`); ship one with any new library factor.
- `hytale:tool_power` and `tool_tier` take a `GatherType` `Param`, and a named type the tool lacks reads null. `tool_tier` (the per-gather-type `ItemToolSpec.Quality` harvest gate) is not `tool_quality` (item rarity).
- `hytale:permission` reads null, not 0, with no subject or for a non-player.
- A feature an admin page may flip declares its writer beside its supplier (`FeatureFlags.registerWriter`); the writer persists where the declaring mod keeps the switch, and a feature without one shows read-only.
- The `ziggfreedcommon:` quest and achievement readings belong to zc-progression's `ProgressionFactors`; their rules are in its `progress/runtime/CLAUDE.md`.
- `ModGates.keep` is the fold-time mod gate: a file whose plain top-level `hytale:mod_installed` condition (no `Max`, `Min` of 1 or more) names a mod reading a definite 0 never enters its store. "Cannot tell" (null) keeps it for the live hide axis, a bounds-less condition is not a gate, and a nested one never reaches it. Test it through `useProbeForTests`, never a fake plugin table. `missingMod` names the mod that drops a file (null exactly when `keep` is true), and `reportPackFiles`/`reportOwnerOverrides`/`reportRewardRows` (a reward row gated on its own `Requires`) write the one drop line per store per mod, never an id. Each line is a running total per fold, so the last line wins and a parser never sums them; its wording is a contract mmo-skills' `dev-server.ps1 -SeasonPair` parses, so pin a change through `reportIntoForTests`.
