# i18n/ - client-resolved Message factory

Router for `com.ziggfreed.common.i18n`. Mod-agnostic localization primitive lifted from the MMO Skill Tree's own `i18n.Msg` (RPG Stations extraction, phase 1 leg 1); the MMO's copy stays untouched (no churn - an existing, working call site does not need to move).

- **[`Msg`](Msg.java)**: builds Hytale `Message` values the CLIENT resolves against the viewer's own locale - the server never reads, caches, or persists a per-player locale. `tr(prefix, key, args...)` binds `{0},{1},...` under a CALLER-SUPPLIED namespace prefix (this class carries no fixed namespace of its own, so several consumer mods share one implementation); `key(fullKey, args...)` skips prefixing for a fully-qualified / another mod's / native key; `trNamed`/`keyNamed` bind `{name}` tokens instead. `raw(text)` is untranslated data (numbers, ids, player names) - never a localized name. `join(...)` glues parts for DIRECT placement only (a bare join carries neither `rawText` nor `messageId`, so it renders blank if nested as a `tr`/`key` param); `cat(...)` is the param-safe composite, folding pairwise through a shipped locale-neutral glue key so every fold node carries a `messageId` and resolves recursively even when nested - the registered id is `ziggfreedcommon.fmt.cat` (authored as `cat = {0}{1}` in `ziggfreedcommon.fmt.lang`; `I18nModule` derives the prefix from the lang FILENAME and preserves its dots verbatim, which is exactly why the original un-prefixed `common.fmt.cat` id never resolved on any client and rendered as a literal key). `bold(m)`/`color(m, hex)` are thin fluent wrappers over the engine `Message#bold`/`Message#color` (no import of the engine type needed at a call site that only wants styling).
- **The arg-binding invariant** (carried over from the MMO's own `i18n.Msg`, restated here since it is the entire correctness story): an arg that is ITSELF localized (a name, a nested template) MUST be passed as a nested `Message`, never pre-resolved to a String - and even a plain String arg is wrapped as a nested `Message.raw(...)`, not the bare `param(key, String)` overload (the client cannot deserialize a raw `StringParamValue` against a plain-String host property and disconnects).
- **A consumer wanting a prefix-free call site** wraps this with its own tiny facade (a one-line `Msg.tr("rpgstations." + key, args)` or a per-mod class), mirroring how the MMO's own `i18n.Msg` already reads.
- **[`GeneratedLangPack`](GeneratedLangPack.java)**: ship a RUNTIME-GENERATED localization overlay to clients - `writeLocaleFiles(root, filename, perLocale, header)` writes one `<root>/Server/Languages/<locale>/<filename>` per locale (idempotent overwrite, empty-value entries skipped), and `registerZipPack(root, zip, group, name, version, desc)` builds an IMMUTABLE zip from it and registers it RUNTIME via `AssetModule.registerPack` (ordering is load-bearing: unregister BEFORE the rebuild - a registered zip is held open by the engine and Windows refuses the move-into-place over the open handle; a failed rebuild re-registers the previous on-disk zip best-effort so the overlay never vanishes). The catalog-sync chain is `registerPack -> I18nModule.loadMessagesFromPack -> per-client sendTranslations at join`; keys land under the `filename`-minus-`.lang` PREFIX (`storedKeyPrefix`/`storedKey` are the pure authority a consumer's display + generator share so a lookup key never drifts from a generated entry key). **IMMUTABLE zip, never a watched directory** (the reason this primitive exists): a mutable dir pack's `AssetMonitor` PRUNES the entire matching vanilla namespace (all `server.*`/`client.*` keys) on any post-registration MODIFY; a zip is never watched. Intended use is boot-once generation (joining clients covered); the already-connected live push a mutable dir would add is not worth the catalog-prune hazard. Guarded (register failures return `false`, never throw). **Consumer**: the MMO Skill Tree's `i18n/StatTooltipLangGenerator`, which writes a per-skill tooltip-label `client.lang` per locale and registers the pack through `registerZipPack`; it keeps only its own policy on top (which keys, the staging gate that defers the build until plugin start, and a loud `severe` on the `false` return). That is currently the ONLY consumer, so the shape is settled by one caller rather than two - weigh a signature change accordingly, and note that two behaviours the consumer inherited rather than chose are the value ESCAPING (`escapeValue`) and the skip of an empty-valued entry.
- **Shipped `.lang` layout: one file per DOMAIN, and the FILENAME is the key prefix.** `I18nModule` recursively globs `*.lang` under `Server/Languages/<locale>/` and uses each file's basename minus `.lang` as a key PREFIX, dots preserved verbatim: `ziggfreedcommon.fmt.lang` registers `ziggfreedcommon.fmt.*`, `ziggfreedcommon.progression.lang` registers `ziggfreedcommon.progression.*`. So a key's RESOLVED id is filename-prefix plus in-file key, and splitting a file along an existing prefix boundary is invisible to every call site as long as the moved entries DROP the segment the filename now carries. Two rules follow, both load-bearing: a resolved key must be defined in exactly ONE file (merging is first-writer-wins with a warn, in filesystem order, so a key left in two files is silent data loss - MOVE entries, never copy), and a lang file lives in the module owning the code that reads it (`ziggfreedcommon.fmt.lang` here in zc-core beside `Msg`; a domain's own file with its domain). A file whose entries have all moved out is deleted rather than left empty.
- **Conventions**: `@Nonnull`/`@Nullable`; no em-dashes; rich text (colour/bold/`\n`) still renders ONLY on a `TextSpans` sink, never `.Text` - this factory builds the `Message`, it does not choose where it gets set.
