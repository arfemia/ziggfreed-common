# i18n/ - client-resolved Message factory

Router for `com.ziggfreed.common.i18n`. Mod-agnostic localization primitive lifted from the MMO Skill Tree's own `i18n.Msg` (RPG Stations extraction, phase 1 leg 1); the MMO's copy stays untouched (no churn - an existing, working call site does not need to move).

- **[`Msg`](Msg.java)**: builds Hytale `Message` values the CLIENT resolves against the viewer's own locale - the server never reads, caches, or persists a per-player locale. `tr(prefix, key, args...)` binds `{0},{1},...` under a CALLER-SUPPLIED namespace prefix (this class carries no fixed namespace of its own, so several consumer mods share one implementation); `key(fullKey, args...)` skips prefixing for a fully-qualified / another mod's / native key; `trNamed`/`keyNamed` bind `{name}` tokens instead. `raw(text)` is untranslated data (ids, player names) - never a localized name, and never a server-formatted NUMBER: a bare display figure is `num(value)`, a typed param on the shipped `ziggfreedcommon.fmt.num` key (`num = {0, number}`) so each player's own client decides the digit grouping (the root `NumberDisplayHygieneTest` fails a `raw(NumberFormatter...)`). `join(...)` glues parts for DIRECT placement only (a bare join carries neither `rawText` nor `messageId`, so it renders blank if nested as a `tr`/`key` param); `cat(...)` is the param-safe composite, folding pairwise through a shipped locale-neutral glue key so every fold node carries a `messageId` and resolves recursively even when nested - the registered id is `ziggfreedcommon.fmt.cat` (authored as `cat = {0}{1}` in `ziggfreedcommon.fmt.lang`; `I18nModule` derives the prefix from the lang FILENAME and preserves its dots verbatim, which is exactly why the original un-prefixed `common.fmt.cat` id never resolved on any client and rendered as a literal key). `bold(m)`/`color(m, hex)` are thin fluent wrappers over the engine `Message#bold`/`Message#color` (no import of the engine type needed at a call site that only wants styling).
- **[`ContentKeys`](ContentKeys.java): the AUTHORED-KEY seam, and the bug it exists to prevent.** `I18nModule` namespaces a key by the `.lang` FILENAME it was defined in, so an entry written `shop.general.title` inside `mmoskilltree.lang` registers as `mmoskilltree.shop.general.title`. Content is authored WITHOUT that namespace, because that is what an author typed into their own lang file. A library surface that hands the client the authored key verbatim therefore hands it an id nothing resolves, and the raw key is what a player reads on the screen (this shipped: board titles, shop titles, contract titles and category labels all rendered as their keys). `ContentKeys` is the ONE resolution authority every render site asks: `resolved(key)` gives the registered id, `tr(key, args...)` the client-resolved `Message`, `known(key)` the existence probe, `pick(explicit, convention)` the explicit-over-convention choice a content surface makes before emitting either. Consumers: zc-dialogue (the page), zc-commerce (`CommerceText`, `CurrencyText`, `CommerceLabels`, `ZigShopPage`, `ZigBoardPage`), zc-objectives (`ProgressionDefaults`, `AchievementGrouping`), zc-loot (`RewardChips`), zc-presentation (`FeedbackEngine`), zc-progression (`ContentText`, `NeutralObjectiveComposer`, `ProgressionTextSource`), plus the MMO Skill Tree and Kweebec Nightmare through those shared surfaces.
- **NOTHING is registered - the loaded catalogue IS the attribution.** There is no consumer registry (the old `ContentI18n` fill interface, `I18nModuleContentI18n` and `ContentKeys.install`/`installed`/`reset` are deleted; a consumer's shipped `.lang` files are the whole declaration). Resolution order, deterministic on every boot: (1) the catalogue carries the key EXACTLY as authored - a fully-qualified or native `server.items.*` id - and it goes out untouched; (2) any loaded id ending in `.<key>` claims it, the LEXICOGRAPHICALLY SMALLEST id winning, since only a rule over the ids themselves resolves the same way whatever order the server loaded packs in; (3) the key passes through exactly as written, so an unfilled server behaves as one did before this seam existed, never throwing and never blanking a name. A mod that shipped a key is the mod that shipped its translation, so presence answers ownership - the only attribution available, since a folded asset (`asset/AbstractKeyedAssetConfig` layers keyed by id alone) records no owner. A key two mods both ship goes to the alphabetically first registered id - deterministic but arbitrary, which is why shared-store content ids stay owner-prefixed. Step 2 memoizes per catalogue instance (the engine's `getMessages` map is identity-stable per message version), so the suffix scan runs once per distinct key per load.
- **[`LangCatalog`](LangCatalog.java) is the English-only existence probe AND the catalogue view** (PUBLIC and the ONE probe repo-wide - the factor naming walk and the neutral objective composer read it too; never throws: a unit JVM or a pre-init window has no catalogue, and "no catalogue" reads as "no key" so a caller falls through to its own fallback). `has`/`value` probe one full id (through the engine's `getMessage`, which also sees the server jar's bundled en-US defaults); `catalogue()` is the whole loaded probe-language map `ContentKeys` scans; `overrideForTests(map)` pins the catalogue to a plain map - the ONE test seam, public because consuming modules' unit tests drive production surfaces that resolve through this class with no engine module standing. `NativeNames` carries the probe-then-fallback name ladders: `itemNameMsg` (the two item families), `entityNameMsg` (`server.npcRoles` then `npcs`), `zoneNameMsg` (`server.map.zone` then `.region`), and `targetNameMsg` - the category-unknown ladder (items then characters then prettify) an objective target or a loot subject reads through, with a probe-injectable overload as its testable core.
- **The arg-binding invariant** (carried over from the MMO's own `i18n.Msg`, restated here since it is the entire correctness story): an arg that is ITSELF localized (a name, a nested template) MUST be passed as a nested `Message`, never pre-resolved to a String - and even a plain String arg is wrapped as a nested `Message.raw(...)`, not the bare `param(key, String)` overload (the client cannot deserialize a raw `StringParamValue` against a plain-String host property and disconnects).
- **A consumer wanting a prefix-free call site** wraps this with its own tiny facade (a one-line `Msg.tr("rpgstations." + key, args)` or a per-mod class), mirroring how the MMO's own `i18n.Msg` already reads.
- **[`GeneratedLangPack`](GeneratedLangPack.java)**: ship a RUNTIME-GENERATED localization overlay to clients - `writeLocaleFiles(root, filename, perLocale, header)` writes one `<root>/Server/Languages/<locale>/<filename>` per locale (idempotent overwrite, empty-value entries skipped), and `registerZipPack(root, zip, group, name, version, desc)` builds an IMMUTABLE zip from it and registers it RUNTIME via `AssetModule.registerPack` (ordering is load-bearing: unregister BEFORE the rebuild - a registered zip is held open by the engine and Windows refuses the move-into-place over the open handle; a failed rebuild re-registers the previous on-disk zip best-effort so the overlay never vanishes). The catalog-sync chain is `registerPack -> I18nModule.loadMessagesFromPack -> per-client sendTranslations at join`; keys land under the `filename`-minus-`.lang` PREFIX (`storedKeyPrefix`/`storedKey` are the pure authority a consumer's display + generator share so a lookup key never drifts from a generated entry key). **IMMUTABLE zip, never a watched directory** (the reason this primitive exists): a mutable dir pack's `AssetMonitor` PRUNES the entire matching vanilla namespace (all `server.*`/`client.*` keys) on any post-registration MODIFY; a zip is never watched. Intended use is boot-once generation (joining clients covered); the already-connected live push a mutable dir would add is not worth the catalog-prune hazard. Guarded (register failures return `false`, never throw). **Consumer**: the MMO Skill Tree's `i18n/StatTooltipLangGenerator`, which writes a per-skill tooltip-label `client.lang` per locale and registers the pack through `registerZipPack`; it keeps only its own policy on top (which keys, the staging gate that defers the build until plugin start, and a loud `severe` on the `false` return). Two behaviours that consumer inherited rather than chose are the value ESCAPING (`escapeValue`) and the skip of an empty-valued entry. A generated pack registers only at plugin start, after every asset has decoded, so it can never satisfy a key the engine validates AT decode (an item's `TranslationProperties.Description`, checked against the catalogue by `ItemTranslationProperties.SERVER_LANG_KEY_VALIDATOR`): such a key belongs in a boot pack, never in a generated overlay.
- **[`PlainText`](PlainText.java)**: the plain characters behind a `Message`, for the engine sinks that take only a `String` (an item slot's hover name, a dropdown entry's label) and for server-side READS that want characters (a search haystack, an A-Z sort key). `of(message)` is the sink call (null reads as the empty string); `render(formatted, catalogue)` is the same decision core over an explicit key-to-value function, public so a test or a tool can drive substitution with no engine standing. It resolves each translated part against the SAME default-language catalogue `ContentKeys` probes (the server never reads a viewer's locale, so a one-string-for-everyone sink gets the probe language) and substitutes the `{0}`-style slots, a nested message arg recursively and a scalar as written, which is what makes a `Msg.cat` fold read whole. A part the catalogue does not carry contributes its own id on purpose - a missing translation shows on screen as the key that needs writing rather than as a blank - and a JVM with no catalogue degrades the same way and never throws. Consumer: `zc-presentation`'s `ui/UiText`; tests `PlainTextTest` here and `zc-progression`'s `LockReasonsTest`. It never weakens the model: display text stays a client-resolved `Message` everywhere a sink can take one.
- **Shipped `.lang` layout: one file per DOMAIN, and the FILENAME is the key prefix.** `I18nModule` recursively globs `*.lang` under `Server/Languages/<locale>/` and uses each file's basename minus `.lang` as a key PREFIX, dots preserved verbatim: `ziggfreedcommon.fmt.lang` registers `ziggfreedcommon.fmt.*`, `ziggfreedcommon.progression.lang` registers `ziggfreedcommon.progression.*`. So a key's RESOLVED id is filename-prefix plus in-file key, and splitting a file along an existing prefix boundary is invisible to every call site as long as the moved entries DROP the segment the filename now carries. Two rules follow, both load-bearing: a resolved key must be defined in exactly ONE file (merging is first-writer-wins with a warn, in filesystem order, so a key left in two files is silent data loss - MOVE entries, never copy), and a lang file lives in the module owning the code that reads it (`ziggfreedcommon.fmt.lang` here in zc-core beside `Msg`; a domain's own file with its domain). A file whose entries have all moved out is deleted rather than left empty.
- **Conventions**: `@Nonnull`/`@Nullable`; no em-dashes; rich text (colour/bold/`\n`) still renders ONLY on a `TextSpans` sink, never `.Text` - this factory builds the `Message`, it does not choose where it gets set.
