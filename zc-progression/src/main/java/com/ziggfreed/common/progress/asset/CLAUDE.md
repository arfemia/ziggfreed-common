# progress/asset/

- A leaf here reaches both engines at once; a leaf only one engine wants belongs in that engine's own codec.
- Extend a group through its `appendLeaves`; never copy its leaf declarations into a second codec.
- Every leaf is `appendInherited`. Content inherits through native `Parent`, and `Abstract` alone is a plain `append` in every content codec, so a child of a skeleton is real content.
- `QualifierMatchMode` is the qualifier's own comparison (`EXACT` / `CONTAINS` / `PREFIX`, the words `MatchMode` gives the target), defaulting to `EXACT` so files authored before it keep their meaning. It rides `ObjectiveDef.qualifierMatchMode()` into `ObjectiveMatch.qualifierMatches(authored, mode, event)`.
- `Qualifiers` (a string array) accepts more qualifiers beside `Qualifier`: the union counts, each entry under `QualifierMatchMode`, blanks ignored. It rides `ObjectiveDef.qualifiers()` into `ObjectiveMatch.qualifierMatches(authored, list, mode, event)`; a consumer that rebuilds an `ObjectiveDef` carries it through `Builder.qualifiers` or loses it.
- `Targets` (a string array) accepts more targets beside `Target` the same way: the union counts, each entry under `MatchMode`, blanks ignored, a kind alias rewriting each entry. It rides `ObjectiveDef.targets()` (and `authoredTargets()`) into `ObjectiveMatch.targetMatches(authored, list, mode, event)`; `ObjectiveDef.hasTarget()` is the one "names anything" read and `namedTarget()` the one a line or a picture names. A consumer that rebuilds an `ObjectiveDef` carries it through `Builder.targets` or loses it.
- `While` (zc-core `GateSpec`) is a step's own condition: it rides `ObjectiveDef.countsWhile()` (an empty block reads as none) and is asked only through `progress/ObjectiveWhile.holds` wherever a step is credited (each engine's dispatch, a hand-in and its offer, a standing value's seed and re-read, the native `ZigMoment` task), and audited only through `ObjectiveWhile.findings`. A step writing none asks nothing; a surface that credits a step without asking it is the bug. A consumer that rebuilds an `ObjectiveDef` carries it through `Builder.countsWhile` or loses it.
- Never import `quest/` or `achievement/` from this package.
- `ContentTextAsset` (`Text`) lives in zc-core's `text/`, because a module below this one needs it.
- `ObjectiveLeafAsset.toDefBuilder` is the one place a kind alias is applied.
- An editor dropdown is authoring convenience, never validation: a hand-written file never passes through the editor.
- `ProgressEditorDataSets` lists the shared vocabularies by default (`ProgressionRuntime.objectiveKinds()`'s producible kinds and aliases, `RewardKinds.shared()` spelled), so a consumer advertises only a private registry of its own. A `Rewards` list a file declares goes through `RewardEntryAsset.rows()`, and a steps or criteria map through `ObjectiveLeafAsset.row(codec)`, whose `Kind` picks the row's form in the Asset Editor (a reward kind's described `Params`, an objective kind file's `Pick` on `Target` and `Targets`); any other group keyed on an objective kind (a moment table's `When`) goes through `ObjectiveKindPicks.selector`, never a second copy of the arms. A kind file's target `Pick` is a suggestion `List`, never a strict `Asset` picker: targets are matched as patterns.
- A consumer's own knob goes in `Meta` (`ContentMeta`), inherited per namespace with the block replaced whole; never argue it into a shared leaf.
- A reward row's own `Requires` (zc-core `GateSpec`) gates that row alone, every condition read: `toSpec` answers null where its mod is missing, so every payer drops it; a validator reading authored entries audits `RewardEntryAsset.present`, and a store's fold counts the rest (`collectMissingMods` into `ModGates.reportRewardRows`, and `collectWidened` into `StoreGates.reportWidened`). The rest of the block rides the spec (`RewardSpec.requires`) and zc-loot's `RewardGrants` asks it of the receiving player, paying a player it refuses nothing for that row; a surface listing the rows before payment still lists it.
- `GeneratorCore` is the one expander for every content type that writes a family from one file. It merges nothing (each generated body is an ordinary child carrying `Parent`); a value that is exactly one token keeps that token's type; an unbound token is an error that skips the entry. `Base` takes tokens like `IdPattern` (each body's `GeneratedBody.baseId` is its own, lower-cased after filling), so one family can sit under a parent per row (zc-track's pick generators: `Base` `Yours_Tree_{Skill}`); a store reads `baseId()` per body, never the generator's `Base`.
- The second pass is the core's `Fill`, the one substitution (`substitute` and `substituteString` too): a bound value holding tokens is filled from the same combination on first use, a loop an ERROR `TOKEN_CYCLE` that skips the entry. A value holding no token lands as before; the family build's `ShippedGeneratorRestampTest` holds every shipped generator that walks no rows and binds no token-holding value to the one-pass output (a file using either is passed over).
- The rows source (`GeneratorRows.SOURCE`, `ziggfreedcommon:rows`, `Filter.Set`) is answered in the core before any source a store hands in, so no store registers it; its tokens are never `UNUSED_TOKEN`. Rows are `GeneratorRowAsset` (`GeneratorRowConfig`, owner file `generator-rows.json`). A store re-expands after its rows move only through `GeneratorRows.onRefold(<its generator type>, ...)`, registered by whoever registers the store (the root for the library's three, which load after the rows); every fold of the rows ends in `GeneratorRows.settle` (`GeneratorRowConfig.reloadOwner` runs it).
