# progress/ - the shared cores under both lifecycle engines

- Two peer lifecycle engines, `quest/` and `achievement/`, share these cores and are deliberately not unified: lifecycle special-casing would thread through everything.
- THE runtime, one quest engine and one achievement engine per server, lives in `runtime/`: a mod registers its parts and reads the pair back. `builder()` on either engine is only for a unit test or a genuinely private engine.
- Nothing here may name a lifecycle: no quest or achievement type, no import from `../quest/`. A core that needs owner data takes the owners plus accessors, the way `ObjectiveIndex.of` does. Consumer vocabulary anywhere in the module fails `QuestModuleAgnosticismTest`.
- A new shared core lands here only when both engines want it; one engine wanting it keeps it with that engine.
- A category or subcategory name and a category accent come only from `CategoryNames` (authored `TitleKey`, the kind's convention key, a caller's key, the id tidied; the accent authored or hashed into its palette). It takes the shared `asset/CategoryPresentationAsset`, which both category types extend (with `CategoryPresentationConfig` for their folds), never a lifecycle type.
- A content name's convention key comes only from `ConventionKeys`: an achievement's `.title` / `.desc` by its BASE id (`AchievementDefinition.conventionId`, so one line names every yearly copy), a quest's and a board contract's `.title` / `.flavor`. Each fold's `textOf` stamps them into `ContentText`; `ConventionKeys.unresolvedTitle` is the one load-time check (skipped while no catalogue is loaded), run by both pool validators and the board validator.
- An unresolvable reading (a blank target, an unregistered factor, a provider that cannot answer or throws) contributes 0, and 0 as a high-water value is a no-op, so a re-check can never roll a player back.
- Matching is one forgiving rule (`ObjectiveMatch`): targets compare case-insensitively, an empty target matches everything under every mode, and an empty qualifier matches only an unqualified event. Never add a second dialect or a per-engine knob.
- A place (`targetsPlace`) is compared whole id to whole id, ignoring case, never through a `MatchMode`, and a blank target points nowhere.
- `DispatchOptions` stays two independent booleans with named factories; a new combination never needs a new constant. `ObjectiveProgressState`'s `"current/required"` wire form is byte-stable: changing it is a data migration.
- `ObjectiveDef` carries two pairs: `kind()`/`target()` are what the engines dispatch, index and settle on; `authoredKind()`/`authoredTarget()` are what the file said, and every text and icon surface reads them.
- `STAT_THRESHOLD` names a state, so nothing may fire it. The quest engine re-reads it at accept, in `selfHeal` and after a dispatch that progressed the same quest; the achievement engine only in `selfHeal`. Never add a poll.
- A kind alias (`ObjectiveKindRegistry.alias`) is sugar applied once at the fold: never listed by `ids()`, never producible, and registered at setup before the publish. The engine never learns an alias exists.
- Add a `BUILT_IN_*` kind only when it means something in any game. `BUILT_IN_ACCUMULATING` and `BUILT_IN_VALUE_BASED` partition the kinds by arithmetic; the target facets (`BUILT_IN_PLACE_TARGETED` and its siblings) are orthogonal to them and to each other. A consumer registering its own vocabulary skips every `isBuiltIn` id.
- `ObjectiveComposer` is the consumer-installable slot over the neutral ladder: the step's authored key, then its kind's `Presentation.TextKey`, then `ziggfreedcommon.progress.objective.<kind>`, then `objective.default`. A new kind joins the ladder with a kind file or a lang key, never a closed switch.
- `INSTANCE_ROUND_WON` and `INSTANCE_ROUND_ENDED` target `<modId>:<modeId>` (a `<modId>:` prefix matches any mode) with the preset id as qualifier. The `ENCOUNTER_*` kinds target the encounter script id, never the boss creature's, so a step survives an in-place role swap.
- `LOOT_RECEIVED` targets the item a reward payout handed over (`Qualifier` the payout's source id, `Amount` its count). zc-loot's `RewardDeliveries` announces it once per outermost payout and zc-objectives' `ZigLootReceivedProducer` produces it; a paid stack the overflow policy dropped at the player's feet counts here at payout, while an item a loot pass drops on the ground itself is `PICKUP_ITEM` once picked up, never this.
- `COMPLETE_QUEST` targets the finished quest's id with its cadence word as qualifier (`QuestCadence.qualifier()`: `NORMAL`, `REPEATABLE`, `DAILY`, `WEEKLY`, unless a `QuestCompletionQualifier` answers), amount 1. zc-objectives' `ZigQuestCompletionProducer` produces it once per collect, so a parked quest counts when its reward is taken, never when it parks.
